# Orca 梁津晶访谈 Notes：ADE、多 Agent 协作、产品方法与“松弛感创业”

> 嘉宾：梁津晶（Jinjing Liang），Stably AI / Orca 联合创始人兼 CEO  
> 主题：ADE 概念、多 Agent 协作、Orca 产品路径、AI 时代的创业方法  
> 整理依据：播客 ASR 转写稿；产品现状于 2026 年 8 月 20 日参考 Orca 官方网站、文档、GitHub 与 YC 公司页校准  
> 说明：文中“梁津晶认为”“访谈提到”表示嘉宾在节目中的判断或案例；“我的归纳”是基于访谈机制做出的分析，不等同于 Orca 官方表述。

## 一句话总览

这场访谈最有价值的地方，不是介绍了又一个 coding agent 产品，而是给出了一个更接近下一阶段软件工程现实的判断：**当开发者同时使用多个模型、多个 coding Harness 和几十个并行任务时，真正稀缺的资源不再只是模型智力，而是人的注意力、任务状态的可观察性、结果验收和跨 Agent 的协作秩序。**

Orca 将自己定义为 ADE（Agent Development Environment）。它不试图重新训练模型，也不以替代 Claude Code、Codex、OpenCode 等 Harness 为起点，而是位于这些工具之上，统一管理任务、worktree、终端、浏览器、状态、审查和交付。换句话说，IDE 的主要管理对象是文件和代码，ADE 的主要管理对象开始变成一组正在工作的 Agent 及其工作流。

梁津晶的创业方法与这一产品选择高度一致：借助已经形成的模型和平台势能，解决其规模化使用后暴露出的新问题；让小团队成为产品最重度的用户；通过高频发布、兼容现有习惯和中立性获得增长。她所谓的“松弛”，并非降低目标，而是把个人身份与某一个项目解耦，同时尽量把上游技术、开源社区和平台分发变成自己的杠杆。

## 核心结论

1. **多 Agent 时代的新瓶颈是注意力调度。** 同时启动更多 Agent 很容易，知道它们在做什么、何时需要人、结果是否可信，才是难点。
2. **ADE 的管理单位不是一次对话，而是一条可交付的工作流。** 一个任务要关联需求、worktree、终端、浏览器、变更、测试、审查意见和 PR，而不是停留在 chat history。
3. **Orca 的核心价值是控制面，而非另造一个底层模型或单一 Harness。** 它利用 Claude Code、Codex、OpenCode 等已有能力，在其上增加统一工作空间、状态和编排。
4. **并行不等于吞吐量。** 如果每个 Agent 都持续向人索要确认，Agent 数量越多，人的等待、切换和审查债务越大。
5. **多 Agent 系统首先是可观察性问题，其次才是智能问题。** 状态索引、异常暴露、阻塞识别和可恢复性，往往比再增加一个“总管 Agent”更基础。
6. **模型中立既是产品价值，也是商业立场。** 用户可以按任务、速度、额度和偏好切换模型；Orca 的利益不要求用户只使用一家模型。
7. **中立不是自动形成的护城河。** 上游厂商可以吸收部分界面和并行能力，Orca 仍要依靠跨平台兼容、迭代速度、工作流深度和用户留存证明差异。
8. **AI 缩短了原型时间，没有消灭生产工程。** 状态恢复、性能、缓存、进程生命周期、分支冲突、测试和交付，仍是产品能否长期运行的分界线。
9. **模型选择不应只看 benchmark。** 在人仍需参与设计和验收的工作流里，响应速度、可控性、单次任务总成本和错误方向的损失同样重要。
10. **“松弛感创业”是一种结构，而不只是性格。** 它来自创始人和用户高度重合、能借上游势能、团队足够小、试错成本可控，以及不把一次项目成败等同于个人成败。

## 先把四个概念讲清楚

访谈中最容易混淆的是 Model、Harness、ADE 和 Orchestration。它们不是四种互斥产品，而是不同层级。

| 层级 | 主要职责 | 典型对象 | 关键问题 |
| --- | --- | --- | --- |
| Model | 理解、推理和生成 | Claude、GPT、开源模型 | 能不能完成任务，速度、价格和可靠性如何 |
| Harness | 把模型放进可持续执行的 loop，提供工具、上下文和运行机制 | Claude Code、Codex、OpenCode、Pi | 模型如何读写文件、调用工具、继续执行和压缩上下文 |
| ADE | 组织人与多个 Agent 的工作空间 | Orca | 多个任务在哪里运行，状态如何聚合，人在哪里介入，结果如何交付 |
| Orchestration | 把复杂目标拆成任务、派发给 worker，并处理依赖、消息与决策门 | Orca 当前实验性 orchestration 能力、团队自建脚本 | 谁做什么，何时交接，失败如何重试，何时必须找人 |

### IDE 到 ADE 的变化

传统 IDE 围绕“一个人直接编辑代码”设计：文件树、编辑器、调试器和版本控制都服务于人的手工操作。Agent 加入以后，人的工作逐渐转向提出目标、审查设计、处理例外和验收结果。

因此，ADE 不是简单地在 IDE 里放一个聊天框。它至少要回答五个问题：

1. 一个目标如何变成独立、可追踪的任务？
2. 多个 Agent 如何避免修改同一工作区而相互覆盖？
3. 人如何快速看见哪些任务正常、阻塞或正在等决策？
4. Agent 的输出如何被压缩成可审查的 diff、页面、测试结果或报告？
5. 中断、升级或应用重启后，任务如何恢复，而不是从头再来？

Orca 的答案是把任务、worktree、Agent 终端和浏览器视图绑定在一起，再在上层提供状态、搜索、通知、审查和编排。

### “Orca 不做 Harness”需要怎样理解

梁津晶在访谈中的表达是，Orca 不自己做一个替代 Claude Code 或 Codex 的底层 Harness，而是直接运行用户已有的 coding agent。这一选择的意义在于：

- 上游 CLI 一更新，用户可以更快获得新模型和新能力；
- 用户不用放弃已经付费、熟悉或信任的工具；
- 产品可以将资源集中在跨 Harness 的管理与协作；
- 不同模型之间可以按任务切换，而不是把整个工作流锁死在一家厂商。

但从当前官方文档看，Orca 已经提供实验性的 Run、Task、Dispatch、worker、消息与 decision gate 等结构化编排能力。更准确的说法是：**Orca 不以重造底层模型调用 loop 为核心，但会在现有 Harness 之上建设编排控制层。**

## Orca 的产品闭环

把访谈和当前官方文档合在一起，Orca 想形成的不是“同时打开很多终端”，而是一条从需求到交付的闭环：

```text
Linear / GitHub issue / 人的自然语言需求
                    ↓
          独立任务与 Git worktree
                    ↓
    Claude Code / Codex / OpenCode 等 Harness
                    ↓
   终端、文件、浏览器、测试与运行状态同步呈现
                    ↓
       状态聚合、异常提醒、Agent 间消息
                    ↓
       人审查设计、关键决策与可视化结果
                    ↓
           diff / 测试报告 / PR / 交付物
                    ↓
           回写任务系统，进入下一轮
```

这里真正影响效率的并非“同时开了多少个 Agent”，而是每个箭头是否可靠。如果需求没有完成定义，worktree 只是制造更多分支；如果没有验收标准，自动生成 PR 只是把工作转移给 reviewer；如果状态不可信，控制面会变成另一块需要人工轮询的看板。

## 管理几百个 Agent：三层注意力压缩

访谈最具实践价值的部分，是梁津晶描述小团队如何管理大量并行 Agent。其方法可以归纳为三层。

### 第一层：状态索引，让人不必逐个查看

Orca 会围绕会话标题、worktree、任务关键词和 Agent 状态建立搜索与索引。人的第一步不再是打开二十个终端读日志，而是先回答：

- 哪些任务仍在运行？
- 哪些已经完成？
- 哪些在等待输入或权限？
- 哪些可能偏离目标？
- 哪些与某个 Linear ticket 或 GitHub issue 相关？

这其实是 Agent 系统的 observability。索引需要在实时性和查询性能之间权衡，也要避免把“进程仍在运行”误当成“任务正在取得进展”。

### 第二层：让 Agent 管理 Agent

对于跨多个步骤的任务，团队会让管理线程或编排脚本承担中间协调，例如：

1. 收集和澄清需求；
2. 生成设计并交给另一个 Agent 审查；
3. 派发实现任务；
4. 调用浏览器或移动模拟器做 QA；
5. 汇总成 PR、HTML 报告或其他可视化产物；
6. 只在关键选择上通知人。

其核心不是层层叠加“总管 Agent”，而是把任务之间的依赖、交接物和需要升级给人的条件写清楚。管理 Agent 如果没有稳定状态和明确 contract，只会增加一层会出错的自然语言转发。

### 第三层：把重复 SOP 变成自动化

访谈举到的内部实践包括 release agent 检查分支与 bug、社区和社交内容管理等。Orca 当前官方文档也提供 scheduled automations，可定期触发 triage、review 和 maintenance 类提示词。

适合自动化的是规则相对稳定、输入来源明确、结果可检查的流程。高风险发布、模糊需求、架构抉择和不可逆操作，仍应设置 decision gate。

### 最终目标：让人的注意力变成事件驱动

传统管理方式是人不断轮询：“做完了吗？卡住了吗？结果在哪？”好的多 Agent 系统应当把这种轮询改成事件驱动：

- 正常推进时保持安静；
- 出现阻塞、冲突、预算异常或低置信度时升级；
- 需要人判断时呈现选项、依据和影响；
- 完成时提供能快速验收的产物，而不是几万行过程日志。

因此，Agent 数量的上限并不首先由 GPU 或终端数量决定，而由组织可以消化多少决策和审查债务决定。

## 访谈中的高价值观点

### 一、ADE 与产品架构

#### 1. ADE 的核心对象是 Agent fleet，而不是单个 chat

如果产品仍围绕一个聊天窗口设计，多 Agent 只是多开几个窗口。ADE 需要在任务层组织 Agent，并保留任务与代码、进程、测试和交付物之间的关系。

#### 2. “多 Agent”不等于“多模型”

同一个模型可以运行多个 Agent，不同模型也可以承担同一工作流中的不同任务。多 Agent 解决并行和分工，多模型解决能力、速度、成本和供应商选择，两者不应混为一谈。

#### 3. 直接容纳上游 CLI，是一种产品速度策略

第一方 coding agent 往往先更新 CLI，再更新第三方集成接口。Orca 选择直接承载终端，使新功能更容易被继承。这减少了重复开发，但也要求终端、PTY 和状态恢复足够扎实。

#### 4. GUI 与 TUI 不必二选一

梁津晶认为，用户可以在图形界面完成全局管理，在终端里保留熟悉的 Agent 交互。GUI 负责空间、状态和审查，TUI 负责高频操作和上游兼容，两者承担不同工作。

#### 5. Worktree 是并行开发的基础设施，但不是全部隔离

每个任务使用独立 Git worktree，可以降低多个 Agent 同时改写同一文件的冲突，并让 PR 生命周期更清晰。不过，worktree 只隔离代码工作副本；数据库、端口、缓存、凭据和外部服务仍可能共享。若任务会运行应用或迁移数据，还需要容器、命名空间或其他运行环境隔离。这一条是对产品机制的边界归纳，并非嘉宾声称 Orca 已经解决了所有环境隔离。

#### 6. 恢复能力决定 ADE 能否成为日常工作台

如果应用升级或崩溃就丢掉几十个 Agent 的终端和上下文，用户不会把关键工作放进去。官方文档显示，Orca 会恢复 worktree、分屏、滚动历史和焦点标签，并通过后台 daemon 在应用退出或更新后保持 PTY 进程。主机重启后进程仍会终止，这也是清楚的运行边界。

#### 7. 高频发布的前提是状态连续性

“每天发布”只有在更新不会破坏用户正在进行的任务时才有价值。发布速度和会话持久化是同一个产品承诺的两面，而不是两个孤立 feature。

#### 8. Agent 状态不能只靠标签名

“运行中”“等待输入”“已完成”“失败”背后需要可靠的状态来源。仅凭终端最后一行或进程存活推断状态，容易产生假阳性。状态 API、任务事件和可恢复日志比颜色标记本身更重要。

#### 9. 搜索是多 Agent 产品的基础能力

Agent 数量增多后，用户记不住某个任务在哪个标签页。按需求、worktree、issue 和内容检索，是控制面的入口，而不是锦上添花。

#### 10. 插件不只应该扩展 Agent，也要扩展人的审查界面

现有插件通常强调 skill、command 和工具调用。梁津晶认为，未来还需要 UI plugin：例如针对 Markdown、网页、幻灯片、视频、芯片设计等产物提供专门的查看、标注和比较界面。Agent 能生成更多格式以后，人的验收工具也必须同步升级。

### 二、多 Agent 协作与组织效率

#### 11. 多 Agent 系统首先是可观察性系统

在没有统一状态、事件和结果索引时，增加 Agent 只会增加不可见的并发。模型是否更聪明固然重要，但团队能否定位偏航、阻塞和失败，是规模化之前的条件。

#### 12. 并行任务会把编码瓶颈转换成审查瓶颈

Agent 可以同时开二十个 PR，人却未必能同时判断二十个设计是否正确。若没有验收标准、自动测试和结果压缩，所谓并行只是在更快积累 review queue。

#### 13. 人应只处理高价值决策，而非过程噪声

理想的 Agent 不是每一步都向人报告，而是在方向选择、权限升级、不可逆操作和验收争议时请求介入。其他进展应被压缩为状态和证据。

#### 14. 最好的交接物是可审查产物

与其让 Agent 说“功能已经完成”，不如让它提供页面、截图、diff、测试结果、HTML 报告和失败日志。自然语言总结可以导航，但不能替代证据。

#### 15. Agent 间协作需要 contract，不只是 prompt

一个 Agent 将任务交给另一个 Agent 时，需要明确输入、产出格式、约束、验收条件和失败处理。没有 contract 的多 Agent 协作很容易变成信息逐层损耗。

#### 16. Manager Agent 不能替代真实状态机

管理 Agent 可以做计划、归纳和异常判断，但底层任务状态、依赖关系、权限和重试最好有结构化表示。完全靠自然语言“记住”几十个子任务，可靠性会随任务长度下降。

#### 17. 自动化应从稳定 SOP 开始

Release、triage、定期检查和格式化汇报通常比模糊的战略任务更适合自动化，因为输入、流程和验收更容易定义。先把重复性高的环节跑稳，再增加自主性。

#### 18. 长时间运行不等于有效工作

一个最强模型沿错误方向运行两天，可能不如较快模型在半小时内交付一个可检查设计。长时任务必须有中间检查点、预算和退出条件。

#### 19. 多 Agent 的上限由组织吸收能力决定

即使技术上可以运行几百个 Agent，团队仍需处理产品选择、风险、冲突和最终责任。Agent fleet 的合理规模，应由有效交付和人工决策吞吐量决定，而不是用“同时在线数量”衡量。

#### 20. 管理 Agent 的目标是压缩人的上下文切换

跨项目切换时，人的损失不只是几分钟操作，还包括重新构建问题背景。好的控制面应把“当前状态、上次决定、未解决问题、下一步”压成一个可快速恢复的单元。

### 三、模型、成本与中立控制面

#### 21. 模型选择是动态路由问题

梁津晶在访谈中多次提到自己的模型偏好变化。真正可复用的结论不是某个模型最好，而是最优选择会随任务类型、延迟、价格、额度和版本快速变化，工作环境不应把用户绑定在一次选择上。

#### 22. 快模型可能改善人机协作闭环

当人需要反复确认设计、纠正方向时，低延迟会增加检查频率，降低一次错误运行的沉没成本。此时“单位时间内完成多少次可靠迭代”可能比单次 benchmark 分数更接近真实生产力。

#### 23. 应比较任务总成本，而非 token 单价

任务成本至少包括模型调用、重试、人的等待、review、错误修复和机会成本。便宜但频繁偏航的模型可能更贵；昂贵但两天后才暴露方向错误的模型也未必划算。

#### 24. 订阅价格优势是阶段性红利，不是长期保证

梁津晶提到，团队通过多个第一方订阅而非纯 API 支撑高并发使用，成本显著降低。这是创始人报告的当期实践，不能外推为所有企业都能获得同样经济性，也不能假定厂商会长期维持相同额度和使用条款。

#### 25. 多供应商同时解决能力与容量风险

跨 Claude Code、Codex、OpenCode 等运行任务，既可按能力选择，也可在某一订阅额度或服务容量受限时分流。但跨供应商会增加权限、上下文迁移、结果一致性和合规管理成本。

#### 26. 中立性来自激励一致，而不只是兼容列表

模型厂商有动力扩大自家模型和平台占比；Orca 作为独立控制面，理论上更愿意让用户自由选择。这种激励差异是其价值来源之一。但是否构成护城河，还要看用户是否真的依赖跨模型工作流，以及迁移成本是否足够高。

#### 27. “上游会不会把你做掉”没有静态答案

Claude 和 Codex 桌面产品可以吸收并行任务、worktree 和状态管理。Orca 的应对不是押注它们永远不做，而是持续扩大跨 Harness、跨工具、编排和审查层的深度。风险始终存在，不能用“中立”两个字消除。

#### 28. 基准测试只能提供局部信号

梁津晶偏好更接近真实软件工程任务的 benchmark，但她的日常选择也受速度和体验影响。这说明 benchmark 可以缩小候选范围，不能替代在自己的仓库、流程和验收条件下做 shadow test。

### 四、产品方法与增长

#### 29. 从 Stably 到 Orca，是从垂直任务走向通用工作台

Stably 聚焦 AI 驱动的软件测试。团队在实际使用中发现，通用 coding agent 正在覆盖更多开发工作，而管理这些 Agent 的需求比单一测试环节更广。Orca 因此不是凭空换赛道，而是从原产品内部暴露的管理问题向上抽象。

#### 30. 好产品来自端到端执行，不只来自写代码

梁津晶将执行理解为：找到真实问题，理解已有替代方案，做出产品，交给用户，再根据使用行为迭代。AI 可以加快实现，但无法替团队决定该服务谁、解决哪个问题和何时放弃一个方向。

#### 31. 团队是产品最重度用户，缩短了反馈链

Orca 四人团队用 Orca 开发 Orca，使大量细节可以在内部高频暴露。这个 founder-user fit 是产品速度的重要来源。但它也有边界：专业工程师的需求未必代表普通开发者，更不自动覆盖大企业的安全、治理和采购要求。

#### 32. 用户访谈要问历史行为，不问假设意愿

梁津晶提到团队深入访谈约一百位用户，并采用《The Mom Test》式问题：为什么开始找方案、试过什么、过去付过多少钱、目前如何绕过问题。历史行为比“如果有这个功能你会不会买”更可信。

#### 33. 理解预算位置，比听到痛点更重要

Michael Seibel 给她的建议是理解客户的收入、增长和最大成本。一个问题让用户烦恼，不代表它在预算中足够重要；能否节省高成本、增加收入或降低风险，才决定商业价值。

#### 34. 先研究用户的 workaround，再设计新交互

用户已经如何用终端分屏、worktree、issue 系统和脚本拼出流程，往往揭示了真正需求。Orca 吸收 Ghostty、iTerm2 等成熟交互，而不是要求用户完全学习一套陌生工作方式。

#### 35. 定性与定量数据是输入，不能代替产品判断

功能使用率低，可能说明功能无价值，也可能是入口难找、性能差或目标用户尚未触达。小团队最终仍需结合场景做判断。所谓 product taste，不是拒绝数据，而是解释数据并承担选择后果。

#### 36. 产品细节需要多轮试错

访谈提到 Agent 状态在界面中的位置经过多次变化。方向正确并不意味着第一版交互正确；真正的产品能力体现在对使用摩擦的持续修正。

#### 37. 降低迁移成本比宣称颠覆更有效

Orca 没有要求用户放弃 Claude Code 或 Codex，而是让已有订阅和习惯在一个工作台中更好用。这使产品更容易借助上游增长，而不是先说服用户更换全部工具。

#### 38. 最聪明的营销是放大上游势能

团队会围绕 Claude、Codex 等新功能制作使用技巧，并展示它们如何在 Orca 中工作。上游厂商负责教育市场，Orca 承接因使用规模扩大而产生的新痛点。这里的“借势”有明确产品基础，不只是内容营销。

#### 39. 创造品类词可以获得早期分发

Orca 使用 ADE 描述自身，并借助 GitHub 搜索和开源传播获得关注。一个清晰品类词能帮助用户理解产品，也能承接搜索需求。但 4.9 万左右 GitHub stars 只说明开发者关注度，不能单独证明活跃用户、留存、收入或企业部署。

#### 40. 日更是组织设计的结果

官方仓库和访谈都强调高频发布。对于四人团队，这依赖其自身重度使用 Agent、较短决策链和产品内自动化。频率本身不是目标；修复反馈到进入用户工作流的周期才是价值。

### 五、创业心态与机会判断

#### 41. “松弛”来自不把自己锁在一次项目上

梁津晶经历过虚拟活动产品、Stably 和 Orca。她的表达不是“这个项目必须证明我成功”，而是只要资源允许，就继续尝试正确的问题。项目可以切换，积累的产品、工程和市场能力不会清零。

#### 42. 乐观来自看见非零和机会，而非忽视竞争

她在硅谷周围看到许多小团队在巨头旁边找到市场，因此更倾向于把 AI 视为扩张中的经济空间。这个判断支持了她的轻盈感，但它仍受所在网络、融资环境和市场阶段影响，不能机械复制。

#### 43. 小团队会被迫寻找十倍杠杆

美国工程人才昂贵、招人困难，小团队不得不利用模型、开源、订阅和平台分发提高单人产出。资源约束在这里转化为产品方法：不重复造底层能力，把有限精力放在用户看得见的控制面。

#### 44. 创始人最好与早期用户高度重合

当创始人每天面对同一问题，需求判断、体验反馈和优先级可以快速闭环。其前提是创始人确实代表目标市场中的一个重要群体，而不是把个人偏好误当成普遍需求。

#### 45. AI 机会不只在替代现有软件

梁津晶更看好扩展新行为、新消费和新生产能力的产品，而不是只在固定注意力池中互抢份额。她提到消费者应用、软硬结合、算力基础设施、AI 服务和传统行业改造等方向。

#### 46. 消费级 AI 的进入成本下降，但竞争没有消失

模型降低了开发成本，用户对 AI 服务的付费意愿也可能增加；与此同时，获客、留存、信任和差异化依旧困难。能做出产品不等于能建立业务。

#### 47. 中国供应链可能让软硬结合更有优势

访谈认为，硬件制造和供应链能力为中国创业者提供了差异化空间。更稳妥的理解是：供应链是一个重要条件，产品定义、软件体验、渠道和品牌仍决定能否形成长期价值。

#### 48. 企业 AI 落地会产生服务机会，也会承受需求快速变化

传统企业需要把通用模型接入真实流程，咨询、实施、行业软件改造和并购整合都有机会。但模型能力快速升级会让项目范围和采购判断频繁变化，服务商必须持续重估哪些环节仍有价值。

## Orca 的价值、护城河与风险

| 维度 | 当前价值 | 可能形成的积累 | 主要风险 |
| --- | --- | --- | --- |
| 多 Harness 兼容 | 用户可以并行使用不同 coding agent | 跨供应商工作流、迁移经验和统一状态 | 上游接口变化，兼容维护成本高 |
| Worktree 工作流 | 降低并行修改冲突，任务与 PR 更清晰 | 围绕任务生命周期的操作习惯 | 只解决代码隔离，未自动解决运行环境冲突 |
| 状态与搜索 | 减少逐个轮询终端 | 历史任务索引、异常模式和恢复体验 | 状态识别不准会快速损害信任 |
| 编排与自动化 | 将 SOP、派发和 decision gate 结构化 | 团队工作流和任务 contract | 仍属实验性能力，复杂度可能超过收益 |
| UI 插件 | 为不同产物提供专门审查界面 | 插件生态和专业场景适配 | 生态冷启动，接口稳定性和安全问题 |
| 开源与 GitHub 分发 | 降低试用门槛，获得开发者关注 | 社区贡献、品牌和品类心智 | stars 不等于留存，商业化仍需验证 |
| 小团队高频发布 | 快速吸收用户反馈和上游变化 | 产品节奏与内部自动化 | 关键人员风险、维护压力、企业支持能力 |
| 中立立场 | 与用户的多模型需求更一致 | 可信的第三方控制面定位 | 模型厂商捆绑、补贴和桌面产品挤压 |

### 对“护城河”的进一步判断

Orca 当前最有说服力的不是某一个 feature，因为分屏、worktree、通知和并行任务都可能被复制。更有潜力的积累是：

1. 跨多个 Harness 的稳定兼容；
2. 围绕真实任务生命周期形成的状态模型；
3. 用户把团队 SOP、审查方式和自动化沉淀进平台；
4. 针对多种交付物形成的人类验收界面；
5. 在上游频繁变化时仍保持可迁移性。

这些只有在用户长期把关键工作放进 Orca 后才会形成。若产品只是“一个更好看的多终端窗口”，迁移成本和防御性都会有限。

## 从 Stably 到 Orca：一次有逻辑的战略迁移

梁津晶的创业路径可分为三段：

### 第一段：虚拟活动与直播产品

团队进入 YC，产品获得增长和收入，但活动场景频率与留存有限。例如婚礼直播可能有明确需求，却天然不是高频行为。这段经历让她意识到，市场热度和一次性收入不等于长期使用。

### 第二段：Stably AI 测试

团队转向 AI 原生的软件测试和 Playwright 工作流，并服务企业客户。这个阶段积累了让 Agent 操作浏览器、执行测试和管理任务的实际经验。

### 第三段：Orca 通用 ADE

随着 Claude Code 等通用 coding agent 能覆盖更多软件工作，垂直测试工具的一部分价值可能被通用 Agent 吸收。团队看到的新问题是：用户开始同时运行越来越多 Agent，却缺少统一管理、并行隔离和审查环境。

因此，Orca 的迁移逻辑可以概括为：

> 当底层通用能力迅速上升时，不要死守可能被吸收的单点功能；观察能力扩散后产生的新协调成本，并向那个新瓶颈移动。

这也解释了 Orca 为什么不优先自建模型或底层 Harness。其战略建立在“上游继续快速进步”这一假设上，团队希望成为承接这种进步的工作空间。

## “松弛感创业”到底是什么

主持人将梁津晶描述为一种少见的“松弛感”。如果只把它理解为情绪稳定，会漏掉背后的经营结构。

### 1. 目标很高，但身份不与单个项目绑定

她对成功的定义并不低，访谈中甚至以十亿美元级公司为参照。松弛之处在于，一个项目失败不等于职业和人生失败，只要能力、资源和选择权仍在，就可以继续寻找下一个问题。

### 2. 借助势能，而不是与平台正面消耗

Orca 接受用户已有的 Claude、Codex 等订阅，承接上游发布带来的需求，并通过 GitHub 和品类词获得分发。产品、商业和营销使用的是同一套杠杆逻辑。

### 3. 资源约束让团队保持聚焦

四人团队无法同时训练模型、维护所有 Harness、建设 IDE、销售大企业并覆盖每个垂直行业。它必须选择最能形成差异的控制面，并依赖开源和现有生态完成其余部分。

### 4. 自己就是标准用户，减少抽象争论

当团队每天使用产品，很多优先级可以通过实际摩擦判断，而不必完全依赖宏大叙事。优势是速度，风险是视野偏向技术 power user。

### 5. 对未来的乐观降低了零和焦虑

梁津晶相信 AI 会释放新的生产能力，人类与 AI 在相当长时间里仍会互补。这个信念让她更愿意寻找新增量，而不是把每个竞争者看成对自身生存的直接威胁。

因此，“松弛感创业”可以被更准确地概括为：**高目标、低身份捆绑；高强度执行、低无效内耗；顺着技术和平台势能行动，同时保留切换方向的能力。**

## 反共识判断与金句式提炼

以下内容以忠于访谈原意的中文转述为主，不作为逐字引语。

1. **未来开发环境管理的不是代码文件，而是一支 Agent 队伍。**
2. **同时启动一百个 Agent 不难，知道哪三个现在需要你才难。**
3. **多 Agent 的第一性问题不是更聪明的主管，而是可信的状态、清楚的交接和可验收的结果。**
4. **模型能力越强，错误方向的代价可能越大，因为它能在错误方向上走得更远。**
5. **最快的模型未必最强，却可能更适合仍需人参与的协作闭环。**
6. **AI 把 prototype 推向 production 的速度提高了，但没有替你完成 production engineering。**
7. **如果每增加一个 Agent 都要增加一份人的注意力，系统就没有真正扩展。**
8. **好的 Agent 汇报不是“我做完了”，而是把 diff、测试、页面和失败证据摆到你面前。**
9. **Orca 不需要用户放弃喜欢的 coding agent；它要让这些工具能够一起工作。**
10. **模型中立不是品牌姿态，而是产品利益与用户选择权是否一致。**
11. **第一方厂商可以复制 feature，却未必愿意支持用户同时使用竞争对手。**
12. **创业产品最好的需求文档，常常是用户已经搭出来但很难用的 workaround。**
13. **不要问用户未来会不会付钱，要问他过去为这个问题花过什么。**
14. **GitHub stars 是注意力资产，不是商业模式。**
15. **小团队的优势不只是快，而是做产品的人每天都在承受产品的问题。**
16. **真正的 product taste 不是无视数据，而是在数据无法替你做决定时仍敢承担判断。**
17. **与其对抗一个正在变强的平台，不如解决这个平台变强以后新产生的问题。**
18. **松弛不是不想赢，而是不把一次输赢变成对自我的终审。**
19. **一个项目可以结束，已经获得的判断力、用户理解和执行能力不会归零。**
20. **AI 创业的空间不只来自替代旧工作，也来自过去因为成本太高而没人去做的事情。**

## 对创业者和产品负责人的可操作启示

### 如果在做 Agent 产品

- 先定义产品处于 Model、Harness、ADE 还是业务应用层，避免在不同层重复造轮子。
- 用真实任务单位设计信息架构，不要把所有东西都压进对话线程。
- 将状态、恢复、日志、权限和验收作为核心产品，而不是后台工程。
- 用任务完成成本衡量模型，不只看 token 价格或公开榜单。
- 让 Agent 输出可验证 artifact，并为高风险动作设置 decision gate。
- 在承诺“多 Agent”之前，测试团队能否消化并行带来的 review queue。

### 如果在做小团队创业

- 找到已经高速增长的平台，并观察其扩张后产生的新摩擦。
- 研究用户当前的 workaround，它比抽象问卷更接近真实需求。
- 把创始团队变成产品的高频用户，但主动补足企业和非专家用户的盲区。
- 选择能继承上游进步的架构，减少与资源雄厚厂商的重复建设。
- 区分关注、使用、留存、付费和组织级部署，不用单一增长数字替代业务判断。
- 保留方向切换能力，但每次切换都应来自新证据，而不是对困难的条件反射。

## 需要保留的证据边界

1. **“约 4.9 万 GitHub stars”是时间点数据。** 截至 2026 年 8 月 20 日，Orca 官方 GitHub 页面显示约 4.9 万 stars；该数字会变化，也不能证明商业收入。
2. **“四人团队”来自 YC 公司页与访谈。** 团队规模可能随时间变化。
3. **“每天稳定发布”“每天数百个 PR”等是公司或嘉宾口径。** 官方仓库可观察到高频更新，但具体内部产出和质量不能仅由访谈验证。
4. **数百个 Agent、二十个 PR review、API 月费可能达到数万美元等，均为嘉宾报告的内部实践或估算。** 它们展示可能的工作方式，不是通用 benchmark。
5. **模型偏好和 coding benchmark 排名高度时效化。** 本文保留模型路由方法，不把节目中的当期排名写成长期结论。
6. **Orca 当前的结构化 orchestration 被官方文档标为 Experimental。** 不应把它描述为已经在所有生产环境成熟验证。
7. **Worktree 不等于完整沙箱。** 文件工作区隔离之外，运行环境、数据和凭据还需额外治理。
8. **主持人对中美创业者气质和资源结构的对比属于节目观察。** 本文只提炼其启发，不将其扩展为普遍国家结论。
9. **关于 AI 就业、财富分配和未来行业机会的讨论属于个人判断。** 它们适合用作情景假设，不构成投资建议或确定性预测。

## 最终结论

Orca 所押注的并不是“未来只有一种 coding agent”，恰恰相反，它押注模型和 Harness 会长期快速变化，用户会同时使用多个能力来源。在这个前提下，稳定的价值可能向上移动到一个中立控制面：它知道每项工作从哪里来、由谁执行、运行在什么隔离空间、进行到哪一步、何时需要人，以及用什么证据证明完成。

这也是本期访谈最值得保留的判断：**Agent 工程的下一阶段，不只是继续提高单个 Agent 的自主性，而是重新设计人如何管理并行智能。** 真正可扩展的系统不会要求人盯住更多窗口，而会将人的注意力留给方向、例外和责任。

至于梁津晶所呈现的创业“松弛感”，其可学习之处也不是表面姿态。它来自一套很具体的选择：做自己真正使用的产品，接住上游平台的进步，围绕新增瓶颈建立价值，用小团队和自动化维持速度，并始终保留在新证据出现时切换方向的自由。
