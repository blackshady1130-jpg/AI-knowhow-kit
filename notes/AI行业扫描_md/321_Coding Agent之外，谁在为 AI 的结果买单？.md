# Coding Agent之外，谁在为 AI 的结果买单？AGI Bar 上海闭门交流后的几个观察

6 月 14 日晚上，我在上海的 AGI Bar 做了一场小范围闭门交流。

一开始定的题目是：**Coding Agent 之后，下一波 AI 爆发场景在哪里？**这个问题最近被问得很多。Coding Agent 已经跑出了相对明确的使用体感和付费意愿，大家自然会追问：下一个会是谁？客服、金融、法律、教育、内容生产、企业工作流、游戏、医疗，似乎每个方向都能讲出一套理由。

那天晚上聊到后面，问题慢慢变了：与其继续猜“哪个行业会爆”，不如先问清楚一件更基本的事：

**谁在为 AI 的结果买单？**

如果这个问题答不清楚，场景讨论很容易变成赛道竞猜。每个行业都有痛点，每个工作流都能被 AI 改造一点，但最后能不能形成商业化，取决于这件事原来有没有预算、结果怎么验收、失败谁兜底、数据和工作流能不能沉淀。



## 我先抛出的几个观察

这次交流开始前，我准备了一小段开场分享。最近半年，行业里有几个变化连在了一起。

**第一个变化是，企业客户开始算账了。**

前一段时间，很多团队会用 token 消耗、调用量、员工使用量来证明 AI adoption。早期这么看有意义，至少说明用户真的开始把任务交给 AI。但到了企业采购、预算复盘和续费阶段，客户会继续问：这些 token 到底换来了什么？

现场后面的讨论，基本都围绕这件事展开。



## token 消耗不是结果

那天现场有几个数字，虽然都是交流口径，但很适合作为判断锚点。

一个做企业内部 AI 落地的朋友提到，他们在医疗行业里做过内部报告工具。原来很多报告只有研发部门能做，一周大概做两三份。用了 AI 之后，业务侧也能直接生成报告，数量可以到二三十份。这个数字有意思的地方，不是“AI 写报告”这件事本身。真正的变化在产能分布：一件原本被研发资源卡住的工作，变成了更多业务人员可以直接完成的工作。

内容方向也有类似现象。现场有人提到，短剧、影视二创、内容矩阵已经带来很大的 token 消耗和收入规模。这个方向肯定有真实需求，但也要小心另一件事：token 消耗很容易被误读成商业价值。一个内容团队每天烧掉很多 token，可能是因为它真的提高了内容产能、获客效率和交易转化；也可能只是把批量生成、投流和平台内循环放大了一遍。

所以我对 token 的理解更接近“成本分母”。它能说明 AI 被使用了，但不能说明 AI 创造了结果。结果要看另一边：减少了多少人工，提升了多少转化，缩短了多少周期，降低了多少风险，或者让原来做不了的任务变成可交付。

如果 token 没有进入具体工作流，也没有对应业务指标，那它更像一张用量账单。



## 同一个场景，在不同市场可能是两种生意

客服是现场讨论最充分的案例。有做北美语音客服 Agent 的朋友讲到，北美客服是一个很现实的机会。人工贵，等待时间长，用户体验差，很多行业还有明显的电话服务习惯。保险、医疗、航空、银行这些场景里，用户并不总是愿意打开 App 或网页自助，打电话仍然是自然入口。

AI 在这里能算账：减少等待，降低转人工，覆盖长尾请求，处理催收、续费、upsell，也能减少季节性扩容和培训成本。

现场也聊到一个指标：containment rate，也就是 AI 能自己解决、不转人工的比例。按那位朋友的经验，海外很多场景做到 50% 已经不错；国内某些头部客服项目可以到 80%，但那往往依赖更好的业务条件和更成熟的流程。

同样是客服，国内电商给出的反馈就谨慎很多。有甲方朋友去年调研了半年国内大模型客服方案，最后放弃了。原因并不复杂：国内人工成本相对低，传统规则机器人已经覆盖了大量标准问题，商品和活动知识更新很快，RAG 稳定性还不够，乙方沟通和调优成本也不低。更重要的是，品牌方不愿意让大模型直接面对消费者乱承诺。简单错了可以补券，碰到舆情、投诉、敏感权益，成本就不是一张优惠券能解决的。

这组对照给我的提醒很直接：场景名没有那么重要，场景条件更重要。客服在北美可能是高 ROI 场景，在国内某些电商链路里就未必成立。判断一个 AI 场景，要看人工成本、客户体验、风险容忍度、知识更新速度、现有系统成熟度和买单方式。



## 已有预算的地方，更容易长出结果

聊了一圈之后，我会更关注已经存在预算的地方。

企业内部工作流是一类。报告、经营分析、标书、金融报送、合同审核、图纸提取，这些事情本来就有人在做，也本来就有成本。AI 不需要从零创造需求，只要把其中一段做得更快、更便宜、更稳定，就能进入预算讨论。

但这里也有一个边界。很多企业工作流的价值，最后会被压回“节省多少人力”。这当然有价值，但如果每个客户都要重新梳理流程、重写规则、重做知识库，标准化产品就会很难。它可能更适合企业内部效率工具、FDE 项目，或者平台加解决方案的组合。

内容生态是另一类。律师、保险、财经自媒体、旅游地陪、短剧和影视二创，看起来都在做内容，但背后的生意不同。有些人在卖咨询，有些人在获客，有些人在做订阅，有些人在招募团队，有些人在把流量导向交易。AI 在这些场景里真正改变的，不只是“生成一条视频”。它降低的是内容生产、信息整理、脚本生成、剪辑和分发的成本。只要后端有交易、订阅、线索或服务承接，前端内容效率提升就有可能变成收入。没有后端承接的内容生产，风险会更高。平台规则、AI 标识、投流成本、用户疲劳，都可能把表面繁荣压回去。

所以我更愿意把内容方向拆成两类看：一类是有明确收入池的内容工作流。  另一类是单纯的内容生成和流量套利。前者值得持续看，后者要看周期。



## 高价值场景，往往没有标准答案

会计和审计的讨论，是那天晚上我印象很深的一段。做 Coding Agent 时，很多结果可以被测试。代码能不能跑，bug 有没有修，CI 过不过，反馈链路相对清楚。会计不是这样。一台电脑怎么折旧，费用怎么分摊，账和报表怎么映射，在准则范围内可能有多种处理方式。审计里也不一定是一笔账对应一行报表，经常会有 m 对 n 的关系。更麻烦的是，有些时候连行业里的老师傅也未必能给出一个唯一答案。他可能能给出经验、口径和可接受范围，但很难把所有情况都变成一个清晰的 ground truth。

这类问题不只存在于会计。法律、教育出题、心理咨询、战略研究、创意写作，都会遇到类似情况。越是高价值、专业化、带判断的场景，越难用“唯一正确答案”来评估。这会带来一个很现实的变化：非 Coding Agent 的评估，很多时候要从 answer 走向 rubrics。也就是看它是否自洽，是否可追溯，是否符合某套专家标准，是否把风险说清楚，是否能让客户或专家承担结果。

这个标准未必对所有人都成立。只要它在一个客户、一个组织、一个市场里足够稳定，就可能形成商业化。



## FDE 的价值可能被低估了

最后聊到护城河时，FDE 这个角色反复出现。我以前会把 FDE 更偏向理解成“懂技术的解决方案/交付角色”。但这次交流之后，我觉得这个定义有点窄了。客户现场往往没有想象中干净。文档可能不一致，API 可能不稳定，SOP 可能只在老员工脑子里，权限和系统边界也不一定清楚。业务负责人想要 AI 提效，但他自己也未必能把任务定义成模型能执行的形式。

这种情况下，FDE 的工作会变得很具体：把模糊需求翻译成任务，把业务流程拆出来，把知识库整理到 AI 能读，把测试集搭起来，再把客户现场的问题反哺产品。

更有意思的是，Coding Agent 反过来增强了 FDE。过去 FDE 发现产品问题，很多时候只能提 ticket，等研发排期。现在他可以直接用 Coding Agent 看代码、改代码、跨 repo 发 PR，再让核心研发 review。FDE 从“反馈问题的人”，变成了能直接推动产品变化的人。

现场还聊到 skill 的沉淀。一个项目里踩过的坑、整理过的 SOP、写过的脚本、积累的 sample 和测试方式，可以被整理成 skill。下一次做相似客户时，新的 FDE 不必从零开始。Skill 本身未必适合裸卖。它容易泄露，也很难单独定价。但放在 FDE 体系、平台服务或托管 API 里，就会变成一种复用能力。

这也是我对 Agent 产品护城河的一个判断：模型会继续变强，浅层 prompt 和通用问答会被压缩。更难被压缩的，是客户工作流、历史任务、badcase、测试集、权限系统、专家标准和交付经验。

这些东西往往不是坐在办公室里想出来的，是在客户现场一点点磨出来的。



## 写在最后…

如果要判断一个非 Coding Agent 场景能不能跑出来，我现在会先问几个问题。

- 这件事原来有没有预算？

- AI 替掉的是哪段成本，放大的是哪段收入？

- 结果能不能被验收？

- 失败时谁兜底？

- 有没有真实任务、SOP、badcase 和人工修正记录可以沉淀？

- AI 是嵌进工作流，还是只停留在 demo？

- 模型继续变强后，这个产品会变厚，还是会被模型吞掉？



这些问题比“下一个爆发行业是什么”更麻烦，但更接近商业化本身。上海这一场的讨论更像把问题拆开了：token、结果、预算、评估、风险、FDE、数据，每一层都要重新看。

7 月我们计划在北京再做一场类似的小范围交流，继续聊 AI Agent、结果买单、评估标准和真实落地场景。也期待北京的朋友到时候一起参与。
