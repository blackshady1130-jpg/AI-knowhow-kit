## Key Takeaways

1. **自动 Memory 当前暴露出的主要问题，是误写和隐性调用。** 

    现场举手调查中，有十余位参与者表示会主动删除、重置或关闭 Coding Agent 的 Memory。有人遇到单一对话session中的要求、项目阶段和临时偏好被长期保留；也有团队在生产环境和自动评测中直接关闭 Memory，以隔离不同客户，并避免回归结果无法归因。

    **Comments：** Memory 的产品优先级应先放在写入准确性、任务边界、可见可删和调用可追踪上。用户主动关闭 Memory，并不说明长期记忆没有价值，只是凸显了当前agent产品做context积累机制上的“粗糙”，目前自动化程度已经超过了质量控制能力。

    

2. **Context 需要根据来源和生命周期放在不同位置。** 

    制造业规范、产品权益、代码仓库和项目阶段都可能持续变化；Agent 无法自行确认旧信息是否仍然有效。已有实践包括：把长期知识放进版本化文档仓库，把当前任务留在工作空间，压缩或切换 Session 后再按映射读取；知识库中的过期与冲突则交给业务人员确认。

    **Comments：** 实时事实、任务状态、长期 Memory 和可复用经验不宜共用同一套写入逻辑。动态事实应回到权威系统查询，任务状态随任务结束而失效，只有相对稳定并经过确认的内容才适合长期复用。

    

3. **Context 的问题经常发生在“选错和塞多”，并非单纯召回不足。** 

    有参与者明确反对把检索到的材料全部交给模型判断，因为无关内容会占用注意力并误导结果；现场讨论的方案包括用向量检索缩小候选，再用关系字段处理时间、版本和其他硬条件。多 Agent 场景中也有人观察到，Context 增长数倍后，产出只提升到约 1\.1\-1\.2 倍，甚至出现相互冲突、无法产出的情况。

    **Comments：** 运行时需要同时优化 Precision、过滤条件和 Context Budget。Markdown、向量库或图结构只是底层选项，真正影响任务质量的是系统在此刻选择了什么、排除了什么。

    

4. **Context 与 Memory 评测还没有形成稳定、可比的统一口径。**

    不同 Memory 项目采用的 Benchmark 和评分方法并不一致；字符级指标可能给关键数字错误的答案较高分，LLM\-as\-a\-Judge 也会随模型和提示词发生明显波动。做 Coding Agent 产品的参与者进一步指出，产品体验还取决于项目、语言和用户习惯，只能持续积累真实 Bad Case。

    **Comments：** 单一总分暂时不足以证明 Context 有效。评测至少要拆开检索是否正确、模型是否采用、任务是否完成，以及问题最终应归因到 Prompt、Skill、工具还是 Memory。

    

5. **主观任务需要拆成更窄、更稳定的判断，小样本用户和单一专家反馈也不能直接当金标。** 

    内容产品的实践显示，让模型评价“是否有吸引力”或打 0\-100 分并不稳定，但检查重复、事实错误、前后矛盾等问题相对可靠；修图产品将脸部比例等内容量化，同时用“是否导出”观察用户是否采用。工业场景则遇到另一种风险：现场专家给出的故障判断本身也可能错误，需要复核或升级。

    **Comments：** 主观场景可以把客观约束、专家规则、用户行为和人工复核组合起来，各自承担不同证据角色。一次修改、一次采用或一个专家意见，都不足以直接写回长期 Context。

    

6. **有限场景可以建立较强的 Context 工程闭环，但成本远高于一次 Benchmark。** 

    一家垂直售前 Agent 团队从历史对话中人工整理约 30 个典型案例，每个案例重复运行约 20 次；Simulator 负责模拟客户，Evaluator 按维度判断，Attributor 尝试定位 Prompt、Skill 或工具问题。团队只使用“符合 / 无法判断 / 不符合”三档结果，一个晚上可运行十余轮候选版本，往往只有一轮可用；测试时还会关闭 Memory，防止历史结果污染评测。

    **Comments：** Context 工程更容易先在任务边界清楚、场景可以枚举、验收条件能够拆解的垂直工作流中跑通。它的竞争力来自持续回归和故障归因，并不来自一次性接入更多知识。

    

7. **企业 Know\-how 的难点包括“说不清、意见冲突和谁有权拍板”。** 

    本场交流人员提及的企业实践中，业务专家难以完整表达隐性经验，不同营养师会对同一问题给出不同答案，技术团队与 HR 也会对服务范围是否合适产生分歧。已有团队要求 Skill、Agent、知识库或工具的提交者同时提供评测样本，由 AI 先复盘，再由对应负责人 Review 后合入新版本。

    **Comments：** 企业 Context 需要明确权威来源、业务 Owner、适用范围和发布流程。知识收集只是第一步，真正困难的是把分歧转化为可执行规则、例外条件和可回归的验收样本。

    

8. **Context Infra 的产品空间真实存在，但独立产品边界仍未形成共识。** 

    现场一方面认为，企业私有知识、业务口径和历史决策不可能被模型或 Harness 全部吸收；制造、半导体等行业还明确提出私有化部署、数据主权和导入导出需求。另一方面，讨论也指出企业内买单者、使用者和维护者经常分离，部门墙来自预算、权限和组织目标，单靠连接器无法解决。

    **Comments：** 更可能长期保留的能力包括多源连接、版本与权限、私有部署、评测回归和跨 Harness 可迁移；检索、压缩和基础 Memory 则可能逐步成为 Harness 标配。Context Infra 能否成为独立产品，最终取决于它能否给一线使用者带来直接收益，同时让组织获得可治理、可验证的结果。

## Topic 1｜真实工作中的 Context 从哪里来，为什么会失效

### 1\. 三类高频失败

现场案例可以归到三类：

- **信息缺失**：Agent 看不到现实世界和业务系统里的状态，例如设备报警、库存、客户进展、组织流程和临时决策。问题不在模型推理，而在系统没有给 Agent 足够的“传感器”。

- **信息过期或冲突**：规则、代码、产品权益和业务口径已经变化，旧版本仍被隐式召回。Agent 很难仅凭文本判断哪条规则具有当前效力。

- **信息被错误使用**：相关信息虽然存在，却没有被找到、没有被模型采用，或与大量无关内容一起进入工作集，造成注意力污染。

#### 讨论起点：Context 的工作定义

为了避免把模型、Context 和 Harness 层的问题混在一起，Jomy 在开场提出了一个便于讨论的工作定义：

```Plain Text
Agent = LLM + Context + Harness
Context = Memory + 知识库
```

这里的 Memory，主要指 Agent 在运行和交互过程中产生的信息；知识库则泛指来自 Agent 运行之外的人、文档、业务系统和现实世界的信息。这个二分法帮助现场区分了两类问题：制造业数据治理、企业文档和外部专业知识更多落在知识库一侧；跨 Session、跨 Agent 和长期偏好管理更多落在 Memory 一侧。

后续讨论也说明，这是一种便于交流的简化定义。当前任务状态、工具执行结果、实时业务数据和权限信息，很难完全塞进传统知识库或长期 Memory，仍需要在具体系统中进一步分层。



### 2\. 自动 Memory 可能成为隐蔽变量

现场最强的一组信号来自 Memory 的实际使用：十余位参与者表示会主动删除、重置或关闭 Coding Agent 的自动 Memory。原因并非拒绝长期记忆，而是当前产品经常把临时任务、阶段性要求和偶发偏好写成长期事实。

典型问题包括：

- 某次为比赛、演示或特定受众准备的要求，被系统理解为长期偏好；

- 项目已经进入新阶段，Memory 仍带着内测或早期设计时的旧认知；

- 不同代码仓库和业务域持续变化，隐式召回混入旧版本规则；

- 用户看不到系统为什么记住、何时调用，也难以判断删除是否已经传播到摘要、索引和其他 Agent。

一位企业 Agent 团队在生产环境和自动评测中直接关闭 Memory：不同 Session 对应不同客户，需要严格隔离；Memory 一旦参与召回，团队就无法判断回归来自 Prompt、Skill、业务知识还是隐藏状态。这说明 Memory 在产生价值之前，先要成为可观察、可控制的变量。



### 3\. 信息应该留在哪里

讨论中逐渐形成了一个比“全部写入 Memory”更稳妥的分层：

|**信息类型**|**更合适的位置**|**原因**|
|---|---|---|
|实时事实、价格、库存、设备状态、政策|原始业务系统 / Source of Truth|高频变化，需要保留权限、时间和权威来源|
|当前目标、约束、中间状态、待办|任务工作集|生命周期与任务绑定，任务结束后应归档或失效|
|稳定偏好、长期关系和对象属性|长期 Memory|需要明确 Scope、TTL、用户可见性与撤回机制|
|规则、案例、Skill、评测集、失败模式|可复用经验层|需要 Review、版本、适用范围和回放验证|

有参与者采用了较为明确的外部化方案：把项目进度、讨论结论和领域知识放在版本化仓库中，并与真实代码目录建立映射；Context 压缩或切换 Harness 后，Agent 必须回到对应节点重新读取。这种做法牺牲了一部分“自动记忆”的便利，但提高了可追溯性和跨 Harness 复用能力。



### 4\. 这一轮的共识与分歧

**共识**：Context 不能默认永久写入；过期、冲突和删除最终需要业务 Owner 或用户保留决定权。

**分歧**：面向大众的 Agent 产品仍需要默认 Memory，产品要服务没有能力自建系统的多数用户；重度用户更希望 Memory 可选择、可检查、可关闭。两者并不冲突，真正缺失的是分层控制，而非简单决定“要不要 Memory”。

**Comments**：如果关闭 Memory 后效果和可评估性反而提高，产品当前优化的重点应从 Recall 转向写入 Precision、调用 Precision、隔离和可解释性。

## Topic 2｜企业 Know\-how 怎样被 Agent 消费，哪些 Context 值得共享

### 1\. 保存格式不是唯一问题

现场讨论了 Markdown、向量检索、知识图谱以及更结构化的图关系方案。比较一致的判断是：单纯把资料转换成某种格式，不会自动解决 Context 问题。

- Markdown 对人友好，易于版本管理和跨 Harness 搬运，但不擅长表达时序、对象关系和精确权限。

- 向量检索能降低关键词漏召回，但仍需要结构化条件处理时间、版本、区域和权限。

- 图结构有助于表达实体关系，但构建和维护成本高；如果输入质量、责任人和更新机制没有解决，图只会把脏数据结构化。

- 让模型读取所有候选材料，会把检索成本转移到推理阶段，并增加上下文污染。

现场提出的一条技术路径是：先用轻量语义检索缩小候选，再通过关系数据库或结构化字段完成时间、版本和权限筛选。其价值不在某一种数据库，而在于把“语义相似”与“业务上当前有效”拆成两步。



### 2\. Know\-how 需要任务化表达

企业 Know\-how 分散在流程、历史决定、案例、专家修改和验收标准中。Agent 真正能消费的形态可能包括：

- 可直接执行的规则和 Skill；

- 带适用条件的案例与反例；

- Workflow 中的检查点和人工接管条件；

- 业务 Rubric 和评测样本；

- 失败模式、回滚方法和责任边界。

一项社交内容分析实践暴露了典型难题：系统容易提取客观事实，却会丢掉随时间和作者变化的主观观点；但对内容创作而言，观点恰恰可能比事实更有价值。此时不能把“客观事实”当成唯一高质量知识，需要同时保留时间、作者、受众、立场和使用目的。



### 3\. 运行时选择比全量注入更重要

Context 是否应该 Push 给 Agent，还是由 Agent 在运行时 Pull，取决于任务：

- 稳定规则、权限边界和验收标准适合提前注入；

- 实时状态和大体量资料适合按需查询；

- 当前任务状态应留在具体工作空间；

- 跨 Harness 共享的内容应以项目事实、版本化决定、稳定 Skill 和权限规则为主。

Session 噪声、未经验证的自动总结、工具私有状态和快速变化的事实，不适合直接进入共享层。统一 Context schema 可以降低迁移成本，但不应抹掉不同 Harness 所需的任务状态和原生能力信息。



### 4\. 治理必须发生在结构化前后两端

人更适合审查原始文档、业务规则和权威来源；信息被切片、向量化或转成复杂关系后，逐条人工治理的成本会迅速上升。更现实的分工是：

1. 结构化之前，由业务 Owner 确认来源、范围、版本和权限；

2. 结构化之后，由系统监测冲突、异常使用和结果退化；

3. 命中异常后，再回到原始材料和责任人处理。

**Comments**：Context Infra 的重点不应被压缩成“更好的知识库”。它至少还包括运行时 Router、权限继承、版本失效、工作空间隔离和跨 Harness 的调用协议。

## Topic 3｜怎样证明 Context 有效，真实反馈何时能成为经验

### 1\. 现有评测离真实使用仍有距离

现场对两类常见评测方法提出了质疑：字符级 F1 可能给关键事实错误的答案较高分；LLM\-as\-a\-Judge 对模型选择和提示词高度敏感，同一答案的评分可能明显波动。Memory 论文和产品使用的 Benchmark 也缺少统一口径，SOTA 分数之间未必可比。

更重要的问题是，检索正确并不等于任务成功。Context Eval 至少要检查五层：

```Plain Text
信息是否存在
→ 来源、版本与权限是否正确
→ 是否被运行时选中并被模型采用
→ 任务结果是否改善
→ 能否在其他任务稳定复用
```



### 2\. 主观任务先拆成可判断的小问题

内容创作、美学、会计判断等场景缺少单一 Ground Truth。现场较可行的实践并非直接让模型打一个 0\-100 分，而是先拆出更稳定的判断：

- 是否前后矛盾、重复或存在明显事实错误；

- 是否违反业务边界或做出不应有的承诺；

- 是否符合可量化的专家规则；

- 用户是否采用、导出、修改或放弃结果。



### 3\. 企业场景需要把业务口径写成硬约束

数据分析 Agent 的案例显示，同一句“用户数”在不同部门可能分别指设备 ID 去重或账号 ID 去重。如果口径只靠模型临时理解，同一个查询在不同时间可能得到不同结果。对于财务、政企和管理汇报，一次口径漂移就足以失去用户信任。

因此，关键指标、字段选择和禁止动作需要进入可版本化的语义层或规则层，而不是只依赖自然语言检索。Context Eval 也要检查 Agent 是否使用了正确口径，不能只看最终数字是否“像是合理的”。



### 4\. 用户和专家反馈都不是天然 Ground Truth

To C 产品可以从大样本行为中寻找概率信号；To B 和工业场景频次低、风险高，每一次专家修改都可能影响后续任务，不能默认写回。

现场给出了三种处理方式：

- 客服场景比较 AI 草稿与人工最终发送版本，将差异拆成语气偏好、知识缺失和无标准答案三类；

- 工业设备场景对专家判断设置复核或升级机制，避免单个“老师傅”的错误反馈污染知识库；

- 企业平台要求 Skill、Agent 或知识能力的提交者同时提供评测样本，AI 先复盘，责任人 Review 后才能进入新版本，并定期跑回归集。

    

### 5\. 有限场景可以建立工程化闭环

一家垂直售前 Agent 团队将目标客户、典型问题和业务边界视为有限集合：

- 从历史对话中人工整理了约 30 个典型评测案例；

- 每个案例重复运行约 20 次，降低单次采样波动；

- 结果不强行打连续分，只分为“符合 / 无法判断 / 不符合”；

- Simulator 模拟客户，Evaluator 检查不同维度，Attributor 尝试归因到 Prompt、Skill 或工具；

- 候选改动重新跑完整回归，只有全面优于旧版本才进入下一轮。

这套方法成本不低：一个晚上可跑十余轮，可能只有一轮产生可用版本，本质上是用时间和 Token 换稳定性。团队同时关闭 Memory，确保测试 Agent 无状态，避免召回历史结果造成污染或“作弊”。



### 6\. 反馈写回需要一道发布验收机制

现场案例可以归纳成一条较完整的链路：

```Plain Text
用户行为 / 专家修改 / 下游结果
→ 形成候选经验
→ 判断问题属于事实、规则、Skill、Memory、评测还是模型
→ Owner Review
→ 回放与回归验证
→ 带 Scope、版本和有效期发布
→ 支持回滚与删除传播
```

现场没有出现把反馈直接训练进模型的成熟案例。大部分团队仍优先修改 Prompt、Skill、规则和知识层，这也是当前归因成本最低、回滚最容易的路径。

**Comments**：Context Eval 的第一目标是帮助团队定位故障，而不是生产一个漂亮总分。能够说明“用了哪条 Context、哪个版本、在什么步骤影响了结果”，比单独提高 Recall 更接近生产需要。

## Topic 4｜Context Infra 会成为哪一种产品

### 1\. 模型与 Harness 会吸收什么

更长上下文、更强模型和成熟 Harness 会继续吸收通用能力：

- 基础检索、重排与压缩；

- 自动摘要和一般性的 Memory 写入；

- 常见 Skill 发现与工具路由；

- Session 管理和基础工作区能力。

这些能力如果没有行业数据、权限和责任链，很难单独支撑一家 Context Infra 公司。



### 2\. 组织仍需要自己控制什么

模型公司很难替企业决定以下内容：

- 哪个系统是权威事实源；

- 哪条规则当前有效，谁有权修改；

- 哪些信息可以跨部门、跨 Agent 使用；

- 企业特有的业务口径、历史决定和验收标准；

- 一次反馈是否足以写回，以及如何撤销和追责。

因此，较长期的控制点仍会落在连接器、真源管理、权限、版本、审计、Context Eval 和反馈生命周期上。现场也提出了一种更开放的设想：Context 最终可能形成可导入、导出和迁移的格式，避免个人或企业被单一 Harness 锁定。这仍是产品假设，尚未形成行业标准。



### 3\. 产品化不能绕过组织问题

企业里的 Context 既是数据，也是信息权和决策权。现场形成了几组有价值的分歧：

- **自上而下还是自下而上**：管理层希望统一规则和全局视角，一线人员掌握真实案例和例外。更可行的机制是由上层定义边界和目标，再让真实 Case 持续攻击、修正这些规则。

- **共享还是隔离**：跨部门共享能减少重复沟通，但预算、数据和 OKR 并不一致。技术连接器可以打通数据，不能自动解决部门是否愿意共享。

- **买单者、使用者和维护者是否一致**：企业采购者往往不直接使用，使用者也未必承担 Context 质量。产品必须明确谁负责更新、谁承担错误、谁能看到使用日志。

- **私有化还是云服务**：半导体、制造、医疗等行业更强调本地部署和商业机密；Context 越完整，企业对数据主权和可迁移性的要求越高。

企业规模不是判断 Context Infra 成熟度的好指标。小型 AI Native 团队更容易统一工具和工作方式，但不代表其治理更成熟；传统企业的推进速度更多取决于任务是否明确、业务 Owner 是否投入，以及是否有可验证结果。



### 4\. 更可能出现的产品形态

现场没有形成唯一答案，但几种路径已经比较清楚：

|**产品形态**|**主要用户**|**可能的切入点**|
|---|---|---|
|个人 Memory / Context 控制台|重度 Agent 用户|查看、修改、删除、跨 Harness 搬运与任务归档|
|企业 Context 控制层|AI 平台、数据与安全团队|多源接入、真源、权限、版本、审计和运行时组装|
|垂直行业解决方案|业务部门、FDE、专家团队|Know\-how 提取、Rubric、评测集、反馈 Review 与交付|
|Context Eval / 可观测性|Agent 产品与工程团队|故障归因、Context 使用链路、回归和单位成功任务成本|
|可移植 Context 格式|工具厂商与开发者|导入导出、跨 Harness 共享和避免平台锁定|

**Comments**：短期更容易形成预算的形态，是嵌入具体工作流的“Context 治理 \+ Eval \+ FDE”。企业只有在结果可验收、责任可归因时，才会持续投入维护 Context 质量。

## 现场共识与反共识

### 相对明确的共识

- Context 必须服务具体任务，不能为了积累而积累。

- 更多 Context 不等于更好结果；错误或无关 Context 会直接降低质量。

- 高价值 Context 大量存在于业务系统、现实状态、历史决定和人工修改中，不只来自 Agent 对话。

- 自动写回必须保留人工 Review、版本和回滚机制。

- 企业私有 Know\-how、权限和评价标准不会因为基础模型变强而自然消失。

    

### 被现场案例推翻或削弱的直觉

- **“Memory 越多，Agent 越懂用户”**：当前重度用户反而频繁删除 Memory。

- **“用户或专家修改就是金标”**：高风险、低频场景需要复核和权威来源。

- **“召回正确就说明 Context 有效”**：还要检查是否被采用、是否符合权限和业务口径、是否改善结果。

- **“统一存储格式就能解决 Context 问题”**：格式只能解决一部分迁移和检索，责任、版本和生命周期仍在。

- **“跨部门共享主要是技术问题”**：信息权、预算和组织激励常比接口更难处理。

    

## 总结

本场讨论把 Context Infra 从抽象概念拉回了生产问题：系统记住什么、为什么在此刻调用、谁确认它仍然有效、错误如何被发现，以及一次修改何时有资格影响下一次任务。

Context Infra 仍处于很早的阶段。当前最缺的是一套能把优质“真值”信息源、任务状态、运行时选择、结果验证和经验写回连起来的工程机制。对于企业，这套机制最终还必须回答三个角色问题：谁使用，谁维护，谁为结果和错误负责。
