## 正文

写在最前: 上一篇刚扒完 RSI，我已经开始闻到下一轮 fancy narrative 要起来的味道了。Loop、Recurrent Depth、MoR、Latent Reasoning、Adaptive Compute、Reasoning Token Efficiency，接下来大概率都会被往一个更大的故事里塞。再把 GPT 新发的 Astra 往中间一摆，很容易就从一个模型结构问题，一路画到“下一代 reasoning paradigm”。

所以这篇我想赶在大家正式开始崩之前，先把底裤扒了，顺便把路数堵一堵。Loop 本身一点都不新。真正值得看的，是大模型开始从“固定计算”往“动态计算”走，而且计算本身正在从 architecture 里写死的东西，变成可以被模型学习和分配的资源。

Scaling 大家肯定都不陌生，过去 scaling 最常见的是给模型更多东西：更多参数、更多数据、更多 token。Loop 这波重新带回来的，反而是一个过去被 Transformer 暂时压下去的轴：时间 / 迭代深度。同一组能力，不一定只能调用一次。它能不能被重复调用？每次调用能不能承担不同 computational role？能不能从粗理解到 deeper representation，再到 reasoning 和 solution？

如果这条线真的跑通，真正变化的不是“Transformer 会不会 Loop”，而是：模型开始自己决定 Compute 应该怎么花。

再往深一点，我现在更愿意把这几条路线放在一起看：MoE 在参数空间上 scale capacity，Loop / MoR 在时间和深度上 scale computation，CoT 在 token 轴上 scale working memory，Sparse Attention 在 context-access 轴上 scale memory access，Recirculation 在 state 轴上 scale internal persistence。未来真正的大问题可能根本不是“选哪个架构”，而是：Parameter、Depth、Time、Explicit Memory、Latent State、Context Access，这些资源到底应该怎么动态组合。

大家看到这些名词先别害怕，我马上拆开最通俗的方式给大家说清楚。

### 先把 CoT、MoE、MoR、DSA、Recirculation 全拆开

现在最容易发生的问题，就是看到大家都有 router、都有 loop、都有 sparse，就觉得是一回事。其实它们控制的是完全不同的计算资源。

#### CoT，Chain of Thought

原来 Question → Answer，现在变成 Question → Thought 1 → Thought 2 → Thought 3 → Answer，本质上是在增加 token-space compute，把更多 test-time compute 显式展开成 reasoning token。简单来说就是“多说几步”。

更深一点看，CoT 不只是“多算”，它还顺手得到了一块会不断变大的 scratchpad：每吐一个 token，就把一个新的中间状态写进 context，后面的计算可以继续读取。所以 CoT 的优势不只是 sequential computation 更多，还包括显式 working memory 会随着 reasoning 长度一起增长。

它的问题也很直接：“多想”和“多说”基本被硬绑在了一起。想得越久，往往吐得越长，latency、token cost、KV cache 一起涨。

#### MoE，Mixture of Experts

模型里可以有很多 expert，但每个 token 不需要全部跑，由 router 选择少量 expert。它做的是 width routing。简单来说就是“让这个 token 去哪个专家那”。

更深一点看，MoE 真正重要的不是“参数多”，而是它把总参数容量和单 token 实际激活成本拆开了。模型可以有巨大 stored parameters，但每个 token 只激活其中一部分。也就是说，从 MoE 开始，模型的计算路径就已经不再完全固定。

#### MoR，Mixture of Recursions

如果刚才讲的 MoE 是“去哪个 expert”，MoR 就是“算多深”。它共享一组 Transformer layers，再让 router 给不同 token 分配不同 recursion depth。简单 token 早点退出，难 token 多跑几轮。简单来说就是“这个 token 值得想几轮”。

MoE 是 width routing，MoR 是 depth routing。真正有意思的是，MoR 把原来写死在 architecture 里的“深度”，变成了 token-level decision。过去一个 48 层模型，大家默认都走 48 层；MoR 在问：为什么“深度”不能像 expert 一样被 routing？

#### DSA / Sparse Attention

长上下文里 full attention 太贵，所以 DSA 这类方法会先筛一遍，挑出当前 query 真正相关的 token，再做主 attention。它优化的是 context access，不是 depth。简单来说就是“这个 token 到底要看谁”。

MoR 在问“谁值得继续深算”，DSA 在问“这一层到底值得看谁”。两者都属于 conditional computation，但条件作用在不同资源上。

#### Recirculation

MoR 更像同一个 token 在 depth 上多跑几轮；Recirculation 更像把前面已经形成的深层 state 回流给后面的计算，让模型能够持续维护一种 belief / internal state，而不是每一步又从浅层重新堆起。简单来说“留着前面已经形成的理解”。

更深一点看，它是在尝试把 Transformer 从“一次前馈映射”重新理解成一个 dynamical system：state 不再只能随着 layer 单向流动，而是可以跨 input step 持续更新。

#### 简单记住这几个概念

如果你想最简单地记这几个概念，不要背全称，直接记它们“在决定什么”。

CoT 决定的是要不要多生成几步 reasoning token，所以它主要动的是“过程长度”；MoE 决定的是这个 token 去哪个 expert，所以它主要动的是“参数路径”；MoR 决定的是这个 token 要算多深、跑几轮，所以它主要动的是“计算深度”；DSA / Sparse Attention 决定的是这个 token 这一层到底要看哪些上下文，所以它主要动的是“信息访问范围”；Recirculation 决定的是前面已经形成的内部理解，要不要继续带到后面的计算里，所以它主要动的是“内部状态”。

我们再简单一点，其实这几个都可以统一成一句话：它们都在给模型做资源分配，只是分配的资源不一样。CoT 在分配“时间/步骤”，MoE 在分配“参数”，MoR 在分配“深度”，DSA 在分配“注意力”，Recirculation 在分配“状态保留”。

我们也可以再用“一个人在做题”的类比：CoT 是这个人把草稿写得更长；MoE 是遇到不同问题叫不同专家；MoR 是难题多想几轮，简单题少想；DSA 是从一堆资料里只看相关那几页；Recirculation 是前面已经形成的判断别忘，后面继续带着这个判断往下推。

所以你以后看到一个模型层新词，先别管它名字多 fancy，就问一句：它到底是在决定“说多少、谁来算、算多深、看哪里，还是记住什么”？

### Loop 和上一篇 RSI 的 R，不是同一个层级，但确实是同一种“递归审美”

有人会问：Recirculation 既然也是 recursive，那它是不是我上一篇 RSI 里的那个 R？不是，但确实有同一种递归审美。

上一篇 RSI 的 R 是：AIₜ → 改进 AIₜ₊₁ → AIₜ₊₁ 更擅长继续改进 AI。这是 system-improvement recursion。

Recirculation 的 R 是：internal state → 回流 → state update → 下一步继续用。这是 computation-state recursion。

一个发生在“AI 怎么改进 AI”的系统层，一个发生在“模型内部怎么持续计算”的模型层。层级不同，但背后都是把“一次性前馈”改成“上一轮结果重新进入下一轮”。

这也是为什么我觉得这两篇文章其实能连起来看。上一篇讲的是系统级 feedback loop，这篇讲的是模型内部 feedback-like dynamics。两条线不是同一回事，但都在把智能从静态函数往持续状态更新的动态系统推。

所以更准确地说：Recirculation 不是 RSI，但它可以理解成“递归更新”这套思想在模型内部的一个版本。

### LoopMoE 真正证明了什么：同参数、同 FLOPs，Loop 还有没有独立价值？

说到这里可能就会有人问了：“Loop 不就是同一组权重多跑几遍吗？如果你给它更多 compute，它当然可能更强。那到底是 Loop 有用，还是你偷偷给了更多算力？”

这一直是 Loop 研究里最难拆清楚的问题之一。比如原来模型有 12 个独立 layer，你改成 6 个 layer 跑两遍。参数少了，但 FLOPs 可能没少。最后效果变化，到底来自 parameter sharing、effective depth、FLOPs、capacity，还是其他变量，很难干净拆开。

今年有一篇叫《LoopMoE: Unifying Iterative Computation with Mixture-of-Experts for Language Modeling》的论文，专门想回答这个问题：Loop 的收益，到底来自“反复计算”本身，还是只是来自额外的 compute / capacity confound？

它的做法，是把 MoE 和 Loop 放进同一个框架里，然后尽量把这些变量拆开。作者把 MoE 和 Loop 看成两个相对正交的 scaling axis：MoE scale parameter capacity，Loop scale effective depth。 然后在总参数量、per-token FLOPs、active sublayer structure 尽量匹配的情况下，让 LoopMoE 和 Vanilla MoE 正面对照。

这篇 paper 真正有价值的地方，就在于它不是简单做“加了 Loop 以后分数涨没涨”，而是在尽量做一个 controlled comparison：如果我不给 Loop 更多参数，也不给它更多 per-token FLOPs，它还有没有额外收益？

结果很有意思：3B 规模里大部分 benchmark 胜，平均优势大约 1 point；9B 规模 9 个 benchmark 全部提升，平均优势接近 3 points。这个结果至少给了一个比较干净的答案：Loop 在 matched budget 下确实有独立收益的初步 evidence。

但这里绝对不能直接跳成：“Loop scaling law 已经成立。” 还远。两个主要 scale point 不够。真正要叫 scaling law，你至少想看到 1B、3B、9B、30B、70B，多 seed，不同 training token budget，以及 loop count × width × depth 的系统 trade-off。

所以现在最准确的判断是：Loop 的收益没有随着规模扩大而消失，而且目前有扩大趋势。

### Loop 真正难的是“共享权重但不能共享行为”

Loop 最容易被低估的地方，就是大家会觉得：同一层再跑几遍不就行了？没那么简单。

如果每一轮都是同一个：hₖ₊₁ = Fθ(hₖ)。你希望发生的是：粗理解 → deeper representation → reasoning → solution。但也完全可能发生：差不多 → 差不多 → 差不多 → saturation。甚至 drift。

所以 Loop 真正的难点不是“共享权重”，而是：共享权重以后，怎么让不同 iteration 承担不同 computational role。

LoopMoE 里的 IterAdaLN 就是在解决这个问题。简单说，就是让模型知道：“我现在是第几轮，而且当前 token 处于什么状态。”physical weights 虽然共享，但不同 iteration 通过 modulation 可以表现出不同的 effective transformation。

所以真正值得看的不是：weight tying。而是：weight tying + iteration-conditioned computation。

同一套参数，在第 1 轮和第 4 轮能不能承担不同功能，这才是 Loop 的难点。这已经开始接近一种：Conditional Recurrent Computation。

另一个核心设计 Capacity Balancing 也不是小修小补。因为一旦 loop，Attention 和 MoE FFN 的 effective capacity composition 会发生变化：Attention 每轮还是那一套参数，但 FFN 每一轮可能 route 到不同 experts。一个 token 随着 loop 次数增加，在 trajectory 上见过的 unique FFN capacity 可能变多。

如果不控制这个变量，你以为“Loop 赢了”，其实可能只是它偷偷激活了更多 FFN capacity。

所以 Capacity Balancing 本质上是在防止：Loop 偷吃 capacity。这也是为什么认真比较 Loop 远比“绑几个 layer 跑几遍”复杂。

### 为什么同样参数、同样 FLOPs，Loop 还是可能更强？

然后就到了最本质的问题：“参数没多、FLOPs 也没多，那凭什么 Loop 还能更强？” （FLOPs 大家可以简单理解成模型实际需要做多少计算）

现在没有一个被完全证明的答案，但至少有几种合理解释。

第一种是迭代式修正。一次计算不够，那就让内部状态连续更新：state₀ → state₁ → state₂ → state₃。它不是一步把输入直接映射到答案，而是允许模型先形成一个粗判断，再不断修正。这个机制天然更适合那些“答案不是一次算出来，而是越算越接近”的任务，比如数学推理、代码调试、规划、搜索、复杂决策、长链条分析。你可以把它理解成：不是一次想对，而是允许自己改答案。

第二种是重复执行同一种算法。很多任务本来就不是“每一步做一件完全不同的事”，而是不断重复同一个过程。比如图搜索是在反复扩展和筛选节点，长除法是在重复同一套计算规则，多步推理是在不断更新当前结论，belief update 本质上也是拿到新信息以后持续修正当前状态。这种任务很适合 Loop，因为它天然对应：学会一个步骤，然后反复执行。

第三种是共享计算规则带来的归纳偏置。普通深层 Transformer 每一层都可以学完全不同的东西，而 Loop 强迫多个计算阶段共享一套参数。好处是，模型可能更容易学出一种可以重复使用的通用规则，而不是每一层各自记一点模式。但这一点现在更多还是 hypothesis，还不能说已经被证明。

所以一定要分清两件事：Loop 有 gain——现在已经有比较好的 controlled evidence；Loop 为什么有 gain——还没有被完全解释清楚。

但这里还有一个非常重要的边界：Loop 擅长的，不等于所有任务。

它更适合的，是那些本身就有明显“反复处理”结构的任务。比如数学题，一步算错了可以继续修；代码生成和调试，可以先写、运行、报错、再改；搜索和规划，需要不断扩展候选、回看结果、重新选择；复杂推理，需要把中间结论带到下一步继续更新；长文理解和信息整合，也可能需要多轮压缩、校正和重组。简单说，凡是“越做越接近答案”的任务，Loop 都比较有直觉上的优势。

但它不一定适合那些更依赖知识容量、模式覆盖和表示多样性的任务。比如海量事实记忆、广泛领域知识、特别依赖不同抽象层级和不同特征提取的任务，更多独立参数可能反而更重要。因为重复调用同一套参数，毕竟不会凭空创造新的知识槽位和新的表示空间。

一个老师把同一道题想八遍，和八个不同领域专家各看一遍，不是一回事。所以一个 1B 的 block loop 8 次，绝不能写成“相当于 8B 模型”。它只是把同一套能力调用得更深，不是获得了 8 倍独立容量。

这里真正的核心其实是一个很经典的权衡：模型容量，和计算深度，到底怎么分。

过去的大模型 scaling，几乎一直在往“模型容量”那头堆：更多参数、更多专家、更宽的网络。Loop 重新把另一头拉回来：同样的参数，能不能通过更多轮计算被用得更充分。

所以真正值得看的不是“Loop 会不会取代 Parameter Scaling”，而是：给定同样的训练和推理预算，到底有多少应该花在更多独立参数上，有多少应该花在重复计算上。

如果未来发现，模型做到一定规模以后，继续加参数的边际收益越来越小，而让现有参数多想几轮反而更划算，那 Loop 就可能成为一个很重要的新 scaling axis。反过来，如果共享参数很快就饱和，那它可能更像一种对特定任务有效的效率技巧，而不是普适范式。

所以未来真正应该证明的，不只是：“我比 matched baseline 高了 2.8 分。”更重要的是：随着总预算扩大，模型容量和重复计算之间的最优比例，会不会发生系统性变化。

这个问题现在还完全没有答案。当然我想解决，但钱都被表演艺术家崩走了，老头好不容易募来的金币又被耍了，反过来又感叹人家美国怎么进步这么快呢。

### Scale、Data 和 Loop：哪些是证据，哪些只是忽悠人的猜想

这里最容易被下一轮 narrative 放大。先说 scale。

“小模型不 work，所以 Loop 不 work”这种判断很弱。LLM 本来就是极度 scale-dependent 的系统。很多机制在几百 M 上没有，在几十 B 才出现明显收益。所以用特别小模型实验没 gain，不能直接外推 frontier model。

LoopMoE 从 3B 到 9B 的优势扩大，至少给“更大模型可能更吃 Loop”这个 hypothesis 一点支持。但反过来也一样：3B → 9B gap 变大，不等于 Loop scaling law 已经成立。

两个 scale point 不够。真正值得继续看的，是更大规模以后 gain 是继续扩大，还是开始 saturation。

然后是一个更深的猜想：Loop 会不会更省数据？这个逻辑非常漂亮。过去 More Parameters 往往要求 More Data 才能把参数训透，但高质量数据不一定能一直同比 scale。

Loop 提供另一条路：不增加 stored parameters，但增加同一组参数参与计算的次数。也就是提高：compute / parameter ratio。

这在一个“数据越来越贵，但 compute 还能继续增加”的世界里，确实可能很有吸引力。甚至很容易形成一个新的 narrative：

The next scaling frontier is not more data, but deeper reuse of computation over shared parameters.

这句话听起来非常对。但注意：现在还没有被证明。LoopMoE 证明的是同样 training token budget 下效果更好，不是达到同样效果真的需要更少 training data。真正证明 data efficiency，你得看：performance vs training tokens。而不是只看最终 benchmark，但这帮崩钱的和老头们就只看 benchmark。

马上一定会有人把：same-data better偷换成：requires less data。这个等号先堵死。

### Loop 和 CoT 到底什么关系：Latent Reasoning、显式 Working Memory、PT/SFT/RL

这里是另一组特别容易吵起来的问题。有人会说：“CoT 既然有效，Loop 大概率也有效，因为 CoT 本质上也是一种不精确的 Loop。”

从上层想有点道理。两者都在做：More Sequential Computation → Better Result。但它们真正不同的是：中间状态存在哪里。

CoT 把中间状态写成 token，存在 context 里。Loop 把中间状态放在 hidden activation / latent state。所以 CoT 每生成一个 token，都在扩大显式 scratchpad；一个 compressed latent loop 很可能只有 fixed-size latent state。

这意味着它们不只是“显式版和隐式版”。

CoT = discrete token scratchpad。

Loop = continuous latent scratchpad。

两者 working-memory mechanism 不同，更可能互补，而不是替代。

还有一个常见疑问：“假设 loop 三次，前两轮不映射成 token，是不是前两轮思考完全看不见？”

不一定。这是训练设计，不是 Loop 的必然属性。完全可以给每一轮 hidden state 接 LM head。真正的问题是：你有没有训练中间 state 对齐可读 reasoning。

如果只对最后一轮做 next-token loss，中间 state 不一定可读；如果加 deep / intermediate supervision，就可以让 latent 对齐 reasoning step。

所以：Hidden ≠ 必然不可解释。更准确是：你有没有训练它可读。这又引出一个比 architecture 更重要的问题：PT / SFT / RL 哪个阶段引入 Loop？

如果 pretraining 从来没见过 Loop，模型就是一次前馈训练出来的。deployment 时突然让一个 block 多跑 5 次，它凭什么知道第 3、4、5 次该干嘛？

但如果 PT 从第一天开始就 Loop，也有问题：训练更贵、stability 更难，中间 iteration 到底应该学什么不明确；如果只对 final output 算 loss，中间几轮甚至可能没有明确 computational role。

所以未来很可能有：PT 原生 Loop。PT 普通、SFT 安装 Loop。PT + Deep Supervision。SFT 教 intermediate reasoning，RL 再 outcome-only。甚至真正的突破可能不是某个新的 block，而是：Loop Curriculum。

什么时候开始 loop？loop 几次？哪一轮监督？什么时候把显式 reasoning 压进 latent？这套 training recipe 可能比 architecture 更关键。

### RNN、Diffusion、Optimizer：Loop 到底是在重新学什么

一看到 recurrence，很多人第一反应：“绕一圈又回 LSTM / RNN 了。”

抽象上也没错。RNN 本来就是：同一组 weights + hidden state + repeated update。

但现代 Looped Transformer 的 inside-loop operator 是一个完整 Transformer / Attention / MoE block，训练规模、优化技术、context handling 都完全不是当年。

所以更准确说：Transformer 当年把大量 recurrence 换成了 depth；现在 recurrence 又开始被重新放回 Transformer。不是倒退，更像两条路线重新合流。

Diffusion / DiT 的类比也很有意思。Diffusion 本来就是：state → refine → state → refine。同一套或者相关参数被多次调用。

它提醒我们一件很重要的事情：stored parameter count 和 computational depth，本来就没有必须绑定。固定一套参数，也可以通过反复迭代增加计算深度。但 Diffusion 从 training objective 开始就是为 iterative denoising 设计的，每一个 timestep 有明确 conditioning。LLM 如果把一个原本一次前馈训练出来的 block 硬跑 N 遍，并不天然 work。

这又解释为什么 IterAdaLN、iteration conditioning、Loop Curriculum 都重要。

还有人会问：“Loop 到最后是不是就是 optimizer？”这个直觉非常准，但 optimizer 还是窄了。我更愿意叫：Iterative Algorithm。stateₖ₊₁ = Update(stateₖ, input)

这个 Update 可以像 optimizer，也可以像 message passing、dynamic programming、search refinement、belief update。

所以 Loop 最深的潜力可能不是：模型学会一个 optimizer。而是：模型学会一个可以反复执行的 algorithm。这可能才是 recurrence 和“堆更多独立 layer”真正不同的地方。

### Bitter Lesson、MoR 和 DSA：Learned Routing 很漂亮，但绝不是 Law

Bitter Lesson 很容易被拿来给这波做理论背书。最常见的推论就是：“既然 learned routing 可以自己长出来，那以后 DSA 这种手工雕花 selector 都没必要了。”

这种说法我理解。Bitter Lesson 最大的启发确实是：长期看，通用学习 + scale 往往比大量人工规则更强。

但我不认它是什么自然 law。“learned”不代表一定赢。Learned router 自己有 cost。会 collapse。会学 shortcut。会 distribution shift。会硬件不友好。会出现理论 FLOPs 很漂亮、真实 serving 很难看的情况。

所以 Bitter Lesson 更适合当一个：engineering prior。提醒你不要迷恋手工雕花，优先把问题变成可以学习、可以 scale 的形式。

但最后仍然要靠：benchmark、scaling curve、infra、real cost来验。

然后回到 MoR 和 DSA。MoR 越往深处 active token 越少，确实会自然产生一种：depth-induced sparsity。所以“MoR 自己长出 sparse attention”这个直觉是成立的。但这不等于 DSA 没用了。

MoR 在决定：谁值得继续深算。DSA 在决定：面对 long context 到底应该访问谁。

如果上下文是百万 token，你即使最后只有 50 个 token 值得 deep compute，也得先找到那 50 个。

所以未来更可能不是 MoR 干掉 DSA，而是：Depth Routing + Expert Routing + Attention Routing一起被统一。这时候真正的 architecture 不再是某个 module。而是：Compute Allocation Policy。

### Astra 为什么可能会把这波点燃：真正变化的是隐藏计算

Astra 具体是不是 MoR、是不是 Recirculation，目前都不能乱画等号。毕竟我也不是 open AI 的，我也不知道。

我真正在思考的是，如果 frontier model 真开始使用 recurrent depth，那么 Reasoning Scaling 可能发生一个很大的变化：过去：想得更多 ≈ 吐更多 token。未来：想得更多 ≠ 一定说得更多。

也就是说，test-time compute 开始从 output-token scaling，往 hidden-compute scaling 扩。这会改变 Reasoning Token Efficiency 的定义。

以前 efficiency 很大程度是：“能不能少吐点 token。”未来会变成：同样一份 compute，哪里值得花。

推理预算可能会从一维变成多维：输出 token 预算、计算深度预算、专家调用预算、注意力访问预算、隐式迭代预算。

而且这里还有一个安全问题：如果越来越多的推理发生在隐藏状态里，那么我们看得到的显式思维链，就越来越不能代表模型真实发生的全部计算过程。

但隐藏状态不等于必然不可解释。它能不能被探测、解码、监督，是另一个问题。

### 理论 FLOPs、Storage、Wall-clock、Dollar Cost 必须拆开：Infra 可能才是最肥的一层

这里有一句特别重要的判断：“Loop Transformer 不一定减少计算量，它更直接减少的是参数存储成本。”

对最朴素的固定 Loop 来说，这句话基本成立。因为同一套权重只需要存一份，但可以被重复使用多次。所以它首先优化的是参数存储效率，更准确地说，是让同一组参数被反复用于更多计算阶段，而不是凭空减少计算量。

这也是“Loop 提升参数利用率”比较准确的解释：同一套参数可以被反复调用，参与更深的计算过程。但这里一定要注意，1B 参数循环 8 次，并不等于 8B 独立参数。因为共享权重限制了模型拥有不同表示和不同能力模块的空间。Loop 扩展的是有效计算深度，不是独立参数容量。

MoE 恰好更偏向另一边，它主要是在扩大参数容量。而进入 MoR 或自适应深度以后，平均计算量才有机会真正下降；如果隐式推理能够替代大量显式思维链，也有可能进一步减少自回归生成、KV Cache 和 token 带来的开销。

但真正到了商业世界，大家不会为“论文里的 FLOPs”买单。真正付钱的是：GPU 时间、实际等待时间、吞吐量、显存和带宽占用、批处理效率、算子执行效率，以及 KV Cache 的搬运成本。

而自适应计算最大的一个现实问题，就是计算路径开始变得不规则。比如 token A 跑 2 轮，token B 跑 8 轮，token C 跑 4 轮。GPU 最喜欢整齐、规则的大批量计算，这种不规则任务反而最折磨调度器。

所以这一波如果真的起来，最肥的一层是条件计算运行时。不同深度怎么批处理？不同专家怎么调度？稀疏注意力怎么和 KV Cache 配合？不同循环次数的 token 怎么避免 GPU 空转？这些才是把算法优势真正变成系统优势的地方。（如果一个人崩钱或者接受访谈的时候这些都编不出来，那完了，某x机构没领投肯定也跟了）

真正能把这种不规则计算跑快的基础设施，才有机会把论文里的优势变成数据中心里的真实成本优势。算法效率，不等于系统效率。

如果有人大讲特讲：FLOPs 降低 30%。先问问：实际花的钱少了多少？（当然ta很有可能不敢告诉你）

### 下半年/年底算力环境一变，“给你一批卡，你敢不敢训”这套 Founder Narrative 又要回来了

还有一个时代背景不能漏。过去两年国内创业最现实的问题之一就是：卡呢？

没有稳定的大规模训练算力，再性感的 architecture 最后也很容易退回 API、Agent、应用层。

但到今年下半年，据我所知的消息，国内可调度训练算力的环境正在发生变化。无论最后来自受限进口的高端卡，还是国产 accelerator 继续扩量，至少有一个趋势越来越明显：卡重新开始成为真实创业变量。

这会直接改变融资 narrative。对不起，我又要说一级市场投资了，一级市场的一个投资判断是问 “如果我现在直接给你一大批卡，你敢不敢马上开训？”，看 founder 斩钉截铁说敢，就投，犹豫了，就再说。

但背后真正该问的是你到底有没有一个清楚到值得烧真钱验证的模型 thesis？

所以 Loop / Adaptive Compute 这波如果继续发酵，一批人新的福利又来了。

因为它特别适合讲：不是继续无脑 scale parameters。而是：scale effective depth / iterative computation。卡来了。新 architecture thesis 有了。Research narrative 也有了。

然后融资 story 可以直接变成：“以前国内缺卡，我们做不了真正的 foundation model research；现在算力条件改善，这一轮我们终于可以验证新的 scaling axis。” 特别顺。

敢烧卡，不等于懂模型。一个人毫不犹豫地说：“给我 20k GPU，我现在就开训。” 也可能只是：把卡给我，怎么着我都能弄出点名堂，赶紧去雇个懂训模型的。

真正值得投的不是“敢烧卡的人”。而是：知道什么实验值得用大卡验证的人。一个在 1B 模型就能 falsify 的 hypothesis，非要直接上 70B 验证，不叫 conviction。叫研究设计差。

所以真正好的路线应该是：Cheap Falsification → Medium Scale Validation → Scaling Check → Frontier Run。

每一层解决一个 uncertainty。不是：PPT → 十万卡 → 天命。

那句话最基本的过关回答应该是：“给我卡，我知道第一个 1000 GPU-day 要验证哪个 uncertainty，什么结果继续，什么结果马上 stop。” （原话教出去了，我看有没有人学以致用）。 当然，老头们把钱和卡给我也行，毕竟我是真懂，真讲怎么用，但老头们带宽不够而且我咖位不够，不爱听。

### 下一轮 Narrative 会怎么崩、Demo 怎么做、钱怎么赚，我现在基本能替大家写完

如果这一轮真起来，最容易发生的事情不是“大家讲 Loop”，而是会把六件完全不同的事串成一根特别顺的箭头：Loop → Token Efficiency → Lower FLOPs → Lower Cost → Better Reasoning → New Scaling Law → AGI这些箭头，一个都不能自动成立。

我先把几种可能做的demo和路径给崩钱的 founder 堵死，教大家怎么问。别怪我狠心，怪就怪凭啥认真做事的人不好崩钱。

第一种 Demo 一定是 Shorter CoT。

左边传统模型疯狂吐 8000 token，右边 recurrent model 1200 token，最后答案一样，首页写：6.7× Reasoning Token Efficiency。视觉冲击特别强。但第一层底裤就是：Token Efficiency ≠ Compute Efficiency。你把显式 CoT 藏进 hidden loop，不代表总 compute 少了。

直接问：hidden iteration 多少？total FLOPs 多少？TTFT 多少？end-to-end latency 多少？GPU-seconds 多少？

第二种 Demo 会升级成：Same Accuracy, FLOPs -35%。

直接问：wall-clock 呢？Adaptive depth 会破坏 batching。不同 token 跑不同轮数，产生 branch、idle、scheduler overhead、KV irregularity。

FLOPs Efficiency ≠ System Efficiency。

第三种会从 system efficiency 跳到：“我们的 inference cost 低 40%，所以 gross margin 更高。”

直接问：单 request latency 赢，还是 production throughput 也赢？一个 Demo 一次跑一道题很容易。真正 API serving 是几十、几百、几千 request 一起 batch。如果 single request 快 20%，但 datacenter throughput 掉 30%，客户账单可能根本没下降。

Latency ≠ Throughput ≠ Dollar Cost。商业上真正应该看的是：Cost per Successful Task。不是 $/token。不是 $/FLOP。一个模型便宜一半但成功率低 20%，客户最终可能更贵。

第四种 Demo 会是：Same Parameters, 4× Effective Depth。

看起来特别性感。问题是：same parameters 赢，不代表 Loop 是最优 budget allocation。还应该比较：same memory budget、same FLOPs budget、same training budget 下的最优 non-loop baseline。

否则你只是证明 Loop 比你挑的 Vanilla baseline 强，不是证明 recurrence 比最优 capacity allocation 强。

第五种 Demo 是 Scaling Curve。3B +1，9B +2.8，然后画一条漂亮虚线往右上角冲：Loop Benefits Scale with Model Size。

直接问：第三个点呢？第四个点呢？multiple seeds 呢？error bar 呢？两个点之间永远能画直线。两个 scale point 是 evidence，不是 law。

第六种是 Emergent Reasoning Demo。

Loop count 1→2→4→8，模型突然会解难题，然后开始讲“more depth unlocks reasoning”。这时候最公平 baseline 必须包括：Longer CoT。More Samples / Best-of-N。Deeper Unshared Model。More Experts。Search。Self-Consistency。

你要证明的是：Loop 是更好的 Compute Allocation。不是 More Compute 有用。

第七种是 Latent Reasoning Demo。

显式 CoT 很短，但 latent loop 很长，然后配一句：“人类也不是一直用语言思考。”这种话很性感，但技术上几乎什么都没证明。

直接问：latent state 有没有 working-memory bottleneck？长期 algorithmic task 上和 growing CoT scratchpad 比怎样？中间 reasoning 能不能 probe？error 能不能定位？monitorability 怎么解决？

第八种是 Adaptive Routing Heatmap。

简单 token 一轮退，数学符号跑八轮，看起来模型特别懂“哪里难”。

直接问：router 学的是 semantic difficulty，还是 token position、entropy、词形、benchmark pattern？把语义不变、表面形式换掉，它还 route 一样吗？

如果模板一换 routing 就崩，它学的不是 difficulty。是 shortcut。

第九种会是：Self-emergent Sparse Attention。

展示 MoR 越深 active token 越少，然后宣布：Indexer is dead。

直接问：1M context 下怎么找到真正值得 deep compute 的 token？如果前面仍然 full scan，你只是把 sparsity 推迟，不是消灭 retrieval cost。

然后再把可能的商业模式盘一盘，其实 business model 也会开始分叉。

第一类是 Reasoning Efficiency API：同样效果，更少 token、更低成本。这个最直接、最容易验证。

第二类是 Adaptive Compute Runtime：做 router、scheduler、adaptive batching、KV routing、recursive execution，让各种模型的 conditional compute 真正跑起来。这个我觉得非常实在。

第三类是 Enterprise Dynamic Reasoning：简单任务浅算，复杂任务自动加 depth、expert、tools，然后往 Expert Agent、Enterprise RSI 接。

第四类会讲成 Agent Compute OS：整个 Agent workload 怎么分配小模型、大模型、search、memory、CoT、latent reasoning、多 agent。

最后一类我反而觉得商业故事很大。因为未来 intelligence workload 的成本根本不只是 token。而是：model + tool + action + reasoning budget 的整体调度。

再往企业走一步，很容易变成：Enterprise Intelligence Cost Control Plane。公司所有 AI task，哪个用 7B、哪个用 frontier model、哪个值得 8 轮 reasoning、哪个直接 deterministic workflow，统一 routing。甚至最后可能根本不再卖“Loop”。而卖：AI FinOps。这完全有可能是最赚钱的结局。（想照抄，记得看我最后的警告）

### 最后把这轮崩钱路堵死：七账、四条曲线、三组对照，再加一个换硬件测试

如果真想判断下一轮 Loop / 自适应计算项目，我觉得别再只看 benchmark，至少要把这些算清楚：

第一，准确率，到底提升了多少；第二，输出 token，显式输出到底少了多少；第三，计算量，也就是 FLOPs，实际少算了多少；第四，真实延迟，用户到底少等了多久；第五，吞吐，一张 GPU 一小时到底能服务多少请求；第六，显存和带宽，KV、通信、数据搬运到底占多少；第七，单次成功任务成本，客户真正完成一个任务到底花多少钱。还应该再加第八个：训练成本。如果推理阶段每次省 10%，但为了让这种循环架构真正 work，训练阶段多烧了 5 倍算力，那到底要跑多大规模的使用量，才能把前面的训练成本摊回来？

然后还必须看四条曲线：第一条是性能随着模型规模怎么变，看是不是模型越大，Loop 的收益越明显；第二条是性能随着训练数据量怎么变，看它到底是不是真的更省数据；第三条是性能随着推理计算量怎么变，看 Loop 是不是一种更优的测试时计算方式；第四条是性能随着真实美元成本怎么变，这个最重要。因为论文里算力省了，不代表真实世界里钱也省了。

最后还要看三组最基本的对照：同参数、同计算量、同真实成本。这三个必须一起看。同参数下赢，可能只是你多算了；同 FLOPs 下赢，可能硬件利用率更差；只有在同样真实成本下还能赢，商业故事才真正成立。

我甚至还想再加一个很狠的测试：换硬件。如果一家公司的核心判断真的是“让模型自己学会怎么分配算力”，那在 H100 上学出来的路由策略，换到国产 GPU 上以后，还是最优的吗？因为真正成熟的算力分配策略，不应该只理解“这个任务难不难”，还得理解不同硬件上什么计算最贵、什么计算最便宜。有的硬件更怕注意力，有的更怕显存搬运，有的更怕专家通信。
