# 六大前沿模型发布评测集审计

**对象：GPT-5.6 Sol、Claude Opus 5、GLM-5.3、Hy4 preview、Qwen3.8-Max、Kimi K3**  
**资料截止：2026-08-29（Asia/Shanghai）**  
**口径：只统计模型发布时，厂商用来说明目标模型能力的评测；竞品列里顺带展示的分数，不计入该竞品自己的发布评测集。**

---

## 一、先说结论

### 1. 六家真正形成共识的，是“长程任务”，不是又一套考试题

严格按 benchmark 名称与变体统计，六家都测了两类：

- **DeepSWE**：长程软件工程；
- **AutomationBench 系列**：跨 SaaS 工具完成真实业务流程。

如果按 benchmark 家族而非精确版本归并，**Toolathlon、Terminal-Bench / FrontierBench、HLE、GDPval / 职业工作、PostTrainBench** 也构成明显的共同主线。发布评测的重心已经从“模型能不能答对一道题”，移到：

1. 能否在陌生代码库或终端环境里持续工作；
2. 能否选择并编排工具，把环境改到正确状态；
3. 能否交付文档、表格、演示文稿、代码仓库等可验收成果；
4. 能否在几小时、几十万 token、多次失败之后仍保持目标和验证闭环。

GPQA、HLE 这类静态题仍然存在，但更像“基础认知体检”。厂商用来证明旗舰模型差异的主证据，已经越来越依赖 Agent 环境。

### 2. “大家都测同一个榜”不等于“这些分数可以直接横比”

至少要同时对齐：

> **模型 × reasoning effort × Harness × 任务环境/版本 × 轨迹与上下文管理 × Verifier/Judge × Runtime × 重复次数与聚合方式 × 成本**

几组典型反例：

- **Terminal-Bench 2.1**：GPT-5.6 Sol 用 Codex；GLM-5.3 和 Hy4 preview 用 Claude Code，但超时分别为 6 小时和 12 小时；Qwen3.8-Max 用 Claude Code、每题 10 次、5 小时；Kimi K3 用 Kimi Code。名称相同，测到的是不同的“模型 × Harness”系统。
- **AutomationBench**：Claude Opus 5 的 26.0%来自官方私有 held-out leaderboard；Qwen、Kimi 明确使用公开 600 题；GLM、Hy 使用 v1.0.6 或其修订设置。它们属于同一评测家族，但并非同一 test set。
- **Toolathlon**：OpenAI 发布表写的是旧版 **Toolathlon**；另外五家写的是 2026-06-30 后的 **Toolathlon-Verified**。不能把 58.0 与 Verified 分数放在同一列排名。
- **SWE-bench Pro**：Qwen 修复了问题任务并重新跑全部基线；这已经不是原始公开集的原样复现。OpenAI 此后又审计称公开任务中约 30%存在问题，说明版本冻结和任务修复记录比榜名本身更重要。

因此，下文的“多家采用”表示行业共识，不表示得分天然可比。

### 3. 自建评测集暴露了各家的产品方向

| 厂商 | 自建/私有评测重点 | 它实际想验证什么 |
| --- | --- | --- |
| OpenAI | 管理咨询、药物化学、内部研究调试、KernelGen、NanoGPT、RSI Index | 从知识工作延伸到“模型帮助研发下一代模型”的 AI R&D 自动化 |
| Anthropic | 生命科学、蛋白设计、有机化学、实验协议、自动行为审计、OSS-Fuzz | 高价值科研与安全边界；同时关心长程协作是否可靠、是否会产生高风险行为 |
| Z.ai | Z.ai Code Bench；真实本地开发环境与细粒度 checklist | 真实 Coding Agent 用户体验，以及 effort—token—完成率曲线 |
| Tencent Hy | Hy-Backend、Hy-SWE、Hy-CompanyBench、Hy-LifeSearch、E-Bench、金融 Agent/模型评测 | CodeBuddy/WorkBuddy 对应的工程、办公、搜索、金融生产力 |
| Qwen | QwenSWE、QwenQoder、QwenReact、QwenSVG、CoWorkBench、RecreationBench | 编码不只看 patch，还看 Qoder 体验、双语前端/SVG、视觉反馈和 Cowork 交付 |
| Moonshot | Kimi Code Bench 2.0、PerceptionBench | Kimi Code 的真实长程工程能力，以及原生多模态的“原子视觉感知”短板 |

共同趋势是：**私有评测越来越接近厂商自己的训练环境、产品 Harness 和真实用户任务。** 这提高了业务相关性与抗污染性，也降低了第三方复现能力。公开榜适合建立共同坐标，私有榜更像各家产品的 release gate；两者不能互相替代。

### 4. 六家的能力分类，反映了不同的“模型观”

- **OpenAI** 分得最细：Professional、Coding、Science and health、Computer use、Cybersecurity、Self-improvement、Multimodal、Academic、Tool use、Long context、Abstract reasoning。它把模型视为一组横跨知识、行动、科研和自我改进的能力模块。
- **Anthropic** 的 System Card 更像能力与风险全景：软件工程、数学/科研、搜索、多 Agent、视觉与计算机使用、职业工作、健康、多语言、生命科学，另有完整安全评测。它最强调“能力评测”和“危险能力/行为评测”分账。
- **GLM-5.3** 只有 Coding、Cyber、Agentic 三条主线，叙事最聚焦：用扩大的后训练环境解释长程编程和网络安全能力增长。
- **Hy4 preview** 用 Agentic Coding、Agentic Search、Working Agent、STEM Agent、Reasoning 分类，分类依据主要是 Agent 所处的工作环境，而非传统学科。
- **Qwen3.8-Max** 分为 Coding Agent、General Agent、General Capabilities；静态能力被压缩成一组，主要篇幅给 Coding 与 Cowork。
- **Kimi K3** 用 Reasoning & Knowledge、Coding、Agentic、Vision 四象限，最清楚地把原生多模态当作独立能力面。

视觉能力的处理尤其能说明问题：Kimi K3 有完整 Vision 区；GPT-5.6 Sol 有 Multimodal 区；Claude 在各章节分散报告 SWE-bench Multimodal、Chartography、BenchCAD、gdp.pdf 等；Qwen3.8-Max 服务支持视觉输入，却在模型卡主评测表中没有单列视觉 benchmark，视觉能力主要由发布稿的 Vision Arena、RecreationBench 和案例承担；**GLM-5.3 与 Hy4 preview 本体是文本模型，所以发布表没有独立 VL 榜。**

### 5. 配置披露的结论：GLM 最逐项，Claude 最系统，Kimi/Qwen 最愿意暴露“混合口径”

按“能否复现实验和判断可比性”而非分数高低看：

1. **GLM-5.3：逐 benchmark 脚注最细。** Harness 版本、effort、temperature/top_p、context、output、turn、timeout、重复次数、反作弊修改和 verifier 基本都有交代。
2. **Claude Opus 5：System Card 最完整、统一实验基线最好。** 默认 max effort、默认采样、平均 5 次、上下文不超过 1M；各章节再补工具、judge 与例外。发布新闻本身较简，完整信息要进入 190 页 System Card。
3. **Kimi K3：披露范围广，异常运行也有记录。** 统一 max/temperature，区分 single-step 与 agentic top_p，披露不同 Harness、H20 替代 H100、fallback/refusal、结果引用日期和上下文压缩。
4. **Qwen3.8-Max：脚注丰富，但比较表混合了自测、官方 leaderboard 和“跨 Harness 最优值”。** 适合看 Qwen 自己的运行口径，不适合把整张表当 apples-to-apples 对照实验。
5. **Hy4 preview：中高披露。** 很多任务给出 Harness、turn、超时、CPU/RAM、judge 和 avg@3；但方法写在图片脚注中，Agentic Search 又统一称内部 Harness，采样和版本信息并非每项都有。
6. **GPT-5.6 Sol：覆盖面最广，但逐榜复现信息最少。** 能看到 Ultra=默认 4 Agent、部分 cyber 的 seeds、延迟重标定和成本模拟；大量主表分数仍未逐项披露 Harness、timeout、repeat、judge。

这组排序只衡量发布材料能否支持复现和横向判断。OpenAI 的页面偏产品与效率叙事；Anthropic/Z.ai/Qwen/Kimi 的模型卡或 System Card 更接近实验附录。

## 二、研究口径与标签

### 2.1 三种数据开放状态

| 标签 | 含义 | 例子 |
| --- | --- | --- |
| **P：公开** | 数据/任务和运行代码大体公开；可能用加密答案、gated 下载或防泄漏机制 | DeepSWE、Terminal-Bench 2.1、ProgramBench、BrowseComp |
| **H：部分公开/held-out** | 方法公开，但正式 leaderboard 使用私有题；或公开、held-out、商业 split 并存 | AutomationBench 官方榜、SWE-bench Pro、MCP-Atlas、ALE 全量库 |
| **I：厂商自建私有** | 只披露方向、分数或少量样例，第三方不能复现正式结果 | Z.ai Code Bench、QwenQoderBench、Hy-CompanyBench、PerceptionBench |

“由厂商创建”和“数据私有”是两条轴。例如 OpenAI 创建了 BrowseComp，但 BrowseComp 是公开 benchmark；Artificial Analysis 创建了 AA-Briefcase，但正式题是私有的。

### 2.2 统计规则

- 只计厂商在目标模型发布页、模型卡、System Card 或同时发布的技术报告中，主动用于说明目标模型的 benchmark。
- 竞品对比列不反向计入竞品。例如 GLM 发布表出现 Qwen3.8-Max 的分数，不代表 Qwen 发布时采用了这个 benchmark。
- 同名但不同版本/变体分开记：Toolathlon ≠ Toolathlon-Verified；PostTrainBench Lite ≠ PostTrainBench；HLE no tools ≠ HLE with tools；OSWorld-Verified ≠ OSWorld 2.0。
- 目标模型的分数按其发布材料冻结，不用 2026-08-29 的滚动 leaderboard 值覆盖；滚动榜只用来核对方法和出题方。
- 厂商没有披露的字段写“未披露”，不从相邻模型、产品默认值或第三方复现倒推。

#### 配置披露

- 同一正式发布页对 Agents' Last Exam 有 **53.6（正文）与 52.7%（详细表）** 两个值。本文为保持逐表口径采用 52.7%，不在官方未解释时自行合并或判断哪个应覆盖另一个。
- `max` 是单 Agent 最高 reasoning effort；`ultra` 默认协调 **4 个 Agent**。Ultra 不是更高的单模型 effort，不能当成同一系统的一个普通采样点。
- ExploitBench：API Harness、5 seeds、保留 reasoning continuity。
- ExploitGym：先在更快的 alpha API 跑，再按公共 API 速度重标定；重标定后的估算延迟可能超过名义 2h/6h。
- 页面中的延迟和 API 成本是基于生产行为、token 和工具调用的离线模拟，不是每题实际墙钟与账单。
- 大多数主表条目没有逐项给出 Harness、context、output cap、timeout、重复次数、聚合和 judge，因此**能读产品结论，难做完整复现**。

#### Z.ai Code Bench 测什么

它把 Agent 放进复杂本地开发环境，任务来自真实用户场景，既看端到端完成率，也按细粒度 checklist 打分，并在不同 effort 下报告完成率与 output tokens。它服务于 Z.ai Coding 产品的离线 release gate，测量对象与单函数式 HumanEval 不同。

#### 配置披露

GLM 的发布脚注几乎逐项给参数。代表性条目：

- Terminal-Bench 2.1：Claude Code 2.1.207、temperature 1、top_p 1、65,536 output、6h。
- Terminal-Bench 3.0：Claude Code、max、400K context、128K output、avg@3、最多 600 turns、10h、关闭 Tool Search、官方 verifier。
- ALE-CLI：官方 105 题、Claude Code、max、1M context、64K output、默认 4h、题目上限可到 8h、官方 evaluator。

## 五、高频公开 benchmark 词典

这一节按四个选型问题整理：谁出的、题目实际长什么样、怎么判分、什么变量会让分数失去可比性。下面的“公开”指任务定义、论文或部分数据可查；不等于完整测试集、参考答案和线上环境都公开。

### 5.1 六家共同采用的核心

| Benchmark | 出品方与开放形态 | 能力与典型任务 | 评分与可比性 |
| --- | --- | --- | --- |
| [DeepSWE](https://deepswe.datacurve.ai/) | Datacurve；公开任务与 verifier。约 113 个原生任务，覆盖 91 个仓库、5 种语言 | 真实仓库级软件工程。给出 GitHub issue 和代码仓库，让 Agent 修 bug、做功能、重构或性能修改，例如终止 pending body read、修 PromQL label 排序 | 运行项目测试和任务专用 verifier。分数强依赖 Harness、容器、超时、上下文压缩和多次尝试策略 |
| [AutomationBench](https://zapier.com/benchmarks) | Zapier；任务环境公开。公开 600 题与官方私有 held-out 不是同一 split | 跨 SaaS 业务流程。在 CRM、邮件、表格、客服、财务或 HR 系统里读取初始状态，找到记录、发跟进、更新字段或创建对象 | 以最终环境状态做确定性校验。必须核对版本、公开/私有 split、应用数量、工具 schema 和重试策略 |

AutomationBench 的 47 个模拟 SaaS 应用覆盖销售、营销、运营、客服、财务和人力资源。它代表了一个很清楚的行业转向：工具调用评测不再只问“API 选对没有”，而是检查一段业务流程结束后，系统里的真实状态有没有被正确改变。

### 5.5 从这些题目能看出的公开 benchmark 演化

公开评测正在从四类旧范式——选择题、短答案、单函数代码和静态图片问答——转向四类新范式：

1. **环境有状态**：AutomationBench、Toolathlon、OSWorld 看最后的系统状态，不只看文本答案。
2. **轨迹很长**：SWE-Marathon、FrontierSWE、PostTrainBench 需要数小时、数百万到数千万 token，开始暴露上下文管理和恢复能力。
3. **交付物可验**：GDPval、ALE、BenchCAD、gdp.pdf 要交代码、表格、PDF、CAD 或被修改的应用状态。
4. **专业 rubric 与 verifier 并用**：开放式职业任务难以只靠 unit test；行业同时在寻找专家 rubric、LLM judge、程序 verifier 和盲测 pairwise 的组合。

### 6.1 共性

- **代码不再等于 HumanEval**。六家都把真实仓库、终端或从零建仓放在核心位置，且 DeepSWE 6/6。
- **工具调用从“会选 API”升级为“能完成业务”**。AutomationBench 6/6，Toolathlon 家族 6/6。
- **职业任务成为新的价值锚**。GDPval、ALE、JobBench、OneMillion、Briefcase 分别从职业覆盖、交付物和经济价值切入。
- **长上下文被拆成两种能力**：一是 needle/graph/文档理解，二是 Agent 在长轨迹里压缩、恢复、继续工作。后者更难，也更接近产品体验。
- **越来越强调 verifier**。能用测试、环境状态或几何指标判定的 benchmark，比纯 LLM judge 更容易做回归。

### 6.2 主要差异

- **模态能力决定目录边界**。GLM-5.3 与 Hy4 preview 是文本模型，发布时没有 VL 主表；Kimi K3 把原子感知、文档、视频、数学视觉和 Python 辅助视觉拆开。GPT 与 Opus 还把 CAD、PDF、桌面操作纳入多模态证据。
- **产品形态决定 Agent 分类**。Claude 强调 Computer Use 与企业知识工作；GLM、Qwen、Kimi 强调 Coding Harness、MCP、SaaS 和深度搜索；OpenAI 把网络安全、科研自我改进单独拉出。
- **是否把 safety 混入能力表不同**。Anthropic 的 system card 有独立 safety/behavior 审计；Kimi 在代码评测中直接披露 cyber guard、拒绝和 fallback；多数发布表只给能力分，不给拒绝率。
- **“专业能力”定义不同**。有的按行业分，有的按交付物分，有的按职业经济价值分。GDPval 的一项任务、医疗问答和真实临床工作虽然都可叫 professional，但证据含义完全不同。

因此，更稳妥的分析单位是：

> **模型 × Harness × 真实任务环境 × 轨迹 × Verifier/Judge × Runtime × 成本**

同一分数只有在这几个维度大体对齐时，才接近模型间比较；否则它首先是一个完整系统的结果。

## 七、各家的自建/内部评测在测什么

公开 benchmark 负责给市场一个共同坐标，自建集负责覆盖产品真实分布、前沿能力或不适合公开的数据。六家的方向并不一样。

| 厂商 | 自建或内部评测 | 主要测试方向 | 开放程度与证据边界 |
| --- | --- | --- | --- |
| OpenAI | Management Consulting、MedChem、Internal Research Debug、RSI | 咨询交付物、药化研究、内部科研调试、递归自我改进 | I；多披露任务定位和汇总分。题量、抽样、污染控制、完整 rubric、方差与成本通常不足 |
| Anthropic | Organic Chemistry、Protein Design、Scientific Protocols、Model Behavior Audit、OSS-Fuzz/安全研究 | 科学设计与协议、行为审计、模糊目标研究、安全漏洞发现 | I/H；system card 方法较多，但数据多不公开，许多评测无法独立复跑 |
| Z.ai | Z.ai Code Bench | 以自家 Coding Plan/Code Harness 运行真实长程代码任务 | I；给目标和主结果，缺任务分布、重复次数、仓库和 verifier 细节；跨 Harness 不可直比 |
| Tencent Hunyuan | 内部 coding、browser、knowledge work、长上下文/Agent 任务 | 复杂代码、浏览、文件和长程 Agent | I/H；附录披露较多运行字段，但任务名称、规模、泄漏检查和样本多不可复核 |

| Moonshot | Kimi Code Bench 2.0、PerceptionBench | 长程代码；拆解原子视觉感知，避免综合 VQA 掩盖基础错误 | I；披露 Harness、effort、fallback/拒绝较多，但完整题集、类别占比与 verifier 未公开 |

### 7.1 自建评测的五个共同方向

1. **真实产品分布**：从自家 Code Agent、浏览器、SaaS 和用户任务中抽取，让评测能预测产品体验。
2. **长程、可恢复的执行**：公开榜常给固定时限和干净环境；内部集更关心跨小时、失败恢复、上下文压缩和工具错误。
3. **高价值垂直领域**：咨询、药化、蛋白设计、医疗、金融、法律、科学协议，通常需要专业 rubric 或专家判断。
4. **AI 研发与自我改进**：研究调试、kernel、post-training、RSI。它们测模型能否改进模型或训练流程，是前沿实验，不宜和普通 SWE 分数混成一个“编码榜”。
5. **基础薄弱点诊断**：例如 PerceptionBench 不追求综合炫技，而是找视觉系统最原子的失误，适合训练和回归。

### 7.2 私有评测的正确读法

私有集并非天然不可信：隐藏答案能降低针对榜单过拟合，真实用户分布也可能比公开题更有效。问题在于，外部读者无法判断样本选择、失败归因、去污染、judge 偏差与方差。因而私有集更适合证明“厂商在持续测什么”，不适合单独证明“比竞品强多少”。

一个可信的私有 benchmark，至少应公开：任务来源与抽样规则、任务数、时间窗口、模型和 Harness 版本、允许的工具、超时/算力、重复次数、聚合方式、grader 设计、拒绝/fallback 处理，以及若干匿名化样例。

## 八、发布结果是怎么汇报的：披露审计

### 8.1 审计字段

| 字段 | 为什么重要 |
| --- | --- |
| benchmark 版本与 split | public、held-out、private、Verified、Pro/Lite 往往不是同一难度 |
| 模型 checkpoint 与服务日期 | 同名线上模型会更新；第三方滚动榜也会更新 |
| Harness 与版本 | Claude Code、Codex、Kimi Code、Qwen Code、Terminus、Harbor 会改变规划、工具和上下文管理 |
| effort、temperature、top_p | 决定推理预算与采样；更高 effort 不保证每项单调变好 |
| context/output 上限 | 长程 Agent 可能因压缩、截断或输出预算差异改变结果 |
| 工具与网络权限 | 浏览、Python、shell、并发和网页搜索会把静态题变成系统题 |
| 运行时间与计算资源 | Terminal、SWE、post-training、research task 对超时和 GPU 极敏感 |
| 重复次数与聚合 | 单次、avg@3、mean@5、pass@k、best-of-k 回答的问题不同 |
| verifier/judge | 单元测试、环境状态、专家 rubric、LLM judge 与 pairwise Elo 的误差结构不同 |
| refusal、fallback、无效运行 | 不披露会把安全拒绝或系统故障悄悄从分母中移走 |
| token、延迟与成本 | 两个相同成功率的 Agent，可能消耗相差一个数量级的资源 |

| GLM-5.3 | 两项均高 | 两项均高 | **很高**：逐榜脚注明确 Harness、超时、重试/聚合和拒绝处理；私有 Code Bench 仍不可复跑 |
| Hy4 preview | 两项均高 | verifier 高；异常运行中 | **高**：附录把大量设置写到 benchmark 级；文本模型无 VL，内部集样本披露仍有限 |
| Qwen3.8-Max | 时间/资源中；重复/聚合高 | verifier 高；异常运行中 | **高**：模型卡脚注丰富；云端 Max、开放权重文本模型与不同 thinking 模式容易被混读 |
| Kimi K3 | 两项均高 | 两项均高 | **很高**：披露视觉 avg@3、H20/H100、context compaction、fallback 和 cyber guard；竞品仍常用不同 Harness |

### 8.3 六家汇报方法的典型差异

- **OpenAI** 常给 `xhigh/Ultra` 等 effort 对照，把专业工作、编码、科研、浏览和安全执行放在同一发布叙事中。优点是覆盖前沿，缺点是读者容易忽略某一分数究竟来自 Codex、第三方 Harness 还是内部环境。
- **Anthropic** 用 system card 做统一方法说明，例如默认/最大 effort、采样和多次平均，再在能力章节分领域汇报。它还把安全和行为评测单列，证据边界相对清楚。
- **GLM、Hy、Qwen、Kimi** 更依赖超长模型卡表格和逐榜脚注。这里往往能找到真正决定可比性的字段：哪套 Agent Harness、几小时、几次、怎样处理拒绝、是否用了工具和上下文压缩。
- **第三方值被引用进发布表** 很常见。AA、ALE、GDPval、Terminal-Bench 等会滚动更新；发布材料里的竞品分只代表一个引用日期，不是永久的“官方成绩”。

### 8.4 建议采用的标准结果行

以后无论厂商还是内部团队，至少应按下面一行汇报：

```text
Model/checkpoint | effort/sampling | harness+version | benchmark+split+commit |
tools/network | context/output | timeout/compute | n runs | aggregation |
verifier/judge | refusal/fallback policy | tokens/latency/cost
```

例如只写“Terminal-Bench 92”几乎不可用；写成“模型 A，max effort，Terminus 2/Harbor commit X，TB 2.1 89 题，无外网，每题 2h，5 runs，mean success，官方 verifier，拒绝计 0，平均 token/时延/成本……”才具备审计意义。

## 九、如何使用这批发布评测

### 9.1 做模型比较时

第一步只取交集，不把所有分数简单平均。六家严格交集可以从 DeepSWE 和 AutomationBench 开始；再按任务选 Terminal-Bench、Toolathlon-Verified、ALE、GDPval-AA、HLE 等五家交集。

第二步逐项对齐协议：同一版本/split、同一 Harness 或至少同类型 Harness、相近 effort、相同超时和工具、相同重复与聚合。对不齐的结果应标注为“系统上限/发布展示”，而不是“纯模型胜负”。

第三步保留多目标。真实选型至少同时看成功率、方差、拒绝/无效运行、token、延迟、成本和可复现性。特别是 SWE-Marathon、FrontierSWE、深度搜索和电脑操作，单个 pass rate 会掩盖巨大的资源差异。

### 9.2 自建评测时

一套更稳健的企业评测组合可以分四层：

1. **公开锚点**：选择 2–4 个与业务最接近、verifier 较强的公共集，用于外部校准。
2. **真实 held-out**：从自己的用户任务、失败记录和工作流抽样，按时间切分并持续防泄漏。
3. **诊断与回归**：把失败拆成模型、Harness、Context、Tools、Verifier、Runtime 六类；形成小而稳定的回归集。
4. **运行经济性**：每次都记录成功率、P50/P95 时延、token/工具调用、成本、拒绝、重试和方差。

对于高风险场景，再加独立 safety/permission 评测。不要用“能力强所以安全”或“拒绝多所以能力弱”互相代替。

### 9.3 这轮比较最值得持续追踪的方向

- **真实业务状态评测**：AutomationBench、Toolathlon、MCP-Atlas。
- **长程代码与可恢复轨迹**：DeepSWE、FrontierSWE、SWE-Marathon。
- **职业交付物**：ALE、GDPval、AA-Briefcase、gdp.pdf。
- **Agent 自我改进**：PostTrainBench、RSI、research debug。
- **多模态工程闭环**：BenchCAD、OSWorld 2.0、专业 PDF。
- **成本与方差标准化**：目前六家都远未形成统一报告规范，这是下一轮比“多上一个榜”更有价值的改进。

## 十、证据边界与限制

1. **时间边界**：本文冻结的是各模型发布时的表格、脚注和模型卡，以及截至 2026-08-29 可查的 benchmark 官方说明。没有用后续滚动榜替换发布快照。
2. **能力边界**：这里审计的是发布材料采用了什么评测，不是对六个模型做新的独立复测，也不据此给出综合排名。
3. **系统边界**：代码、终端、浏览、SaaS、Computer Use 和深度研究分数通常属于模型+Harness+工具+环境的系统结果。
4. **私有集边界**：内部 benchmark 的任务规模、完整题目、采样与 grader 往往不可复核。本文把它们用于判断评测方向，不把私有分数当成可独立验证的横向证据。
5. **同名边界**：AutomationBench public/private、Toolathlon/Verified、OfficeQA/Pro、PostTrainBench/Lite、SWE-bench Pro 不同 split、HLE 有/无工具，都按不同配置处理。
6. **模型边界**：Qwen3.8-Max 的云服务能力、发布模型卡中的开放权重 artifact、thinking/non-thinking 配置需分开理解；不能把其中一套表自动外推到另一套部署。
7. **多模态边界**：GLM-5.3 与 Hy4 preview 发布定位为文本模型，未列 VL 主榜属于能力范围差异，不应按“缺测=零分”处理。
8. **转录边界**：Hy4 preview 的细节来自官方 GitHub 发布附录图表逐项转录；文中保留其原始 benchmark 名和配置，不对模糊字段做补猜。

## 结语

六家在发布时已经形成一个相当一致的最低共识：前沿模型不能只用静态知识题来证明，必须进入代码仓库、终端、SaaS、浏览器、文件和职业交付物；结果最好能被程序或环境状态验证。DeepSWE 与 AutomationBench 的 6/6 重合，就是最直接的信号。

“怎么报告”仍没有形成共识。同一 benchmark 经常混着不同 Harness、effort、split、超时、算力、上下文策略和重复次数。下一步应对共同 benchmark 做协议对齐，同时公布成功率、方差、拒绝、耗时、token 和成本。做到这些，release benchmark 才能从营销证据变成工程决策工具。
