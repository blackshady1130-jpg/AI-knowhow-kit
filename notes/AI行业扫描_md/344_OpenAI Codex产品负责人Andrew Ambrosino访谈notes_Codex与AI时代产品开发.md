# OpenAI Codex 产品负责人 Andrew Ambrosino 访谈 Notes：Codex 与 AI 时代的产品开发

## 一句话总览

这期访谈真正有价值的地方，不只是介绍 OpenAI Codex 的产品路线，而是从一个正在高强度 dogfood AI 编程工具的团队内部，观察 AI 如何改变产品开发、设计流程、组织分工、管理方式和软件入口。

Andrew Ambrosino 的核心判断是：AI 让“实现”从最昂贵、最需要提前规避风险的环节，变成可以大量并行尝试的环节。随之变化的不是某一个岗位会不会消失，而是产品组织的稀缺能力从“能不能把东西做出来”，迁移到“能不能判断什么值得做、做到什么程度、以什么形式验证、何时收敛进产品”。

---

## 最高价值观点清单

### 1. Codex 的目标不是 IDE，而是工作入口

Andrew 对 Codex 的定位非常高：它不只是一个编程工具，也不是传统意义上的 IDE 或终端增强，而是一个能承接大量知识工作的新桌面入口。

他提到，OpenAI 内部已经有非常高比例的人在使用 Codex，不只是工程师，而是整个公司不同职能的人都在用。这个信号很关键：如果一个工具在界面上还带着代码、终端、repo、审批等工程痕迹，却仍然被非工程团队持续使用，说明它捕捉到的不是“写代码”这个窄需求，而是“把想法变成可运行工作流”的更大需求。

Codex 的长期愿景更接近一个可以启动工作、跟踪工作、自动化工作、连接外部工具并结束工作的 home base。它不一定替代 Excel、Premiere、Linear、Chrome 或 IDE，而是能调用、连接和扩展这些专业工具。

### 2. AI 让产品开发的成本结构反过来了

过去做产品时，团队会花很多时间写 PRD、做研究、画原型、开评审会，本质上是因为真正实现很贵，所以要在开工前尽量降低不确定性。

现在实现变便宜了，甚至很多 PM、设计师、运营都可以直接用 Codex 做出一个原型。于是问题不再是“谁能把东西做出来”，而是“这么多可以被做出来的东西，哪些值得变成产品”。

这会带来一个新瓶颈：判断力、品味、取舍、组织收敛。团队会同时产生大量原型、分支、实验和局部解法，真正稀缺的是有人能看懂这些探索背后的产品含义，把正确的部分吸收到正式路线里。

### 3. “PRD 已死，原型万岁”是过度简化

访谈里一个很反共识的点是，Andrew 并不认为文档会被原型完全替代。

他的判断更细：媒介要服务于你想表达的问题。如果你要验证一个交互、一个流程、一个界面反馈，原型当然更直接；但如果你要澄清一个模糊方向、建立共同语言、解释系统性取舍，文档可能仍然是更好的媒介。

危险之处在于，AI 生成的原型可能看起来太完整，从而制造“这东西已经接近可上线”的假信号。实际上它可能只是一个探索性的外壳，内部没有经过产品、技术、质量、权限、稳定性和边界条件的验证。

### 4. Taste 不是审美，而是产品组织的新核心能力

Andrew 对 taste 的理解远远超过“界面好不好看”。

在他的语境里，taste 包括：你知道该做什么、不该做什么；知道一个点子属于哪个更大的产品主题；知道什么时候应该写文档，什么时候应该做原型；知道哪些细节只是噪音，哪些细节会改变用户行为；知道一个功能放进系统后会造成什么长期后果。

这意味着 AI 时代的产品能力不是从执行能力迁移到抽象空谈，而是迁移到更高密度的判断：在可实现性大幅提升之后，人的价值更集中地体现在方向选择、系统感和最终质量标准上。

### 5. AI 还不擅长真正的设计，原因不是不会画界面

Andrew 认为模型在设计上的问题，不只是“生成的 UI 不够漂亮”。

代码相对容易评估：能不能编译、测试过不过、运行结果对不对，都有外部信号。设计则更难，因为它涉及人类品味、文化语境、情绪预期、交互连贯性和新颖性。

更深一层，真正的产品设计不只是像素和组件排列，而是建立一套抽象层：视觉语义、品牌系统、交互模式、组件系统、状态逻辑、信息层级如何在代码库里对应起来。模型可以生成局部界面，但要稳定理解和维护这种设计系统，还需要更好的工具链和反馈机制。

### 6. 设计流程不会消失，但实现会被拉进设计过程

他对“设计师会不会被取代”的看法也很有层次。

如果所谓设计流程只是旧工具、旧会议、旧交付物的组合，那当然会被冲击。但如果设计流程指的是发现问题、建立概念、探索交互、表达取舍、校准用户体验，那它不会消失。

真正变化的是，实现不再是设计之后的遥远步骤，而会被拉进设计过程本身。设计师、PM、工程师可以用一个简化版代码库、baby Codex 或 vibe-coded prototype 来探索真实交互，而不是只停留在静态稿或说明文档里。

### 7. 岗位边界会变软，但专业能力不会消失

Andrew 观察到，Codex 相关团队内部的角色重叠比传统产品组织更强：设计师理解工程，PM 会写代码，工程师也参与产品和设计判断。

但他不赞成简单说“所有岗位都会合并”。他的判断是：围栏会降低，重叠会增加，但学科本身仍然重要。工程、设计、产品、研究都有可学习、可积累、可犯错的专业知识。

更合理的描述是：角色越来越像一个人时间分布的平均值，而不是固定边界。你可能仍然主要是设计师或 PM，但你需要能跨到实现、数据、调研和系统判断里。

### 8. 管理不会消失，只是管理对象变了

一个很有意思的判断是，AI 并不会让管理工作消失。

过去管理者管理人、项目、资源和优先级；现在高能力 IC 自己也在管理多个 agent、多个分支、多个工作流、多个并行实验。管理能力从 manager 专属技能，变成更多知识工作者都需要掌握的能力。

管理者的工作也会迁移到更高并发的层面：如何让组织覆盖更多方向，如何避免探索碎片化，如何决定哪些原型进入正式路线，如何让不同 agent 产出的成果被团队吸收，而不是堆成噪音。

### 9. 产品组织会从 man-to-man 变成 zone defense

Andrew 用了一个很有启发性的比喻：产品团队需要从盯人防守变成区域防守。

AI 让许多想法都能被快速做成原型，产品人员不再只是守住自己负责的一条功能线，而要更主动地铺开，看哪里有缺口、哪里有重复、哪里有信号、哪里需要收敛。

这要求产品团队里有更多高 agency 的人：能自己发现问题、建原型、做判断、推进到完成，而不是等一套清晰需求从上游流下来。

### 10. 长期规划必须保留模糊性

Andrew 对 roadmap 的看法很现实：短期计划需要具体，长期计划需要保持一定模糊。

原因在于，AI 产品高度依赖模型能力边界。一个产品形态在 11 月可能完全不可用，到 2 月因为模型变强就突然可行。过早把长期路线写得过于精确，会制造虚假的确定性。

因此，团队需要保留一些“现在可能跑不通，但未来模型能力到了就值得重试”的 artifact。写出来的代码不一定马上要 ship，也可能是未来模型能力的测试器。

### 11. Codex Web 曾经过早押注完全委托

Andrew 复盘了一个很有价值的产品教训：Codex Web 一开始有点太 “AGI-pilled”，过早假设用户可以把任务完全委托给远程 agent。

但当时模型能力和用户心智还没有准备好。相反，Claude Code 这种本地、交互式、可随时介入的形态，在当时更适配模型能力边界。

这说明 AI 产品不是越自动化越好，而是要精确匹配当前模型能力、用户信任程度和任务风险。过早全自动，反而可能错过真正可用的产品形态。

### 12. “AI 写了多少代码”已经不是好问题

Andrew 认为，问一个产品有多少代码是 AI 写的，已经越来越没有意义。

如果沿用去年的标准，很多产品可以说几乎全都有 AI 参与。但真正重要的问题是：这些代码是在什么监督程度下产生的？是人类提出设计、审查 diff、跑测试、做取舍，还是模型自己观察反馈、决定策略、改进产品？

他认为更好的问题是：supervised vs unsupervised。AI 参与写代码不稀奇，难的是 AI 能否在没有明确人类目标和审查的情况下，真正改进产品。

### 13. 模型还需要学会“删除代码”

Andrew 有一个很尖锐的观察：模型天然倾向于增加复杂度。

它们擅长添加功能、写新模块、堆更多逻辑，但不够擅长判断哪些东西应该删除、哪些抽象已经过期、哪些复杂度不值得维护。

这对软件工程非常关键。AI 编程如果只会加法，会让代码库越来越臃肿。真正高级的 agent 需要懂得做减法，能够用更少代码、更少状态、更少概念解决问题。

### 14. 个人工作流会先爆发，然后沉淀为产品 primitives

Andrew 描述了自己对 Codex 的使用：构建 Codex、跟踪状态、做内部 deep research、处理 release、生成每日简报、分析 Slack、连接工具、写自动化任务。

这些用法一开始可能只是个人工作流，但如果大量用户不断重复某类模式，产品团队就应该把它抽象成 first-class primitive。

例如 memory 就不应该只靠每个人维护自己的 Obsidian、Notion 或“心智宫殿”。如果长期个性化上下文是 AI 工作入口的核心能力，它就应该成为产品底层能力。

### 15. Codex 不一定替代专业软件，而是给专业软件长出 AI 操作层

访谈中最能体现 Codex 愿景的例子，是 OpenAI 内部视频团队用 Codex 操作 Premiere Pro。

用户不是让 Codex 替代 Premiere，而是让 Codex 自己做了一个 Premiere 扩展，然后通过这个扩展完成视频编辑任务。

这个例子说明，AI 工作入口的终局未必是一个超级应用吞掉所有专业工具，而是一个 agent 能理解任务、调用专业软件、必要时为自己补工具、在真实工作流里完成动作。

## 访谈大框架

### 一、产品开发：从“实现稀缺”到“判断稀缺”

过去的软件开发组织围绕实现成本搭建流程。因为工程实现慢、贵、不可逆，所以产品团队要提前写文档、做用户研究、画流程图、反复校准需求。

AI 改变的是这个成本结构。现在很多实现可以被快速生成，原型可以并行出现，甚至非工程角色也能直接做出可运行版本。于是团队的主要风险从“做不出来”变成“做太多、太散、太快，但不知道哪些该留下”。

这会让产品经理、设计师、工程经理的价值更集中到三个动作上：

- 定义真正重要的问题；
- 识别原型里的有效信号；
- 把探索结果收敛进长期产品系统。

### 二、设计：不是被 AI 消灭，而是被迫更接近真实系统

AI 让设计过程更容易接触真实实现。设计师不必只依赖静态稿表达交互，也可以直接做出可点击、可运行、可连接数据的原型。

但这并不意味着设计变简单。恰恰相反，当实现变便宜后，设计要承担更多判断：什么样的交互值得存在？什么样的状态应该被系统化？怎样避免一个漂亮原型误导团队？怎样把局部界面放回整体产品语义里？

因此，AI 时代的设计不是从“画界面”降级为“让模型画界面”，而是升级为对系统、语义、交互和产品方向的综合判断。

### 三、组织：角色重叠增加，但专业训练仍然重要

Codex 团队呈现出一种更流动的组织形态。PM 可以写代码，设计师可以理解实现，工程师也参与产品方向。

但这不是“人人都一样”。更准确地说，AI 降低了跨边界工作的门槛，但没有取消专业能力本身。一个人可以更容易地跨到邻近领域，但仍然需要知道那个领域的基本功、质量标准和常见陷阱。

未来高价值人才更像 T 型甚至π型：有一个足够深的主专业，同时能用 AI 跨进其他环节，把想法推进到更完整的状态。

### 四、计划：AI 产品路线要和模型能力共同演化

AI 产品规划的难点在于，底层能力变化太快。

某个功能今天失败，可能不是方向错，而是模型还差一点；某个交互今天显得笨重，可能几个月后就因为模型推理、工具调用、上下文管理变强而变得自然。

因此 AI 产品团队需要同时做两类工作：

- 把当前产品做扎实，让今天的用户得到可靠价值；
- 保留足够多的未来探索，持续测试模型能力边界。

这也是 Codex 这类产品的难点：既要服务当下的开发者和知识工作者，又要不断寻找下一代工作入口的形态。

### 五、入口：Codex 可能成为 AI 时代的桌面操作面

从访谈看，Codex 的野心不是“更好的代码编辑器”，而是“更好的任务执行环境”。

它的界面里可以有代码、终端、浏览器、外部工具、自动化、记忆、任务状态、连接器和文件系统。但它不一定把这些都做成一个巨型套件，而是像一个能调度其他软件的智能工作台。

这和传统 SaaS 最大的不同在于：过去软件的入口是应用，用户进入应用完成某类工作；未来入口可能是任务，AI 根据任务调用应用、生成工具、连接数据、维护状态。

## 可复用判断框架

### 1. 判断一个 AI 产品原型是否值得进入正式路线

- 它验证的是交互问题、需求问题，还是模型能力问题？
- 这个原型的“看起来能用”是否掩盖了权限、数据、稳定性、质量和边界条件问题？
- 它是一个孤立 feature，还是能沉淀为产品 primitive？
- 用户是否愿意反复回到这个入口完成真实工作？
- 它依赖当前模型能力，还是需要等待下一代模型能力？

### 2. 判断一个岗位在 AI 时代的护城河

- 这个岗位的价值是工具熟练度，还是结果判断力？
- 是否能跨到相邻环节，把想法推进成可运行 artifact？
- 是否能判断 AI 产出的质量，而不是只会接受或拒绝？
- 是否能做减法，减少系统复杂度？
- 是否能把个人工作流抽象成组织可复用流程？

### 3. 判断一个 AI 工作入口是否有长期价值

- 用户是否自然地从这里开始工作？
- 它是否能连接用户已经使用的专业工具，而不是强迫替代？
- 它是否能保存上下文、状态和长期记忆？
- 它是否能从个人工作流中发现可产品化的 primitives？
- 它是否能在模型能力变化时快速调整形态？

## 反共识与金句

- AI 的核心变化不是让实现消失，而是让实现便宜到判断力成为瓶颈。
- PRD 没死，原型也不是万能；正确媒介取决于你要表达什么问题。
- 角色不会简单消失，但角色边界会变软。
- 管理不会消失，每个高能力 IC 都会开始管理 agent 和并行工作流。
- 长期 roadmap 写得太精确，可能只是虚假的确定性。
- 问“多少代码是 AI 写的”已经不够，应该问“是在什么监督程度下写的”。
- 模型需要更擅长删除代码，而不是只会添加功能。
- Codex 的长期想象不是替代所有软件，而是让 AI 学会使用、连接甚至扩展专业软件。
- 不要嫁给你今天的流程，要嫁给你真正能交付的结果。

## 精简结论

这期访谈最值得带走的判断是：AI 产品革命首先不是岗位替代，而是组织生产函数变化。实现变便宜之后，产品、设计、工程和管理的价值会更多转向判断、收敛、系统化和质量控制。

Codex 的意义也不只是“AI 写代码”。它更像一个工作入口实验：当 agent 能读上下文、写代码、查资料、连工具、开浏览器、操作专业软件并维护任务状态时，软件的边界会从“应用”迁移到“任务”。谁能成为任务入口，谁就可能拥有下一代工作流的分发位置。
