# Tensor Mesh 创始人访谈 Notes：KV cache 三层理解与大模型推理瓶颈

## 一句话总览

这期访谈最重要的观点是：KV cache 不只是大模型推理过程里可以缓存的一堆中间张量，而可能是 AI 时代最重要的“模型原生数据”。它既能被存储和复用，也能被压缩、迁移、更新、分发，甚至在更激进的方向上被改写语义，从而影响模型注意力和输出质量。

Tensor Mesh 的判断是，随着 agent、长上下文、企业内部知识、多模态输入和推理规模继续增长，推理瓶颈不会只靠更强 GPU 或更便宜存储解决。未来真正有价值的是一套围绕 KV cache 的数据基础设施：既懂系统，也懂 ML，既能省算力，也能管理模型记忆。

---

## 最高价值观点清单

### 1. 推理瓶颈已经从普通聊天转向 agentic workload

嘉宾开场强调，现在的 AI workload 和两年前非常不同。

过去很多场景是短对话，输入输出都相对有限；现在越来越多场景变成 agent、长上下文、代码库理解、企业知识库、法律金融文档、多轮任务和多模态输入。

这类 workload 有两个显著特征：输入越来越长，历史越来越多，模型每轮都需要重新理解大量上下文；同时 agent 会反复和环境交互，每一次交互都会增加新的 history，下一轮输入又更长。

因此，推理瓶颈不只是“模型生成慢”，而是模型反复读取、理解、存储和使用上下文的成本越来越高。

### 2. input token 看起来便宜，不代表计算成本真的低

一个很重要的反共识观点是：input token 的定价便宜，不等于它真实计算成本便宜。

在大模型服务商的价格表里，output token 通常比 input token 贵很多，这会让人误以为 prefill/input 不重要。但嘉宾指出，从真实计算量看，处理一个 input token 和生成一个 output token 的计算成本在同一量级。

之所以用户感觉 output 更贵，是因为 output 是线性生成的，用户会盯着屏幕等；而 input prefill 可以高度并行，时间上看起来更短。但在很多真实场景里，input token 数量可能是 output 的十倍甚至更多，整体 prefill 成本反而很高。

### 3. prompt caching 只是 KV cache 价值的一小步

现在很多模型服务商已经提供 prompt caching 或 cached token 定价，这证明缓存输入上下文有价值。

但嘉宾认为，这只是 KV cache vision 的第一小步。多数服务商的缓存更接近把 token 处理后的状态存下来，下次遇到相同前缀时复用。它解决的是“存下来再拿来用”的问题，但没有真正理解 KV cache 内部包含什么信息。

Tensor Mesh 想做的是更大的一层：把 KV cache 看作可管理、可优化、可计算的数据层，而不是一次性黑盒缓存。

### 4. KV cache 有三层理解：黑盒、白盒、语义可改写

这期最核心的框架，是嘉宾对 KV cache 的三层理解。

第一层：KV cache 是可缓存的计算状态。它是模型处理输入后产生的一堆张量，可以存下来，下次遇到相同或相似上下文时复用。这是工业界当前最容易理解、也最常做的一层。

第二层：KV cache 是带语义信息的白盒数据。它包含模型的注意力和内部理解，因此可以被压缩、更新、变换，只要不破坏语义，就仍然可以复用。比如 lossy compression、非前缀复用、跨文本相似语义复用、甚至跨模型复用，都属于这一层。

第三层：KV cache 的语义本身可以被改写。因为模型输出不仅取决于 weights，也取决于推理过程中生成的 KV cache。如果能够改变 attention，让模型更多关注某些内容、减少关注另一些内容，就可能提升准确性和输出质量。

### 5. 工业界多停留在第一层，学术界已经走到第二、第三层

嘉宾认为，工业界每天都接触 KV cache，但多数工程师会天然把它当黑盒：既然是一堆浮点数，那就存起来、搬运、压缩、加速，而不是改它。

学术界则更容易问另一个问题：这些张量里到底有什么语义？能不能改？能不能对注意力做干预？能不能让模型更好地利用中间状态？

这造成一个断层：懂 KV cache 语义的人通常接触不到真实工业系统，接触真实系统的人又往往不懂其语义。Tensor Mesh 的创业机会就在这里：把系统工程和 ML 研究打通。

### 6. KV cache 是 AI 时代的大数据

嘉宾反复强调一句判断：KV cache is big data for AI。

传统大数据处理的是 human-readable data，比如日志、表格、文本、用户行为。KV cache 则是 model-readable data，是模型自己在理解输入时产生的内部状态。

如果未来世界里大量任务由模型执行，那么模型可读的数据本身就会成为新基础设施。KV cache 的价值不只是省掉一次重复计算，而是可以被分析、优化、分发和再利用。

### 7. 企业场景的最佳客户是共享知识反复被模型读取

Tensor Mesh 当前最适合的场景，是企业内部存在大量共享知识，并且这些知识会被多个 agent 或应用反复读取。

典型例子包括：

- coding agent 反复读取同一个 codebase；
- 企业 chatbot 反复读取 policy documents；
- 金融、法律、客服场景反复读取内部知识和文档；
- 多个 RAG、agent、多模态应用共享同一批上下文。

这些 shared knowledge 如果每次都让模型从头读一遍，会造成巨大浪费。如果能以 model-native 的方式存成 KV cache，模型下次可以更快、更便宜地接入这些记忆。

### 8. KV cache 不只降本，也可能提升模型质量

很多人会把 KV cache 理解为成本优化，但嘉宾认为它也可能提升模型输出质量。

原因在于，模型第一次读长文本时是单向扫过去的，容易出现 lost in the middle：开头和结尾的信息记得更好，中间的信息容易被忽略。

如果把 KV cache 存下来，并在存储层对其做优化，比如让模型重新加强某些重要部分的 attention，下一次复用时模型对长文档的理解可能更精确。

这意味着 KV cache 不是简单缓存，而可能成为模型记忆质量的调优层。

### 9. Token maxing 是野蛮生长，KV cache 是更聪明的上下文管理

嘉宾对当下很多 agent 的上下文管理方式有明显批评：模型看过什么、说过什么，就一股脑塞回 context，让模型每次重新读一遍。

这种 token maxing 方式非常粗暴，会快速推高成本，也不一定带来更好质量。很多公司正在做 compression，但压缩并不能解决所有问题，因为有些信息不能随便压掉。

更聪明的方式是复用模型已经理解过的中间状态，尤其是非前缀位置的复用。Tensor Mesh 提到的 CacheBlend，就是为了解决传统 KV cache 只能复用前缀的问题，让中间文本、相似上下文也能被更新后复用。

### 10. CacheBlend 说明 KV cache 系统不只是存储，而是存储加计算

传统理解里，缓存系统主要是存储：把热数据放近一点，把冷数据放远一点。

但 KV cache 不同。很多情况下，缓存不能原样复用，需要被更新、改写或重新对齐，才能适配新的输入位置和上下文关系。

这就意味着 KV cache 基础设施不仅需要存储层，还需要计算能力。它要知道什么时候复用、复用哪一段、如何改写、怎么保持语义不变、如何在 GPU、CPU、SSD、远端存储之间调度。

这也是为什么嘉宾认为这个领域需要同时懂系统和 ML 的团队。

### 11. 多模态会进一步放大 KV cache 的重要性

长文本只是第一阶段。图像、视频、3D 视频进入模型后，也会被表示成 token，而且 token 数量可能远超文本。

一个几十秒视频转成 token，可能相当于一本大书的 token 量。多模态输入天然有大量冗余信息，也存在巨大的压缩和复用空间。

这会让 KV cache 的问题变得更复杂：同一个视频的 480P 和 1080P，在语义上可能是同一个输入，但转成 token 后长度和表示完全不同。未来如何定义多模态 KV cache 的相似性、复用和压缩，会成为新的研究和工程问题。

### 12. KV cache 存储是经典计算-存储 tradeoff，但 AI 场景有新收益

嘉宾把 KV cache 存储看成经典系统问题：用存储换计算。

如果存储足够近、传输足够快，例如 CPU、本地 SSD、GPU Direct Storage，那么加载 KV cache 可能比重新计算更快。这样既能降低 GPU 成本，也能降低延迟。

如果存储太远，例如跨国拉取 KV cache，延迟会显著增加，但仍可能在降本上有价值。最终要根据热度、网络、模型大小、复用频率、硬件价格来权衡。

### 13. 热冷分层不能完全自动化，必须允许 operator 表达 domain knowledge

一个很具体但很关键的产品判断是：系统很难单靠自己判断哪些 KV cache 是热的、哪些是冷的。

有些 cache 可能每天下午 8 点必用，有些可能明天还会用，有些只在某个业务流程里会复用。真正知道这些模式的人，是使用系统的 operator 或企业内部工程团队。

因此 Tensor Mesh 不想只做一个完全透明的 KV cache 系统，而是希望提供接口，让用户把自己的 domain knowledge 写进缓存策略里。

### 14. KV cache 基础设施短期像 data center 内 mini-CDN，长期像 knowledge delivery network

嘉宾用了一个很好的类比：早期互联网需要 CDN，把网页和内容放到离用户更近的位置。KV cache 未来也可能需要类似的分发网络。

今天大多数 AI 推理还发生在同一个 data center 内，所以更像 data center 内部的 mini-CDN，把 KV cache 放到离 GPU 更近的位置。

但随着 edge AI、低延迟 agent、分布式推理发展，模型可能离用户越来越近，而模型之间距离变远。那时就可能需要 internet-scale 的 KV cache / knowledge delivery network。

### 15. 大模型市场更像在线视频，而不是搜索

嘉宾对大模型公司格局的判断是：它可能不像搜索那样一家独大，而更像在线视频。

搜索领域最终高度集中到 Google；但视频领域虽然 YouTube 最大，仍然有 Netflix、HBO、BBC、Hulu 等多个重要平台长期存在。

他认为大模型也会有少数巨头，但很多场景需要独立模型和独立部署：主权 AI、企业机密、客户数据保护、本地控制、开源生态等。因此推理基础设施不应该只服务一家模型公司，而要支持多模型、多部署形态。

### 16. “KV cache”只是当前名字，本质是 model-native data

当被问到如果未来 Transformer 被 Mamba 或其他架构替代怎么办，嘉宾的回答是：KV cache 只是当前 Transformer 时代的名字。

更本质的概念是 AI native data 或 model-native data，即模型运行过程中生成的中间状态和内部理解。Mamba、diffusion model、CNN 也都有自己的中间状态，只是形式不同。

这让 Tensor Mesh 的命题从“Transformer KV cache 优化”扩展成“模型原生数据基础设施”。这是一个更长期、更架构无关的叙事。

## 访谈大框架

### 一、为什么现在推理瓶颈变得更严重

推理瓶颈来自 workload 变化，而不只是模型变大。

Agent 会不断把环境反馈、历史动作、工具输出、代码 diff、错误日志、用户约束加入上下文。企业应用会把共享知识、私有文档、代码库和政策材料放进 prompt。多模态模型会把图像和视频转成更长 token 序列。

这些变化让 input side 的成本快速上升。用户看到的是 output 慢，服务商价格表里也是 output 更贵，但系统真实压力越来越多来自 prefill 和长上下文。

### 二、Tensor Mesh 解决的不是缓存小优化，而是模型记忆管理

Tensor Mesh 把自己的任务定义为大模型记忆管理。

模型处理输入后会生成 KV cache，这里面包含模型对上下文的内部理解。传统推理完成后，这些状态会被丢弃，因为模型默认是 stateless。Tensor Mesh 要做的是把这些记忆保存下来，在未来相同、相似或相关上下文中复用。

如果只停留在第一层，这像是缓存；如果进入第二、第三层，它就变成了模型可读数据的管理、优化和调度。

### 三、为什么这个机会适合 startup

大厂当然有人、有资源、有 GPU，也能看到 KV cache。但嘉宾认为，真正打通三层理解很难。

第一层需要强系统工程能力：GPU、后端、存储、网络、推理服务。第二、第三层需要 ML research 能力：理解 attention、语义、压缩、改写和模型行为。

大厂内部可能两类人才都有，但 attention 分散、组织优先级复杂，很难把它们快速整合成一个专注产品。而 startup 可以围绕这一个 vision 长期集中投入。

### 四、经济账：不是买更多硬件，而是用软件提高硬件效率

Tensor Mesh 的商业逻辑不是押注某一种存储硬件，而是押注计算和存储之间的软件优化层。

企业当然可以购买更多 GPU memory、SSD、CPU、存储设备和一体机，但这些都很贵，而且供应周期不稳定。另一条路是用更聪明的软件，让已有 GPU 和存储承担更多 workload。

如果 KV cache 加载比重新计算更快，那么它既能省 GPU 计算，也能提升速度。这是非常强的系统收益。

### 五、未来：从 KV cache 到 AI 原生数据基础设施

访谈最后把 KV cache 类比成汽油：它原本像模型运行中的副产品，被短暂存放后丢掉；但一旦有人发明“内燃机”，这个副产品就可能变成驱动产业的核心燃料。

这个类比的重点不是说 KV cache 一定等于汽油，而是说行业对某类中间产物的认知可能发生翻转：从废料，到缓存，到数据资产，到基础设施。

如果这个判断成立，未来围绕 model-native data 会出现一整套公司和产品：存储、压缩、检索、热度管理、分发、语义改写、质量优化、安全治理和多模型兼容。

## 可复用判断框架

### 1. 判断一个场景是否适合 KV cache 优化

- 是否有大量长输入或共享上下文？
- 是否存在同一批文档、代码库、policy、知识库被反复读取？
- agent 是否多轮运行，history 是否越来越长？
- input token 总量是否显著高于 output token？
- 是否有低延迟要求，重新 prefill 是否成为瓶颈？
- 是否有企业私有部署或自管推理基础设施？

### 2. 判断一个 KV cache 公司是否只是“缓存”，还是更深的数据基础设施

- 只支持相同前缀复用，还是支持非前缀复用？
- 只做存储，还是能对 KV cache 做更新和计算？
- 是否理解 KV cache 里的语义和 attention？
- 是否支持压缩、迁移、热冷分层和策略接口？
- 是否能让 operator 表达业务知识？
- 是否有开源生态和实际系统集成能力？

### 3. 判断未来 model-native data 的长期价值

- 模型中间状态是否能被持久化？
- 这些状态是否能跨任务、跨用户、跨模型或跨模态复用？
- 改写这些状态是否能提升模型质量？
- 它是否降低 GPU 成本或延迟？
- 它是否能形成新的数据治理、安全和分发层？

## 反共识与金句

- input token 价格便宜，不等于真实计算成本便宜。
- Prompt caching 只是 KV cache vision 的第一小步。
- KV cache 不是黑盒废料，而是模型自己的记忆。
- KV cache 是 AI 时代的大数据，只不过它是 model-readable，不是 human-readable。
- 现在懂 KV cache 的人接触不到真实系统，接触真实系统的人往往不懂 KV cache。
- Token maxing 是野蛮生长：把模型看过和说过的一切都塞回上下文，让它每次重读。
- KV cache 系统不只是 storage story，而是 storage plus compute。
- 多模态会让上下文问题进一步爆炸，因为视频和图像会变成更长的 token 序列。
- 今天是 data center 内 mini-CDN，未来可能是 AI 的 knowledge delivery network。
- KV cache 只是暂时的名字，更长期的命题是 model-native data。

## 精简结论

这期访谈最重要的启发是：大模型推理的关键瓶颈正在从“模型能不能生成”转向“模型如何反复读取、记住、复用和改写上下文”。当 agent、长上下文、企业知识和多模态输入成为主流，KV cache 不再只是临时中间状态，而可能成为新的 AI 数据层。

Tensor Mesh 的真正命题也不是“做便宜缓存”，而是围绕模型原生数据建立系统：让模型记忆可以被保存、压缩、分发、更新和优化。这个方向如果成立，KV cache moment 可能会类似早期大数据或 CDN：一开始是工程优化，后来变成基础设施市场。
