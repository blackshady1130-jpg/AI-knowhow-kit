## DeepSeek V4 on my Mac

其实这两个月我的开发工作并不算太多，因为之前 db9.ai 已经基本成型也已经上线，系统进入稳定期，更多的工作在架构优化和提升稳定性上。在这个部分，我觉得 AI 能帮的不太多，大多数跟 AI 的讨论都是在运维方案和 Review 这些场景。纯粹从写代码来说，这个项目其实已经进入了一个稳定期，不会有特别疯狂的堆代码阶段，所以这俩月，我 AI 使用的绝对消耗量肯定是少了很多。但是另外相反，我开始慢慢把一些原来只有顶级模型才能做的事情，迁移到本地模型（DeepSeek v4）上。

这里有一个很有意思的点：哪怕 DeepSeek V4 的 API 已经非常便宜了，但只要它是付费的，我觉得仍然会有一部分需求是被压抑的。我的这种体感来自于我现在把 DeepSeek 跑在本地。我在 Mac Studio 上跑的是 DeepSeek V4 Flash，这是一个 281B 的 Tier-1 顶级模型。它的智商处理很多日常工作完全在线，比如：

- 归纳总结文章
- 回复 IM Messages
- 查看邮件 / 整理日历
- 以及一切日常的助理型工作

对于这些需求，DeepSeek V4 Flash 完全够用。更有意思的是，因为它是一个完整的本地模型，一旦你在本地有一个免费能跑的模型，你就会发现很多原来不敢尝试的"粗放型"需求现在都可以试了。

举个例子：我下载了几百篇论文，但没有时间一篇篇看。你可以很轻易地让 Claude Code 写一个程序，让它遍历这 100 篇论文，每一篇都送到本地的 DeepSeek 里通过 CC 给出的总结 Skill，让它慢慢去总结。即便一天的 Token 消耗量达到几十亿、上百亿，用起来也一点都不心疼。

我觉得核心点就在于，原来被压抑的一些需求现在能被发现和满足，还有一些因为合规问题不能使用顶级模型的行业（医疗，保险，法律）中存在大量的类似场景，过去受限于本地模型的能力问题，没有办法大规模落地，现在有机会了。

使用模式上，我让顶级模型来做 planning，再由本地模型来干一些重复性的、不需要长程推理的、确定性（recurring）的活。所以我是觉得未来这种家用的 Local AI Machine 其实是非常有用的。DeepSeek V4 是第一个给我这种感觉的本地模型。之前的开源模型跑在本地，一方面是你很难在家自己买一块 H100 这种顶级的显卡，也就很难用上顶级的模型，而我现在用一台 Mac Studio，基本上就能以比较低的功耗跑起来。而且电费比起机器成本比起网上 API 还是便宜非常多的。

所以我觉得本地模型会是一个很大的趋势，尤其在不远的未来，本地模型的能力也会持续进步。我相信一定会突破一个临界点，到那个点我们已经几乎没有办法评估本地模型的智商了——也就是说，我们大多数的工作本地模型都能完成。

到那个时间点（也许是未来 1～2 年，也许更快），我觉得当前的 Token 经济学可能就会发生很大的改变。

当然想把本地模型用好，其实也没那么容易。

我觉得 DeepSeek V4 是一个非常有意思的模型，1M 上下文能解锁很多 Agent 的场景（尤其是多 Skill 和长程工具调用），但这个模型本身其实并没有设计跑在家用的显卡上，所以能让我在 Mac 上跑起来，是多亏了这么一个项目：https://github.com/antirez/ds4。这个项目其实是 Redis 的作者开发的，这个项目是针对 DeepSeek V4 定制化的一个本地推理框架。它不像 vLLM 或者 Ollama 这种通用的本地推理框架，它是专门针对这一款模型的这一套权重和网络结构去定制的。

另一方面，它的第一版是针对苹果的 Metal 框架去定制的，几乎没有什么迁移性（当然，后来的更新开始支持越来越多不同种类的硬件）。因为对于 AI 来说，针对不同硬件去实现算子的成本其实是非常低的，对了，这个项目其实也是由 Vibe Coding 开发而成的，作者完全不避讳这个事情。

这个项目一开始就让我觉得非常惊艳，带着传统 Infra 项目硬核气息。所以从它开源的第一天起，我就在我的 Mac 上用起来了。随着研究和使用越来越深入，就发现如果你想把 ds4 用好，你会发现上层的 Harness 其实也要针对这个模型和推理框架去设计：比如它的一些 Tools Prompt 的缓存策略，你就得根据 DeepSeek V4 的特定规范去写，这里就得出一个非常简单的推论：要把一款本地的开源模型用好，你可能得从本地的推理端一直到上层的 Agent 端，都实现完整的控制。

以前这件事其实很难做，但现在随着 LLM 的能力提升和 Coding Agent 的成熟，我觉得开发这样的针对具体的某一个模型的全栈工具链的成本已经非常低了。我最近自己用的 Agent 就是一个自己在开发的，基于 Pi，开发了 Pie（https://github.com/c4pt0r/pie）：

- Pie 把 Pi 改写成了 Rust（对于大型项目 Rust 是 Vibe Coding 首选）；
- 加入了非常多针对 DeepSeek V4 和 antirez/ds4 的优化，我把这些优化放到了：https://github.com/c4pt0r/pie/blob/main/docs/ds4.md 这里；
- 增加了一些我自定义的、符合我日常工作的贴心小功能：例如主动事件触发 trigger / 定时任务 / auto skill builder / loop engineering pattern 等

过去我很难让 Claude Code 去给我定制某些特定的功能，但现在在我自己的 Agent 框架上，我基本想做啥就做啥，这种灵活性其实是完全不一样的。而且这整个项目其实并不是说花了很多时间和精力，活跃的开发阶段也就是一个周末，消耗几亿 Tokens（Opus / Gpt-55 为主），就是这样的一个数量级，非常简单，一个人就能完成。

其实提到这个 Agent 的开发，我之前在前几个月的文章里也提到过，我们现在整个团队已经进入到了 Agent Native 或者说完全依靠人指挥 Agent Team 的这种研发模式，以至于公司的组织架构都正在大规模地转变。

在这样的背景下，确实发现了一些以前没有遇到过的需求。我举一个小例子，当我们一个小团队里大概有两三个人同时在用自己的 agent harness 时，其实 agent 比人掌握的信息更全。这时候人与人之间基本上只能讨论一个大致的分工或者大方向，但真正执行的时候，如果没有 agent 的协同还是会有非常多的冲突。

这时候可能就需要多个人的 agent 在一个讨论组里互相 share、互相讨论。虽然 Slack 其实能干这个事情，但并不能强制要求大家都用 Slack，所以这类团队 memory 就会产生一个需求。

这是第一个点。关于这一点我之前也说过，像 Linear 或者直接用 GitHub Issue 做看板，其实适合共享一些非常具体的任务。但像一些 memory，或者一些临时性的讨论和分析（尤其是这类分析可能比较冗长），目前的情况其实不太好解决。

所以我现在在做一些方案，但总体还不是太理想。这是第一点。第二个需求就变成了：因为目前开发的项目越来越庞大，本地环境和开发所依赖的组件变成了一个特别大的问题，而且我越来越不倾向于用我本地的开发机作为开发环境。所以我们需要一个沙箱或者云平台，来标准化多个人之间的开发环境。

## Sys9.ai: The Agent Cloud

其实这也是前几个月我们开始做 sys9.ai 的初衷，一个主要目的打造一个存算分离的多 Agent 开发平台，初步的用法是用于我们自己团队的 Agent Team 的开发环境，但是搞着搞着就发现这个系统已经很像一个未来的 Agent Cloud 的雏形。

先说为什么要做成这种存算分离呢？其实第一个核心原因是我们观察到 Agent 的使用模式有个特点：

- **Event-driven**：Agent 永远是由消息触发的，不论是对话型任务，还是长程 Tool use 任务，总体上都是 Agent 通过某些信息或事件（例如 Crontab 或者 Trigger）进入后才会开始工作。
- 但是不管什么样的触发方式，最后你会发现它大多数时间其实都是空闲的。

真正的计算或底层资源消耗主要集中在两方面：

1. 运行调用 LLM 的框架（Agentic loop）的进程以及操作系统
2. 进行工具调用，目前的工具以开发相关的工具为主：shell / unix cli tools

在 idle 的时候，它是不会消耗系统资源的。所以完全可以把沙箱本身变成纯弹性的、无状态的，有需要的时候再拉起来运行，只要你能保证存储是可以跨 sandbox 持久化的即可。现在像 MicroVM 或者一些容器方案（包括 gVisor 或 Firecracker 之类），都能做到几乎让用户无感知的启动时间（50ms ~ 1000ms）。相比起大语言模型本身的思考时间，这个启动延迟实在是短太多了。第二个好处是，由于存储本身的成本很低，如果您能找到一个方案来提供全局持久化的共享存储，在真正有工作负载时，再调用一个无状态的沙箱并将存储 mount 进去，其实能够节省非常多的计算成本。

其实这样就可以提供一个非常有意思的平台型的 Agent 应用场景：

例如 sys9 几乎可以无限地几乎免费的提供无穷多个 Agent，而且每一个 Agent 都有自己独立的记忆和状态，但只有在真正有消息或者请求到具体的某个 Agent 时，才去动态地找一个 Sandbox，挂载上它之前时刻存储的镜像，处理完这条消息后再把计算资源还回去。这样就给用户一个假象，觉得这些个 Agent 是实时在线的，其实物理上并不是。但对平台商来说就拥有了一个非常大规模的 Agent 云平台，只有这样在成本上才是可行的。

这个模式唯一的问题在于：

- 你不能同时让几百、几千万个 Agent 在一秒钟之内全部都在处理事情。当然，这可以通过快速扩容来解决，但它本质上遵循的是"酒店逻辑"：只要你保证酒店的房间不同时被住满，那么对于任何一个过来的人，其实都是有房间可用的。
- 这种模式不太适合计算密集型的工具调用。比如某个调用可能要运行一个小时，会长时间占据计算资源。

我觉得总体来说，学过计算机的人肯定知道，这其实就是一个"分时操作系统"的概念。在 Agent 云平台上，可能也会出现类似的模式。

这种模式其实会跟传统的云计算模式不太一样。Agent 面临的场景大多比较灵活，最好的方式就是给每个 Agent 都分配一台计算机，目前来说这是对 Agent 最友好的方法。但在传统的云计算里，你不可能给每个应用或每个 Agent 都分配一个 EC2，这肯定是很不划算的。

## 关于今天的 Harness

关于今天的 Harness，我觉得有一些跟前几个月不一样的地方。

当然，不得不提最近最火热的 /goal 模式（我自己就是重度的 goal 用户）和 Loop Engineering。大家不要被这些名词吓到，其实从去年下半年开始，大家似乎就发现，让 Agent 在对话中持续长时间地运行、不要停下来，是一个重要的优化方向。

所谓的 Raphl Loop 或者 goal，其核心思想很简单：每次运行要停止的时候，就重新强制性地把一开始的 Prompt 循环发送给语言模型，让它继续工作。这就是一种迭代。

我觉得 Loop Engineering 在思想层面上也是一模一样的，唯一的区别在于：

- 它更强调多 Agent、多阶段的大循环。
- 在评估最终结束状态的条件时，它可能会用一个单一的 Agent 去做一个更客观的评估。

这样整个 Loop 更像是一个建立在多个 Agent（不共享上下文）、更大的循环工作流。你看，这地方又是以 Dify、n8n 为代表的 workflow 模式了，我觉得本质上其实没有差太多，唯一的区别是：模型能力的增强了很多倍，所以它能够通过这种更简单的模式，为 Agent 提供更大灵活性的前提下，同时把自主工作的时间拉得更长。

而且随着模型的能力越来越强，其实前几个月我非常依赖一个模式，就是多 Agent 在同一个上下文或者同一个对话里互相讨论。这个模式之所以有效，是因为它通过消耗更多的 token，让这些 Agent 或者模型之间互相 challenge，实现一种"左脚踩右脚"式的提升。但是今天的模型确实已经非常强了，对于最顶级的模型，编排和讨论甚至都不太重要了。比如说，我前几天在 Fable 5 被封之前，就经历过一个情况：在一个很复杂的 Bug fix 场景里，需要涉及多个模块，横跨上万行代码。面对这种级别的复杂且隐秘的问题，我花了一下午的时间让 Agents（Opus 4.8 和 GPT 5.5）互相讨论，但最后仍然没有解决，后来我干脆中止，将这个烂摊子，完全交给 Fable 5 加上 cc 的 /goal 模式，于是 fable 5 在几乎没有过去任何团队记忆的情况下，大概工作了半个小时，One Shot 就搞定了，非常强，可惜现在不能用了，我至今还非常想念它。对，这再一次说明了一个事实：**在绝对的智商面前，所谓的这些编排工具可能最终都没有太多意义。编排其实只是去弥补模型智商的不足吧。**

所以，我现在在开发软件的模式慢慢变成了：

1. 我会在一个项目里让 AI 从头到尾负责若干个功能，我想到什么，就让 agent 直接做，技术方案评审和 code review，ci 单元测试什么的我完全不做，AI 做完觉得没问题，直接合并。
2. 我主要的时间花在深度使用 AI 做出来的这些新功能。
3. 其中一大半功能，哪怕在逻辑上是完备、正确的，但只要我自己觉得用起来不好用，我就会直接让 Agent 删掉。

上面的模式往复的循环。其实和 Claude Code 内部，他们开发团队的工作模式也有点类似，我记得某一次 Boris 的访谈里提到过，这个模式最大的挑战其实并不是 Agent 和模型能力，而是基础设施。其实从 Anthropic 的工程师的背景分布，就能看出，大多数 A 社的工程师都是 Infra 背景。

大概就是这些吧，虽然不知道下个月会变成什么样子，但是还是要 Keep Thinking, Keep Building!
