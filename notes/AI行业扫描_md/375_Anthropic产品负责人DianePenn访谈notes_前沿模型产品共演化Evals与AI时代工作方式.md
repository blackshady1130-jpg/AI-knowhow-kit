# Anthropic 产品负责人 Diane Penn 访谈 Notes：前沿模型、产品共演化、Evals 与 AI 时代的工作方式

> 说明：本文基于英文播客 ASR 转写稿整理。Diane Penn 在节目中被介绍为 Anthropic AI Research 与 Labs 团队的产品负责人，2023 年加入公司，是早期技术产品经理之一。原稿对部分新模型和产品代号识别不稳定，本文只保留上下文能够确认的名称；涉及未发布能力、安全策略及未来模型的部分，均按访谈当时的观点理解。广告内容、主持人的推测性财务数字及无法核验的转述未纳入正文。

## 一句话总览

这期访谈最重要的贡献，是解释了前沿模型公司里的“产品”究竟在做什么。

Anthropic 的经验不是先把模型训练好，再让产品团队包装成界面。模型与产品需要共同演化：研究团队通过产品看见用户真正怎样使用模型，产品团队通过 traces、失败轨迹和 evals，把模糊反馈翻译成可训练、可测量的问题；新的模型能力又会反过来催生 Claude Code、computer use、MCP、Skills 等此前不存在的产品形态。

Diane 对 AI 产品管理给出了一套很具体的方法：

- 像打磨像素一样研究 token、上下文和模型轨迹；
- 把“Claude 不好用”拆成工具调用、检索、综合、格式遵循或 alignment 等具体失败；
- 用 eval 描述用户需求并验证模型迭代，因此“evals 是新的 PRDs”；
- 但 PRD 并没有消失，它仍负责跨团队对齐和探索尚未成形的产品愿景；
- 产品负责人和管理者必须亲手使用、构建和发布 AI 产品；
- 在能力快速跳变的阶段，对方向有强判断，对具体产品形态保持开放。

访谈的另一条主线是人的位置。Diane 并不认为 AI 越强，人只需退到监督席。她认为，人仍需提供经长期经验积累的判断、目标选择、坚持、主动性和独立观点。AI 最好的角色不是顺从地完成指令，而是知道什么时候执行、什么时候提出新方案、什么时候反驳。

## 最高价值观点清单

### 1. Anthropic 早期最稀缺的不是资源，而是“我们是谁”

Diane 2023 年加入时，产品工程团队只有约五名工程师，整个 API 业务一度只有一位工程师负责。公司尚未形成今天清晰的产品身份，最初也从 Claude.ai 这样的聊天助手开始。

她认为，早期真正稳定的资产是文化、使命和价值观。团队还不知道最后会做出哪些产品，但成员愿意跨研究、工程、设计和产品边界协作，也允许一线工程师和设计师自下而上发起实验。

Anthropic 后来的产品节奏，不应只用融资、算力或模型规模解释。组织在规模很小时建立的信任和决策方式，决定了它能否在模型能力突然跃迁时快速行动。

### 2. Golden Gate Claude 的意义不在流量，而在建立产品身份

2024 年，Anthropic 的 interpretability 研究发现，可以识别并放大模型内部与某些概念相关的 feature。其中一个 feature 与金门大桥高度相关；把它调高后，Claude 会在几乎任何回答中都谈到金门大桥。

团队在约 24 小时内把这个研究原型做成 Claude.ai 上的体验。它可能只触达约 2,000 人，却让团队第一次明确感受到：

- 研究成果可以被快速转化为普通人能感知的产品；
- Anthropic 不必只做另一个聊天机器人；
- 研究、工程、设计和产品可以围绕一个新体验迅速协作；
- 有趣、古怪但忠于研究本身的产品，也能形成公司独特身份。

这是一个典型的“低流量、高组织价值”项目。衡量探索性产品时，不能只看用户量，也要看它是否改变了团队对自身能力和方向的认识。

### 3. Opus 3 带来的首先是组织信心

Opus 3 发布前，Anthropic 仍不足约 200 人。预训练、后训练、推理和产品团队围绕同一目标密集协作，证明公司能够训练并发布真正的前沿模型。

Diane 特别强调，这段经历建立了跨团队信任。后来负责 RL、character 等方向的研究负责人，许多都参与了当时的共同冲刺。产品与研究能够在后续模型上高效合作，基础并不是流程图，而是早期一起解决真实训练问题形成的信任。

组织能力经常具有路径依赖。一次成功发布的价值，不只是当期模型收入和口碑，也包括它留下的协作网络、判断标准和共同语言。

### 4. Claude 的 coding 优势起初来自对用户行为的早期判断

2023 年，行业更多把大模型用于代码补全或零散问答。Diane 观察到，一部分用户已经开始让模型编写长段代码。

团队因此在 Opus 3 训练中加强了这类能力。她说，从训练规模看，这可能只是相对小的改动，却帮助 Claude 在开发者中建立差异化，也吸引了最早的一批忠实用户。

这里的产品洞察不是“coding 市场很大”，而是识别一种尚未成为共识的新行为，并及时把它变成训练目标。前沿模型产品经理需要同时看见今天的用户问题和明天可能扩大的行为。

### 5. 前沿模型需要前沿产品，模型和产品互相放大

Diane 用 Opus 4.5 与 Claude Code 说明了这一点：

- 如果没有 Claude Code，很多用户无法直观感受到 Opus 4.5 的 agent 能力；
- 如果没有更强的 Opus 4.5，Claude Code 的采用也不会以同样速度增长。

因此，模型发布并不是完整交付。一个高能力模型需要合适的产品载体，让用户能够提供上下文、调用工具、观察进度、介入决策并验收结果。

反过来，产品也不能脱离模型能力独立存在。过早设计的 agent 产品可能被模型局限拖累；模型跨过某个能力阈值后，同一个产品形态可能突然从“有趣 demo”变成“日常工作工具”。

### 6. 模型能力具有跳变，固定路线图很容易过期

规模化训练中的总体 loss 可以平滑下降，但具体能力可能不连续地出现。模型可能在某一代突然学会稳定计算、调用工具或完成端到端任务。

这会同时带来产品和安全问题：

- 产品团队可能已经拥有能力，却还没有发现它；
- 用户可能不知道现有模型已经能完成某类任务；
- 安全团队也可能错过突然出现的新风险；
- 数月后的产品计划，可能因新模型提前具备能力而需要立即前移。

Diane 将适应能力视为关键组织能力：面对新证据时，及时调整计划，而不是为了维护原路线图忽略模型已经发生的变化。

### 7. AI 公司同时存在“产品过剩能力”和“用户过剩能力”

Diane 使用了 product overhang 和 user overhang 的说法。

**产品过剩能力**：模型已经具备某种能力，但尚无产品把它组织成稳定体验。

**用户过剩能力**：产品已经提供能力，但多数用户不知道如何使用，或者还没有形成新的工作习惯。

这解释了为什么模型提升不会自动转化为商业价值。实验、原型、教育、默认工作流和分发，决定了潜在能力能否成为真实使用。

AI 产品团队的重要任务之一，就是持续寻找“模型已经会了、产品和用户还没跟上”的区域。

### 8. 处在指数变化中，真正重要的是适应速度和第一性思考

当下一代模型能力无法被准确预测时，照搬消费互联网或 B2B SaaS 的成熟模式会失效。

Diane 所说的第一性思考是：针对当前用户、当前技术和当前约束，重新回答“什么创造用户价值”，而不是把过去做过的 PRD、增长实验或产品流程重复一遍。

她常问团队：

> 假设 Claude 8 到来，用户行为会发生什么变化？这对今天的产品设计意味着什么？

这个问题把“更有野心”变得可操作。产品需要兼容更强模型，而不是只针对当前模型的缺陷堆叠临时功能。

### 9. 高 token 消耗只是投入，真正目标是高质量实验

主持人引用一种观点：如果今天愿意每年花 10 万美元使用模型，就能提前体验 2028 年普通人的工作方式。

Diane 没有把高 token 消耗本身当作目标。她认为，token spend 是输入，实验和学习才是输出。

高用量只有在以下情况下有价值：

- 团队不断探索新任务；
- 对模型失败形成具体认识；
- 原型真正进入工作流；
- 实验结果被他人复用；
- 使用反馈转化为产品和模型改进。

如果只是更频繁地调用模型，却没有积累新判断，高 token 消耗并不自动带来领先优势。

### 10. 最有创造力的人，通常也是最频繁接触研究模型的人

Diane 观察到，Anthropic 内部最有创造力的思考者和原型开发者，会花大量时间使用每一版研究模型。

原因很直接：当技术变化极快时，不亲手接触模型，就很难形成可靠的产品 taste。文档、榜单和他人演示都不能替代实际体验。

好的策略常常来自对模型边界的体感：

- 它在哪些任务上突然变好；
- 哪些失败是偶发，哪些是系统性；
- 什么时候应该增加 harness；
- 什么时候应该修改训练；
- 哪些体验现在已经可以端到端完成。

### 11. 实验不是个人运动，组织应让探索过程公开

Anthropic 早期有一个几乎全公司参与的 Slack 频道，成员会公开测试 Claude、分享提示词和工作场景。一个人的用法会被其他人继续修改，数次迭代后就可能形成新的产品机会。

Diane 认为，共同发现比每个人独自寻找“完美 use case”更有效。公开实验带来三种复利：

- 使用方式扩散得更快；
- 不同职能能从同一案例看到不同问题；
- 原型获得自然的内部用户和反馈；
- 对模型边界的认识成为组织资产，而不是个人经验。

对普通团队而言，推动 AI 使用不应只发账号和培训资料，还要建立公开展示、复用和二次改造的场所。

### 12. Labs 的任务不是做更多原型，而是寻找非连续性机会

Anthropic Labs 关注的不是核心路线图里的渐进功能，而是可能带来 10 倍、100 倍乃至更大变化的方向。Claude Code、Skills、MCP 等都来自这类探索。

Diane 对 Labs 的描述可以概括为：

- 对主题和机会方向有强判断；
- 对具体产品形态保持开放；
- 用小团队快速做原型；
- 允许实验暂时没有产品结果；
- 在一到两代模型后重新检查曾经失败的方向。

Labs 的产出不仅是正式产品，也包括关于“为什么现在还不行”的学习。对于快速变化的底层技术，这些失败会形成未来可重新激活的期权。

### 13. 模糊的大赌注，不适合一开始就配置大团队

Labs 的 pod 很小，有些项目从一名工程师开始。Diane 认为，大团队面对高度不确定的问题，往往会被沟通、分工和维护组织本身拖慢。

小团队的优势是：

- 发起人拥有近似 founder 的完整责任；
- 试错成本低；
- 方向变化快；
- 更容易关闭没有进展的项目；
- 成功后再获得资源，而不是先用资源证明重要性。

这要求团队主动选择喜欢 zero-to-one 工作的人。实验被停止时，成员需要能够接受“方向尚未成立”，而不是把关闭项目理解为个人失败。

### 14. 研究者既做局部优化，也要拥有未来愿景

Diane 不把 AI 研究者描述成只调算法和数据的人。优秀研究者通常同时工作在两个时间尺度：

- 中长期：判断 AI 最终可以怎样使用计算机、工具和现实环境；
- 短期：通过数据、训练和 eval 改善今天的 Claude。

她观察到，优秀研究负责人往往具有几项共同特征：

- 用第一性原理推理；
- 对研究方向有强烈兴趣和大胆愿景；
- 持续接近训练 run、底层数据和 eval；
- 能在宏大目标与具体细节之间往返；
- 对方向坚持，对实现路径保持弹性。

“有远见”和“看细节”不是对立项，前沿研究需要两者同时存在。

### 15. 研究产品经理的核心，是把用户语言翻译成训练语言

用户会说“Claude 在幻觉”“它不听指令”“它不够聪明”。这些反馈对研究人员几乎不可执行。

研究 PM 要回到完整轨迹，拆解问题究竟发生在哪个环节：

- 是否应该调用工具却没有调用；
- 是否调用了错误工具；
- 是否检索到正确文档却抽取了错误事实；
- 是否检索正确但综合失败；
- 是否格式遵循失败；
- 是否表现得过度自信；
- 是否属于 alignment 或 character 问题。

只有形成足够细的失败分类，研究团队才知道应修改训练数据、工具使用、检索、奖励还是产品 harness。

### 16. “Evals 是新的 PRDs”，因为 eval 能把用户价值变成训练目标

传统 PRD 描述用户、问题、方案和产品要求。在模型产品中，很多用户价值最终必须表现为模型在一组输入上的行为变化。

一个好的 eval 能回答：

- 哪些真实用户场景正在失败；
- 失败是否稳定复现；
- 正例和反例的分布是否合理；
- 新模型是否真的改善；
- 改善是否引入新的副作用；
- 研究团队应优化哪一种能力。

因此，eval 不是发布后的质量检查，而是产品定义的一部分。它把“用户需要更可靠的 Claude”转化成可训练、可比较的行为要求。

### 17. 像打磨像素一样研究 token 和轨迹

Diane 的原话是：产品团队需要像重视 pixels 一样重视 tokens。

在传统软件中，产品经理会逐屏检查用户流程；在 AI 产品中，还要逐步阅读模型看到的上下文、生成的 token、工具调用和失败轨迹。

界面可能完全正常，失败却发生在：

- 系统提示未包含必要约束；
- 上下文顺序让重要信息被忽略；
- 工具描述导致错误选择；
- 检索结果噪声过高；
- 中间推理在某一步偏离；
- 验证器没有捕捉错误。

AI 产品的“像素级体验”已经扩展成“轨迹级体验”。

### 18. JSON 格式问题说明：宽泛反馈必须压缩成小而稳定的 eval

早期用户常说 Claude 2“不遵循指令”。团队逐条查看案例后发现，大约 80% 的抱怨实际是 Claude 无法稳定输出正确 JSON。

团队最初只整理了约 30 至 40 个例子，构成一个小型 eval。此后每版模型都会运行这组测试。节目称，这项能力后来已接近 100%。

这个案例说明，建立 eval 不一定先做大规模 benchmark。更实用的顺序是：

1. 收集真实失败；
2. 找到主导失败模式；
3. 用少量可复现案例形成测试；
4. 持续在新模型上运行；
5. 能力稳定后，把注意力转向新的失败分布。

### 19. PRD 没有消失，只是使用边界改变了

Diane 不赞成把“evals 是新的 PRDs”理解为 PRD 已死。

PRD 仍然适合两类问题：

**跨团队对齐。** 每次模型发布涉及产品、工程、法律、安全和商业团队，需要一份共同的目标与事实来源。

**高不确定性愿景。** computer use 等能力尚无成熟用户流程时，团队仍需描述潜在用户、产品价值和初始切入点。

Eval 更适合已经观察到具体行为问题、需要推动模型改进的场景。两者承担不同工作：PRD 对齐方向与体验，eval 定义行为与验收。

### 20. AI 产品负责人的管理权威，必须来自亲手构建

Diane 的团队三年来没有因为 AI 热潮改变招聘标准，仍然强调第一性思考、用户价值和深入细节。但她对中高层 PM 有一个更强要求：必须亲手使用和发布 AI 产品。

管理者不能只在评审会上谈策略。他们需要：

- 阅读经过同意的用户反馈；
- 与客户交流；
- 使用研究模型；
- 参与具体工作流；
- 在模型发布中亲自负责一到两个 workstream；
- 对好坏形成一手判断。

如果管理者没有经历模型的随机性、上下文问题和工程取舍，就很难判断团队提出的方案是否优秀。

### 21. AI 时代的产品 taste，来自持续 shipping，不是持续 tinkering

Diane 区分了“玩一玩模型”和“端到端发布”。

随手尝试提示词能建立初步感知，但真正的产品判断来自完整闭环：

`发现问题 → 构建体验 → 交付用户 → 观察失败 → 修改产品或模型 → 再次验证`

只有经历这个过程，产品负责人才能理解用户愿不愿意采用、模型错误会怎样影响信任，以及一个 demo 与生产体验之间还差多少工作。

### 22. 面对工具焦虑，最好的方法是与人一起深入一两个问题

模型和原型数量太多，试图追踪一切会让实验变成打卡任务。

Diane 给出的建议很克制：

- 找一个真正关心的问题；
- 与已经对 AI 有热情的人结对；
- 选择一到两个产品或工作流深入；
- 让 AI 带来一次完整、可感知的改善；
- 公开分享过程，让他人继续探索。

乐趣来自解决真实问题和共同发现，而不是使用了多少新工具。

### 23. AI 不只提高工作产出，也可以改善人与人的互动

Diane 会用 Claude 准备困难谈话，并基于《Crucial Conversations》的方法制作了一个 Skill，帮助自己判断沟通层级、预演对方反应、提高直接性并更快建立信任。

她把这种使用方式视为个性化 coaching。AI 不代替最终沟通，也不保证建议都被采用；它提供了一个低成本的排练和反思空间。

这是一类容易被忽略的 AI 价值：它不直接替人写代码或文档，而是帮助管理者成为更好的教练、同事和支持者。

### 24. 防止思考能力退化，关键是按任务保留不同程度的主导权

Diane 将自己的任务分成两类。

**高判断、高个性任务。** 先形成自己的观点，再让 Claude 质疑、补充和改进，同时保留自己的语气。

**标准化、低个性任务。** 如月度业务回顾，可以让 Claude 承担更多整理和写作，自己转为审核者和验证者。

这比“是否应该用 AI 写作”更有操作性。问题不是用了多少 AI，而是这个任务的价值主要来自原创判断，还是来自准确、规范地整理既有信息。

### 25. 好的 AI 不应永远服从，它需要知道什么时候反驳

Diane 认为，AI 的价值不只是 assistant 或 doer。真正有用的同事会在观点不成熟时提出异议，会指出价格决策中的漏洞，也会主动提出新的方向。

这将 alignment、character 与能力连接起来。一个拥有明确行为原则的模型，不一定更受限；如果它能在合适时机拒绝迎合、提供校正，反而会成为更好的思考伙伴。

“主动性”也不只是定时执行任务。更高级的主动性是判断：

- 什么时候应直接执行；
- 什么时候需要补充信息；
- 什么时候应提醒风险；
- 什么时候值得提出新方案；
- 什么时候必须反对用户。

### 26. AI 写作的核心治理问题，可能从“谁写的”转向“谁验证的”

主持人担心 AI 写作越来越难辨认。Diane 的回答把问题转向责任：

- 谁核验了事实？
- 谁确认结论符合目的？
- 谁愿意为内容签字？
- 哪些观点来自作者本人？

对于月度业务回顾等标准化文档，她并不介意 Claude 端到端起草，只要有人可靠验证。对于表达立场和个人判断的文本，则需要保持作者自己的观点和声音。

未来内容治理的重点，可能不只是检测 AI 痕迹，而是建立清楚的审核、签署和责任机制。

### 27. AI 写作差，不一定是语言模型的永久缺陷

Diane 认为，模型能力具有明显的“锯齿边缘”。一段时间里，训练重点可能是 agent、工具调用和端到端任务；这些能力提升后，写作、语气和 character 的粗糙处就变得更显眼。

因此，AI 写作的模板感部分来自训练优先级，而不是语言模型天然无法写好。写作可以通过数据、训练目标和评测继续改善。

这也提醒产品团队：模型某项能力停滞，不应立即判断它不可解决。需要先看该能力是否被明确纳入训练和 eval。

### 28. 人的长期优势更像“判断资产”，而不只是某项操作技能

Diane 认为，判断来自长期经验、情境细节和后果反馈。模型拥有广泛知识，却没有像人一样在组织和生活中经历那么多真实后果。

她认为短中期仍然重要的人类能力包括：

- 判断哪些问题值得做；
- 在信息不完整时做取舍；
- 坚持推进长期方向；
- 主动发现机会；
- 建立自己的观点；
- 在生物、生命科学等尚未完全进入 AI 指数增长的领域积累专业知识。

当执行成本下降，选择目标和承担责任会更重要。

### 29. 对孩子最重要的准备，不是更早使用最强模型

Diane 有两个孩子。她认为，面对 AI 未来，家庭仍应培养一些非常传统的品质：

- 对学习保持好奇；
- 遇到困难时坚持；
- 形成自己的内在声音；
- 愿意表达意见并采取立场；
- 相信经过思考形成的判断。

这与她对成年人使用 AI 的建议一致：先建立自己的观点，再让 AI 扩展，而不是把观点形成也完全外包。

### 30. AI 让个人杠杆变大，也可能让工作更孤独

agent 能让更小团队完成更多工作，但人与模型长时间协作，也可能减少人与人之间的共同工作。

Diane 对抗 burnout 的主要方法不是更精细地管理个人时间，而是建立真正可替代、互相支持的团队：

- 发布前不是 DRI 的同事也会主动帮助；
- 成员理解彼此的第一性原则和判断方式；
- 休假时团队能继续做正确决策；
- 返回后不是面对三倍积压工作；
- 招聘时强调低 ego 和团队贡献，而不是扩大个人组织。

技术放大个人后，人类协作反而成为维持判断质量、归属感和可持续性的基础设施。

### 31. PM 不会因为工程更容易而消失，用户理解反而更稀缺

Diane主动回应了“模型这么强，还需要 PM 吗”这个问题。

当工程师和 agent 能更快构建产品时，团队仍需有人：

- 深入理解用户要完成什么；
- 找到真实失败而非表面抱怨；
- 把反馈变成研究和工程可执行的描述；
- 判断应该构建哪一种体验；
- 持续完成枯燥、细致的验证工作；
- 在技术驱动的组织中维护用户视角。

构建成本降低，会让“做什么、是否做对、是否值得继续”成为更大的瓶颈。这正是优秀产品人的价值。

## Anthropic 的产品与研发闭环

### 一、从用户反馈到模型训练

Anthropic 的闭环可以概括为：

`真实使用 → 同意使用的轨迹 → 失败分类 → Eval → 训练或 Harness 修改 → 新模型/产品 → 再次验证`

每一环都有不同责任：

1. **产品与用户研究**发现真实痛点，不满足于“模型不好用”。
2. **研究 PM**阅读轨迹，将问题拆成可行动的能力类别。
3. **Eval**固定失败分布，成为研究目标和回归测试。
4. **研究团队**判断应修改数据、训练、奖励、tool use 或其他能力。
5. **产品与工程团队**调整上下文、工具、交互和验证方式。
6. **新版本发布后**重新运行 eval，并继续观察真实用户反馈。

模型产品的迭代对象不只是 UI，也包括模型、提示、上下文、工具和评测系统。

### 二、用户反馈如何变得可行动

以“幻觉”为例，至少可能对应四类问题：

| 用户表述 | 可能的真实失败 | 主要责任方向 |
| --- | --- | --- |
| “Claude 瞎编了” | 应调用工具却直接回答 | Tool-use 训练或 Harness |
| “找错了事实” | 检索到错误文档 | 检索与数据源 |
| “文档是对的，答案仍错” | 抽取或综合失败 | 模型训练、上下文与 synthesis |
| “它说得太肯定” | 不确定性表达失真 | Alignment、character 或校准 |

产品团队的工作，是从表面反馈追到失败机制。没有这一步，用户研究无法进入模型训练。

### 三、Eval 与 PRD 的分工

| 情况 | 更适合 Eval | 更适合 PRD |
| --- | --- | --- |
| 已发现稳定的模型失败 | 是 | 可作为背景 |
| 需要比较模型版本 | 是 | 否 |
| 需要定义正例、反例和边界 | 是 | 可补充原则 |
| 多团队需要统一目标和发布范围 | 可作为验收项 | 是 |
| 产品形态仍高度模糊 | 暂时难以建立 | 是 |
| 需要探索未来用户价值 | 后期补充 | 是 |
| 需要持续回归测试 | 是 | 否 |

结论不是“Eval 替代 PRD”，而是模型行为第一次成为产品规格的一部分。

### 四、前沿产品与前沿模型共同演化

模型能力只有进入合适的 product harness，用户才能持续使用。一个前沿产品至少要解决：

- 怎样给模型提供足够上下文；
- 怎样授权和约束工具；
- 怎样显示进度与中间状态；
- 怎样允许用户介入；
- 怎样处理模型失败和 fallback；
- 怎样验证任务真的完成；
- 怎样把真实失败反馈给训练团队。

Claude Code 的价值不只是一个编码界面，而是把模型能力组织成可观察、可干预、可验证的工作流。

## Labs 的创新机制

### 1. 寻找非连续性，而不是填满路线图

核心产品团队通常优化现有用户和明确指标。Labs 则主动寻找那些一旦成立会改变产品边界的机会。

它评估的不是“能否提高 5%”，而是：

- 如果能力提高 10 倍，用户行为会怎样变化？
- 如果模型再强一代，这个原型是否会突然成立？
- 这个方向能否变成新的产品类别？
- 是否值得脱离核心路线图单独探索？

### 2. 对问题强信念，对答案弱信念

团队可以坚定认为“AI 应该承担更完整的软件工程任务”，但不预设最终一定是某个界面、命令或工作流。

这种结构允许模型能力、用户反馈和原型结果共同塑造产品，而不是让早期方案绑架长期方向。

### 3. 把失败原型当作带时间条件的知识

原型失败可能有三种含义：

- 用户问题并不重要；
- 产品方案不对；
- 当前模型能力尚未达到阈值。

第三类尤其重要。Labs 会在一到两代模型后重新审视某些方向。快速模型迭代让“现在不工作”不再等于“永远不工作”。

### 4. 小团队先证明学习速度

在问题和方案都模糊时，先增加人手往往只会增加协调。Labs 更看重：

- 一名或少数发起人的完整 ownership；
- 每周能学到什么；
- 哪个假设已经被推翻；
- 下一代模型会改变哪个约束；
- 何时应停止或扩大投入。

## AI 时代的产品经理

### 仍然不变的核心

- 第一性思考；
- 深入理解用户；
- 对结果负责；
- 形成产品判断；
- 推动跨团队协作；
- 持续验证是否创造用户价值。

### 明显上升的能力

- 阅读模型轨迹和工具调用；
- 设计与维护 evals；
- 区分模型、Harness、数据和交互问题；
- 使用研究模型做快速原型；
- 亲手 shipping；
- 根据模型代际调整路线图；
- 将模糊用户反馈翻译为研究问题；
- 设计人机协作与最终验证。

### 明显下降的能力

- 依赖过去行业模板做 pattern matching；
- 把写 PRD 当作产品工作的主要产出；
- 只管理流程、不接触模型；
- 只看 aggregate 指标、不阅读失败样本；
- 把 AI 使用变成工具采购或培训打卡。

### 一个合格研究 PM 的工作循环

1. 选择一个高价值用户问题；
2. 阅读真实任务轨迹；
3. 建立失败分类；
4. 判断问题是否足够普遍；
5. 创建包含正例和反例的 eval；
6. 与研究人员确定可改变的训练变量；
7. 与工程团队检查 Harness 和产品约束；
8. 在新模型上运行回归；
9. 回到用户场景确认改善是否真实；
10. 将新的失败加入下一轮。

## AI 时代的个人工作方式

### 一、先按任务判断 AI 应该拥有多少主导权

| 任务类型 | 人的角色 | AI 的角色 | 关键控制点 |
| --- | --- | --- | --- |
| 战略、定价、人员沟通 | 先形成观点并承担判断 | 质疑、补充、模拟反应 | 防止 AI 迎合，保留本人立场 |
| 创意与产品探索 | 定义问题、选择方向 | 提供变体、原型和反例 | 评估是否真正产生新信息 |
| 月度回顾、标准化更新 | 定义格式和事实标准 | 整理、起草、结构化 | 人负责核验和签署 |
| 批量执行任务 | 设定目标与边界 | 端到端执行 | 工具权限、进度与结果验证 |
| 高风险决策 | 保留最终决定 | 提供分析和挑战 | 明确责任，不把判断外包 |

### 二、从个人试用升级为共同实验

一个更有效的团队采用方法是：

1. 选择一到两个真实工作流；
2. 由有热情的人与业务使用者结对；
3. 公开展示尝试、失败和改进；
4. 让同事复制并产生变体；
5. 记录节省时间之外的新能力；
6. 将稳定模式固化为 Skill、模板、Eval 或产品功能。

### 三、保护自己的内在声音

AI 可以让表达更顺滑，也可能让人的观点在生成过程中被模型默认风格覆盖。

Diane 的做法是：

- 高判断任务先写自己的 POV；
- 要求模型明确反驳，而不是只优化措辞；
- 区分“我的观点”和“模型提供的可能性”；
- 保留最终语气和取舍；
- 对标准化任务大胆委托，但坚持审核。

### 四、把 AI 用作更好的同事，而不是更少的同事

个人拥有 agent 后，不应默认减少所有人际协作。高质量工作仍需要同事：

- 补充不同经验；
- 发现假设错误；
- 在高压时接替工作；
- 帮助判断哪些结果值得信任；
- 提供归属感和共同责任。

AI 增加认知杠杆，人类团队维持判断、信任和可持续性。

## 可复用判断框架

### 框架一：从用户抱怨建立 Eval

1. **收集原始反馈**：保留提示、上下文、输出、工具调用和最终结果。
2. **复现失败**：确认不是单次随机波动。
3. **拆解轨迹**：定位错误发生在哪一步。
4. **建立分类**：区分模型、检索、工具、Harness、格式和 alignment。
5. **判断分布**：确认它在目标用户中是否足够常见、足够重要。
6. **加入反例**：定义何时不应触发该行为，避免过度修正。
7. **形成小型测试集**：先用几十个高质量样本，不盲目追求规模。
8. **运行基线**：记录当前模型表现和主要失败。
9. **验证改进**：比较新模型，并检查副作用。
10. **回到用户结果**：确认 eval 提升确实改善真实任务。

### 框架二：判断一个产品是否“面向下一代模型”

可以用五个问题检查：

1. 当前功能是在弥补暂时缺陷，还是组织长期工作流？
2. 模型能力提高十倍后，这个界面仍然有价值吗？
3. 产品是否允许模型承担更长任务，而不是限制在单轮问答？
4. 用户能否观察、介入和验证 agent？
5. 新能力出现后，产品能否快速暴露给用户并收集反馈？

### 框架三：决定使用 Eval 还是 PRD

- 已有稳定失败、需要改进模型行为：先做 Eval。
- 产品形态未知、需要探索价值：先做 PRD 或 vision doc。
- 多团队共同发布：PRD 作为事实和目标来源，Eval 作为验收标准。
- 行为随机、无法 exact match：用分布化 eval、grader 和人工判断。
- 只有宽泛抱怨：先阅读轨迹，不急着写任何文档。

### 框架四：Labs 项目的继续、暂停与重启

每个实验记录五项内容：

| 项目问题 | 需要回答的内容 |
| --- | --- |
| 核心主题 | 哪个非连续性机会值得长期坚持？ |
| 当前方案 | 这一次用什么最小原型验证？ |
| 失败原因 | 用户问题、产品设计还是模型能力？ |
| 重启条件 | 哪项模型或基础设施能力出现后值得重试？ |
| 扩大条件 | 哪个用户信号或技术结果足以增加资源？ |

### 框架五：AI 产品人才判断

优先寻找能够同时做到以下事情的人：

- 对用户保持同理心；
- 对技术保持真实兴趣；
- 能在抽象愿景和底层细节之间切换；
- 敢于质疑已有流程和假设；
- 亲手构建并承担发布结果；
- 接受实验被停止；
- 低 ego，愿意帮助其他 DRI；
- 对方向有 conviction，对方法保持弹性。

## 反共识与金句

以下为对访谈观点的中文提炼，非逐字翻译。

1. **前沿模型需要前沿产品；没有产品载体，用户感受不到模型的前沿。**
2. **Evals 是新的 PRDs，但 PRD 并没有死。**
3. **像打磨像素一样打磨 token、上下文和失败轨迹。**
4. **模型调用量只是投入，真正的产出是实验、学习和新工作方式。**
5. **实验不是个人运动，公开探索会形成组织级复利。**
6. **对机会方向保持强信念，对具体产品形态保持松弛。**
7. **“Claude 会幻觉”不是研究问题；明确它在哪一步失败，才是研究问题。**
8. **AI 产品管理越来越像测试驱动开发：先把用户价值写成 Eval。**
9. **管理者如果不亲手 shipping，就很难领导 AI 产品团队。**
10. **最好的 AI 不会永远同意你，它知道什么时候应该反驳。**
11. **比“谁写了这段文字”更重要的问题，是谁验证并愿意为它签字。**
12. **模型越能替人构建，人的判断、目标选择和责任越稀缺。**
13. **AI 让工作更高效，也可能让工作更孤独；人类团队不是旧时代遗留物。**
14. **构建变容易后，PM 的价值不会消失，真正稀缺的是知道该构建什么。**
15. **保护思考能力的方法不是拒绝 AI，而是先形成自己的观点，再要求 AI 挑战它。**

## 对不同角色的启示

### 对模型公司

- 模型与产品路线应共同规划，不能把产品视为发布后的包装。
- 用户 traces、失败分类和 eval 是训练资产，需要建立清晰的同意、治理与反馈路径。
- 模型能力跳变后，安全、fallback 和用户体验必须同步升级。
- 研究成果应有机制快速转化为普通用户能理解的体验。
- 不能只奖励成功产品，也要保存因模型能力不足而暂停的原型。

### 对 AI 产品团队

- 把用户反馈追到模型轨迹，不接受“体验不好”这种终点描述。
- 建立自己的 eval repository，让用户痛点能跨模型版本持续测试。
- 同时检查模型、Harness、工具、上下文和交互，不把所有失败归因于模型。
- 为下一代模型设计产品，减少对当前缺陷的永久性依赖。
- 公开内部实验，让个人技巧转化为团队资产。

### 对产品负责人和管理者

- 固定时间亲手构建，并承担至少一项端到端 workstream。
- 用一手使用经验校准团队的产品 taste。
- 高判断任务保留自己的 POV，让 AI 负责挑战而不是替代。
- 招聘重视第一性思考、低 ego、细节深度和真实的 tinkering 精神。
- 判断团队是否可持续，看成员休假后系统能否继续正确运行。

### 对普通知识工作者

- 不必追逐所有工具，选择一两个真实问题深入使用。
- 找到愿意共同实验的人，比独自寻找完美场景更有效。
- 把标准化整理交给 AI，把判断、责任和个人声音留给自己。
- 关注谁验证、谁签字，不把流畅表达误认为可靠结果。
- 积累专业经验、判断、坚持和清晰立场，这些能力会随执行成本下降而升值。

### 对父母和教育者

- 不必把“最早用上最强 AI”当作教育目标。
- 优先培养好奇、坚持、独立观点和面对困难的耐心。
- 让孩子学会使用 AI 扩展想法，同时保留形成自身判断的过程。
- 技术会持续变化，内在声音和学习能力更具长期价值。

## 精简结论

这期访谈呈现了 Anthropic 的一套完整产品操作系统。

第一，模型和产品不是上下游，而是共同演化。Opus 4.5 需要 Claude Code 才能被用户感知，Claude Code 也需要更强模型才能跨过采用阈值。前沿实验室必须同时建设模型能力和承载能力的产品 Harness。

第二，AI 产品管理的核心正在从描述功能转向定义行为。研究 PM 需要阅读轨迹、拆解失败、建立 eval，并把用户语言翻译成训练语言。“Evals 是新的 PRDs”成立，但 PRD 仍负责跨团队对齐和探索未知产品形态。

第三，组织需要对方向坚定、对方案开放。小团队负责高不确定性原型，失败项目记录模型依赖条件，在一到两代模型后重新判断。适应速度比维护原路线图更重要。

第四，AI 产品负责人必须亲手构建。只有持续使用研究模型、完成端到端 shipping、观察真实失败，才能形成可靠的产品 taste。高层管理不能替代这种一手经验。

第五，人的价值不会简单地随模型能力下降。执行更便宜后，经长期经验形成的判断、目标选择、主动性、责任和独立观点会更重要。AI 应承担整理和执行，也应成为能够提出异议的思考伙伴；人则负责选择方向、验证结果并签字。

最终，这期访谈给出的不是一套追赶 AI 变化的工具清单，而是一种工作方式：接近用户、接近模型、公开实验、用 eval 形成共同语言，并在更强工具面前保留自己的判断。
