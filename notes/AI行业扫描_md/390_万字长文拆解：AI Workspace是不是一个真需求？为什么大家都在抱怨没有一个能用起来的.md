# 万字长文拆解：AI Workspace是不是一个真需求？为什么大家都在抱怨没有一个能用起来的

> **作者：**梦琪  
> **公众号：**不一道视界  
> **发布时间：**2026-06-24 19:43  
> **原文链接：**[https://mp.weixin.qq.com/s/OD06BES89Wp9qsTv6qY9Fw](https://mp.weixin.qq.com/s/OD06BES89Wp9qsTv6qY9Fw)

引：从我们成立开始，就一直在思考如何改造组织，毕竟字节出来的嘛，时刻记着develop a company as a product ；)

我们也去试了很多ai workspace产品，让组织更native最简单直接的方式可能就是买个AI native 的 Workspace但是都不太能用的起来。

不是因为这些产品做得不好，也不是因为它们没有想象力。相反，很多产品看起来都很 AI native，很未来，很完整。但一旦把它们放进日常工作里，就会遇到一个非常朴素的问题：我的搬家成本太高了。

我原来的房子里堆满了历史的东西。群聊、截图、PR、issue、表格、负责人、默认规则、历史争论、组织默契，全都在那里。现在你让我搬到一个新空间里去，哪怕那个新房子再智能、再漂亮、再“原生”，我也可能要叫十车货拉拉才能把家搬过去。

这不是一个很小的体验问题。组织上下文不是一团可以随意复制粘贴的文本。它长在人和人的关系里，长在群聊的惯性里，长在评论、截图、链接、负责人、历史争论、默认规则和那些“大家都知道但没人写下来”的默契里。你让一个团队为了 AI 再打开一个新空间，本质上不一定是在减少复杂度，也可能是在原来的复杂度上又加了一层。

所以在回答“AI Workspace 是不是一个真需求”之前，我想先讲讲我们自己在搭建一个更 AI native 的组织时踩过的坑。我们在做 Invoko的时候（对，我们做了一个personal proactive agent，一个品类词而非需求主导的产品） 当我们让 Agent 承担更多组织责任时，经历了很多非常细碎、非常不性感，但又非常真实的问题。它们让我越来越意识到，Agent 进入组织以后，最难的不是让模型说话，而是让它进入真实工作流，知道谁在提问、上下文在哪里、被授权做什么、当前跑到哪一步、结果应该回到哪里、最后由谁验收（验收是最最重要没有之一的事！！）

这些经验，也构成了我后来判断 AI Workspace 这个命题的底层依据。

## 我们在搭建更 AI native 的组织时，真正踩到的坑

我们内部反馈bug的地方是lark群。

大家会在群里发一句话，贴一张截图，补一段语音转写，顺手 @ 某个负责人。这个状态非常真实，也非常高效，因为没有人愿意为了每一个体验细节切到另一个系统里（比如多维表格）填字段。人不是这样工作的。真实组织里的协作经常是顺手的、流动的、带着上下文的。一个人看到问题，就在原来的地方说一句；另一个人看到，就顺手补充；负责人看到，就在 thread 里回一句“收到”或者“这个先别做”。

但问题也在这里。群聊是最真实的事发现场，但它不是天然的系统记录。

它是流式的、非结构化的、带噪声的。它非常适合表达上下文，却不适合承载组织状态。表格、Issue、PR、项目管理系统刚好相反：每一行都有主键、状态、负责人、优先级、更新时间和验收路径。群聊和系统记录之间有一层非常硬的摩擦。

我们一开始做过一个很朴素的系统。群里有人提到“闪退”“卡死”“有 bug”，系统就自动建一条记录。刚开始它看起来挺聪明的，因为确实减少了手工提单。但很快，它就暴露出一个灾难级的问题：关键词不是意图。

开发说“刚才那个闪退已经修好了”，它会误判成新问题。晨报里总结历史“闪退”“卡住”的数量，它也会误判成新问题。更糟糕的是，机器人自己发出的报表里也可能包含这些词，于是系统开始读取自己发出的内容，再创建新记录，再触发新的回复，最后形成一种自吞噬循环。属于自己吃了自己拉的S，agent人体蜈蚣。

这件事让我印象非常深。因为它说明自动化不是看到信号就行动。自动化应该先判断，这个信号是否真的应该进入组织状态机。

所以我们后来引入了意图判定。一条消息是不是新的可执行问题？是不是只是进度同步？是不是开发说“我已经修好了”？是不是社交确认，比如“收到”“辛苦了”？是不是机器人或报表自己产生的内容？这些判断看起来很琐碎，但放在真实组织里非常重要。因为一旦判断错了，系统就会开始制造垃圾记录，而不是减少人的负担。

这个痛点也解释了为什么我们后来越来越喜欢 mention 这个入口。不是所有聊天都应该触发 Agent。更安全、更克制的方式，是让用户明确写出@opentag investigate this、@opentag review this PR、@opentag fix this这样的意图。一次明确的召唤，比一套永远在后台偷听的自动化系统，更适合真实组织。对的这里是广告，我们今天上线了一个开源项目https://github.com/amplifthq/opentag，开源版的Claude tag，你可以从slack等各种渠道去tag各种agent，the world shouldnt be claude only;( 求star求fork，好人一生平安。

回到正题，但 mention 只是开始。真实协作不是“提单以后就结束”。

很多关键变化发生在 thread 里。有人补一句“这个 P0”，有人说“这个给方圆”（方圆是我们可怜的设计师老师），有人说“先别做，等发版”，有人说“已修，待验收”。如果系统只会新建记录，而不会理解 thread 里的纠偏，那么它很快就会和人的协作脱节。

我们后来做了 thread 锁根机制。子回复不会直接被当成新问题，而是先找到它所属的 root message，再用 root message 去匹配已有记录，然后原地更新优先级、负责人、状态或备注。这样用户不需要离开飞书，也不需要打开表格，只要在原来的上下文里回复一句，就能完成状态纠偏。

这背后的抽象很重要。组织协作不是一次性提单，而是在同一个上下文里不断修正状态。一个问题被提出以后，它不是静止的。它会被补充、被纠正、被降级、被升级、被转交、被暂停、被验收。真正的系统不能只理解“创建”，还要理解“状态如何被人不断修正”。

我们还遇到过一个很典型的底层工具事故。表格里的“紧急程度”曾经被默认填充为 P2。结果是，即使 AI 或用户想把问题标成 P0 或 P1，底表默认值也可能在记录创建时把它悄悄拉回 P2。表面上看，这只是一个字段配置问题，本质上却是组织信号被工具默认值静默改写。

这类问题危险的地方在于，它不会大声报错。大家只是慢慢发现，真正高优的问题没有浮上来，普通问题和阻断问题被抹平了，组织的注意力被错误分配。

我们的解决思路是去掉底表默认值，把优先级变成显式判断和可纠偏机制。AI 可以初判，但用户、PM 或负责人必须能在群里覆盖它。工具不能在无人知情的情况下替组织做判断。

还有一个更大的问题是推进。

很多协作系统最容易高估“创建记录”的价值。真实问题不是把反馈变成一行，而是这一行后面能不能被推进。我们的内部问题表里有大量中间态：待处理、处理中、已解决待验收、已处理待发版、Archive。真正消耗组织信任的，往往不是没有创建记录，而是中间态的黑洞。

有人接手了，但几天没有推进；开发说修完了，但没人验收；问题进入待发版，却长期没人关注；一个老问题刚刚被修复，系统却因为创建时间太久把它自动归档。最后大家看到的不是一个更高效的系统，而是一堆沉默的僵尸卡片。---CTO说，验收的卡点主要是我，所以这个行业真的需要一个验收agent，coding agent的游戏结束了朋友们。谁来调好一个computeruse做个验收agent啊！没人做我可就…

我们后来把很多提醒逻辑从“创建时间”改成“状态更新时间”。一个问题是否该提醒，不应该只看它是什么时候被创建的，而应该看它在当前状态停留了多久。P0、P1、P2 也应该有不同 SLA。系统每天不需要把所有记录念一遍，而只需要把真正超期、阻断、需要人介入的例外推出来。

这也是我们后来总结的“例外管理”：好的 AI 组织系统不是制造更多日报，而是只把快要失控的例外推到人面前。

再往后，我们遇到的另一个坑是“开发说 done，不等于组织闭环”。

在传统研发流里，“开发修完”常常被误认为“问题完成”。但在真实产品里，完成应该是上下文里的责任人确认闭环。尤其是体验问题、交互问题、用户反馈问题，开发视角的 done 和用户视角的 done 中间经常隔着一层验收。

所以我们把提问用户设成默认验收人。开发解决后，状态不是直接 Archive，而是进入“已解决待验收”。系统在晨报或 thread 里把验收任务挂回提问人。只有验收通过，或者符合明确规则的长时间无反馈，才进入归档。

这件事让我形成了一个非常强的判断：完成不是 executor 说 done，而是上下文里的责任人确认闭环。

Agent 系统也是一样。一个 Agent 跑完了，不等于组织闭环了。它需要告诉人它做了什么，改了哪里，验证了什么，还有什么风险，下一步应该谁来做。如果它改了代码，应该有 changed files、verification、PR 或 artifact。如果它失败了，应该有可读原因。如果它需要授权，应该明确把人拉回来。否则它越强，人的焦虑反而越大。因为你不知道它到底是在做事、卡住、失败，还是已经完成但没有回写。

我们内部反复出现过这样的反馈：任务已经完成，但界面还显示 running 或 thinking；失败了，但详情页还在转；回复没有进入 history；retry 以后状态不一致；Agent 说自己会提取链接，但真正执行时又做不到；用户最后会说“还是忍不住回到 Codex”。

这些反馈很有价值，因为它们说明用户不是单纯在抱怨 UI。用户真正需要的是可见的状态、可解释的失败、能回到原处的结果。一个 Agent 越强，如果它的执行过程越不可见，用户反而会越不信任它。

最后一个问题，是上下文。

过去一年，大家非常迷恋长上下文。好像只要上下文窗口足够大，我们就可以把 Slack thread、GitHub issue、PR diff、CI log、文档、聊天记录全部塞进去，然后 Agent 就会更聪明。但我们的实践越来越让我觉得，上下文不是越多越好。

上下文太长，很快就等于上下文污染。噪音变多，边界变模糊，Agent 更容易被带偏，人也更难审计。

桌面 Agent 里尤其明显。用户当前看到的可能是一段长文档、一组聊天截图、一个有多张图片的卡片、一个登录态 WebView，或者一个无法通过平台 API 抽取的私有内容。让用户复制粘贴当然很低效，但让 Agent 静默扩大观察范围也很危险。

比如用户只是想让 Agent 看某个卡片里的几张图，但如果系统让 Agent 自己滚动整个聊天窗口，它可能会把整段聊天历史都误当成上下文。再比如长文档只露出一小段，Agent 如果假装看完全文，就会制造幻觉。

我们内部形成的思路是：上下文采集要有边界协议。系统应该先告诉用户缺什么，再请求一个具体动作，比如“把鼠标停在这个卡片上，左右翻图几秒”或“慢慢滚动这个文档几秒”。Agent 要知道自己采集的是这个卡片、这个图集、这个文档，而不是无限扩展到整个屏幕或整段聊天。

一个靠谱的人接手任务前，会先问清楚：所以你到底要我做什么？看哪几个材料？哪些不要动？做好以后交给谁？Agent 也应该这样。

所以我们踩完这些坑以后，越来越确定一件事：Agent 进入组织以后，最难的不是“会不会回答”，而是工作流能不能承接住它。谁触发了 Agent？上下文来自哪里？授权它做什么？由哪个 runner 执行？当前状态是什么？结果回到哪里？失败如何解释？谁来验收？这些问题如果不回答清楚，Agent 进入组织就会变成另一个黑盒。

## AI Workspace 是真需求，但成立是有条件的

现在回到一开始的问题：AI Workspace 是不是一个真需求？

我的答案是：需求是真的，但今天很多产品可能答错了题。

很多 AI Workspace 产品的默认假设是：既然 AI 会改变工作方式，那我们就需要一个全新的空间，让人和 Agent 在里面协作。于是它们会做新的 inbox、新的任务系统、新的聊天流、新的历史记录、新的协作面板。人说一句话，几个 Agent 都来回应。有种多个舔狗同时上线，或者屌丝支配牛马干活的意味。

但我越来越觉得，如果一个场景里，主要沟通主体仍然是人，Agent 只是偶尔参与或深度参与但只提供相对有限的信息，那么它一定不需要一个全新的 Workspace。

因为人和人之间的协作空间已经非常成熟了。Slack、飞书、GitHub、Lark、企微、Linear、Notion、Jira，这些产品不完美，但它们承载的是组织行为学。人的带宽、人的表达习惯、人的责任关系，并没有因为 AI 出现而突然改变。我经常开玩笑说，我作为一个智商还可以的智人，应付n多个session的一个codex已经有点捉襟见肘了，你更别提让我应付8个agent。

更何况，上个时代我们就已经可以在聊天里使用机器人了。你可以在 Slack 里叫一个 bot 查数据，在飞书里叫一个机器人发提醒，在 GitHub 里让 CI bot 回写状态。今天 Agent 更强了，能写代码、能读文档、能操作工具，但这不意味着我们必须为“人和 Agent 偶尔协作”重做一个工作空间。

如果一个组织里，99% 的沟通还是人和人之间的沟通，只有偶尔 @ 一下 Agent，让它查个东西、写个 PR、总结一下 thread、修一个 bug，那我不认为这个组织需要搬进一个全新的 AI Workspace。它真正需要的，可能是一层更可靠的 Agent 接口：能让 Agent 在已有工作现场被召唤、被授权、被执行、被回写、被审计。

这也是搬家成本的问题。

很多 AI Workspace 产品的问题，不是它们不够 AI native，而是它们低估了人类组织上下文的搬家成本。你的群聊历史不会搬家，你的 PR 讨论不会搬家，你的组织默契不会搬家，你的表格字段、默认规则、负责人关系、验收习惯都不会轻易搬家。一个新产品如果要求所有人把这些东西重新组织一遍，那它面对的不是一个软件迁移问题，而是组织迁移问题。

这件事太难了。

但这不代表 AI Workspace 一定不成立。相反，我认为它成立，只是它有比较明确的条件。

如果一个协作场景里，Agent 和 Agent 之间的协作比例已经大于人与人之间的协作比例，那么它就很可能需要一个新的产品形态。因为这已经不是传统 IM 擅长的事情了。

Agent 和 Agent 之间的信息交换速度可能是人的几百倍、几千倍。它们不需要像人一样寒暄，不需要把每一个中间过程写成一条聊天消息，也不需要为了让人看懂而把所有东西都表演出来。它们需要的是任务图、状态机、权限边界、产物交换、执行轨迹、冲突解决和最终验收。

如果我们做一个 IM 产品，把 Agent 之间的高速协作展示成一群人在聊天，本质上是一种向人类习惯的降级兼容。它可能适合 demo，但未必适合真实协作。

真正的 Agent-to-Agent workspace，可能不是一个聊天产品。它更像一个任务网络、一个执行控制面、一个 artifact exchange、一个 trace viewer、一个权限和状态系统。人类不应该旁观一堆 Agent 聊天。人类应该看到的是：这个任务被拆成了什么，谁执行了哪一部分，哪里失败了，哪里需要人判断，最后产物是什么，这件事有没有闭环。

这里面尤其值得关注的是本地 Agent 和本地 Agent 之间的协作。

如果只是云端 Agent 和用户一对一协作，ChatGPT、Claude、Codex 这种聊天形态已经非常接近最佳形态了。用户说目标，Agent 执行，结果回来。这个链路自然、直接、低摩擦，不一定需要再套一个新的 Workspace。

但本地 Agent 和本地 Agent 之间的协作不一样。它涉及不同机器、不同仓库、不同权限、不同上下文、不同人的工作空间。我的本地 Agent 怎么和你的本地 Agent 协作？它们怎么交换上下文？自然语言是不是一种落后的交换手段？怎么知道彼此能看什么、不能看什么？怎么交付 artifact？怎么让人类知道需要介入的点？这些问题确实可能需要一个全新的产品。

所以我现在对 AI Workspace 的判断更分裂，也更清楚：

如果主要是人和人协作，偶尔加 Agent，不需要一个新房子。如果主要是人和云端 Agent 一对一协作，聊天形态已经很好。如果主要是 Agent 和 Agent 协作，尤其是本地 Agent 之间协作，那才可能真的需要新空间。

这也是为什么我不想简单地说“AI Workspace 是伪需求”。我觉得它是真需求，但今天很多产品把这个需求提前套到了人类已有协作空间上。并且我悲观的认为大部分组织不需要、也没能力用好ai native workspace，人性作为最大的不确定和阻碍，甚至有些组织也不配用上。

但如果有一天，我们组织里的沟通结构真的变了，我会非常愿意搬家。

具体一点说，当 Agent 之间的交流，尤其是我们本地 Agent 之间的交流，开始大于人与人之间的交流时，我一定会义无反顾地搬到一个 AI native 的产品上。因为那时候，原来的 Slack、飞书、GitHub 这些人类协作空间，可能就真的不再是最合适的系统了。

目前看起来，这个趋势其实相当明显。我们内部已经在越来越多地让 Agent 承担组织责任，让本地 Agent 参与真实工作流。也许就在下个月，正好我们 Lark 到期的时候，我们就会正式开始考虑：到底搬到哪一家 AI native workspace 上，还是干脆自己做一个。

所以问题从来不是“要不要 AI Workspace”。

问题是：什么时候搬家值得？什么时候新房子真的比旧房子更适合我们的新生活？

而 OpenTag 要解决的不是“重做一个 AI Workspace”。它要解决的是中间这一层：在人类已有的工作现场里，让 Agent 能被可靠地召唤和执行。

你可以继续在 GitHub issue、PR comment、Slack thread、飞书群、本地仓库里工作。你只是在需要的时候 @ 一个 Agent，让它把这次请求变成一个结构化事件，带着 actor、target、command、context pointer、permission grant、callback route、run state 和 audit log，交给本地或托管 runner 执行，再把进度和结果回写到原处。

这听起来没有“八个 Agent 一起聊天”那么有未来感，但它更接近真实组织。

它不是 AI Workspace 的替代品。它更像是 Agent 进入现有工作流的接口层。

## 好的 Agent 协作系统，首先应该保护组织

如果说前面讲的是我们对 AI Workspace 的判断，那落到我们自己的产品和价值观里，问题就变成了：一个真的好的 Agent 协作系统，或者一个真的好的多 Agent 和人的协作系统，应该是什么样子的？

我现在越来越觉得，它首先不应该制造热闹。

很多所谓的 AI native workspace，把 Agent 设计成了气氛组。只要人类说话，Agent 就要回应。人说一句话，八个 Agent 全部出来表达意见。短期看确实很有未来感，也很有情绪价值。但长期来看，这会变成一种新的信息污染。

因为人的带宽没有变。

一个人处理一对一的信息已经很累了，更何况他说了一句话以后，八个 Agent 全部出来回应。你得看它们说了什么，判断谁是对的，回看历史，打开审计，理解每个 Agent 做了什么，最后还要自己负责决策。

这不是帮人减负，这是把机器输出变成了人的新工作。

所以好的 Agent 协作系统，第一条原则是少打扰。

我们要把人的注意力当成系统里最贵的资源。一次 Agent run 不应该把所有过程都倾倒到主线程里。它应该分层：刚开始，只需要说一句“我收到了”；中间过程，只有长任务或关键节点才更新；结束时，只给结论、变更、验证结果和下一步；完整细节当然要有，但默认放在审计记录里，不要逼人全看。

这件事的关键不是“少说话”，而是知道什么信息应该出现在人的面前，什么信息应该安静地留在系统里。

一个好的 Agent 系统，不应该和人抢注意力。它应该知道什么时候出现，什么时候沉默，什么时候只留档，什么时候必须把人叫回来。

第二条原则，是先把上下文收拾干净。

长上下文不是解药。没有边界的上下文，本身就是一种污染。

Agent 执行前，系统应该先把上下文收拾成一个干净的包：这次任务的意图是什么？哪些事实是相关的？原始来源在哪里？允许它看什么？允许它做什么？风险点是什么？哪些内容只是背景噪音？哪些敏感信息不应该进入模型？哪些地方需要保留原文引用，方便人回看？

这不是为了显得系统更复杂，恰恰是为了让 Agent 不要在一团乱麻里工作。

OpenTag 里的 context pointer，本质上就是这个思想。上下文不是把一切都塞进模型，而是带来源、带边界、带可见性、带权限地交给 Agent。GitHub issue、PR comment、Slack thread、Lark thread、file、URL、text，都应该是结构化上下文指针，而不是一团复制粘贴的文本。

我们在 AtS（本周也会开源）里想解决的也是类似问题。Agent 和人协作时，真正困难的不是“信息够不够多”，而是“信息有没有被整理成可行动、可追踪、可验收的形态”。当上下文爆炸以后，系统最重要的能力不是继续吞更多上下文，而是判断什么值得进入工作流、什么只是噪音、什么需要人确认、什么应该被隔离。

第三条原则，是让 Agent 学会闭嘴。

这听起来很反直觉，因为过去一年大家都在让 Agent 更会说话、更主动、更像人。但组织里的 Agent 首先要学会闭嘴。

没有被明确召唤，不主动插话。低置信度时，不要把猜测塞进主线程。多个 Agent 都能做时，不要让它们一起刷屏，而是让一个路由层决定谁来做。Agent 和 Agent 之间的过程，可以进入审计记录，但不要默认进入人的主线程。人类需要看到的是结果，不是每一个中间 token。

这不是削弱 Agent，而是尊重人的带宽人类的极限。

未来的组织里，Agent 的数量一定会越来越多。如果每个 Agent 都觉得自己应该表达，人的工作现场会很快被机器淹没。所以我甚至觉得，未来每个组织都需要一套 Agent 的行为规范。它不只是技术协议，也是一种组织行为学：什么时候可以说话，什么时候必须说话，什么时候应该沉默，什么时候需要请求授权，什么时候只记录不打扰，什么时候必须把人拉回来。

很多年前我看过一本书，叫《罗伯特议事规则》。它讲的是人类在一个正式会议里应该怎么讨论问题：谁可以发言，什么时候可以发言，一个议题怎么被提出，怎么被修正，什么时候进入表决，少数意见如何被保留，多数意见如何形成决议。它表面上是一本很枯燥的会议规则书，但我当时看完以后有一个很强的感受：人类社会之所以需要“议事规则”，不是因为人类天然热爱流程，而是因为只要人一多，讨论就很容易被嗓门、情绪、权力关系、随机插话和跑题带走。规则的作用不是让讨论变得僵硬，而是让一群人还能在复杂和分歧里形成一个可追踪、可执行、可负责的结果。

这件事放到 Agent 时代，我觉得会变得更重要。

所以我写了一个Agent议事规则或者说agent宪法放在了AtSpace里哈哈，大家感兴趣我也可以私发，太长了我就不放在这里了。

第四条原则，是模型和执行器必须可以替换。

我们不希望这个世界是 Claude-only，也不希望它是 Codex-only、Gemini-only 或任何单一模型厂商绑定的。模型能力变化太快了，最好的 Coding Agent、最好的桌面 Agent、最好的推理模型都会变化。团队不应该为了一个模型迁移，重建自己的工作流。

所以 OpenTag 关心的不是绑定哪个 Agent，而是把 Agent 当成可以替换的执行者。今天可以是 Codex，明天可以是 Claude Code，后天可以是 Hermes、OpenClaw，或者团队自己的本地 runner。

工作流应该稳定，模型和执行器应该可以换。

这也是为什么我们把 OpenTag 做成协议，而不是一个封闭产品。它要回答的不是“Agent 在哪里聊天”，而是：谁触发了 Agent？触发的是哪个 Agent？命令是什么？上下文来自哪里？授权它做什么？由哪个 runner 执行？当前状态是什么？结果回到哪里？失败如何解释？谁来验收？

这些问题不回答清楚，Agent 进入组织就会变成另一个黑盒。

第五条原则，是结果要回到原处。

这也是我们踩了很多坑以后最相信的事情。一个 Agent 做了事，但工作现场没有同步，信任会快速崩塌。用户不应该为了看一个任务有没有完成，再打开一个新的系统、一个新的历史、一个新的审计页面。结果应该回到原来的 thread、comment、PR、issue 或任务上下文里。

OpenTag 的 callback route 和 thread key，本质上就是这个思想。Agent 不只是执行任务，还必须回到原始工作现场，把进度、结果和需要人介入的地方写回原处。否则你只是把工作从一个黑盒搬到了另一个黑盒。

所以如果要总结我们对 Agent 协作系统的价值观，我会说：

它不应该制造更多空间，而应该降低空间之间的摩擦。它不应该制造更多消息，而应该保护人的注意力。它不应该吞掉所有上下文，而应该建立上下文边界。它不应该让 Agent 用热闹证明存在，而应该用闭环证明可靠。它不应该锁定在某个模型或厂商里，而应该让组织保留切换的能力。

这也是 OpenTag 和 AtSpace 背后共同的世界观。我们不是为了做一个更热闹的 AI 工作台，也不是为了让组织看起来更 AI native。我们真正关心的是，当 Agent 开始承担组织责任时，它能不能被召唤、被授权、被审计、被验收，并且不增加人的信息负担。

过去很多 AI 产品解决的是“一个人如何更快完成任务”。但当 Agent 进入团队，问题会从个人效率变成组织治理。

谁有权让 Agent 做事？它能看到什么？它改了哪里？它失败了吗？它是否需要人批准？结果有没有回到原处？这件事有没有被验收？它有没有制造新的信息负担？

这些问题听起来不像模型能力问题，但它们会决定 Agent 能否真正被组织信任。

所以回到最开始的问题：AI Workspace 是不是一个真需求？

我的答案是：是，但它不是一个可以用“新建一个聊天空间”轻易回答的问题。

如果一个组织主要还是人在协作，Agent 只是偶尔进来帮忙，那它不需要搬家。它需要的是在原来的工作现场里，有一层可靠的 Agent 接口。我甚至觉得这是大多数公司的理想的工作模式。

如果一个组织真的进入了 Agent 和 Agent 大规模协作的阶段，尤其是本地 Agent 之间需要交换上下文、产物、权限和状态，那它可能真的需要一种新的 workspace。但那个 workspace 未必长得像今天的人类 IM，也未必是一个更热闹的群聊。它可能更像一个组织的执行控制面。或者什么别的东西，那种我也没能力描述的东西。
