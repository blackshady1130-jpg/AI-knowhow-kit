# 硅谷坐标 Benny Chen 访谈 Notes：开闭源格局、Fireworks 推理平台与定制模型

>
> 本文主要还原嘉宾的判断，不代表对公司经营数字的独立审计。Fireworks 披露的 token 规模、定制模型占比和 ARR，均标为公司口径。为校准转写中的关键案例，本文参考了 Fireworks 的[融资公告](https://fireworks.ai/blog/series-d-announcement)、[Harvey 联合实验](https://fireworks.ai/blog/open-source-agents-frontier-advisors)、[Nexus 产品说明](https://fireworks.ai/blog/fireworks-nexus)和[微软合作页面](https://fireworks.ai/partners/microsoft)。这些材料能够确认“超过 40 万亿 token/日”“95% 以上来自专用模型”“开放权重 worker 加前沿 advisor”等说法，但仍属于公司及合作方发布的一手材料。

## 一句话总览

这期访谈最值得保留的，不是“开源会不会打败闭源”这一道二选一题，而是一套更接近产业真实运行方式的框架：**开放模型可以赢得更多调用量，闭源实验室仍可能凭品牌、默认采购地位和最强效果拿走更多利润；真正可持续的企业价值，则可能从单一模型迁移到 eval、Harness、路由、后训练和推理系统组成的完整交付闭环。**

Benny 对 Fireworks 的定位也因此十分明确。它不训练通用基础模型，不买地建数据中心，也不只卖一次性的 GPU 时长或模型微调项目，而是试图成为开放模型之上的“智能生产平台”：帮助客户选择模型、建立 eval、定制模型、优化推理，并持续承接上线后的 token 流量。

整场对话可以压缩成八个判断：

1. **开放模型与闭源模型可以同时增长，但赢得 token、收入和利润的未必是同一方。**
2. **蒸馏可以缩短追赶时间，却不是开放生态的长期制度性优势。**
3. **frontier lab 有能力进入垂直行业，但未必有经济动机把大量资源投入每一个垂直工作流。**
4. **AI 推理的正确计量单位不是 token 单价，而是完成一个任务的质量、总成本和可靠性。**
5. **多模型系统不只是“便宜模型分流”，还可以让开放模型承担执行、闭源模型稀疏地提供判断，从而同时改善质量和成本。**
6. **企业 AI 的稀缺能力正在从“会调用模型”转向“会定义 eval、解释失败并维护模型生命周期”。**
7. **Fireworks 真正想建立的不是某个 kernel 的护城河，而是训练、评测、部署和持续推理之间的业务闭环。**
8. **Fireworks 最大的竞争者不是某一家推理初创公司，而是拥有算力、采购入口和客户关系的云服务商。**

## 最高价值观点清单

### 1. 开源追上闭源是方向判断，追得这么快才是意外

Fireworks 的核心团队来自 PyTorch 和开源软件生态。Benny 的先验是：只要一种软件能力足够有价值，开放生态最终通常会形成可用替代，从操作系统到数据库都出现过类似路径。

真正超出他预期的，是开放模型在较短时间里同时提高能力和价格性能比。这个判断并不等于“闭源已被抹平”，而是意味着企业不能再把开放模型视为永远落后一个代际的低价备选。

### 2. “开源赢使用量，闭源赢利润”并不矛盾

Benny 用 Android 与 iPhone 类比未来格局：开放生态可能拥有更大的 run rate 和更广的部署面，闭源产品仍能凭峰值效果、完整体验、品牌和用户心智获得高利润客户。

所以行业份额至少要拆成三张表：token 份额、收入份额和利润份额。把其中任意一张表当作最终胜负，都会误判价值流向。

### 3. 闭源模型眼下最强的护城河之一，是采购者的保守心理

企业采购不是纯 benchmark 优化。采购者还会考虑供应商是否能支持一至两年合同、是否会持续更新、合规体系是否成熟，以及选择出问题后自己是否需要承担责任。

“No one gets fired for buying IBM”在 AI 时代仍然成立。闭源实验室建立的品牌和默认选择地位，可能比某一代模型的领先多维持两三年。开放模型要跨过的因此不只是一条能力曲线，还有信任与组织惯性。

### 4. 闭源实验室的 ARR 会继续涨，但 ARR 不是全部经济真相

嘉宾认为 frontier lab 的 ARR 仍会快速增长，但提醒要看收入确认和云渠道分成。如果一笔 API 收入需要与云服务商或分发伙伴大比例共享，名义 ARR 上升不必然带来同幅度的净收入和利润。

评价模型公司的商业质量，至少应继续追问：谁持有客户关系、谁承担算力成本、谁获得预付款、谁能提价，以及收入增长是否被更高的推理成本和渠道分成抵消。

### 5. 蒸馏是短期追赶工具，不是长期可依赖的制度红利

访谈谈到一种典型路径：通过闭源 API 输出和推理痕迹训练较小模型。Benny 认为，闭源供应商可以修补推理 token 泄露、加强接口检测和限制异常采样，所以把开放模型长期进步建立在对方的安全缺口上并不可靠。

但这不意味着开放模型离开蒸馏就无法成功。有足够的人才、GPU、明确 eval 和逐步下降的数据成本，开放团队仍能独立训练出有竞争力的模型。蒸馏影响追赶速度，不决定开放生态能否存在。

### 6. 开放模型不必每次都成为第一，才有商业价值

如果开放模型能以显著更低的成本完成大部分任务，它就已经足以支持大规模部署。闭源模型可以继续在最困难任务上保留小幅优势，并向不敏感于价格的客户收费。

这是一个重要的非零和框架：开放模型的机会不是“彻底替代闭源”，而是进入足够多的任务、承担足够多的基础工作，并让企业获得可控制、可定制的能力。

### 7. frontier lab 能做垂直行业，但不代表它应该做

Benny 直言，如果某家 frontier lab 把资源全部投入法律或医疗，它当然有可能超过垂直应用公司。问题是，这种做法无法支撑一家面向全球通用智能市场公司的经济目标。

解决黎曼猜想与做好医疗记录、法律审阅，是两种完全不同的优化方向。frontier lab 追求广泛能力边界，垂直公司追求局部分布上的极致可靠，两者的资源配置逻辑不同。

### 8. 垂直智能的价值来自 jagged intelligence

模型智能不是均匀球面。一个模型可能擅长数学和代码，却在法律格式、引用纪律、医疗缩写或行业流程上频繁失误。垂直应用公司的机会，就是在一个狭窄但高价值的分布上建立更细的 eval、数据清洗和工作流。

这类“锯齿状智能”也解释了为什么通用模型整体升级后，垂直模型不一定再次归零。只要垂直任务的改进方向已经与通用 benchmark 分化，产品方积累的局部能力就不会自动被一次基础模型发布冲掉。

### 9. 垂直模型被新基础模型“洗掉”的频率正在下降

Benny 的观察是，早期定制模型经常在新一代 frontier model 发布后失去优势；近期这种情况变少。这是因为医疗、法律等产品不再只是在通用模型上加一点 prompt，而是在数据、评价标准和工作流上形成自己的前进方向。

这仍是访谈观察，不是普遍定律。判断某个垂直能力是否可持续，仍要看新基模替换后，历史 eval 上的净增益是否保留、重训成本有多高，以及客户流程是否真正嵌入产品。

### 10. 该不该定制模型，首先看你是否覆盖一类客户，而非是否拥有数据

Benny 建议垂直 SaaS 公司定制模型，却不建议单家医院或律所直接训练模型。前者可以从大量客户中看到任务分布、边界案例和共同需求，能够判断一个模型是否覆盖了整个行业；单一终端客户往往只有局部样本。

对单家企业，更现实的路线通常是先把规则、工具、知识和审批方式写进 workflow 或 skills。只有当任务分布足够稳定、调用量足够大、评价体系成熟，模型定制才可能优于持续改 Harness。

### 11. token 数量是一个极易误导的市场指标

一枚低价小模型 token 与一枚高价推理模型 token，在流量统计中都算作一枚，但它们对应的成本、任务价值和付款意愿完全不同。长输出、视频或 Agent 循环也会机械地放大 token 数量。

因此，“每天处理多少 token”更适合衡量基础设施规模，不适合单独衡量商业价值。更诚实的指标是收入、毛利、完成任务数、每任务成本，以及客户愿意为结果支付多少。

### 12. Fireworks 的 40 万亿 token/日很大，但必须附带口径

节目中嘉宾给出“四五十万亿 token/日”的量级。Fireworks 2026 年 7 月融资公告披露，公司每天处理超过 40 万亿 token，超过 95% 来自基于客户专有数据、面向特定任务优化的模型。

这个数字可以说明平台的工作负载规模，却不能直接推出 Fireworks 比所有闭源 API 拥有更高收入或更强终端需求。不同厂商公开口径并不统一，B2B API、消费产品内部调用、输入输出 token 与缓存 token 也可能采用不同统计边界。

### 13. 编程和深度研究仍是当前最主要的 token 消耗场景

编程 Agent 会长时间读取仓库、生成代码、运行测试、修复错误，天然产生多轮调用。深度研究同样包含搜索、阅读、交叉验证和反复综合，因此比普通聊天消耗更多 token。

但访谈还提出一个更深的判断：大量办公室任务正在被重新表达为编程问题。表格、幻灯片、文档和专业软件一旦拥有可调用接口，模型就在用代码操纵业务对象，而不只是在回答文本问题。

### 14. 下一波增量可能来自非工程师的 co-work，而非更多聊天机器人

Benny 认为行业把太多注意力放在服务 STEM 用户，而文档、幻灯片、Word、视频和日常知识工作仍有巨大未满足需求。这些场景的单次 token 量未必最大，但覆盖人群远大于专业程序员。

它们的技术要求也不同：不是追求一道题的最高分，而是理解模糊意图、操作多个应用、保留格式和上下文，并产出可以直接交付的文件。

### 15. 文本 Agent 占主导，不代表 computer use 没有价值

API 和文本工具目前更受欢迎，主要因为便宜、稳定、容易验证。视觉模型持续处理屏幕会消耗更多算力，点击坐标也比调用结构化接口更脆弱。

随着视觉语言模型的成本下降、界面理解变强，computer use 仍可能进入无法提供 API 的长尾软件。更可能的终局不是二选一，而是 Agent 优先调用 API，在必要时切换到视觉操作。

### 16. 北美开放模型在 coding 场景中的渗透，受限于 GTM 和信任

即便开放模型的性价比已经很强，Claude Code、Codex 等闭源产品仍占据更高用户心智和商业收入。技术能力逼近，并不会自动转化成开发者更换工具。

开放模型若想进入主流 coding，需要同时解决日零上线、工具兼容、稳定性、企业采购、数据安全和默认集成。模型只是产品的一部分，分发和体验决定能力能否变成流量。

### 17. 编程 token 的 TAM 可以暴涨，收入 TAM 却未必同步

当单位 token 价格持续快速下降时，调用量增长可能被价格下降抵消。AI 编程也可能像电力一样成为无处不在的基础能力，但创造最大利润的未必是最初生产这种能力的公司。

因此，分析 coding 市场不能只外推 token。更关键的是谁控制开发入口、谁能按席位或任务收费、谁拥有企业工作流，以及模型成本下降后，节省下来的价值落到模型商、工具商还是用户手中。

### 18. 模型流量会追逐最新发布，静态排行榜很难代表长期份额

开放模型市场中，最新且最强的模型会快速吸走流量，下一次发布又会重新洗牌。公共路由平台还可能存在免费额度、补贴或渠道激励，进一步放大短期排名。

观察模型生态时，更有意义的是留存、付费流量、生产任务占比和版本切换后的净迁移，而不是某一周的 token 排名。

### 19. 企业采用开放模型的前提，是相信供应链能支持合同周期

企业通常要为生产系统签一至两年合同。它们关心的不只是今天的模型效果，还关心模型是否持续更新、平台是否稳定、旧版本是否可保留，以及供应商能否承担支持责任。

这也是开放模型平台存在的原因之一：企业采购的并不是一份权重，而是一套模型供给、部署、监控、升级和责任边界。

### 20. 云部署常常比企业自建更省钱，关键在利用率

很多企业难以让一组专用 GPU 长期满载。多租户云可以聚合不同客户的峰谷需求，提高总体利用率，再把效率转化为更低的单位成本。

一旦 VPC、数据保留策略和合规信任到位，企业未必坚持把开放模型放在本地。开放权重提供的是部署选择权，不等于每家公司都应自己管理硬件。

### 21. 企业 AI POC 最常见的失败，是没有清楚的 eval

Benny 发现，一些企业即使已经把 AI 用于呼叫中心等核心流程，仍然主要靠少数人试用和“感觉不错”判断效果。需求没有拆成测试分布，模型切换和 prompt 修改就无法稳定比较。

结果是 POC 看似能演示，上线时却暴露长尾问题；或者团队无法证明开放模型是否真的优于闭源模型，只能回到品牌采购。

### 22. eval 是 AI SaaS 时代的新单元测试

传统 SaaS 不会在缺少测试的情况下替换 SQL 引擎或核心依赖。AI SaaS 同样需要在每次模型、prompt、工具和工作流变化后，回归验证关键任务。

区别在于，AI 输出通常不是简单的确定性对错。团队必须积累真实任务、边界案例、评分规则和失败分布。会设计 eval 的人少，是因为这项工作同时需要领域知识、数据判断和工程化验证。

### 23. 数据公司的收入结构，可以成为企业 AI 成熟度的侧面指标

如果评价数据、专家标注和第三方测试的买家仍主要是 frontier lab，说明大多数企业还没有进入系统化优化阶段。若应用公司和普通企业的采购占比上升，则意味着它们开始建立自己的模型选择和改进闭环。

这不是精确先行指标，却比“企业都在探索 AI”更接近真实投入。愿意为 eval 和测试基础设施付费，通常意味着系统已从演示走向经营责任。

### 24. 新模型日零性能远未到峰值，推理优化有持续空间

新模型发布时，Serving Stack 往往只完成基本适配。随后还需要围绕模型结构、量化、并行、内存、批处理和具体 workload 反复优化，性能才会逐步接近上限。

因此推理平台的工作不是“一次写完一个引擎”。模型架构持续变化，硬件持续更新，客户请求形态也在变化，优化对象始终在移动。

### 25. cache 命中率不是推理引擎单方面决定的

能否复用 KV cache，取决于请求之间是否拥有稳定前缀、上下文如何组织、调度是否识别共享结构，以及外围系统能否把相似请求送到正确实例。

这意味着推理效率不能只看 kernel benchmark。Harness 的 prompt 结构、路由策略、会话管理和调度基础设施，都可能决定真实成本。

### 26. Fireworks 的信息优势来自同时看到模型与 workload

单一模型公司最了解自己的模型，却只看到有限的外部工作负载；单一应用公司最了解自己的任务，却缺少跨模型和跨客户的比较。Fireworks 试图位于两者之间：同时接触多个开放模型、定制模型和生产流量。

这种位置只有在经验能被复用时才形成优势。例如，一个模型上的量化、缓存或路由方法能否迁移到其他模型，一个客户的任务结构能否抽象为平台能力，决定了它是规模优势还是单纯项目经验。

### 27. 多模型路由不只是降价，也可能提高最终质量

传统路由叙事是：简单任务交给便宜模型，困难任务交给最强模型。Harvey 案例展示了另一种结构：开放模型作为 worker 承担主要推理、写作和工具调用，在自己不确定时把闭源 frontier model 当作 advisor 调用。

这种分工让强模型提供稀缺判断，而不是承包整条长轨迹。系统可以减少昂贵模型的调用，同时让 worker 在得到建议后继续完成更多步骤。

### 28. Harvey 案例把“模型选择”改写成了“角色设计”

Fireworks 与 Harvey 在 100 个法律任务切片上测试：GLM 5.1 worker 平均每任务调用 Claude Opus 4.7 advisor 0.83 次，严格 all-pass 从 worker 单独运行的 12/100 提高到 18/100；Opus 端到端为 14/100。该组合总成本为 368 美元，约为 Opus 单独运行 954 美元的 39%。

这是一项由厂商与客户联合发布的小样本实验，all-pass 标准误约 2.5 个百分点，不宜外推为所有法律任务。但它验证了一个重要机制：**前沿模型可以从系统的唯一依赖，变成在高价值节点被调用的工具。**

### 29. 长任务的优化对象不是单次调用，而是整条轨迹

长上下文容易积累无关信息，模型能力也会随轨迹变长而退化。Harness 可以把任务拆分为规划、执行、检索、验证等阶段，并让不同模型承担不同角色。

Benny 把模型类比为处理器：系统需要理解“处理器”擅长什么，再重构 workload。评价一个模型是否便宜，也应计算完成整项任务需要多少轮、多少失败重试和多少顾问调用。

### 30. 后训练与 Harness 是两种互补的系统优化

Harness 改变模型在推理时如何被调用，后训练改变模型本身在目标分布上的行为。Harvey 官方实验中，Kimi K2.6 的 SFT 将 all-pass 从 11/100 提高到 15/100；RFT 则把连续平均分从 0.863 提高到 0.886。

真正有平台价值的不是“同时有两个按钮”，而是训练、评测和线上 Serving 使用一致的模型与数值实现，减少 checkpoint 从研究环境迁移到生产后出现偏差。

### 31. 硬件能效是模型、kernel 与芯片共同决定的

芯片的算力与内存带宽比例，会反向影响什么样的模型结构最容易高效服务。已经围绕 NVIDIA 或 AMD 特征设计的模型，迁移到计算和带宽比例不同的 ASIC 时，可能需要重新设计并行方式、kernel，甚至模型形状。

因此“某芯片理论 FLOPS 更高”不足以说明真实推理更便宜。部署成熟度、模型适配、软件栈和工作负载共同决定有效吞吐。

### 32. 新硬件真正缺的可能不是参数，而是让模型团队优化它的经济激励

如果一种硬件没有足够装机量和稳定需求，模型团队就缺少动力专门调整架构和 kernel。即使芯片规格与 GPU 接近，也很难形成从模型发布到日零适配的完整生态。

Benny 对 NVIDIA 优势的解释因此不只落在 CUDA，而是“硬件能快速回本、开发者愿意优化、客户愿意部署”组成的循环。生态护城河本质上也是一套经济激励系统。

### 33. 定制模型最大的成本，不只是 GPU，而是环境与奖励设计

RL 训练需要稳定环境、可重复任务和不容易被模型投机利用的奖励。团队还要处理 reward hacking、环境崩溃、数据覆盖不足和训练波动。

GPU 仍是最大显性成本，但“准备数据”远不止标注答案。真正昂贵的是把业务流程变成模型可以反复行动、获得反馈并被可靠评分的训练环境。

### 34. 一千个环境可能产生十万级轨迹，但数量不等于覆盖

嘉宾举例，一千个环境每个生成 128 条 rollout，就会得到 12.8 万条轨迹。这说明 RL 可以从有限环境中放大训练数据，不必人工编写每一条过程。

但这个估算不能被理解为“一千题足够训练任何垂直模型”。如果环境同质、奖励可被投机或缺少真实长尾，更多 rollout 只是在重复同一分布。核心仍是环境多样性和验证质量。

### 35. 模型 rebase 的成本，取决于 eval 是否稳定

开放基础模型频繁更新，定制团队需要把自己的能力迁移到新 base model。如果评价集、训练环境和目标行为已经固定，rebase 可以相对快；若工作流和任务本身也在变化，团队就要重新定义需求和数据。

这进一步说明，企业最可复用的资产未必是某个 checkpoint，而是持续保存的 eval、轨迹、失败案例和训练 recipe。

### 36. Fireworks 做的是两门相互咬合的生意

第一门是推理优化：让开放模型和定制模型以更低成本、更高吞吐稳定运行。第二门是模型定制：用 SFT、RFT、LoRA 等方式把基础模型变成客户任务上的专用模型。

两者相互增强。训练服务帮助客户形成差异化模型，推理服务承接模型上线后的长期流量；生产流量再生成新的失败样本和评价反馈，推动下一轮定制。

### 37. Fireworks 希望收入与客户的推理成功绑定

一次性咨询公司在训练项目交付时获得收入，GPU 云在机器被租出时获得收入，它们未必关心模型最终是否为客户创造更多业务。Fireworks 更希望在训练阶段帮助客户把效果做对，再从持续增长的 inference 流量中获得回报。

这是一种更对齐的商业叙事，也对平台提出更高要求：客户的模型若没有进入生产、调用量没有增长，前期训练工作就难以转化为长期收入。

### 38. Fireworks 不想拥有硬件，而想成为算力之上的软件与需求聚合层

公司不计划自己建设和持有大规模数据中心，而是从不同云与基础设施伙伴获得容量，再通过软件优化和客户流量提高利用率。

这减少了直接资本开支，但不会消除算力风险。容量采购价格、供应稳定性和预付款条款，仍会决定毛利与增长速度。嘉宾也把未来一至两年的最大挑战概括为：能否以合理价格获得足够 compute。

### 39. neocloud、训练咨询公司与 Fireworks 的收入逻辑不同

neocloud 更接近卖容量和基础模型 Serving，优势是硬件供给；训练咨询公司更擅长交付单个定制项目；Fireworks 想覆盖从模型选择、eval、训练到 Serving 的生命周期，并让定制模型成为主要流量来源。

边界并非固定。硬件公司会收购软件能力，咨询公司会建设托管平台，Fireworks 也需要采购大量算力。最终竞争会围绕谁能把整条链路做成低摩擦产品，而不是今天的公司标签。

### 40. 真正强大的终局竞争者是 CSP

AWS、Azure、Google Cloud 同时拥有计算基础设施、企业采购入口、安全合规、销售关系和模型平台，理论上可以覆盖 Fireworks 的完整能力。

Fireworks 与 CSP 因此是竞合关系：一方面借助云的容量和客户渠道，另一方面用更快的开放模型适配、更深的推理优化和更完整的模型生命周期争取价值。公司目前与 Azure 合作最深，Fireworks 已成为 Microsoft Foundry 的第一方推理提供商，可通过现有 Azure 账户计费。

### 41. 单点 kernel 不是足够长期的护城河

如果更强 AI 能自动写 kernel、优化训练和 Serving，某一项底层技巧会更快扩散。Benny 对此并不回避：若 AGI 真能把所有工程工作做好，现有基础设施公司的技术护城河都会受影响。

他认为更难自动化的是客户需求发现。系统或许能解决复杂科学问题，却未必自动知道一家医院、律所或软件公司的真实完成标准。平台的长期价值因此要沉淀在需求、eval、数据和生产反馈，而不只是代码。

### 42. 超大云厂商的 AI 资本开支，更像购买生存期权

从常规 ROIC 看，部分数据中心投资可能显得过度。但对超大云厂商而言，错过下一代计算平台可能伤及整个云业务，过度建设的代价反而可以通过折旧和多年资产利用逐步消化。

因此，hyperscaler 的投资逻辑不能简单套用短期供需模型。它们在为“AI 成为下一代平台”购买战略期权，允许自己在局部项目上承受较低回报。

### 43. neocloud 没有同样的资产负债表容错

新云厂商更依赖外部融资、长期容量合同和高利用率。一旦项目延期、客户集中度过高或借款成本上升，现金流压力会更快传导到经营。

判断这个市场是否健康，应关注债券评级、融资能力、项目交付、容量合同和潜在重组，而不仅是 GPU 数量与订单公告。即便基础设施资产仍有价值，股东价值也可能在资本结构调整中被稀释。

### 44. 开放模型追平闭源，可能把更多价值推向基础设施层

如果模型能力差距持续缩小，客户更容易在模型之间切换，也更需要统一的部署、路由、评测和定制平台。模型层的部分租金可能被竞争压低，推理需求却继续增长。

这对 Fireworks 一类平台是利好假设，但不是自动成立。基础设施也可能商品化，云厂商可能垂直整合，客户还可能采用开源 Serving Stack 自建。平台必须证明跨模型优化和完整生命周期带来的增量，足以超过它收取的价差。

### 45. 他对未来算力仍偏紧的判断很强，对两年后的可见度却很克制

Benny 认为未来一年左右仍可能 compute constrained，Fireworks 自身收入也受到可获得算力限制。但他不愿把这个判断线性外推到更远，因为模型效率、硬件供给、需求结构和资本市场都可能快速变化。

这种克制本身值得保留：对 AI 基础设施而言，“明年仍紧张”与“十年都短缺”是完全不同的投资命题，不能用前者替后者背书。

## 开放与闭源：不要只画一条能力曲线

### 1. 四种份额必须分开

| 观察维度 | 它回答什么 | 可能的领先者 | 容易出现的误判 |
| --- | --- | --- | --- |
| 能力份额 | 谁在目标任务上效果最好 | 各任务不同，闭源常保留峰值优势 | 用通用 benchmark 替代垂直任务 |
| token 份额 | 谁承载更多调用量 | 开放模型可能更高 | 把低价 token 与高价 token 等同 |
| 收入份额 | 谁收到更多客户付款 | 闭源模型与应用入口可能更强 | 忽略云渠道分成与补贴 |
| 利润份额 | 谁最终保留经济价值 | 尚未确定 | 用 ARR 或估值替代单位经济性 |

一家公司可以在 token 上落后，却在高价值任务和利润上领先；也可以拥有巨大流量，却因价格战、算力成本和渠道分成无法形成高毛利。行业分析必须明确自己讨论的是哪一种份额。

### 2. 闭源的短中期优势

- **峰值能力。** 对高价值、低价格敏感度的任务，小幅质量差距足以影响采购。
- **默认品牌。** 企业采购者更愿意选择被广泛验证的供应商。
- **产品入口。** Claude Code、Codex 等工具把模型能力包装成稳定工作流。
- **渠道与合规。** 云市场、企业合同、安全审计和支持体系降低采购阻力。
- **快速修补蒸馏接口。** 闭源服务可以调整 API、检测异常调用并减少推理痕迹暴露。

### 3. 开放模型的结构性机会

- **成本与部署选择。** 企业可以根据数据边界、区域和硬件选择部署方式。
- **可定制性。** 权重开放使后训练、量化和模型行为控制更直接。
- **供给竞争。** 多家模型团队快速发布，使单一供应商更难长期维持高价。
- **系统组合。** 开放模型可成为 worker、router 或垂直模型核心，闭源模型只在必要处调用。
- **价值迁移。** 当基础能力趋同，eval、Harness、数据和推理平台的重要性上升。

### 4. 更可能出现的稳态

不是“开源全部替代闭源”，也不是“闭源永远垄断智能”。更可能的结构是：

1. 通用任务在多个开放与闭源模型间快速商品化；
2. 闭源实验室在峰值智能、品牌产品和高价值入口上继续收费；
3. 应用公司用领域数据、工作流和分发形成局部优势；
4. 推理平台负责把多个模型、不同硬件和客户需求拼成可经营的系统；
5. 价值按任务动态分配，而非永久停留在某一层。

## Fireworks 的两门生意

### 第一门：推理优化

Fireworks 的推理业务不是简单转售 API。它需要处理：

- 新开放模型的快速适配；
- 量化、并行和显存管理；
- KV cache 与前缀复用；
- 不同延迟和吞吐目标下的调度；
- 多模型路由与故障切换；
- 专用部署、多租户部署和跨云容量；
- 从 benchmark 性能到真实 workload 性能的差距。

其核心商业问题是：平台带来的单位成本下降和交付速度，能否超过客户自建或直接购买云服务的成本。技术 benchmark 只是手段，客户最终购买的是更低的每任务成本、更稳定的延迟和更快的模型更新。

### 第二门：模型定制

定制业务覆盖 SFT、RFT、LoRA、全参数训练、评价和上线。它的目标不是为每家企业制造一个“自有大模型”，而是让有稳定分布和足够流量的客户，把通用模型改造成任务模型。

适合定制的典型条件：

1. 产品覆盖大量同类客户，能够看见真实任务分布；
2. 已有稳定 eval，可以量化提升和退化；
3. 调用量足够大，效果或成本改进能被长期摊销；
4. 错误模式具有重复性，能通过训练改变；
5. 基础模型升级后，有能力持续 rebase。

不适合直接定制的典型条件：

1. 单家终端企业只有少量局部样本；
2. 需求仍在快速变化；
3. 没有明确完成标准；
4. 问题主要来自工具、权限或流程，而非模型行为；
5. 调用量不足以覆盖训练和维护成本。

### 两门生意为什么必须连在一起

模型定制若停在 checkpoint 交付，平台很难知道它是否真正创造业务价值；推理服务若只托管基础模型，又容易被云容量和价格竞争商品化。把两者连起来后，Fireworks 才能形成如下闭环：

`真实任务 -> eval 与失败样本 -> 后训练 -> 部署 -> 推理流量 -> 新失败样本`

公司最希望看到的不是客户买了一次训练，而是定制后的模型效果更好，产品使用增长，推理收入随之增长。

## 多模型系统：从路由到角色分工

### 1. 三种常见组合方式

| 方式 | 基本逻辑 | 主要收益 | 主要风险 |
| --- | --- | --- | --- |
| 难度路由 | 简单任务给便宜模型，困难任务给强模型 | 降低平均成本 | 难度判断错误会伤害质量 |
| 角色分工 | worker 执行，advisor 在关键节点提供建议 | 同时改善成本和质量 | 调用协议与责任边界更复杂 |
| 垂直集成 | 通用模型加领域模型、检索器和 verifier | 提高专业可靠性 | 系统维护与回归测试成本上升 |

### 2. Harvey 案例的真正含义

这个案例不应被简化成“开放模型已经超过闭源模型”。它证明的是系统设计可以改变比较单位：不是比较 GLM 与 Opus 谁单独更强，而是比较哪套工作流能以更低总成本完成更多法律任务。

开放 worker 负责绝大多数工作，闭源 advisor 只在不确定节点提供意见。平均 0.83 次 advisor 调用说明“稀疏使用最强智能”可以成为连续旋钮，而非必须在全开放与全闭源之间二选一。

### 3. 需要保留的实验边界

- 测试只使用 LAB 中按分布抽取的 100 个任务，而非完整 1,250 个任务。
- all-pass 的标准误约为 2.5 个百分点，18/100 与 14/100 的差异需要更多重复验证。
- 成本按当时公开 API 与 Fireworks serverless 价格估算，价格变化会改变结论。
- 这是法律任务的系统实验，不能直接推广到 coding、医疗或普通办公。
- 联合实验由 Fireworks 和客户发布，适合验证机制，不等于第三方独立背书。

### 4. 对应用公司的启发

与其追问“应该押哪一个模型”，更好的问题是：

1. 哪些步骤必须调用最强模型？
2. 哪些步骤可由便宜、可控的模型承担？
3. 哪个模型应拥有调用其他模型的权力？
4. 系统如何发现自己不确定？
5. 质量提升是否覆盖额外路由、上下文和重试成本？

模型越多，系统不一定越好。只有当角色边界能被 eval 验证时，多模型才是优化；否则只是增加不透明度。

## 企业 AI：真正的稀缺品是 Eval

### 1. 为什么“vibe check”无法支撑生产

演示阶段可以挑选几个样例观察输出，上线后却会遇到用户分布、工具状态、上下文长度和边界案例。没有固定 eval，团队无法回答一次改动究竟改善了多少任务、破坏了多少任务。

更危险的是，生成式系统常表现为“多数时候很好，少数时候严重错误”。平均观感容易掩盖决定业务风险的尾部失败。

### 2. 一套可用的企业 eval 至少包含什么

| 组成 | 需要回答的问题 |
| --- | --- |
| 任务分布 | 线上真正高频和高价值的任务是什么 |
| 完成标准 | 怎样才算完整完成，而非局部看起来不错 |
| 严重度 | 哪些错误可接受，哪些错误必须阻断上线 |
| 可执行检查 | 哪些结果能用代码、状态或规则验证 |
| 专家判断 | 哪些质量维度必须由领域专家评价 |
| 成本与延迟 | 质量提升是否以不可接受的成本换来 |
| 回归历史 | 模型、prompt 和工具变更后是否破坏旧能力 |

### 3. eval 为什么会成为组织能力

eval 不是外包一批题目就结束。它需要持续吸收线上失败、产品变化和新模型行为。领域专家知道什么算错，工程团队知道如何复现，模型团队知道怎样把失败转成数据与训练目标。

因此，一套优秀 eval 既是产品规格，也是测试资产和训练接口。它把“老板觉得模型好不好”变成可复查的采购与迭代依据。

### 4. 开放模型采购的真正入口

企业并不是先决定“我要开放模型”，再寻找任务。更常见的路径是：

1. 建立任务与成本基线；
2. 用闭源模型形成可用上限；
3. 引入开放模型跑相同 eval；
4. 对质量差距、成本、延迟和控制权做组合比较；
5. 决定全量替换、局部路由还是维持闭源。

谁能让这条评估路径低摩擦，谁就更接近企业的模型控制平面。

## Fireworks 的竞争格局与护城河

### 1. 竞争者不是同一类公司

| 类型 | 主要资产 | 强项 | Fireworks 面临的压力 |
| --- | --- | --- | --- |
| frontier lab | 最强模型、品牌、产品入口 | 峰值能力与默认采购 | 开放模型差距扩大时，平台吸引力下降 |
| neocloud | GPU 容量、融资和数据中心 | 大规模专用算力 | 可能向上并购 Serving 软件 |
| CSP | 算力、渠道、合规、客户关系 | 全栈与企业采购入口 | 可以内生复制大部分平台能力 |
| 开源 Serving 项目 | 软件透明、社区迭代 | 客户可自建、无平台锁定 | 压低纯推理软件的溢价 |
| 训练与咨询公司 | 领域服务和项目交付 | 深度定制 | 可能掌握客户需求与数据入口 |
| 垂直应用公司 | 分发、工作流、真实反馈 | 最了解任务 | 能把部分平台能力内部化 |

### 2. Fireworks 想构建的四层优势

1. **模型广度。** 快速支持最新开放模型，降低客户切换成本。
2. **Serving 深度。** 把 kernel、缓存、调度和硬件适配转化为真实 workload 性能。
3. **生命周期完整度。** 将 eval、训练、部署、路由和监控放在同一平台。
4. **生产反馈。** 从长期推理流量中观察失败并推动下一轮定制。

其中最难复制的不是第一个，也未必是第二个，而是第三和第四能否形成真实闭环。若平台只是在每次新模型发布后追求最快 token/s，它会一直面对开源软件与 CSP 的双重挤压。

### 3. 为什么 CSP 是“最终 Boss”

CSP 可以用现有云合同、信用额度、身份权限和安全体系，让客户不必引入新供应商。它还拥有底层硬件采购规模，可以在价格和容量上施压独立平台。

Fireworks 的应对不是脱离 CSP，而是嵌入其中。与 Microsoft Foundry 的第一方合作就是典型做法：客户继续使用 Azure 的计费和治理，同时获得 Fireworks 的开放模型推理能力。这样扩大分发，但也意味着 Fireworks 必须与渠道分享价值。

### 4. 护城河成立所需的可验证条件

- 定制模型流量确实比基础模型流量留存更高；
- 跨模型优化能持续降低每任务成本，而不只是 token 单价；
- 客户从实验到生产的时间显著缩短；
- eval 与训练资产能降低每次 rebase 的成本；
- 云渠道带来的客户增量高于收入分成；
- 平台能在不持有硬件的情况下稳定获得容量并维持毛利；
- 客户不会因为规模扩大而把 Serving 和训练迁回自建系统。

这些条件比“支持多少模型”更能判断 Fireworks 是否拥有可持续平台价值。

## AI Infra 的经济账

### 1. 正确的成本函数

单次 API 价格并不足够。更完整的任务成本可以写成：

`任务总成本 = 模型调用 + 重试 + 路由与顾问调用 + 工具执行 + 上下文存储 + 人工复核 + 失败损失`

一个单 token 更贵的模型，如果能显著减少轮数和人工修复，可能拥有更低任务总成本；一个便宜模型如果频繁失败，反而会把成本转移给应用层。

### 2. 推理平台的利润来源

推理平台可能从四类效率差中获利：

- 跨客户聚合需求，提高硬件利用率；
- 用软件优化降低同等任务的 GPU 消耗；
- 用模型路由降低平均调用成本；
- 用定制模型提高客户产品的效果与使用量。

前两类更像基础设施效率，容易受到硬件价格与 CSP 竞争；后两类更接近智能与产品价值，但依赖 eval、客户数据和持续服务能力。

### 3. 资本约束不能被技术叙事遮住

Fireworks 不持有数据中心，仍需要签容量合同并承担供给风险。neocloud 拥有硬件，仍需要维持高利用率和偿债能力。hyperscaler 资金最充足，却可能因战略防御而接受较低短期回报。

同一批 GPU 对不同玩家的经济含义完全不同。判断行业时必须把技术效率、合同结构、资本成本和客户集中度放在同一张表里。

### 4. 开放模型对价值分配的影响

开放模型提高供给竞争，可能压低基础模型调用价格；更低价格又会刺激更多 Agent 和长程任务，增加总推理需求。最终受益者取决于谁控制新增工作流：

- 如果模型品牌控制入口，价值留在模型公司；
- 如果应用拥有用户和数据，价值留在应用层；
- 如果多模型切换成为常态，控制平面和推理平台价值上升；
- 如果 CSP 把这些能力打包进云合同，价值重新回到云层。

## 给管理层的决策框架

### 问题一：我们需要开放模型吗？

不要从意识形态回答。先选出五十到两百个真实任务，用当前闭源方案建立质量、延迟、成本和人工复核基线，再让候选开放模型跑相同流程。

若开放模型在大部分任务上足够好，可采用 worker + advisor 或难度路由；若质量差距集中在少数高风险任务，则保留闭源模型作为稀疏工具。目标是降低任务总成本，而非追求“全部开放”。

### 问题二：我们应该微调还是改 Harness？

先判断错误来自哪里：

- 工具没有接好，改 Harness；
- 流程与权限不清，改 workflow；
- 知识过时，改检索与数据源；
- 输出格式不稳定，可先做约束与 verifier；
- 同类行为错误反复出现，且已有稳定 eval，再考虑 SFT 或 RFT；
- 调用量小、需求变化快，通常不值得训练。

### 问题三：怎么选推理平台？

至少比较以下指标：

1. 真实 workload 下的每任务成本，而非公开 token/s；
2. 新模型从发布到可生产使用的时间；
3. 专用部署、多租户和跨区域能力；
4. eval、训练与 Serving 是否打通；
5. 版本固定、回滚和 rebase 能力；
6. 云采购、身份、安全与合规边界；
7. 容量保障、价格条款和供应商退出方案。

### 问题四：什么值得成为内部资产？

最应该长期保留的不是某个模型版本，而是：

- 真实任务与完成标准；
- 严格的 eval 与回归历史；
- 线上失败样本与人工修订；
- 工具、权限和审批工作流；
- 路由决策与成本数据；
- 训练 recipe 和模型版本迁移记录。

这些资产让企业能够在开放与闭源、不同平台和新模型之间迁移，而不必每次重新理解业务。

## 反共识与金句

> 以下均为对访谈原意的中文整理，少量保留原句，不视为逐字引文。

### 关于开源与闭源

- 开源可以拿走最大的 run rate，闭源仍可能拿走最大的利润。
- 开放模型不必永远比闭源更强，只要在足够多任务上足够好，就能形成巨大市场。
- 闭源模型未来两三年的优势，可能不是模型差距，而是“采购它不会犯错”的用户心智。
- 蒸馏能帮助追赶，却不能成为长期路线，因为你不能把战略建立在对方 API 永远有安全缺口上。
- 看模型战争不能只看谁第一，还要看谁控制入口、谁承接任务、谁保留利润。

### 关于垂直智能

- 把一个 vertical agent 做好，与解决黎曼猜想是两种不同的工作。
- frontier lab 如果全力投入当然能打赢一家法律 AI 公司，但那不是支撑其通用智能估值的聪明用法。
- 通用智能继续前进，不等于每一个垂直任务都会被自动覆盖。
- 单家医院不一定需要自己的模型；覆盖十万家医院的产品公司，才真正看得到模型应当学什么。
- 垂直公司的护城河不是一批私有数据，而是数据、eval、流程和客户分布形成的局部闭环。

### 关于 token 与商业

- token 是一个很“骗人”的统计单位：便宜 token 和昂贵 token 都只计一次。
- token TAM 可以持续增长，收入 TAM 却可能被单位价格下降吃掉。
- 电力极其重要，不代表所有利润都留在发电厂；模型也可能走向同样的价值迁移。
- ARR 上涨不等于净收入和利润同步上涨，尤其当云渠道掌握分发和分成。
- 衡量 AI 基础设施，应该从每 token 成本升级为每任务成本。

### 关于 Eval 与 Agent

- 2026 年仍有公司用 vibe 来评价已经进入核心运营流程的 AI。
- eval 是 AI SaaS 的新 unit test。
- 真正会做 eval 的人很少，因为它既要求理解业务，也要求理解模型会怎样失败。
- 最强模型不一定应该完成整项任务，它也可以只在关键节点当一次 advisor。
- 多模型系统最有价值的地方，不是让便宜模型多做一点，而是重新设计智能在任务中的角色。

### 关于 Fireworks 与 Infra

- 推理优化不是把一个模型跑快，而是重构 workload 以适应这个“处理器”。
- 训练与 Serving 不连在一起，定制模型很容易停在演示环境。
- Fireworks 想从客户长期 inference 成功中挣钱，而不是在训练项目交付时一次结清。
- CSP 才是完整链条上的强大竞争者，因为它同时拥有 compute、采购入口和客户关系。
- AGI 也许能写 kernel、做训练，却未必能凭空知道客户到底要什么。
- 未来最大的约束可能不是需求，而是能否以合理价格拿到足够算力。

### 关于资本市场

- hyperscaler 多买 GPU 可能伤利润表，错过平台迁移却可能伤到公司生存。
- 对大云厂商是战略期权的资产，对 neocloud 可能是必须按期偿付的负债。
- 判断 neocloud 不能只看订单和卡数，还要看债务、交付和下一轮融资。
- “明年仍算力紧张”不能自动推出“未来十年永远短缺”。

## 最终结论

这期访谈提供的最重要修正，是把大模型产业从“谁的模型更聪明”改写为“谁能把智能稳定地放进任务，并在价格下降中保留价值”。

对开放与闭源，不应寻找唯一赢家。开放模型会扩大选择和压低价格，闭源模型仍可能保留峰值能力、品牌与产品入口。对应用公司，不应把换模型当作产品策略，真正的资产是任务定义、eval、工作流和用户分发。对 Fireworks，则不应只把它看成更快的推理 API；它押注的是模型供给趋于丰富后，企业需要一个跨模型的训练、评测、部署与路由控制层。

这套逻辑能否成立，最后取决于三个问题：

1. Fireworks 能否把推理优化从公开 benchmark 转化为稳定的每任务成本优势；
2. 定制、eval 与 Serving 能否形成持续反馈，而非项目制服务；
3. 在 CSP 向上整合、开源 Serving 向下压价时，平台是否仍控制足够强的客户关系和生产数据。

如果答案是肯定的，模型越多、切换越频繁，Fireworks 的控制层价值越大。如果答案是否定的，它就会被夹在拥有资本和渠道的云厂商、以及免费开放的软件栈之间。**所以这期真正讨论的不是 Fireworks 能不能把模型跑快，而是谁有资格成为企业智能的长期操作层。**
