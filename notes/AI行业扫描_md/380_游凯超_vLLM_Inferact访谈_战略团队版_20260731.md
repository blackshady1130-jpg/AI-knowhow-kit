# 游凯超 × vLLM / Inferact 访谈要点

> 战略团队版｜2026-07-31  
> 来源范围：用户提供的播客总结稿，访谈时长约 2 小时 59 分钟。嘉宾身份、融资、Offer、市场比例及行业排名均按播客口径记录，本稿未做外部事实核验。

## 一、KTA

1. **大模型推理已经从单点软件优化进入系统协同阶段。** 游凯超的核心判断是，模型结构决定推理效率上限，kernel、推理引擎、硬件和 Harness 决定这个上限能否兑现。未来不能只比较模型效果或 `tokens/s`，需要比较特定 Workload 下效果、吞吐、时延、成本和功耗的组合。

2. **后摩尔定律时代，系统可实现性正在反向筛选模型算法。** Transformer、RoPE、Flash Attention 和投机解码能够进入主流，不只因为算法有效，也因为它们适配 GPU 的矩阵计算、内存访问和并行方式。理论上成立、但难以被现有硬件高效实现的结构，可能无法获得足够实验和部署机会。

3. **Agent 将 Test-Time Scaling 从“单次回答更长”推向“与环境交互更多”。** Coding Agent 的主要负载不再是一次生成很长的思维链，而是反复读取 Context、调用工具、执行、验证和修正。推理优化因此需要同时处理前缀缓存、任务状态、流量调度和 Harness 结构。

4. **Harness 的设计细节会直接改变推理成本。** 动态修改工具定义、在 System Prompt 中放入精确时间、删除上一轮思考过程、把定时任务集中在整点，都会造成缓存失效或流量峰值。Agent 团队不能把成本问题完全交给 Infra 团队。

5. **Token 不是可以无差别替换的标准商品。** 不同模型产生的 Token 带有训练经历、模型结构和 Harness 的烙印，在规划、执行、工具调用和表达方式上存在差异。原始 Token 数量不足以衡量价值，MaaS 更应关注成功任务、返工、时延和单位成功任务成本。

6. **面向人的通用模型，上下文窗口可能停在百万级；更长的任务状态由外部系统承接。** 游凯超判断，终身学习和长程任务更可能依赖 Memory、Skill、工具和 Subagent，而不是无限扩大 Context Window。这个判断把竞争重点从“能装多少 Token”转向“如何选择、保存、复用和恢复状态”。

7. **AI 生成代码正在改变开源社区的治理结构。** 当提交代码变得廉价，维护者的历史 Context、架构判断、Review 时间和 Merge 权成为稀缺资源。未来用户可能更多提交 Bug、Feature Request 和运行反馈，由核心维护者借助 AI 完成实现。

8. **Inferact 的公司化是 vLLM 长期治理方案的一部分。** 基金会保证项目持续开源，公司提供全职人力、集群算力、法务实体和发布前适配能力。商业化方向包括托管 Endpoint、BYOC 和按 Token 产出或节省成本收费，但可规模化的专有产品层仍有待验证。

9. **“开源模型最终会赢”是游凯超最明确的长期预测，也是本次访谈中证据最弱、需要持续验证的判断。** 更可直接采用的战略结论是：开放权重模型会持续压缩裸模型 API 的差异和毛利，价值将向快速迭代、推理系统、Harness、产品入口、部署治理和数据闭环迁移。

## 二、推理竞争：从单点优化转向 Co-design

### 2.1 模型结构决定效率上限

游凯超把模型、硬件和推理引擎类比为发电机、自然资源和电力系统。同样的硬件条件下，模型结构是否匹配硬件，决定系统能够把多少理论算力转化为可用 Token。

他用“硬件彩票”解释算法的分化：

- Transformer 以矩阵乘法为核心，适合 GPU 并行计算；
- Capsule Network 在概念上有吸引力，但缺少友好的硬件实现路径；
- RoPE 可以在 Attention kernel 外处理，与 Flash Attention 配合顺畅；
- 需要修改核心 Attention 实现的位置编码，更难获得现成高性能 kernel 的支持。

**本文提炼：** 系统已成为模型设计空间的前置约束，不能等到模型结构确定后再作为实现问题处理。评估新架构时，需要同时检查模型质量、kernel 可实现性、显存占用、通信模式、并行策略和线上吞吐。

### 2.2 “系统彩票”决定算法能否进入生产

游凯超认为，后摩尔定律时代的计算进入特化阶段。芯片通过矩阵单元、低精度算力和特定内存层次继续提升性能，模型结构必须主动适应这些能力。

他列出的代表性案例包括：

| 技术 | 算法侧作用 | 系统侧成立条件 |
|---|---|---|
| Flash Attention | 保留精确 Attention 计算 | 重新组织显存读写，减少高成本数据搬运 |
| PagedAttention | 管理自回归生成中的 KV cache | 借鉴虚拟内存分页，支持动态请求和 Continuous Batching |
| Speculative Decoding | 一次猜测多个后续 Token | 需要高效草稿、验证、接收与线上调度 |
| FP8 训练 / 推理 | 提高低精度计算效率 | 量化粒度、累加方式和芯片单元需要联合设计 |
| MoE | 扩大总参数、控制激活参数 | 需要解决细粒度计算、动态路由和跨卡通信 |

游凯超特别强调，PagedAttention 的论文创新性并不高，真正价值来自做得早、实验充分，并逐步演化成生产级推理生态。系统项目的评价标准应包括用户采用、真实收益和可持续维护，而不只是论文 Novelty。

### 2.3 DeepSeek 的优势来自模型与 Infra 共同探索

游凯超把 DeepSeek 视为全球 Co-design 的领先案例。他将优势归因于算法人员理解 Infra、Infra 团队也参与模型结构探索，双方能够在同一硬件条件下快速验证更多方案。

DSpark 投机解码是一个具体案例：

1. 先并行猜测较长的 Token 序列；
2. 预测这些 Token 的置信度；
3. 丢弃大概率错误的尾部 Token；
4. 只验证更可能被接受的部分，减少无效计算。

游凯超认为，降低低置信 Token 验证浪费并非独有算法发现，真正门槛是把算法实现成能够大规模运行的推理系统。

**边界：** “DeepSeek 的 Co-design 全球最好”属于嘉宾基于合作经验的个人判断。其自建机房、硬件控制能力和历史量化经验，也使这条路线难以被云上团队完整复制。

## 三、Agent Workload：推理、Context 与 Harness 开始合流

### 3.1 Test-Time Scaling 的对象发生变化

游凯超把 Test-Time Scaling 分为三个阶段：

1. 传统集成学习：增加多个模型或多次预测；
2. o1 类推理：让单次回答生成更长的思考过程；
3. Coding Agent：增加模型与环境交互的次数。

第三种负载会反复读取代码库和历史状态，调用工具，执行中间结果，再根据反馈修正。单轮输出可能不长，但完整任务包含大量重复输入和多次解码。

因此，Agent 推理优化不能只看单次请求吞吐，还要看：

- 一个任务包含多少轮模型调用；
- 每轮重复了多少历史 Context；
- Prefix Cache 是否稳定命中；
- 工具调用和权限定义是否频繁改变；
- 任务失败后是否需要从头执行；
- 高峰并发是否来自可调整的产品调度。

### 3.2 Harness 设计会制造或消除系统成本

访谈给出了三类直接影响 Infra 的 Harness 设计：

| Harness 设计 | 系统后果 | 更合适的做法 |
|---|---|---|
| 每轮动态裁剪或重排工具定义 | 前缀变化，缓存难以复用 | 固定稳定工具前缀，按需激活时保持顺序与结构稳定 |
| 在 System Prompt 写入精确时间 | 每次请求都形成新前缀 | 把日期和时间作为工具，模型需要时再查询 |
| 定时任务统一设在整点 | 人为制造并发洪峰 | 在允许的时间窗口内随机打散执行时间 |

部分模型在新一轮推理时删除上一轮思考过程，也会破坏前缀稳定性。模型格式、Harness 状态管理和推理缓存需要共同设计。

**战略含义：** Agent 产品的成本归因需要下钻到任务和 Trace。只看 API 单价或总 Token，会掩盖缓存失效、无效循环、工具错误和集中调度造成的浪费。

### 3.3 长上下文并不等于长程工作能力

游凯超预测，面向人的模型对 Context Window 的通用需求可能停在百万级。生物、化学等特殊任务可能需要千万或亿级输入，但通用 Agent 的长期状态可以借助外部模块管理。

他的隐含框架是：

`模型窗口`承载当前推理所需信息  
→ `Memory`保存跨任务状态  
→ `Skill`保存稳定工作方法  
→ `工具与文件系统`保存外部事实和任务产物  
→ `Subagent`拆分局部 Context 和执行责任

**本文提炼：** Context Infra 的价值不在于把所有历史塞回模型，而在于决定什么进入当前窗口、什么保存在外部、何时召回、如何验证，以及怎样保持缓存友好。

## 四、Token、MaaS 与推理商业模式

### 4.1 Token 类似电力，但不是同质化的电

游凯超使用电力系统解释推理，但同时指出这个类比存在边界：电可以通过统一电压和频率实现互换，Token 无法脱离生成它的模型。

不同模型的 Token 可能在以下方面表现不同：

- 有些模型更适合规划和指挥，有些更适合执行；
- 工具调用格式和稳定性不同；
- 对相同 Harness 和 Prompt 的响应方式不同；
- 同样 Token 数量对应的有效任务进展不同；
- 推理引擎、采样和缓存策略也会影响最终体验。

**战略含义：** MaaS 如果只以输入、输出 Token 数定价和分析，会把质量不同的供给当成同一种商品。更可靠的经营指标是任务完成率、人工接管率、返工次数、端到端时延和单位成功任务毛利。

### 4.2 模型商品化与 Token 异质性可以同时存在

游凯超判断开源模型最终会赢，理由是模型被大量使用后，用户可以积累自己的任务数据，领先模型的能力差难以永久保持。

更稳妥的拆分是：

- 模型权重、API 协议和基础能力会越来越容易替换；
- 具体 Token 的任务价值仍然受模型、Harness、工具和运行环境影响；
- 裸模型推理的毛利可能下降；
- 路由、部署、治理、Context 和结果验收会承担更多商业价值。

用户数据也不会自动形成模型能力。它还需要合法授权、任务标签、环境反馈、Verifier、训练算力和稳定的数据闭环。因此，“模型更可替换”比“开源一定赢得全部市场”更适合作为当前战略判断。

### 4.3 Inferact 的商业化路径

访谈披露了三种方向：

| 方向 | 交付内容 | 可能的收费依据 |
|---|---|---|
| Endpoint Service | Inferact 提供软硬件和模型推理服务 | Token 产出、调用量、SLA |
| BYOC | 客户提供硬件，Inferact 提供推理软件 | 节省成本、吞吐提升、软件订阅 |
| 生态合作 | 与模型、硬件和云厂商共同建设 vLLM 生态 | 联合研发、适配和商业合作 |

团队明确不希望出售工程师时间，而希望按产生的 Token 或节省的成本收费。

商业模式仍有三项未决问题：

1. vLLM 永久开源后，Inferact 的专有产品层位于哪里；
2. 客户为什么持续付费，而不是自行部署或购买云厂商服务；
3. 成本节省如何测量、归因并转化为稳定合同。

## 五、开源治理：代码廉价之后，什么仍然稀缺

### 5.1 公司化解决开源社区无法独立承担的问题

游凯超认为，大型开源项目仅靠学生和兼职贡献者难以长期存续。vLLM 公司化前面对三项现实约束：

- 关键 Feature 需要稳定、长期投入，社区人力不可预测；
- 新模型和新硬件发布前需要签署 NDA，非实体社区无法承担法务责任；
- 集群级优化需要长期可用的大规模算力，临时借用资源无法保证排期。

PyTorch 基金会掌握商标和法律所有权，保证项目不被私有公司关闭；Inferact 承担技术路线、日常运营和资源投入。两者分别解决开放性和执行力问题。

### 5.2 AI Slop 改变了开源贡献的信任基础

vLLM 团队观察到，培训机构和机器人开始用 Coding Agent 批量提交低质量 PR。代码供给增加没有降低维护成本，反而消耗核心维护者的 Review 时间。

游凯超据此判断，未来开源社区可能分化为：

- 维护者负责架构、实现、验证和合并；
- 用户负责提出 Bug、需求和使用反馈；
- AI 承担大量编码和重写工作。

开源项目的长期控制点由代码仓库转向维护者的历史 Context、路线判断、测试体系、发布协调和社区信任。

### 5.3 人类仍承担前瞻设计与最终责任

游凯超不认同把 vLLM 交给完全自治的 AI 维护。推理引擎需要提前 3—12 个月预判模型、硬件和 Workload 的变化，很多决策无法从当前 Issue 直接推出。

“AI 完成 90%、人类负责最后 10%”是他的经验表达，不宜固化为比例。更稳定的判断是：AI 可以降低实现成本，但项目目标、技术取舍、兼容性承诺和最终合并仍需要明确责任人。

## 六、中国开源模型与推理生态

### 6.1 中国模型更重视效率，是资源约束下的路线选择

游凯超根据 vLLM 的合作经验判断：

- 欧美模型更偏向优先追求能力效果；
- 中国模型受高端算力约束，更重视推理效率；
- 中国土地和电力相对充足，但高端芯片受限；
- 美国高端算力更充足，下一阶段受土地和电力约束。

这个判断解释了 DeepSeek、MiniMax 等模型为什么更积极地将 MoE、Attention、低精度和推理系统共同设计。它是嘉宾对所接触样本的概括，不能代表所有中美团队。

### 6.2 专用推理引擎与通用推理引擎并存

DeepSeek 可以围绕自有模型、硬件和集群建设高度专用的推理系统，获得更高效率；这类系统离开内部环境后，适配和扩容难度较高。

vLLM 的定位是承接更广泛的模型、芯片、云环境和 Workload。它未必在单一专用环境中达到理论最优，但通过兼容性、社区和部署覆盖形成通用基础设施价值。

**本文提炼：** 专用系统争夺单一模型的效率上限，通用系统争夺多模型、多硬件和多环境的适配效率。两者不会简单互相替代。

## 七、对战略团队的直接启示

### 7.1 MaaS：经营口径从 Token 转向任务经济性

建议把推理经营指标分为四层：

1. **请求层：** 请求数、输入/输出 Token、缓存命中；
2. **Trace 层：** 工具调用轮数、重复 Context、失败重试、运行时长；
3. **任务层：** 完成率、人工接管、返工、端到端时延；
4. **经济层：** 单位成功任务收入、GPU 成本、毛利和客户 ROI。

### 7.2 Agent / Context：把缓存友好纳入产品设计

需要检查：

- System Prompt 中有哪些动态字段；
- 工具定义是否频繁变化或重排；
- 权限、工作目录和模型切换是否破坏稳定前缀；
- Memory 和历史状态是否每轮全部重放；
- 定时 Agent 是否人为形成流量峰值；
- 上述问题分别造成多少额外 Prefill 和失败重试。

### 7.3 模型评估：增加可部署性维度

模型评估除效果外，应增加：

- 主流硬件上的实际吞吐与延迟；
- KV cache 和显存占用；
- 长上下文与 Agent 多轮交互成本；
- 量化后的质量回归；
- MoE 通信与扩容难度；
- vLLM / SGLang 等主流引擎的支持成熟度。

### 7.4 开源合作：判断公司控制的是代码、治理还是商业服务

评估 vLLM / Inferact 一类项目时，需要继续追问：

- 基金会、公司和社区分别掌握什么权力；
- 关键 Roadmap 和 Merge 权由谁控制；
- 模型及芯片厂商为什么愿意提前协作；
- 商业客户购买的是软件、托管、SLA、优化结果还是治理能力；
- 公司如何把社区采用转化为收入，同时避免削弱中立性。

| Inferact 获 1.5 亿美元种子轮融资 | 按播客介绍记录，未作为技术判断依据 | 公司公告、投资机构公告、监管文件 |
