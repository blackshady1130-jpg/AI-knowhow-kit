# AI 产品怎样让用户把事情做完

**讨论需求表达、成果修改、任务管理与授权 · 复核于 2026-09-05**

AI 产品的体验，不能只看模型第一次回答得好不好。用户能否说清要做什么，看到结果后能否方便地修改，执行中断后能否继续，都会决定一项工作到底有没有完成。状态、权限和记忆应帮助完成这些动作，而不应变成用户额外管理的一套系统。

我更看好围绕具体成果组织交互的产品：讨论可以从聊天开始，修改和交付则应使用适合成果的界面。目标是让用户少解释、少寻找、少做无效确认，同时在关键选择上保留足够的控制。

## 模糊需求，要尽快变成可以讨论的对象

“帮我做个分析”“这个页面不太好看”，都是真实但不充分的需求。系统如果立即执行，可能方向错误；如果先问十几个问题，又会把准备工作全部退给用户。

我倾向于让系统先判断哪些信息会改变结果。缺少受众、用途或关键数据时应该询问；颜色、段落顺序等容易撤销的选择，则可以先给一个草稿，明确哪些是暂定的。草稿让用户对具体内容作出反馈，比要求其一开始就写出完整需求更现实。这是设计上的取舍，不是所有任务的统一流程。

同样，收到一句话不等于获得了执行授权。#390 收录的 AI Workspace 实践中，系统看到“bug”“闪退”就自动建单，连历史讨论和进度同步也会触发。这里缺的首先是对意图的判断：用户在报告新问题、讨论旧问题，还是要求系统采取行动？

对于普通使用者，产品应该在原有工作位置提供帮助，例如在已有表格中完成计算，在工单中整理进度。重度用户可以需要更自由的 Agent 工作区，但不能把搭建工作流、挑选模型和配置工具变成每个人获得价值之前的必修课。#397 对企业使用率的讨论，也提醒我们区分工具被开通和工作真正被改变。

## 第一份结果之后，修改应该更容易

Agent 做出一个页面后，用户通常想调整某个区域，而不是重新讲一遍整站需求。研究报告里，用户可能只否定一个判断，希望保留其他部分；表格里，用户可能只是发现一个计算口径不对。

这要求产品保留修改对象与上下文。选中的段落、图表或页面区域，应能成为下一次指令的明确范围；已有内容哪些被保留、哪些被改变，也应容易比较。否则，每次反馈都像重新抽签，用户会逐渐不敢修改一个勉强可用的结果。

#413 对不同产物审核界面的观察值得继续发展。代码适合看 diff 和测试，网页适合直接预览，表格需要公式和来源，研究文章需要定位论点与证据。用聊天气泡承载全部修改，容易丢失这些产物原本已有的操作方式。

我会优先检验一个很具体的能力：用户能否指出局部问题，让系统只改相关部分，并保留已接受的结果。这个过程做得好，才有条件让人放心进行多轮合作。第一次生成得漂亮，无法替代后续修改的稳定性。

## 用户需要的是进度，不是全部日志

长任务中，用户通常关心是否仍在运行、卡在哪里、有没有超出预算，以及何时需要自己处理。将所有工具调用都放在首页，既难阅读，也不一定能回答这些问题。

#390 的经验是默认减少噪声，把异常、关键状态和结果留在用户容易找到的位置。技术人员需要时可以展开完整轨迹，但普通使用者不必先理解终端、进程和工具接口，才能知道任务是否完成。

完成状态也应拆清楚。文件已经生成、自动检查通过、用户接受结果、内容已经发布，是不同的事情。尤其是对外发送和公开发布，不应因为生成阶段顺利就自动继续执行。

并发任务越多，产品越需要帮助人排序。一个任务缺数据、另一个等待权限、第三个已完成且低风险，不应都显示成同一排“需要处理”。界面应明确要求用户做哪个决定，而不是只显示一条无法行动的提醒。

## 暂停以后，能从当前结果继续吗

长程助理的工作可能跨越几天。#410 中 VibeLifeBench 的模拟任务，会让价格、消息和其他条件在后台变化，要求 Agent 重新检查早期承诺。它不能证明真实产品已经具备这种能力，却说明长任务不能仅靠维持一个“运行中”的状态。

产品应让用户看见它在等待什么，什么时候会再次检查，发生什么变化才会通知。没有变化时持续提醒，会消耗注意力；承诺过监测却没有再检查，则会制造错误的放心。

需要人工接手时，最少应交代已完成内容、未知结果和下一步选择。人补充资料、更换方案或撤销授权之后，系统应从新状态继续，而非要求重述全部历史。底层如何保存检查点和处理外部动作，由“架构与工程”展开；用户只需要能理解和操作这些能力。

## 为什么重度用户会主动关闭 Memory

在 7 月组织的一次 Context Infra 交流中，十余位重度 Coding Agent 用户提到，他们会主动删除、重置甚至关闭自动 Memory（#369）。产品把临时任务、项目阶段或偶发偏好当成长期事实，之后又在用户看不见的地方调用，是一个共同困扰。

这组交流不能代表总体用户比例，但问题很具体。用户说“这次简短一点”，不等于希望以后所有报告都简短。一个项目的临时规则，也不应该自动影响另一个项目。如果系统没有说明用了哪条记忆，用户甚至不知道应该去哪里纠错。

我更关心 Memory 是否记得准确、作用范围是否合适，而不是先问它能保存多少。明确表达的长期偏好、模型推断的偏好和一次性任务信息，应有不同的写入方式。用户需要能在错误发生的位置查看相关记忆，修改、删除，或限制只在当前项目使用。

可见不等于把内部字段全部展示出来。默认界面可以只解释“本次使用了什么历史信息”，再提供来源和管理入口。判断记忆是否有用，要观察它有没有减少重复解释、有没有引入旧信息错误，以及纠正后是否仍然复发。

## 让用户确认，并不自动产生安全

Anthropic 的一项实验让 1,053 名付费测试者在测试环境中遇到危险命令提示，人工拦截率为 13.6%，自动分类器为 89%。这支持对机械确认的担忧，但测试环境不是参与者自己的生产项目，结果有明确适用范围。[原始实验说明](https://claude.com/blog/auto-mode-default-in-claude-code)

#396 同时收录了产品中的命令批准率 97% 和计划拒绝率 39%。它们来自不同类型的判断，不能直接证明计划审批更安全。用户拒绝计划，可能因为需求或偏好不匹配；批准常规命令，也可能是命令本来就安全。

我倾向于减少低价值打断，让自动规则检查明确限制，把人留给目标取舍和高后果例外。但这种设计仍需比较实际漏检、误拦截和处理时间，不能只看确认次数下降。

授权也不宜用一条固定阶梯覆盖全部任务。难度、影响范围和可撤销程度是不同维度：读到敏感信息可能造成泄露，删除隔离目录中的临时文件却可能后果很小。相比给每个动作贴统一等级，更有用的是说明操作对象、接收者、可能影响和撤销方式。

分享成果时还要告知用户，文件使用了哪些受控来源，接收者能否查看。输入时有权限，不代表输出可以发给任何人。这一限制应在分享前可见，而非出错之后才让用户从日志里追查。

## 产品有没有省事，需要看第二次、第三次使用

只看首次生成成功率，会低估反复使用中的困难。我会重点观察局部修改是否稳定、用户是否要重复说明、错误记忆是否复发，以及一次中断之后能否顺利继续。

这些指标还应按使用经验分别观察。熟练用户能自己补充指令或查日志，新用户可能在同一步骤就放弃。把两者混成一个平均完成率，会让团队错过需要改进的入口。

如果用户为了管理 Agent，必须不停翻日志、同步资料、重置记忆和重复授权，自动化做得再多，也可能只是改变了人的工作内容。好的交互应让用户把精力放在需要自己决定的部分，并让其余工作容易完成、容易修改、容易继续。
