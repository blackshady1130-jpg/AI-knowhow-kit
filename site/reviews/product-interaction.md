# AI 产品如何展示状态、管理权限和支持人工接管

**讨论 AI 产品、交互和企业工作流 · 更新至 2026.08**

---

## 核心判断：用户需要控制一项任务，不是陪 Agent 聊完整过程

> **一个可用的 Agent 产品要让用户知道：系统为什么启动这项任务，目前依据哪些事实，已经产生什么结果或副作用，下一步需要什么权限，以及何时应该由人接手。**

聊天框适合澄清问题，不足以承载长任务。任务持续时间变长、工具调用增多后，消息历史会把目标、事实、推断、操作和解释混在一起。用户可能看见 Agent 一直回复，却不知道客户记录是否已经修改、后台任务是否仍在运行、哪一步需要自己决定。

产品设计的重点因此从“怎样让对话更像人”转向“怎样让人理解并控制任务”。界面可以朴素，但触发、状态、权限、验收、接管和 Memory 都要有清楚规则。

## 系统要先判断这是不是一项任务

#390 记录的 AI Workspace 实践暴露了最早的一类错误：系统看到“bug”“闪退”等关键词就自动建单，随后把历史讨论、进度同步甚至机器人自己的消息也当成新任务。关键词只能说明文本中出现了某个信号，不能说明用户希望改变组织状态。

任务触发至少要回答三个问题：谁提出了行动请求；它指向哪个对象和当前状态；系统准备产生什么变化。若这些信息不清楚，产品应先请求确认或只生成草稿，而不是直接写入工单、CRM 或日程。一次对话也可能同时包含抱怨、背景、假设和真正指令，不能默认最后出现的动词就是用户意图。

“创建任务”也不等于自动化完成。真实工作中优先级会变化，负责人会更换，任务会暂停，执行者说 done 后还要经过验收。#390 将难点概括为维护 State Machine，比维护 Conversation 更难。这个判断来自一位产品实践者的复盘，不代表所有企业 Workspace；它指出的状态变化和验收缺口却是可检查的产品问题。

#410 的 VibeLifeBench 把持续任务放进会随时间变化的模拟世界，测试 Agent 能否记住约束、等待机会并在环境变化后继续行动。它是模拟任务，不能证明真实生活 Agent 已经可用；对产品的启示是，长期任务需要明确的启动条件、等待状态、重新唤醒条件和结束标准，不能只依赖一条长 Prompt。

## 状态页面只展示会影响判断的信息

长任务需要 task state，但不是把完整 Trace 全部暴露给用户。#21 对生成式 UI 的讨论和 #75 对 Agent-native 工作流的观察，都主张把计划、工具执行、产物与审批从聊天消息中分开。#390 又补充了一个重要限制：可见性不是越高越好，过多日志会把人的注意力淹没。

产品至少要区分五类状态：已经确认的事实；模型根据事实做出的推断；正在等待的外部操作；已经产生的副作用；需要用户决定的分支。用户看到“已完成”时，还应知道完成的是模型步骤、系统写入，还是经过业务验收的结果。

实时语音把这类问题表现得更明显。GPT-Live 使用 full-duplex 前台处理倾听、停顿和打断，并把复杂搜索或工具任务交给后台模型（#359）。当前材料说明了前后台委派，没有给出中文噪声环境、长任务延迟、叠加成本和 API 控制面的完整结果。它适合作为一个交互例子：后台任务可以异步运行，但前台必须说明委派给了谁、正在等待什么，以及用户怎样取消或改向。

状态页面的目标不是证明 Agent 很忙，而是帮助用户决定是否继续、修改、批准或接管。与决策无关的调用细节可以留在 Trace 中，出错时再展开。

## 权限要放在用户真正会判断的位置

权限不应只有“允许/拒绝”两档。只读浏览、生成草稿、修改可回滚的内部状态、向外发送、付款或删除，风险和可逆性不同。AutomationBench-AA 用 Objective 与 Guardrail 同时描述企业自动化：Agent 既要完成 CRM、工单或通知任务，也不能触碰错误客户、过期草稿和无关记录（#357）。这组结果来自模拟 SaaS 应用，不能直接代表生产风险；Objective + Guardrail 的结构可以用于产品权限设计。

Guardrail 不能只写在 system prompt。对象范围、金额、受众、schema、事务和审批属于确定性产品层。#285 的 SaaS-Bench 也说明，日期、字段和客户类型中的小错会沿后续步骤放大。模型负责理解目标和处理例外，系统负责执行可明确写成规则的边界。

#396 收录的 Claude Code 实验中，用户对单条 permission prompt 的批准率很高，对整体 Plan 的拒绝率却明显更高。AI Coding 文章保留了完整数字和实验边界；对产品设计而言，结论是减少高频、低信息量的确认，把人放在目标、对象范围、风险边界和异常分支上。运行时规则可以持续检查，规则外或高责任动作再暂停给人。

Agent Identity 还要求界面显示委托链：谁发起、Agent 代表谁、任务是什么、授权到何时、可以操作哪些对象（#382）。短期凭证能限制范围，却不能自动判断每次操作是否仍符合用户原始意图。高风险动作需要更窄策略、预览和重新确认。

## 数据被读取后，原来的权限仍要保留

传统授权常停在“这个 Agent 能不能调用某个工具”。数据一旦被读取，可能进入 Context、Workspace、Memory、摘要和最终产物；产物被分享时，原数据的权限很容易丢失。

#403 对 Cloudflare OS 源码实践的分析记录了一种做法：Agent 读取外部数据时，把来源和权限写入 Workspace；其他人打开共享 Workspace 时，再用其身份检查历史数据源。若低权限用户已经进入 Workspace，后续读取更敏感的数据也会被阻断。该实现仍有 Workspace 粒度偏粗、Driver 覆盖不完整和出口策略不统一等限制，不能当作成熟标准。

产品层需要让用户理解三件事：当前产物用了哪些受控来源；分享给某个对象后哪些内容会被隐藏或阻断；后续新增数据是否改变可分享范围。权限管理的对象不能只包括 Tool，还要包括 Context、Memory、Workspace 和 Agent 生成的文件。

## 不同产物需要不同的验收界面

Agent 说“任务完成”只是状态声明，不是验收。用户要看到能判断结果的证据。代码适合展示 diff、测试和静态检查；网页需要直接预览页面；表格要保留公式、来源和口径；研究任务需要显示问题、证据、反例和引用；对外消息则要显示受众、最终文本和发送状态。

#413 记录的 ADE 产品实践把 Task、worktree、Terminal、Browser、Review 和 PR 放在同一个管理层。它指出一个普遍的产品瓶颈：Agent 并发可以快速增加，人的注意力不会同步扩张。如果界面只告诉用户“十个任务已完成”，却不能按风险排序、指出异常和提供适合产物的 Review 工具，自动化只会制造更长的待验收队列。

验收界面还应区分“系统检查通过”和“用户接受结果”。测试、格式和规则可以自动检查；需求是否满足、取舍是否合理、是否可以向外发布，可能仍需业务 owner 决定。产品应保存两种状态，避免把机器检查误写成业务完成。

## 人工接管要从当前状态继续

人工接管不是失败后重新打开一个聊天框。系统需要说明卡在哪里，展示相关证据、已经执行的动作、未完成事项和剩余权限。人接手后应能修改计划、补充信息、撤销可逆动作或把任务转给其他负责人。

#166 将 autonomy 解释为 model × user × product 的共同结果。同一个模型在只给建议、修改内部状态、向外发送和执行高责任动作的产品中，会获得不同的实际行动权。接管条件也要随风险变化：规则冲突、置信不足、预算耗尽、外部状态变化、Guardrail 临界和连续失败，都可以触发暂停。

动态工作流把中间状态保存在脚本和文件中，方便不同执行者继续处理（#297）。底层 checkpoint、branch 和 Effect Log 的实现属于“架构与工程”；产品层要保证这些状态能被人看懂，并提供暂停、撤销、改向和恢复入口。每次异常若都要求专家重新阅读全部消息，表面自动化率再高也可能不划算。

## Memory 要允许用户查看、纠正和删除

一次 Context Infra 现场交流中，十余位重度 Coding Agent 用户表示会主动删除、重置甚至关闭自动 Memory，因为产品可能把临时任务、项目阶段和偶发偏好写成长期事实（#369）。这组反馈不能代表总体用户分布，但说明隐藏写入和隐藏调用会直接破坏信任。

每条长期 Memory 至少需要来源、创建时间、作用域、置信度和修改记录。用户明确提供的偏好、系统推断的偏好、项目阶段信息和一次性任务状态不应混存。产品还应显示本次任务调用了哪些 Memory，并允许用户就地更正、删除或限制复用范围。

Memory 指标不能只有 recall。还要抽查 precision、来源和版本是否正确、模型是否实际采用、任务结果是否改善，以及跨任务复用是否引入污染。组织知识必须继承原系统权限，不能因为被压缩成“用户画像”就失去来源和删除规则。

## 实践工具：权限与人工接管分级表

| 等级 | Agent 可以做什么 | 用户需要看见什么 | 默认接管条件 |
| --- | --- | --- | --- |
| L0 建议 | 分析、解释、提出选项 | 来源、假设、置信与反例 | 关键事实缺失 |
| L1 草拟 | 生成待审核 artifact | 版本、差异、引用、验收清单 | 需求或对象不明确 |
| L2 可逆执行 | 修改可回滚的内部状态 | Effect Log、对象范围、撤销入口 | 规则冲突或连续失败 |
| L3 外部执行 | 发信、更新客户、公开内容 | 最终预览、受众、数据来源、发送状态 | 外发范围变化或 Guardrail 临界 |
| L4 高责任执行 | 付款、删除、权限和关键决策 | 限额、双人审批、演练、责任人 | 默认人工批准 |

真实任务可以在不同阶段升降级。浏览资料时处于 L0，形成草稿后进入 L1，写入系统前进入 L2 或 L3。产品必须记录升级原因和授权时限，不能把一次批准变成永久通行证。

产品轨迹只有在用户授权保存、结果得到明确验收、失败位置可归因并完成脱敏后，才适合进入 Eval、Skill 或训练。原始对话和点击量不能自动变成高质量反馈；详细评测方法由“评测与基准”主题负责。

## 这套设计适用于哪些任务

低风险、一次性、可快速检查的任务不需要完整阶梯，过度审批会浪费时间。高责任、多人协作或长期任务则不能因为平均成功率提高就跳过权限和接管。产品应根据本地任务、用户能力、可逆性和失败代价决定控制面，不必追求统一界面。

## 哪些证据会改变以上判断

1. 若用户在长程、多工具任务中只凭自然语言对话就能持续理解状态、纠正错误并安全授权，结构化 task state 的必要性会下降。
2. 若高频逐步确认在真实产品中长期保持高质量审查，并比计划级审批加运行时规则更少漏过危险操作，控制点不必上移。
3. 若长期 Memory 在没有来源、作用域、调用记录和纠错入口时仍稳定降低错误，且不增加隐私、越权和污染，治理字段可以简化。
