# 模型进入工作流之前：状态、权限与接管如何被设计

**覆盖 AI 产品、交互与企业工作流相关判读 · 更新至 2026.07**

---

## 核心判断：AI 产品是一套委派协议

> **成熟的 AI 产品需要回答五件事：用户把什么目标交出去，系统当前处于什么状态，模型拥有哪些权限，何时需要确认，以及失败后谁来接管。聊天框、语音和按钮只是这套委派协议的界面。**

模型接入产品最容易从“增加一个对话入口”开始。用户描述需求，模型返回文字；如果模型会调用工具，再加几个确认弹窗。这个路径能快速上线，却没有处理真实工作流的核心：任务跨越多轮、多系统和多个人，外部状态会变化，动作有副作用，责任也不能停留在一次生成上。

Agent-native 产品的设计单位因此应从 message 转向 task state。系统要让用户知道它理解了什么、做到了哪一步、用了哪些资料、准备执行什么动作、哪里需要人类判断。模型能力越强，这些信息越不能藏在流畅回复后面。

## 交互层正在变成持续运行的前台

GPT-Live 展示了一种值得关注的前后台分工（#359）。前台模型以 full-duplex 方式持续听取、判断停顿与打断，并维持对话节奏；遇到搜索、复杂推理和工具任务，再委派给后台 GPT-5.5。语音由此不只承担输入输出，也承担任务路由和状态维持。

这个架构比“语音版聊天框”更接近运行时。用户说话时，前台要决定继续听、回应、暂停还是启动后台任务；后台耗时较长时，前台仍需解释进度、处理新指令或取消。turn-taking、delegation 和 tool state 成为产品逻辑，而非模型自然对话能力的副产品。

证据边界也很明确。首发材料说明了 full-duplex 与后台委派，并未回答 API 中能开放多少 VAD、打断和工具状态控制，也没有给出前后台叠加后的真实成本、中文噪声环境表现和长任务延迟。本地官方材料对“首发不支持视频或屏幕共享”的支持也不够清楚，因此不把它写进产品结论。

语音只是一个高压力样本。任何常驻 Agent 都会遇到同样问题：前台要保持可感知状态，后台执行可以异步，但委派边界与失败必须返回用户。

## 状态可见性决定协作带宽

传统 SaaS 通过表单、页面和流程节点暴露状态；聊天界面往往把状态折叠进历史消息。任务一长，用户就难以回答“系统现在认为什么”“哪些步骤已完成”“这次修改会影响什么”。#21 对生成式 UI 的讨论、#75 对 Agent-native 工作流的观察，都指向让计划、artifact、工具执行和审批成为可操作对象，而非只显示一串回复。

Plan → Annotate → Execute 在 coding 场景中有效（#163），因为计划成为共享状态：人可以直接标注遗漏、风险和验收条件，Agent 再据此执行。把这一模式迁移到通用产品，需要为不同任务设计相应 artifact。销售流程可能是账户与下一步动作；研究任务是问题树、证据和置信度；内容生产是提纲、素材和版本差异。

进度条不足以表达这些状态。产品至少要区分已知事实、模型推断、等待中的外部操作、需要用户决定的分支和已经产生的副作用。用户只有看见这些差异，才能在正确时机介入。

## 权限设计要跟随任务阶段变化

AutomationBench-AA 用 Objective 与 Guardrail 的组合说明了企业自动化的基本结构（#357）。Agent 要完成 CRM、工单或通知任务，同时不得触碰错误客户、过期草稿或无关记录。headline score 要求目标完成且没有 guardrail violation；这比“有没有调用成功 API”更贴近产品责任。

#285 的 SaaS-Bench 也显示，日期、字段、客户类型和复查步骤中的小错会沿工作流放大。更常见的原因是产品没有把业务规则、状态验证和 checkpoint 变成运行时约束，而非用户少写了一句完美 prompt。

权限因此不应只有“允许/拒绝”两档。浏览和草拟可以默认执行；修改可恢复的内部状态需要记录；外部发送、付款、删除和公开发布需要更高等级确认。系统还要根据对象、金额、受众和可逆性动态升级权限。用户授权的是一类受约束动作，不是一张无限期通行证。

Guardrail 也不能只写进 system prompt。对象级权限、schema 校验、事务、审批和审计日志属于确定性产品层。模型负责理解目标和处理例外，基础边界由系统执行。

## Memory 是有治理的数据模型

“记住用户”可以提高连续性，也可能制造无法追踪的错误前提。#217 对 memory 设计的观察强调了存储、检索和更新；在产品层还要补上 provenance、作用域、确认和删除。用户明确提供的偏好、系统从行为推断的偏好、某次任务的临时状态，不应进入同一张无差别记忆表。

每条长期记忆至少需要来源、创建时间、适用范围、置信度和修改记录。高风险事实应允许用户确认；过期推断需要衰减或重新验证；组织知识则要继承原系统权限。把所有历史压缩成一段“用户画像”，既不利于纠错，也会让模型在错误上下文上持续自洽。

Memory 的产品价值不在于让用户感觉系统“很懂我”，而在于减少重复输入，同时保留更正路径。个性化与可撤回性要同时成立。

## 接管不是失败兜底，而是正常路径

#166 把 autonomy 解释为 model × user × product 的部署结果。相同模型在不同权限、用户能力和接管机制下，会形成完全不同的自主性。产品不应把人工介入视为 Agent 不够成熟；真实工作流本来就包含判断权转移。

好的接管需要满足三个条件。第一，系统能说明卡在哪里，而非只说“发生错误”；第二，人接手时能看到相关证据、已执行动作和未完成状态；第三，处理结果能写回规则、Skill 或 eval，避免同类 badcase 永久依赖人工救火。#297 的动态工作流把中间状态保存到脚本和文件，正是为了让不同执行者可以续接。

接管成本也应被计量。一个表面自动化率很高、但每次异常都需要专家重新阅读全部历史的产品，可能比显式保留审批节点更贵。

## 实践工具：授权与接管阶梯

可以把产品动作放进一套 **授权与接管阶梯**：

| 等级 | Agent 可做什么 | 产品必须提供 |
| --- | --- | --- |
| L0 建议 | 分析、解释、提出选项 | 来源、假设、置信与反例 |
| L1 草拟 | 生成待审核 artifact | diff、版本、验收清单 |
| L2 可逆执行 | 修改可回滚的内部状态 | Effect Log、撤销、对象范围 |
| L3 外部执行 | 发信、更新客户或公开内容 | 明确预览、二次确认、审计 |
| L4 高责任执行 | 付款、删除、权限与关键决策 | 双人审批、限额、演练与人工 owner |

每个任务还要写清接管触发器：规则冲突、置信不足、预算耗尽、外部状态变化、guardrail 临界或连续失败。接管后保留 workspace 和 action log，让人从当前状态继续，而不是从头复述需求。

## 产品判断的边界

低风险、一次性、可快速检查的任务不需要完整阶梯；过度审批会让产品失去效率。相反，高责任场景不能因为模型平均分提高就跳过权限层。GPT-Live、AutomationBench-AA 和动态 Agent 工作流分别提供架构样本、模拟 benchmark 与工程实践，尚不能证明某一种界面会成为统一形态。

产品团队应依据本地任务、用户和失败代价选择交互。页面可以朴素，状态与责任必须清楚。

## 哪些观察会迫使这套判断修正

1. 若用户在长程、多工具任务中仅凭自然语言对话就能持续理解状态、纠正错误并安全授权，结构化 task state 的必要性会下降。
2. 若模型在开放企业工作流中把 Objective 完成率和 Guardrail 违例同时稳定推到接近人工水平，分级确认可以减少；需要以连续运行而非单次榜单验证。
3. 若长期 memory 在缺少来源、作用域和用户纠错界面的情况下仍显著降低错误且不增加隐私与误用，治理字段可以简化。
