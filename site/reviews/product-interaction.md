# AI 产品与交互：当模型越来越强，产品却没跟上——从错位到重构的一年

**覆盖 68 篇判读 · 2024.11 – 2026.05**

---

## 一、当前正在发生什么

这组材料反复指向一个很尴尬的问题：模型一年比一年强，但很多 AI 产品用起来还是别扭。

UI 当然算一部分，但更常见的别扭来自别处：路由错了、记忆乱了、权限说不清、用户不知道模型在干什么、模型也不知道用户什么时候要接管。模型能力越强，这些产品问题反而越刺眼。

#3 最早直接点出这个矛盾：Gemini 模型很强，但 App 层把关键能力阉割掉了。后来 GPT-5 发布后的路由混乱（#35、#38）、SaaS 会不会被 Agent 吃掉的争论（#143、#175）、Agent-native 产品架构的讨论（#196），都在说明同一件事：模型能力不能自动变成产品价值。中间需要一层很重的产品和工程翻译。

4-5 月新增材料把这个问题说得更细。#289 讨论的是身份、权限、上下文、通信、控制感和责任链；Thinking Machines 的 Interaction Models 把 interface problem 重新定义成 model problem（#272）；Anthropic Managed Agents 则把长时任务和状态管理做成托管运行时（#229）。AI 产品正在从“聊天框”往“协作环境”走，但这条路还很早。

产品侧的难点在于，它不只看模型会不会答。它要理解用户需求、嵌进工作流，还要找到愿意付费的方式。这几件事，模型自己不会替产品团队完成。

## 二、核心观察与判断

### 洞察 1：产品-模型错位是现在最常见的失败来源

#3 里的 Gemini 例子不是个案。Claude、Gemini、ChatGPT 的差异经常不在模型本身，而在产品如何暴露能力。#35 的 GPT-5 发布把问题放大了：路由策略出错，很多 badcase 被送给小模型；用户压力一上来，历史模型又被放回去；版本命名也混乱到不像人话。#38 则指出更难的问题：模型到底该用多少计算量，行业还没有好的产品解法。长期记忆如果过度回调，也会从“贴心”变成“烦人”。

#272 补了一个我觉得很关键的错位：很多 AI 产品不是模型不会答，而是协作带宽太窄。用户要把意图压成一句 prompt，模型要一次吐完答案。但真实协作里，人会犹豫，会中断，会看屏幕，会根据后台进度调整计划。下一代交互不一定是更漂亮的聊天框，而是让人的工作状态和模型的行动状态持续对齐。

这个错位的根源在于：模型团队优化 benchmark，产品团队面对模糊意图。两者之间缺一层“把模型能力变成可靠用户价值”的工程。Devin 团队在 #66 说得很代表性：套壳 agent 的挑战，已经从“让它能做事”变成“让它知道何时、如何做得更好”。

### 洞察 2：SaaS 不会突然死，但很多旧逻辑要重写

#175 的分析很尖锐：AI Agent 会冲击 SaaS 按人头收费的根基，商业模式、护城河、信息不对称、交互方式都会受影响。但 #143 给了重要反面论据：美国 SaaS 有组织级基础设施、清晰工作流和 API 生态，AI 可能让它们再涨一轮；中国 SaaS 更像外包能力包装，更容易被 AI + 私有数据替代。

#173 Elad Gil 的观点也很反共识：bundle 的防御价值被低估了。SaaS 时代“只做好一件事”的教条，在企业软件里未必成立。企业级软件里的代码只是一小部分，分发、权限、流程、合规、组织协作同样难。#159 把话说得更硬：AI 模型越强，流程工程越重要。在金融领域，80% 正确率等于 100% 错误，精确性不是加分项，是入场券。

Ramp 的企业支出数据给了一个更实际的方向（#267）：AI 正在让一部分 SaaS 从“工具预算”变成“流程预算”，甚至“人力预算”。老 SaaS 不会因为接一个 agent 就完成升级，关键是旧资产能不能变成 action layer。谁能控制完整工作流，谁就有机会吃掉一组工具和一段人工流程。#285 的 SaaS-Bench 也提醒，真实跨应用流程的成功率还很低。状态、校验、异常处理和责任链，都要重做。

所以我更倾向于 #175 的中间判断：SaaS 不会死，但会蜕皮。机会会从卖工具转向卖结果，可能是 outcome-based pricing，也可能是 consumption-based pricing。#98 Lovable 的案例说明，AI 公司的 PMF 不再是找到一次就稳几年，而是需要持续续费。发布节奏和产品体验，会比一句定位更重要。

### 洞察 3：记忆系统会成为产品差异的一部分

#109 点出一个行业共识和困境：大家都知道记忆重要，但没有标准解法。#106 逆向 ChatGPT 记忆策略后给了一个务实参照：会话元数据、用户记忆、近期会话摘要、当前会话消息，这几层不是同一种“记忆”，也不该用同一种方式处理。

#117 Tolan 的案例更极端：产品护城河不在更强底模，而在每一轮如何重建上下文。动态记忆检索、压缩、语气调度，让陪伴体验做到 SOTA。#66 Devin 团队也观察到，Claude Sonnet 4.5 会自发写 SUMMARY.md、CHANGELOG.md 来保持记忆。这个行为很有意思：模型自己也在想办法绕开上下文限制。

#34 从企业知识库角度说了一个更朴素的问题：很多团队还停在“导入=知识”。但知识要运营，要提炼核心信息、写应用规则、定期检查和降噪。不是搞个 RAG 组件就有知识库。

#252 把记忆问题拉回真实生活：群聊、会议、笔记、行为日志、社区评论，这些碎片比标准知识库更接近个人助手会碰到的材料。#277 则提醒，持续更新 memory 不一定越用越聪明，错误抽象会让有用记忆变成 faulty memory。产品要区分 raw episode、可验证事实、可迁移经验和暂时性偏好。

### 洞察 4：AI 产品的入口正在从“吸引注意力”转向“接住意图”

#40 提出了一个三层框架：商业模式从免费流量到价值付费，产品价值从链接价值到效率价值，经济形态从注意力经济到意图经济。这个框架有点大，但落到产品上就是一个问题：你到底帮用户少切了多少上下文？

#55 从 C 端补了一个物理约束：人的注意力一天只有 24 小时。AI 不是凭空创造注意力，而是让用户更挑剔。谁能把 AI 从降本器变成增需器，谁才有机会拿到用户时间。文章列的四条通道——价值密度提升、并行代理影子产出、零到一结果商品化、内容即交易——可以继续看。

#146 的“数字雇员”视角很有用：用户把 AI 产品当雇员看，订阅费像薪资，付费决策像雇佣决策。免费版太好用反而会伤害付费转化。#125 从分发端给了数据：AI Overviews 出现后，有效点击率下降 61%，付费广告点击率下降 68%。SEO 从抢第一名，变成抢 AI 摘要引用位（#9）。这不是流量小改版，而是入口被改写。

#242 把 To B / To C 改写成 To Human / To Agent。Claude Code、Cursor、Perplexity、Manus 先被 prosumer 采用，再 bottom-up 进入组织，说明消费者采购和企业采购可能发生在同一个人身上。To Agent 更进一步：agent 本身会成为生产者和消费者。产品设计必须问清楚，使用者到底是人，还是另一个 agent。

### 洞察 5：Agent-native 产品要先讲清边界

#196 给了一个很清楚的分层：“Agent 是 OS，垂类做 OS 是找死。”这句话夸张，但有提醒意义。Agent 有两个物理约束：上下文容量和注意力带宽。领域状态不一定要全塞进 Agent，很多时候应该放在 Application 里按需调用。Application 的壁垒来自领域状态、基础设施成本和规模经济。

#185 从工具设计角度补充：为 Agent 设计动作空间，本身就是产品设计。渐进式披露可以在不增加工具数量的情况下扩展能力。#153 描绘 Agent-native Web：Google 的 WebMCP 在“目的地”修站台，Cloudflare 的 Markdown for Agents 在“路上”铺轨道。这些基础设施动作说明，Agent 会从网页使用者变成网页改造者。

#141 则泼了冷水：阈值产物很容易热一阵，比如当年的 AutoGPT。真正能留下来的产品，往往不是给无限灵活性，而是通过限制灵活性创造稳定价值。Perplexity 是典型案例。#155 的说法也好：工具会过气，对工具本质的理解不会。

#166 Anthropic 对 Claude Code 真实数据的分析提醒，用户给模型的自主性滞后于模型能力。经验丰富的用户更愿意自动批准，但也更频繁干预。AI Fluency 不是盲目信任，而是知道什么时候放权、什么时候接管。下一代 agent 的护城河不在 demo 能不能跑，而在上线后能不能观测、治理、回滚。

#229、#280、#289 共同指向一个产品问题：企业买 Agent，最后买的不是“自主性”本身，而是可治理的效率。FDE 解决的是模型能力和企业现实之间的集成之墙；如果现场交付不能沉淀成平台能力，就只是披着 AI 外衣的咨询公司（#280）。Agent-native 产品必须说清楚谁授权、谁执行、谁验收、谁负责。

## 三、正在发生的变化与趋势

- **SaaS 会分层，而不是一起消失**：#15 的“氛围 ARR”让人容易悲观，但 #143、#159、#173 修正了这个判断。美国 SaaS 的组织基础设施、API 生态和企业数据资产仍然有价值。真正要看的不是 SaaS 死不死，而是谁能从卖工具转向卖结果。

- **对话、产物、环境三种交互会并存**：#28 的 artifact-first 是一次重要提醒，AI 产品不一定围着聊天框转。#196 和 #185 进一步说明，很多场景要设计的是 Agent 的运行环境，不能只给用户一个输入框。这条路还没走完。

- **记忆从功能点变成产品底座**：#34 讨论知识库时还停留在“导入=知识”的批评，#106、#117、#66 之后，记忆/上下文系统已经变成产品差异来源。#110 的 agency 讨论也说明，记忆同时牵涉权限、信任和责任。

- **产品既要服务人，也要服务 Agent**：To Human / To Agent（#242）会重写入口、权限、分发和计费。未来很多产品要同时面对人类用户和调用它的 agent。如果通信、授权和责任链没设计好，不确定性只会被层层转包。

## 四、接下来值得关注的问题

1. **Agent OS 与 Application 层的边界在哪里？** #196 的框架很清楚，但也承认：如果 Claude 自己能记住案件进度和判例引用，法律 Application 的领域状态优势会被削弱。边界是动态的，取决于 OpenAI、Anthropic 这些厂商怎么做持久记忆和项目上下文。

2. **AI 产品的定价最后会怎么收敛？** #146 的雇佣逻辑、#40 的意图经济、#175 的 outcome-based pricing，都指向按结果或按消耗付费。但行业还没有共识。#15 的“氛围 ARR”也说明，很多公司连现有收入质量都看不清。

3. **协议主权之争会怎么收场？** #67 指出 MCP 已经超出技术问题。OpenAI Apps SDK 引入 `_meta` 私有扩展，提升效率，也可能让标准分裂。Agent 成为主要网络消费者后，谁定义交互协议，谁就能影响生态控制权。

4. **Agent 产品的责任链怎么产品化？** Make for Agent 不是把 UI 改成 Agent UI（#289）。真正要设计的是任务边界、权限范围、上下文来源、失败处理和验收方式。否则 agent 协作只是把风险从一个系统转给另一个系统。
