# AI 产品如何展示状态、管理权限和支持人工接管

**讨论 AI 产品、交互和企业工作流 · 更新至 2026.07**

---

## 核心判断：AI 产品要让用户知道系统正在做什么

> **AI 产品需要回答五件事：用户交给系统什么任务，任务进行到哪里，模型拥有哪些权限，什么时候需要用户确认，以及失败后怎样转给人处理。**

接入模型时，产品往往先增加一个对话入口：用户描述需求，模型返回文字；模型能够调用工具后，再加几个确认弹窗。这种做法上线快，但没有处理长任务中的进度、外部状态变化、操作风险和责任问题。

长任务不能只显示一串 message，还要展示 task state。系统应让用户知道它理解了什么、完成了哪一步、用了哪些资料、下一步准备做什么，以及哪里需要人来判断。模型能执行的操作越多，这些信息越需要明确显示。

## 实时语音产品如何处理对话和复杂任务

GPT-Live 展示了一种前后台分工（#359）。前台模型以 full-duplex 方式持续听取、判断停顿和打断，并维持对话；遇到搜索、复杂推理和工具任务时，再交给后台 GPT-5.5。语音模型因此既负责对话，也负责决定什么时候启动后台任务。

用户说话时，前台要决定继续听、回应、暂停还是启动后台任务；后台任务耗时较长时，前台还要说明进度、接收新指令或取消任务。turn-taking、delegation 和 tool state 都需要由产品明确处理，不能完全依赖模型自然对话。

证据边界也很明确。首发材料说明了 full-duplex 与后台委派，并未回答 API 中能开放多少 VAD、打断和工具状态控制，也没有给出前后台叠加后的真实成本、中文噪声环境表现和长任务延迟。本地官方材料对“首发不支持视频或屏幕共享”的支持也不够清楚，因此不把它写进产品结论。

实时语音让这些问题表现得更明显。任何持续运行的 Agent 都要告诉用户当前状态；后台任务可以异步执行，但任务交给了谁、哪里失败了，都应返回给用户。

## 长任务需要展示进度和中间结果

传统 SaaS 通过表单、页面和流程节点显示状态；聊天界面往往只留下历史消息。任务一长，用户就很难判断“系统目前掌握了什么”“哪些步骤已经完成”“这次修改会影响什么”。#21 对生成式 UI 的讨论、#75 对 Agent-native 工作流的观察，都建议把计划、产物、工具执行和审批单独展示，而不是只显示一串回复。

Plan → Annotate → Execute 在 coding 场景中有效（#163），因为人可以直接在计划上标注遗漏、风险和验收条件，Agent 再据此执行。其他产品也需要展示适合本任务的中间结果：销售流程可以显示账户和下一步动作；研究任务可以显示问题、证据和置信度；内容生产可以显示提纲、素材和版本差异。

进度条不足以表达这些状态。产品至少要区分已知事实、模型推断、等待中的外部操作、需要用户决定的分支和已经产生的副作用。用户只有看见这些差异，才能在正确时机介入。

## 不同操作需要不同级别的权限

AutomationBench-AA 用 Objective 与 Guardrail 的组合说明了企业自动化的基本结构（#357）。Agent 要完成 CRM、工单或通知任务，同时不得触碰错误客户、过期草稿或无关记录。headline score 要求目标完成且没有 guardrail violation；这比“有没有调用成功 API”更贴近产品责任。

#285 的 SaaS-Bench 也显示，日期、字段、客户类型和复查步骤中的小错会在后续步骤中放大。常见问题是产品没有把业务规则、状态检查和 checkpoint 写进系统，而不是用户少写了一句完美 prompt。

权限因此不应只有“允许/拒绝”两档。浏览和草拟可以默认执行；修改可恢复的内部状态需要记录；外部发送、付款、删除和公开发布需要更高等级确认。系统还要根据对象、金额、受众和可逆性动态升级权限。用户授权的是一类受约束动作，不是一张无限期通行证。

Guardrail 也不能只写进 system prompt。对象级权限、schema 校验、事务、审批和审计日志属于确定性产品层。模型负责理解目标和处理例外，基础边界由系统执行。

## 长期记忆需要记录来源和修改历史

“记住用户”可以减少重复输入，也可能长期保留错误信息。#217 对 memory 设计的观察强调了存储、检索和更新；产品还要记录来源、适用范围，并提供确认和删除功能。用户明确提供的偏好、系统根据行为推断的偏好、某次任务的临时状态，不应混在一起保存。

每条长期记忆至少需要来源、创建时间、适用范围、置信度和修改记录。高风险事实应允许用户确认；过期推断需要衰减或重新验证；组织知识则要继承原系统权限。把所有历史压缩成一段“用户画像”，既不利于纠错，也会让模型在错误上下文上持续自洽。

Memory 应减少重复输入，也要允许用户查看和更正。个性化不能以无法撤回为代价。

## 人工接管应该在产品设计中提前安排

#166 将 autonomy 解释为 model × user × product 的共同结果。相同模型在不同权限、用户能力和接管机制下，会获得不同程度的行动权。真实工作流本来就需要人做判断，因此产品应提前设计人工介入，而不是等系统失败后再补。

人工接管需要满足三个条件。第一，系统能说明卡在哪里，而不是只说“发生错误”；第二，人接手时能看到相关证据、已执行操作和未完成事项；第三，处理结果能用于修改规则、Skill 或 eval，减少同类 badcase 重复出现。#297 的动态工作流把中间状态保存到脚本和文件，方便不同执行者继续处理。

接管成本也应被计量。一个表面自动化率很高、但每次异常都需要专家重新阅读全部历史的产品，可能比显式保留审批节点更贵。

## 实践工具：权限与人工接管分级表

可以按风险把产品操作分成以下几级：

| 等级 | Agent 可做什么 | 产品必须提供 |
| --- | --- | --- |
| L0 建议 | 分析、解释、提出选项 | 来源、假设、置信与反例 |
| L1 草拟 | 生成待审核 artifact | diff、版本、验收清单 |
| L2 可逆执行 | 修改可回滚的内部状态 | Effect Log、撤销、对象范围 |
| L3 外部执行 | 发信、更新客户或公开内容 | 明确预览、二次确认、审计 |
| L4 高责任执行 | 付款、删除、权限与关键决策 | 双人审批、限额、演练与人工 owner |

每个任务还要写清接管触发器：规则冲突、置信不足、预算耗尽、外部状态变化、guardrail 临界或连续失败。接管后保留 workspace 和 action log，让人从当前状态继续，而不是从头复述需求。

## 这套设计适用于哪些任务

低风险、一次性、可快速检查的任务不需要完整阶梯；过度审批会让产品失去效率。相反，高责任场景不能因为模型平均分提高就跳过权限层。GPT-Live、AutomationBench-AA 和动态 Agent 工作流分别提供架构样本、模拟 benchmark 与工程实践，尚不能证明某一种界面会成为统一形态。

产品团队应依据本地任务、用户和失败代价选择交互。页面可以朴素，状态与责任必须清楚。

## 哪些证据会改变以上判断

1. 若用户在长程、多工具任务中仅凭自然语言对话就能持续理解状态、纠正错误并安全授权，结构化 task state 的必要性会下降。
2. 若模型在开放企业工作流中把 Objective 完成率和 Guardrail 违例同时稳定推到接近人工水平，分级确认可以减少；需要以连续运行而非单次榜单验证。
3. 若长期 memory 在缺少来源、作用域和用户纠错界面的情况下仍显著降低错误且不增加隐私与误用，治理字段可以简化。
