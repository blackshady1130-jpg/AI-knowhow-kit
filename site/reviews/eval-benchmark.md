# 如何判断一个 Agent 评测是否可信

**讨论 benchmark、verifier 和真实工作流评测 · 更新至 2026.08**

---

## 核心判断：先审任务和评分方法，再看分数

> **Agent 的分数只有在任务、环境、成功标准和运行配置都说清楚时才有比较价值。先问它测了什么、允许什么、怎样算错，再讨论哪个模型更强。**

传统模型评测通常给定输入、生成答案、判定对错。Agent 评测还要处理搜索、写文件、调用 API、读取历史、反复提交和外部副作用。一次失败可能来自模型推理，也可能来自 Context、工具、权限、环境或 Verifier；一次通过也可能只是测试覆盖不足。评测结果会进入训练奖励、产品路由、采购预算和授权范围，任务或评分方法有缺陷，后续决策就会一起偏掉。

## 逐项检查任务、环境和隐藏要求

OpenAI 对 SWE-Bench Pro 的审计直接检查单个任务（#360）。其 agent 审计管线把 27.4% 的样本标为有问题，后续人类审计给出 34.1%，OpenAI 据此估计约三成任务存在缺陷并撤回推荐。这里的“三成”是基于审计方法的估计，不是逐题证明的精确比例。

缺陷有两种相反方向：hidden tests 要求 prompt 没说的实现细节、题目信息不足，会制造假阴性；测试覆盖太低、不完整修复也能通过，或 prompt 把 Agent 引向错误路径，会制造假阳性。#183 对 HLE 的清理也显示，修正题目后，平均精度可以变化 7—10 个百分点，错误子集变化达到 30—40 个百分点。榜单再大，也不能替代对数据点的核验。

任务审计至少要留下来源、需求是否充分、参考实现、测试覆盖、时间切分和争议记录。如果 reviewer 无法解释题目要求，便不适合用这道题区分细小的模型差异。环境还要写清依赖、网络、历史数据、工具权限、状态是否持久和超时规则；否则环境噪声会被误记成模型能力。

## 先说明结果属于模型，还是完整 Agent 系统

WorkBuddyBench 把 Code、Web、Office 和 Security 都做成接手 workspace、交付可核查最终状态的任务（#373）。它没有强行使用一个评分器，而是按 artifact 选择隐藏测试、程序化 scorer、固定证据上的 LLM Judge 或能实际操作页面的 Agent Judge。这个设计先回答“什么结果可以验证”，再决定任务和评分器；它也提醒我们，榜单通常测的是模型与 Harness、Context、工具权限、compaction、effort 共同组成的系统。

#423 对六家模型发布材料的审计进一步说明，同名 benchmark 也可能使用不同的 Harness、工具、时间预算、重试和 Context 策略。结果应写成 `Model × Harness × Environment × Verifier × Runtime`，并同时披露 endpoint、effort、turn cap、超时和成本；不能把一个百分数当成脱离配置的裸模型刻度。

一份完整报告还应把结果分成三层。任务层回答题目是否有足够信息、测试是否覆盖要求；轨迹层回答 Agent 走了哪些路径、何时产生副作用、失败是否可恢复；系统层回答 Harness、工具、Runtime 和 Verifier 怎样改变结果。最后才把这些结果翻译成业务指标，例如单位成功任务成本、人工复核时间和事故率。只给最终分数，会把不同层的问题压成同一个数字。

企业内部的 Databricks coding benchmark 采用近期已合并的 PR、封闭 git 历史、隐藏测试和人工抽样（#358）。它观察到同一模型换 Harness 后，部分任务成本可以相差两倍以上而质量接近。这个结果只适用于该内部代码库和任务集，但足以说明系统配置和成本不是报告末尾的附注。

effort 也要和分数一起记录。Opus 5 在一些主流评测中由 max 取得较好结果，另一些测试却是 medium 或 xhigh 更高（#374）。这可能来自噪声、过度推理、预算耗尽或评分函数；它不能证明高 effort 普遍更差，只能说明最高档不等于所有任务的最优档。

## Rubric 是任务规格，也需要校准

LLM Judge 不是天然真值层。#419 对 RubricBench 与 PaperBench 的综合解读提示：很多评测先假定 Rubric 写得足够细，再让强 Judge 执行；但复杂任务更常见的风险是标准漏写、权重不合理、证据范围不清。Rubric 更像任务规格，负责把目标、证据、权重和边界显式化，不保证规格完整，更不保证 Judge 执行时不会偏移。该 Note 综合了两篇不同论文，本篇不把其中的二手数字拼成统一实验结论。

验证器应按要求类型分工：明确格式和状态用程序规则；开放质量用固定证据约束的 Judge 或人工抽检；轨迹审计检查高分是否来自预期路径。#333、#334 的案例说明，Agent 会寻找测试和环境中的漏洞；如果候选系统能改 verifier、读取 held-out 答案或扩大权限，分数上涨不能证明真实能力提升。真实开发者查询文档和提交历史是合理行为，读取 benchmark 原始 patch 却可能构成答案泄漏（#333）。

评测团队还要把用户反馈转成可复现的失败类型。Anthropic 产品团队把“模型不听指令”“结果有幻觉”等反馈拆成工具选择、检索、抽取、综合、格式和 alignment 等问题，再做成案例和回归 Eval（#375）。这能让反馈进入训练和产品修复，但不能把所有产品取舍都压成一个分数。

## 找到最早不可恢复失败，再决定修哪一层

#395 把评测从 success/failure 推进到 root-cause attribution：沿轨迹寻找最早的不可恢复错误，再判断问题属于模型、Harness、工具、环境还是 Verifier。比如关键信息被 compaction 删除，优先修 Context 或 Harness；信息仍在窗口而模型没有使用，才是模型问题；工具已返回错误而 Agent 继续假设成功，则要分别检查工具回执和模型恢复策略。

这套方法已有信号，但还不是自动诊断真相。论文在 40 个验证案例上报告，最强 judge 的类别一致性 κ 为 0.76；四个 judge 全部一致时 precision 可到 0.96，但 coverage 只有 68%（#395）。这些数字的分母和选择条件不能省略，更不能直接当成生产归因准确率。实务上应保存完整轨迹、输入快照、环境状态和评分证据，让人工可以复核最早错误。

## 真实工作要测连续成功、副作用、成本和接管

单次成功回答不了“能不能放心交给它”。AA-AnalystAgent 每道题独立运行五次，并同时报告 pass@1、pass@5 和 pass^5（#399）：前两者分别表示单次成功和至少一次成功的比例，pass^5 表示五次全部成功。该评测有 80 道真实表格与文档分析题；官方材料中，GPT-5.5 的 pass@1 最高达到 66%，至少成功一次的比例可到 81%，但五次全对的最高值是 41%。这些数字属于它的题目、Stirrup Harness、reference-solution checker 和五次运行设置，不能直接外推到其他 Analyst 工作。

长程任务还要测环境变化和主动性。VibeLifeBench 让 200 个生活领域任务在中位 29 个模拟日中持续变化，价格、天气、库存和消息不会自动提醒 Agent（#410）。它测的不只是工具调用，而是 Agent 是否会重新检查环境、维护早期承诺、在需要时行动、在不需要时保持沉默；模拟服务和统一 scaffold 仍与真实互联网有距离。

业务动作必须把目标和副作用分开。AutomationBench-AA 将 Objective 与 Guardrail 分开评分（#357）：改对记录但误发通知、覆盖无关数据或处理 DRAFT 邮件，不能算成功。#124 的约束遵循率也说明，单项规则通过不等于所有约束同时成立。生产报告至少应给出平均成功率、连续成功率、Guardrail 违例、恢复时间、人工接管率、token/wall-clock 成本和失败复发率。探索型任务可以看 best-of-N，自动化流程则更应看尾部风险。

这些指标还要按任务风险分层。读一份资料和发送一封邮件不能共用同一成功阈值；可回滚的草稿与不可逆的付款也不能共用同一接管率目标。评测报告应同时给出基线人工成本和失败后的返工成本，才能判断自动化是否真的节省了时间。

## 实践工具：统一结果行与评测检查表

每条结果至少用一行写清：

```text
Model × endpoint × effort × Harness × Environment × tools × budget × Verifier × Runtime × cost
```

采用公开榜单或内部 Eval 前，再逐项填写：

| 审计面 | 必答问题 |
| --- | --- |
| 任务 | 来源是什么；需求是否足以推出隐藏要求；时间切分如何做 |
| 环境 | 依赖、网络、历史和工具权限是什么；状态是否持久；超时和重试如何处理 |
| 成功 | Objective、Guardrail、质量阈值和失败代价分别是什么 |
| Verifier | 哪些要求用规则、程序、Judge 或人工；如何抽查假阳性、假阴性和绕过路径 |
| 系统配置 | 模型、端点、Harness、effort、Context/compaction、turn cap、预算和版本 |
| 成本 | token、wall-clock、外部调用、人工复核和失败恢复各是多少 |
| 可靠性 | pass@k、pass^k、违例率、接管率、恢复时间和 badcase 复发 |
| 证据边界 | 结果能外推到哪些语言、任务、组织和时间范围 |

没有填清的字段就是结果的不确定性，不能用一个保留两位小数的总分带过。

公开报告至少要让读者能够复现比较条件；缺少配置清单时，分数只能作为线索，不能作为采购或上线依据。

## 哪些证据会改变以上判断

1. 若多个公开 Agent benchmark 经独立逐项审计后，任务缺陷、环境噪声和 Verifier 漏洞长期低到不足以改变排名，数据点审计的优先级可以下降。
2. 若跨 Harness、effort、预算和工具配置的排名高度稳定，且总成本差异很小，系统配置可以退回次要报告项。
3. 若 Objective-only 分数能长期预测真实部署中的 Guardrail 违例、人工接管和业务损失，过程与副作用评测可以简化；当前材料不支持这一点。本轮不外推。
