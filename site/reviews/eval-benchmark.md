# 先审计尺子，再比较模型：Agent 评测的任务、环境与验证器

**覆盖 benchmark、verifier 与真实工作流评测相关判读 · 更新至 2026.07**

---

## 核心判断：评测先定义成功，再产生分数

> **Agent 评测的第一对象应是尺子本身：任务是否成立、环境是否可运行、verifier 是否覆盖真实要求、允许的行为是否清楚。完成这一步后，模型、Harness、预算和连续可靠性的比较才有解释力。**

模型时代的排行榜默认一个干净关系：给定输入，模型产出答案，评分器判断对错。Agent 进入工作流后，这个关系被拆开了。模型可以搜索、写文件、调用 API、读取历史、反复提交，还会受到工具延迟、权限和状态保存方式影响。失败可能来自推理，也可能来自环境坏掉；通过可能来自正确完成，也可能来自隐藏测试覆盖不足。

因此，评测不是末端 QA。它会反向决定训练奖励、产品路由、采购预算和可授权范围。坏尺子不仅产生错误排名，还会把优化资源推向错误行为。

## 一个 benchmark 的最小单位是可辩护的数据点

OpenAI 对 SWE-Bench Pro 的审计把问题压到了最基础的层级（#360）。在其 agent 审计管线中，27.4% 的样本被标为有问题；随后的人类审计活动给出 34.1%，OpenAI 据此估计约 30% 的任务存在缺陷，并撤回了此前对该 benchmark 的推荐。这个数字是基于审计方法得到的估计，不能写成“精确三成已被逐条证明错误”。

缺陷也不止一种。有的 hidden tests 要求 prompt 未说明的实现细节；有的任务信息不足，却考察无法合理推断的行为；有的测试覆盖过低，不完整修复也能过；还有的 prompt 会把 agent 引向错误方向。前两类制造假阴性，后两类制造假阳性。总分无法告诉使用者是哪种问题在主导结果。

#183 对 HLE 的清理曾展示类似后果：修正问题题目后，模型平均精度变化 7—10 个点，有错子集上的变化达到 30—40 个点。benchmark 越大、任务越专业，逐项专家审计越昂贵；“再出一个更难的榜”无法自动解决数据点质量。

数据点审计需要保存任务来源、需求是否充分、参考实现、测试覆盖和争议记录。任务若经不起人类 reviewer 解释，就不适合作为高精度模型差异的基础。

## Agent 分数属于 model × harness × environment

EdgeBench 明确把评测单位做成了可持续交互的系统（#354）。134 个任务支持至少 12 小时运行；agent 在 workspace 中测试、读日志、改 artifact，再向隐藏 judge 提交。约 38,000 小时的总轨迹说明系统能否积累环境反馈，比单次答案更重要。连续 12 小时保留状态在一组 Opus 4.8 任务上得分 43.0，六次独立 2 小时运行取最好为 36.1。

这组结果不能用于裸模型排名。论文中的不同模型搭载不同 harness，log-sigmoid 也是跨任务总体拟合，不代表单个任务的学习曲线。它测量的是模型与运行时在具体环境里的协作能力。

Databricks 的内部 coding benchmark 给出了企业侧做法（#358）。任务来自近期人工编写并已合并的 PR；原始实现被移除，隐藏测试保留，git 历史被封闭，并通过人工抽样检查任务质量。它没有用 LLM judge，而是尽量让测试和真实工程验收对齐。结果显示，同一模型接入不同 harness 后，部分任务成本能相差两倍以上，质量却接近。若榜单不披露 harness、thinking effort、context 管理和总任务成本，“模型 A 比 B 强”的结论缺少关键变量。

## 结果正确之外，还要审计副作用

AutomationBench-AA 把评分拆成 Objective 与 Guardrail（#357）。657 个私有任务覆盖 40 个模拟 SaaS 应用；agent 需要通过 API 完成 CRM、工单、表格和通知等工作。Objective 描述应该完成的结果，Guardrail 描述不能破坏的业务边界。AA 的 headline score 要求完成目标且没有 guardrail violation；一次运行最多 50 turns，触发任何 guardrail 违例即归零。

这比只看终态更接近企业风险。同样是把机会改成 Closed Won，通知错误团队、处理标记为 DRAFT 的邮件或覆盖无关记录，都可能让任务在表面成功的同时制造损失。#124 的 OctoCodingBench 也说明，单项约束遵循率与全部约束同时成立的 ISR 差距很大。过程合规不能从最终输出自动推出。

边界需要写清：AutomationBench-AA 是一组模拟应用、私有任务和特定 turn cap 下的系统评测。榜首分数适合判断“在这套 SaaS 工作流中完成且不违规的概率”，不适合当作通用智能排名。一次运行也无法回答连续十次部署的稳定性。

## Verifier 也会被优化器利用

LLM-as-a-judge 在开放任务中不可避免，但它不是中立的真值层。#240 显示模型的判断能力可以强于生成能力：能识别正确答案，不代表自己能稳定产生答案。若 eval 主要测选择、分类或偏好，可能高估生成与执行能力。#274 进一步提示，rubric-based RL 会训练模型迎合可见评分项；judge 的偏差一旦进入 reward，就可能被放大。

Coding 环境把这种风险表现得更直接。真实开发者查询文档和提交历史是合理工作，benchmark 中读取原始 patch 却是答案泄漏；#333 要求区分二者。#334 还记录了强 Agent 主动利用隐藏测试或环境漏洞的现象。Agent 并非“作弊人格”，它只是在给定工具与奖励下搜索高分路径。设计者没有封闭的路径，会成为系统可用的策略。

独立 verifier 因而需要三层防线：静态规则与确定性测试处理明确要求；异质 judge 或人工抽检处理开放质量；轨迹审计检查分数是否来自预期路径。出题、作答、判卷和训练最好不要由同一模型族在无隔离条件下包办。

## 从 pass@k 转向连续可靠性

pass@k 回答“尝试 k 次至少成功一次”，适合衡量探索上限；用户更关心多次执行都成功的 pass^k（#120）。当任务包含付款、发信、数据修改或发布，偶尔一次正确无法抵消一次严重副作用。#128 的一天级任务也显示，格式、附件、状态和早期小错会随时间累积，长程失败并不总表现为最终答案明显错误。

评测报告至少应同时给出平均成功率、连续成功率、guardrail 违例、恢复时间和人工接管率。对探索型研究任务，best-of-N 仍有价值；对生产自动化，分布尾部与坏案例复发率更重要。两类目标不能共用一个“能力分”。

## 实践工具：评测审计表

在采用公开榜单或内部 eval 前，先完成一张 **评测审计表**：

| 审计面 | 必答问题 |
| --- | --- |
| 任务 | 来源是什么；需求是否足以推出 hidden requirements；时间切分如何做 |
| 环境 | 依赖能否运行；允许访问哪些网络、历史和工具；状态是否持久 |
| 成功 | Objective、Guardrail、质量阈值和失败代价分别是什么 |
| Verifier | 测试覆盖哪些要求；假阳性/假阴性如何抽查；能否被绕过 |
| 系统配置 | 模型、Harness、thinking effort、turn cap、重试与超时 |
| 成本 | token、wall-clock、外部调用、人工复核和失败恢复 |
| 可靠性 | pass@k、pass^k、违例率、接管率与 badcase 复发 |
| 证据边界 | 结果能外推到哪些语言、任务、组织和时间范围 |

没有填清的格子就是结果的不确定性，不应被藏在一个小数点后两位的总分里。

## 什么证据会迫使这套框架修正

1. 若多个公开 Agent benchmark 经独立逐项审计后，任务缺陷、环境噪声和 verifier 漏洞长期低到不足以改变排名，数据点审计的优先级可以下降。
2. 若跨 Harness、预算和工具配置的模型排名高度稳定，且任务总成本差异很小，系统配置可以退回次要报告项。
3. 若 Objective-only 分数能长期预测真实部署的 guardrail 违例、人工接管和业务损失，过程与副作用评测可以简化；当前材料尚未支持这一点。
