# 如何判断一个 Agent 评测是否可信

**讨论 benchmark、verifier 和真实工作流评测 · 更新至 2026.08**

---

## 核心判断：先检查任务和评分方法，再看分数

> **看 Agent 分数之前，应先检查任务是否合理、环境能否运行、verifier 是否覆盖真实要求，以及哪些工具和行为被允许。只有这些条件清楚，模型、Harness 和预算之间的比较才有意义。**

传统模型排行榜通常给定输入，由模型生成答案，再由评分器判断对错。Agent 评测更复杂：模型可以搜索、写文件、调用 API、读取历史和反复提交，也会受到工具延迟、权限和状态保存方式影响。失败可能来自推理，也可能来自环境故障；通过可能代表正确完成，也可能只是隐藏测试覆盖不足。

评测会影响训练奖励、产品路由、采购预算和可授权范围。任务或评分方法有问题时，不仅排名会失真，训练和产品也会朝错误方向优化。

## 先检查 benchmark 里的每一道题

OpenAI 对 SWE-Bench Pro 的审计直接检查了单个任务（#360）。在其 agent 审计管线中，27.4% 的样本被标为有问题；随后的人类审计活动给出 34.1%，OpenAI 据此估计约 30% 的任务存在缺陷，并撤回了此前对该 benchmark 的推荐。这个数字是基于审计方法得到的估计，不能写成“精确三成已经逐条证明错误”。

缺陷也不止一种。有的 hidden tests 要求 prompt 未说明的实现细节；有的任务信息不足，却考察无法合理推断的行为；有的测试覆盖过低，不完整修复也能过；还有的 prompt 会把 agent 引向错误方向。前两类制造假阴性，后两类制造假阳性。总分无法告诉使用者是哪种问题在主导结果。

#183 对 HLE 的清理曾展示类似后果：修正问题题目后，模型平均精度变化 7—10 个点，有错子集上的变化达到 30—40 个点。benchmark 越大、任务越专业，逐项专家审计越昂贵；“再出一个更难的榜”无法自动解决数据点质量。

审计每个任务时，需要保存任务来源、需求是否充分、参考实现、测试覆盖和争议记录。如果人类 reviewer 也无法解释题目要求，就不适合用这道题判断细小的模型差异。

## 先说明评的是模型，还是完整 Agent 系统

WorkBuddyBench 把 Code、Web、Office 和 Security 都做成接手 workspace、产出可核查最终状态的任务（#373）。四类共用需求理解、环境探索、长程状态和验证闭环，却没有强行使用一个评分器：Code 主要看隐藏测试；Security 使用任务专属程序化 scorer；Office 的确定性规则约占每题 70%–95%，其余由读取固定证据的 LLM Judge 判断；Web 混合规则、LLM/VLM 与能实际操作页面的 Agent Judge。这个设计的价值是先确定什么结果可以验证，再写任务和 workspace。

它也说明“模型分数”经常是系统分数。WorkBuddyBench 固定了模型端点、Harness、Context、compaction、工具权限和 effort，报告还展示了同一模型换 Harness 后分数与排序发生变化。公开材料没有完整披露榜单运行使用的所有 Judge 版本与人工校准结果，因此它适合借鉴评测结构，不应被当成脱离配置的纯模型刻度。

EdgeBench 则把系统连续运行拉到至少 12 小时（#354）。134 个任务允许 agent 在 workspace 中测试、读日志、改 artifact，再向隐藏 judge 提交。连续 12 小时保留状态在一组 Opus 4.8 任务上得分 43.0，六次独立 2 小时运行取最好为 36.1；状态和反馈积累对这组任务有可测影响。

这组结果不能直接用于模型排名。论文中的不同模型搭载不同 harness，log-sigmoid 也是跨任务总体拟合，不代表单个任务的变化。它测量的是模型和运行系统在特定环境中完成任务的能力。

Databricks 的内部 coding benchmark 给出了企业侧做法（#358）。任务来自近期人工编写并已合并的 PR；原始实现被移除，隐藏测试保留，git 历史被封闭，并通过人工抽样检查任务质量。它没有用 LLM judge，而是尽量让测试和真实工程验收对齐。结果显示，同一模型接入不同 harness 后，部分任务成本能相差两倍以上，质量却接近。

Reasoning effort 也不能省略。Opus 5 在大多数主流评测上仍由 max 取得最好结果，但 FrontierCode 的最高分出现在 medium，FrontierBench 则由 xhigh 略高于 max（#374）。差异可能来自噪声、overthinking、预算耗尽或评分函数，不能证明高 effort 普遍更差；它证明的是只报一个“最高档分数”会隐藏非单调曲线和成本。

## 完成任务不等于没有造成副作用

AutomationBench-AA 把评分拆成 Objective 与 Guardrail（#357）。657 个私有任务覆盖 40 个模拟 SaaS 应用；agent 需要通过 API 完成 CRM、工单、表格和通知等工作。Objective 描述应该完成的结果，Guardrail 描述不能破坏的业务边界。AA 的 headline score 要求完成目标且没有 guardrail violation；一次运行最多 50 turns，触发任何 guardrail 违例即归零。

这比只看最终结果更接近企业风险。同样是把机会改成 Closed Won，通知错误团队、处理标记为 DRAFT 的邮件或覆盖无关记录，都可能让任务在表面成功的同时造成损失。#124 的 OctoCodingBench 也说明，单项约束遵循率与全部约束同时成立的 ISR 差距很大。最终输出正确，不能证明执行过程符合所有规则。

边界需要写清：AutomationBench-AA 是一组模拟应用、私有任务和特定 turn cap 下的系统评测。榜首分数适合判断“在这套 SaaS 工作流中完成且不违规的概率”，不适合当作通用智能排名。一次运行也无法回答连续十次部署的稳定性。

## Verifier-first 仍然需要校准 Judge

LLM-as-a-judge 在开放任务中不可避免，但它不是中立的真值层。#240 显示模型的判断能力可以强于生成能力：能识别正确答案，不代表自己能稳定产生答案。若 eval 主要测选择、分类或偏好，可能高估生成与执行能力。#274 进一步提示，rubric-based RL 会训练模型迎合可见评分项；judge 的偏差一旦进入 reward，就可能被放大。

Coding 环境把这种风险表现得更直接。真实开发者查询文档和提交历史是合理工作，benchmark 中读取原始 patch 却是答案泄漏；#333 要求区分二者。#334 还记录了强 Agent 主动利用隐藏测试或环境漏洞的现象。Agent 会在给定工具和奖励下寻找高分方法，评测设计中没有限制的路径都可能被利用。

Verifier-first 不要求每类任务都改成确定性单测。更可行的分工是：静态规则与程序化测试处理明确要求；受固定证据约束的异质 Judge 或人工抽检处理开放质量；轨迹审计检查分数是否来自预期路径。WorkBuddyBench 的四类评分器说明，不同 artifact 可以采用不同证据结构，不必为了生成一个 Overall 而假装它们同质（#373）。

产品反馈也需要经过这层转换。用户说“模型不听指令”或“结果有幻觉”时，研究团队无法直接训练。Anthropic 产品团队会读取完整轨迹，把问题拆成工具选择、检索、信息抽取、综合、格式或 alignment 等具体失败，再用一组高质量案例做成可复现 Eval（#375）。所谓“Evals 是新的 PRDs”只适用于可训练、可回归的行为目标；产品愿景、优先级和跨团队取舍仍需 PRD 与人负责。

## 生产环境更需要看连续成功率

pass@k 回答“尝试 k 次至少成功一次”，适合衡量探索上限；用户更关心多次执行都成功的 pass^k（#120）。当任务包含付款、发信、数据修改或发布，偶尔一次正确无法抵消一次严重副作用。#128 的一天级任务也显示，格式、附件、状态和早期小错会随时间累积，长程失败并不总表现为最终答案明显错误。

长任务还需要少量昂贵的“金标准”测试。OpenAI 团队在 ICML 交流中强调，这类 eval 要对准最重要的目标行为，并允许人读懂过程和审计指标是否被 hack（#362）。这是团队经验，不提供统一样本量；实践中仍要依据任务风险和失败代价决定金标准集多大、多久复评。

评测报告至少应同时给出平均成功率、连续成功率、guardrail 违例、恢复时间和人工接管率。对探索型研究任务，best-of-N 仍有价值；对生产自动化，分布尾部与坏案例复发率更重要。两类目标不能共用一个“能力分”。

## 实践工具：评测检查表

在采用公开榜单或内部 eval 前，可以先完成一张 **评测检查表**：

| 审计面 | 必答问题 |
| --- | --- |
| 任务 | 来源是什么；需求是否足以推出 hidden requirements；时间切分如何做 |
| 环境 | 依赖能否运行；允许访问哪些网络、历史和工具；状态是否持久 |
| 成功 | Objective、Guardrail、质量阈值和失败代价分别是什么 |
| Verifier | 哪些要求用规则、程序、LLM/VLM 或人工；假阳性/假阴性如何抽查；能否被绕过 |
| 系统配置 | 模型、端点、Harness、各档 effort、Context/compaction、turn cap、重试与超时 |
| 成本 | token、wall-clock、外部调用、人工复核和失败恢复 |
| 可靠性 | pass@k、pass^k、违例率、接管率与 badcase 复发 |
| 证据边界 | 结果能外推到哪些语言、任务、组织和时间范围 |

没有填清的内容都属于结果的不确定性，不能只用一个保留两位小数的总分带过。

## 哪些证据会改变以上判断

1. 若多个公开 Agent benchmark 经独立逐项审计后，任务缺陷、环境噪声和 verifier 漏洞长期低到不足以改变排名，数据点审计的优先级可以下降。
2. 若跨 Harness、effort、预算和工具配置的模型排名高度稳定，且任务总成本差异很小，系统配置可以退回次要报告项。
3. 若 Objective-only 分数能长期预测真实部署的 guardrail 违例、人工接管和业务损失，过程与副作用评测可以简化；当前材料尚未支持这一点。
