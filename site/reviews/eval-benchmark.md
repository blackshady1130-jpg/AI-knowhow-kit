# 如何判断一个 Agent 评测是否可信

**讨论任务、评分方法与模型选择 · 复核于 2026-10-08**

一份 Agent 评测，应该帮助人作出选择：哪种配置适合这类任务，成功和失败各有什么代价，现有差异是否值得更换系统。榜单可以提供候选，却不能替读者完成这些判断。

我看评测时，通常先弄清它要回答什么问题，再检查题目和评分方法。模型、工具和运行环境的影响很难完全分开，但不能因此只剩下一句“结果取决于很多因素”。需要把这些因素变成可以复查的比较条件。

## 研究模型和采购产品，需要两种比较

如果研究问题是“换一个模型能提高多少”，就应尽量固定工具、上下文、时间预算和评分器，或安排对照实验分离各项影响。这种比较有助于归因，却未必展示每个模型最擅长的用法。

如果采购问题是“哪套产品能在预算内完成工作”，则可以让各家使用合理的最佳配置，再比较交付质量、总成本、延迟和接入难度。对模型 A 最合适的 Harness，未必也适合模型 B。强行统一实现，也可能引入新的偏差。这里的 Harness 指模型外部管理工具、上下文和执行循环的程序。

#423 对六家模型发布材料的审计说明，同名 benchmark 下也可能使用不同工具、重试和预算。固定配置用于研究归因，合理最佳配置用于采购选择；报告需要先说自己回答哪一种问题。

读一行分数时，我希望同时看到模型版本、Harness、任务环境、工具权限、推理投入、停止条件、评分方法与费用。缺少哪项条件，就保留哪项归因的不确定性。

## 先确认题目值得测

OpenAI 对 SWE-Bench Pro 的审计是一个具体例子（#360）。其 Agent 审计管线将 27.4% 的样本标记为存在问题，后续人工审计给出 34.1%。这是基于审计方法的缺陷估计，不能理解为逐题确定无疑的比例；但已经足以提醒使用者，题目数量和测试通过并不保证质量。

隐藏测试要求题目没说的细节，会把合理实现判错；测试覆盖不足，又会让不完整修复过关。HLE-Verified 的研究也报告，修正题目和答案后，模型准确率会明显变化（#183）。模型分数的精确小数，无法消除题目本身的歧义。

检查一个任务，我会先看需求能否推出评分要求，再看环境能否正常运行，最后检查参考答案与隐藏测试是否一致。对公开题目，还要记录时间切分和可能的答案泄漏。正常查询文档、阅读代码，与读取 benchmark 原始补丁是不同的行为（#333），应在规则里事先说清楚。

领域任务常有多种合理答案。只接受一个数字或一种实现的评分器，需要说明为什么其他方案不成立。

#434 对主流 benchmark 的批评中，τ³ 的银行任务提供了一个可核验案例。[官方 1.0.1 changelog](https://github.com/sierra-research/tau2-bench/blob/main/CHANGELOG.md) 说明，旧评分器会把额外的验证性读取记入数据库状态：Agent 完成操作后谨慎地再查一次，可能仅因偏离标准轨迹就被判零分。修复后，重评已有轨迹即可移动分数，无须模型重新执行。官方明确要求该领域的新旧口径不能直接比较。

同次发布还修正了退款标准答案。任务内容修复与单纯评分修复要分别记录；这些逐项修复有明确对象，并不能说明整个综合指数大部分无效。

题目来源也影响独立性。#454 的数据行业访谈描述了出题团队销售相邻训练任务的商业路径，并转述了评测材料被出售的警示；后者没有可核实的具体案例。我的判断是，不必将评测方与数据供应方重合一概视为污染，但必须隔离隐藏题、答案、近似等价题和评分漏洞，记录谁能访问哪些材料、训练与评测版本及素材来源，并检查跨库重复。训练同领域的新任务可以带来真实能力，原题或答案泄漏则会破坏测量；区分两者要看材料和迁移结果，而非只看供应商品牌。

## 环境太干净，也会把分数抬高

Datadog 为 SRE Agent 构建评测时，同时保存事故根因与当时可见信号的“世界快照”（#429）。模型看不到根因标签，只能从指标、日志、调用链和服务关系中查找。历史信号会过期，单纯把同一句问题重新发给线上系统，已经不再是同一场测试。

团队早期只重建与根因相关的信号，后来加入无关服务、背景错误和误导线索，报告通过率下降约 11%，并淘汰了一批过窄的旧标签。原文使用百分比表述，没有足够依据将它改写成 11 个百分点。这是该团队的工程复盘，不能当作所有 Agent 的固定降幅。

这个案例改变的是环境保真度：如果只给正确证据，评测等于替 Agent 完成了筛选工作。业务测试应保留必要干扰，又要隔离不同案例，防止一个任务读到另一个任务的状态。离线成绩下降有时是测量更接近线上，并不一定是系统变差。

## 不同成果，需要不同的评分方法

WorkBuddyBench 按代码、网页、办公文档与安全任务选择不同评分器（#373）。可执行测试适合检查确定性行为，页面操作适合检验交互，开放质量则需要评分标准和人工或模型判断。这种分工比给全部产物套同一个 LLM Judge 更合理。

评分标准，也就是 Rubric，本身仍需校准。#419 综合的不同研究不能拼成一个统一实验，但其提醒有共通之处：要求写得细，仍可能权重失衡或证据不清。先抽取通过、失败和临界样本，让熟悉业务的人检查误判；#375 将“不听指令”拆成检索、抽取、工具选择和格式问题，也是在把模糊不满变成可复测案例。

科学复现尤其不能只看程序跑完。PaperBenchX（#468）分开观察建模、执行与科学验证：模型和参数是否适合问题，软件是否实际运行，结果是否有足够证据支撑指定结论。独立重跑先移除旧输出和临时状态，再检查新生成的日志、原始产物、收敛记录及派生指标；可计算属性由程序检查，领域解释仍依赖校准过的规则与裁判。漂亮图表或 Agent 自称成功，都不能代替这条证据链。

其 Full 口径是任务加权得分严格超过 90%，复现范围是指定关键实验，有些只是论文子问题，不能写成整篇论文完全验证。93 项任务中仅 12 项公开、81 项封闭，外部读者无法仅凭公开任务独立核验完整榜单；某一验证环节的得分也不是整项任务的成功率。这个案例有价值的地方是把“完成了哪些步骤”和“证明了什么”分开，而不是凭一个总分宣布通用科学家已经成熟。

候选 Agent 还不应能读取保留测试答案，或自行修改决定成败的验证器（#334）。评分方与参测方的访问权限要分开；修复评分器后保留版本，重新跑必要基线。

AutomationBench-AA 的目标与 guardrail 分开评分有实际价值（#357）：更新正确记录，却越权发出通知，仍不能算合格。但“一票否决”越重要，越要核对触发器的业务语义。#448 中 Wenhao Chai 审查了 600 道公开题的 v1.0.5 rollout，认为其中 18 条字符串匹配 guardrail 不合理：拒绝续约的邮件出现 renew，也可能被判为续约违规。在 AA 的 Score 规则下，任一 guardrail 触发都会清零该题的目标得分，误报因此会从一项判断错误放大为整题归零。

这项审计使用公开运行记录，不是对 v1.0.6、657 道私有题榜单的重评，不能据此解释私有榜单的排名。它要求复查的是“禁止动作”如何被写成判定条件：检查最终状态、政策与具体表达，再重评受影响轨迹。真实的严重违规仍应作为硬否决项；修正误报不等于把安全约束改成可由平均分抵消的扣分。

开放成果的局部指标适合定位问题。Manus 的 Research Bench（#432）发现搜索更多却输出更少信息，沿轨迹定位到中间笔记过早删细节，修改后信息量改善。这支持复测笔记行为，不证明事实点越多质量越高；仍须查来源、相关性与重复，也不能把隐喻率低当作好文章的充分条件。

开放评价中的分歧也未必都是噪声。同一回答都得 6 分，与一半人给 2 分、一半给 10 分，均值相同却代表不同偏好。DRM（#461）的[当前 v2](https://arxiv.org/html/2609.33803)用奖励分布做了选择性预测与分布排序实验；但下游 PPO 把 32 次奖励样本和 19 个维度平均成标量，不能称已证明按人群偏好训练。奖励方差不等于事实置信度或危险程度，低方差也可能是稳定误判。这里需要区分真实偏好分歧、评分器错误和采样不足，再决定复核或保留哪些评价维度。

## 沿轨迹找线索，再用实验确认原因

最终答案错误，只能说明结果不合格。#395 提出沿执行轨迹寻找最早的不可恢复错误，再区分模型、Harness、工具、环境和评分器的问题。这比只记录 success 或 failure 更接近修复工作，但它首先是一套描述性分类。

例如，模型忽略了早期要求。如果上下文压缩把要求删掉了，可以优先检查压缩策略；如果要求仍在，也不能马上断言只需训练模型。信息位置、冲突指令、工具描述和材料组织都可能影响它是否被使用。

下一步应该做重放和对照：补回被删信息，改变信息位置，修正工具回执，或在同样输入下更换模型。每次只改变尽可能少的条件，观察错误是否复发。轨迹提供诊断线索，对照实验才进一步支持因果判断。

该论文的验证集只有 40 个案例，最强 Judge 对类别标签的一致性 κ 为 0.76；四个 Judge 全部一致时，precision 达到 0.96，但覆盖率只有 68%。这些条件意味着，高置信样本可以辅助分流，其余仍需复核。不能把选择后的精度当作全部生产故障的自动诊断准确率。

视觉任务还要分清新增证据与多想几步。HSS（#469）的完整集有 522 项日常视觉推断任务；帧数和语言推理投入是分别考察的维度，视频补帧能帮助找到短暂线索。Harness 则在另一个 388 题配对子集上比较，不能与完整集总榜混用；不同配置额外消耗的推理预算，也不能忽略。

工具检查是否对准不确定性，比调用次数更重要。HSS 的灯泡案例里，Agent 裁剪、测像素、画垂线，把二维重叠算得更精确，却误当成三维对齐，推翻了原先正确答案。深度信息缺失时，重复测二维坐标不是独立验证。读这类评测，我会先问改善来自看到新证据、找对关键帧，还是改变推理策略，再比较质量与成本；不能把结果简化成“多工具更可靠”或“模型没有直觉”。

## 重复做对，与长期不出错还有距离

AA-AnalystAgent 在 80 道分析任务上，对每道题独立运行五次，并报告 pass@1、pass@5 和 pass^5（#399）。它们分别回答单次能否成功、多次尝试能否至少成功一次、以及五次是否全部成功。

这个区分对需要稳定交付的任务很有用：多试几次终于得到正确答案，与每次都能得到可靠结果，节省的人工成本并不相同。但 pass^5 衡量的是同题重复运行的一致成功，不等于一个系统在真实工作中连续五天没有事故。跨任务依赖、环境漂移和相关性错误，需要另外测试。

VibeLifeBench 将任务放在持续变化的模拟世界中，要求 Agent 重新检查价格、消息与早期承诺（#410）。它的 200 个任务中位持续 29 个模拟日，提供了另一类观察角度，但模拟世界仍不能替代真实部署。

可靠性报告还要保留副作用与恢复负担。同题连续成功、动态世界中的持续履约，以及不发生严重越权，回答的是不同问题，适合并列展示。

## 差两分，是否值得换系统

模型 A 比模型 B 高两分，至少还要问：多少题，重复几次，差异集中在哪里？如果优势主要来自少数题、评分争议或一次幸运运行，换模型的依据就很弱。必要时应报告置信区间，并对相同任务做配对比较；重复运行也不能被简单当作完全独立的新题目来扩大样本量。

这里要分开随机误差和系统偏差。前者来自抽题、采样与运行波动，多次重复和置信区间能帮助描述；后者可能来自错误答案、评分器偏好或过于干净的环境，重复一百次也可能稳定地测错。窄置信区间只表明在当前测量规则下结果较稳定，不能替代对规则本身的审计。先修正明确偏差，再讨论小幅领先是否可靠，才有比较意义。

总分接近时，任务结构可能比排名更重要。一个模型擅长复杂代码修改，另一个在大量配置任务上更便宜。Databricks 的内部评测就将近期真实 PR 用于比较配置与成本（#358）。这类结果适合启发本地试验，不适合不经验证地照搬采购名单。

我会把选择记录压缩成下面这张表，而不是只保存总分：

| 决策项 | 要保留的证据 |
| --- | --- |
| 比较对象 | 比模型还是完整产品；哪些配置相同、哪些不同 |
| 效果差异 | 同题结果、任务分层、样本量、重复次数与不确定性 |
| 失败后果 | 严重副作用、漏检、恢复时间与人工复核负担 |
| 全部成本 | 调用、工具、重试、审核，以及接入和迁移成本 |
| 采用条件 | 哪类任务先切换；什么结果会让团队暂停或退回 |

小范围试用的价值，在于把公开评测中的优势放回自己的任务分布。只有收益超过接入、复核和维护代价，更换系统才有意义。评测应当帮助团队减少错误决策，而不是让报告看起来更完整。
