# 如何判断一个 Agent 评测是否可信

**讨论任务、评分方法与模型选择 · 复核于 2026-09-05**

一份 Agent 评测，应该帮助人作出选择：哪种配置适合这类任务，成功和失败各有什么代价，现有差异是否值得更换系统。榜单可以提供候选，却不能替读者完成这些判断。

我看评测时，通常先弄清它要回答什么问题，再检查题目和评分方法。模型、工具和运行环境的影响很难完全分开，但不能因此只剩下一句“结果取决于很多因素”。需要把这些因素变成可以复查的比较条件。

## 研究模型和采购产品，需要两种比较

如果研究问题是“换一个模型能提高多少”，就应尽量固定工具、上下文、时间预算和评分器，或安排对照实验分离各项影响。这种比较有助于归因，却未必展示每个模型最擅长的用法。

如果采购问题是“哪套产品能在预算内完成工作”，则可以让各家使用合理的最佳配置，再比较交付质量、总成本、延迟和接入难度。对模型 A 最合适的 Harness，未必也适合模型 B。强行统一实现，也可能引入新的偏差。这里的 Harness 指模型外部管理工具、上下文和执行循环的程序。

#423 对六家模型发布材料的审计说明，同名 benchmark 下也可能使用不同工具、重试和预算。两种比较都可以有价值，前提是不要把完整系统的优势写成模型本身的优势，也不要将固定配置下的结果直接当作采购结论。

读一行分数时，我希望同时看到模型版本、Harness、任务环境、工具权限、推理投入、停止条件、评分方法与费用。并非每份报告都必须公开全部内部实现，但缺失了哪些条件，就要承认哪些比较仍不确定。

## 先确认题目值得测

OpenAI 对 SWE-Bench Pro 的审计是一个具体例子（#360）。其 Agent 审计管线将 27.4% 的样本标记为存在问题，后续人工审计给出 34.1%。这是基于审计方法的缺陷估计，不能理解为逐题确定无疑的比例；但已经足以提醒使用者，题目数量和测试通过并不保证质量。

隐藏测试要求题目没说的细节，会把合理实现判错；测试覆盖不足，又会让不完整修复过关。HLE-Verified 的研究也报告，修正题目和答案后，模型准确率会明显变化（#183）。模型分数的精确小数，无法消除题目本身的歧义。

检查一个任务，我会先看需求能否推出评分要求，再看环境能否正常运行，最后检查参考答案与隐藏测试是否一致。对公开题目，还要记录时间切分和可能的答案泄漏。正常查询文档、阅读代码，与读取 benchmark 原始补丁是不同的行为（#333），应在规则里事先说清楚。

领域任务还可能存在多种合理答案。如果评测只接受一个数字或一种实现，需要解释为什么其他方案不成立。否则，严苛的判分只是把争议藏进了参考答案。

## 不同成果，需要不同的评分方法

WorkBuddyBench 按代码、网页、办公文档与安全任务选择不同评分器（#373）。可执行测试适合检查确定性行为，页面操作适合检验交互，开放质量则需要评分标准和人工或模型判断。这种分工比给全部产物套同一个 LLM Judge 更合理。

评分标准，也就是 Rubric，本身仍需校准。#419 对 RubricBench 与 PaperBench 的解读提醒，要求写得细不代表没有遗漏：权重可能失衡，证据范围可能不清楚，评分器也可能奖励表面完整而忽视实质错误。该 Note 综合了不同研究，不能把其中数字拼成一个统一实验。

校准不必一开始就做得很庞大。可以先抽取通过、失败和临界样本，由熟悉业务的人独立检查，找出误判和争议最大的要求，再调整评分。#375 中 Anthropic 产品团队将“不听指令”等反馈拆成检索、抽取、工具选择和格式问题，价值就在于让模糊不满变成可以重复验证的案例。

同时要防止系统利用评分漏洞。候选 Agent 不应能读取保留测试答案，或自行修改决定成败的验证器（#334）。修复评分器后，旧分数也可能失去可比性，应保留版本并重新跑必要的基线。

## 沿轨迹找线索，再用实验确认原因

最终答案错误，只能说明结果不合格。#395 提出沿执行轨迹寻找最早的不可恢复错误，再区分模型、Harness、工具、环境和评分器的问题。这比只记录 success 或 failure 更接近修复工作，但它首先是一套描述性分类。

例如，模型忽略了早期要求。如果上下文压缩把要求删掉了，可以优先检查压缩策略；如果要求仍在，也不能马上断言只需训练模型。信息位置、冲突指令、工具描述和材料组织都可能影响它是否被使用。

下一步应该做重放和对照：补回被删信息，改变信息位置，修正工具回执，或在同样输入下更换模型。每次只改变尽可能少的条件，观察错误是否复发。轨迹提供诊断线索，对照实验才进一步支持因果判断。

该论文的验证集只有 40 个案例，最强 Judge 对类别标签的一致性 κ 为 0.76；四个 Judge 全部一致时，precision 达到 0.96，但覆盖率只有 68%。这些条件意味着，高置信样本可以辅助分流，其余仍需复核。不能把选择后的精度当作全部生产故障的自动诊断准确率。

## 重复做对，与长期不出错还有距离

AA-AnalystAgent 在 80 道分析任务上，对每道题独立运行五次，并报告 pass@1、pass@5 和 pass^5（#399）。它们分别回答单次能否成功、多次尝试能否至少成功一次、以及五次是否全部成功。

这个区分对需要稳定交付的任务很有用：多试几次终于得到正确答案，与每次都能得到可靠结果，节省的人工成本并不相同。但 pass^5 衡量的是同题重复运行的一致成功，不等于一个系统在真实工作中连续五天没有事故。跨任务依赖、环境漂移和相关性错误，需要另外测试。

VibeLifeBench 将任务放在持续变化的模拟世界中，要求 Agent 重新检查价格、消息与早期承诺（#410）。它的 200 个任务中位持续 29 个模拟日，提供了另一类观察角度，但模拟世界仍不能替代真实部署。

任务做对，也不代表没有造成其他损失。AutomationBench-AA 将任务目标与禁止发生的副作用分开评分（#357）：更新了正确记录，却误发通知，仍有问题。可靠性报告需要保留这两类结果，不能用一个平均分抵消严重的越界操作。

## 差两分，是否值得换系统

模型 A 比模型 B 高两分，至少还要问：多少题，重复几次，差异集中在哪里？如果优势主要来自少数题、评分争议或一次幸运运行，换模型的依据就很弱。必要时应报告置信区间，并对相同任务做配对比较；重复运行也不能被简单当作完全独立的新题目来扩大样本量。

总分接近时，任务结构可能比排名更重要。一个模型擅长复杂代码修改，另一个在大量配置任务上更便宜。Databricks 的内部评测就将近期真实 PR 用于比较配置与成本（#358）。这类结果适合启发本地试验，不适合不经验证地照搬采购名单。

我会把选择记录压缩成下面这张表，而不是只保存总分：

| 决策项 | 要保留的证据 |
| --- | --- |
| 比较对象 | 比模型还是完整产品；哪些配置相同、哪些不同 |
| 效果差异 | 同题结果、任务分层、样本量、重复次数与不确定性 |
| 失败后果 | 严重副作用、漏检、恢复时间与人工复核负担 |
| 全部成本 | 调用、工具、重试、审核，以及接入和迁移成本 |
| 采用条件 | 哪类任务先切换；什么结果会让团队暂停或退回 |

小范围试用的价值，在于把公开评测中的优势放回自己的任务分布。只有收益超过接入、复核和维护代价，更换系统才有意义。评测应当帮助团队减少错误决策，而不是让报告看起来更完整。
