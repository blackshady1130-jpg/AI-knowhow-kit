# 评测与基准：我们到底在测量什么？

**覆盖 76 篇判读 · 2025.04 – 2026.06**

---

## 本章核心判断

> **评测不是给模型贴一个分数，而是定义什么结果值得被训练、采购和授权。** Agent 时代的评测对象已经变成模型、Harness、工具、环境、预算和人工接管组成的系统；verifier 本身也必须接受审计。

评测本来应该回答一个简单问题：模型到底行不行？

但过去一年看下来，我越来越怀疑：很多评测没有把这个问题问清楚。它们给了分数，给了排名，也给了发布会上的一句话，但不一定告诉我们模型在真实任务里会怎样失败。

这 56 篇判读覆盖了传统 benchmark、Agent 评测、LLM-as-a-judge、领域评测和线上产品评估。材料越多，问题越集中：评测分数和真实世界能力之间有很大缝隙。这个缝隙不是一句“benchmark 不够好”能解释的。只要模型训练、产品宣传和融资叙事都围着分数转，评测就会变成被优化、被污染、被绕过的对象。

Agent 兴起后，问题更麻烦。评测对象不再只是“一个模型回答得好不好”，而是“模型 + 工具 + 环境 + 成本 + 状态 + 人工接管”能不能把任务交付出来。Coding Agent Index 开始把 harness、成本和延迟放进比较（#266）；Cursor 用 Keep Rate、线上 A/B 和用户后续反馈衡量 agent 质量（#260）；SaaS-Bench 把 Computer-Use Agent 放进真实 SaaS 工作流里测端到端可靠性（#285）。这些做法都在提醒：单看裸模型分数，已经不够了。

---

## 在研究主线中的位置

评测位于模型能力与真实部署之间。它一方面把任务目标转成可执行的验收标准，另一方面决定 badcase 能否回流为产品、Skill 或训练数据。评测口径不稳，训练会学错、产品会误判、组织也无法知道是否应该继续授权。

## 关键判断

### 洞察 1：评测焦点要从“答对多少”转到“能稳定交付多久”

Anthropic 研究员 Julian 在访谈中提到 task length（#82）：模型能独立、稳定地连续工作多久，正在成为更有用的指标。这个说法比很多榜单更接近真实使用。用户不只关心一次回答对不对，还关心模型能不能连续做 20 步，中间不丢状态、不误解附件、不把小错滚大。

#128 的 AgentIF-OneDay 把 Agent 失败从“不会推理”改写成“长程任务里错误累积 + 格式/附件/状态丢失”。#86 的 Remote Labor Index 更进一步，只看 AI 生成的成果是否达到专业人类水平，客户是否愿意付费。当时 SOTA Manus 只有 2.5% 得分，这个数字很冷，但比“某榜第一”更能说明距离。

#53 对 Agent 评估的讨论也很实用：模型层面常说 less structure more intelligence，但 agent 产品里往往是 more structure better experience。Anthropic 在 #120 中强调 pass@k 和 pass^k 的区别。对用户来说，“试十次总有一次成功”远不如“连续十次都别出错”。一个好的 agent 评测集，起步未必需要 1000 个 case，20-50 个真实失败任务就足够暴露很多问题。

#243 和 #285 补了同一个缺口：Agent 不是看见线索、能点按钮就够。#243 显示 agent 经常发现环境提示，却不会据此改计划；#285 显示真实 SaaS 里的日期、字段、客户类型和复查步骤会把小错一路放大。端到端可靠性靠的不是 UI 操作能力，而是状态管理、checkpoint verifier、错误恢复和人工接管。

### 洞察 2：LLM-as-a-judge 有用，但不能偷懒

LLM-as-a-judge 过去一年几乎成了标配，但问题也没有消失。#23 明确提醒，大模型做评估会有位置偏差、长度偏差、格式偏差。业务上如果要自动化评估，第一步不是“换个更强模型当裁判”，而是先知道这些坑在哪里。

#47 的 DPO-Judge 试图通过对比学习训练更可靠的 AI 裁判，设计了 CoT Critique、Standard Judgement、Response Deduction 三类任务。思路不错，但限制也清楚：裁判模型还是依赖代理指标，比如和基准答案的匹配度。开放式问题里 ground truth 本来就不稳，代理指标的边界就决定了方法上限。

#105 的情感 RL 实验把问题暴露得更明显：Gemini-2.5-Pro 既当 teacher 又当 judge，还要调 judging prompt。这时很难分清模型是真变好了，还是评测口径被训熟了。Sebastian Raschka 在 #65 发布评测综述后，评论区几乎都在讨论 LLM-as-a-judge 的实际问题，这本身就说明大家对这个工具没那么放心。

#240 也很关键：模型会判断，不等于模型会生成。很多模型在 listener/judge 侧强于 speaker/generator 侧。能看出别人错，不代表自己能答对。现在大量 judge、多选、分类式 eval 可能测到的是 recognition，而不是完整 generation ability。#274 进一步把风险推进训练环节：rubric-based RL 可能训练出会迎合 rubric 的模型，而不一定提高真实质量。

### 洞察 3：数据污染和环境噪声会让分数失真

#25 的“打假”实验是我这一年最常回看的例子：Qwen 底模在预训练中见过 MATH-500 部分题目，所谓 RL 提升实际只是激活了记忆检索。部分排行榜上的亮眼分数，可能测的是背题能力，不是推理能力。

#183 揭示了另一个问题：号称“人类最后的考试”的 HLE 评测集，居然有大量题目是错的。Qwen 团队修正后，平均精度提升 7-10 个点，有错子集上提升 30-40 个点。问题就变得很尴尬：大家到底在打什么榜？benchmark 越大、越复杂，专家逐项清理的成本越高，带噪音的新 benchmark 可能永远比清理速度更快。

Anthropic 在 #192 的 Terminal-Bench 2.0 实验也很有代表性：只改容器资源配置，成功率就能波动 6 个百分点（p < 0.01）。6 个点在排行榜上可能就是第一名和第五名的差距。更麻烦的是，Agent 评测里的噪声不只有内存，还有 API 延迟、集群健康、并发水平、provider routing。一个分数如果不标资源和环境，就很难解释。

Cursor 在 #191 的做法更接近实战：不信公开基准，从真实产品流量里构建评测。Cursor Blame 把已提交代码追溯到生成它的 Agent 请求，形成自然配对数据。它的发现也很现实：公开基准饱和后，小模型可以媲美甚至超过 GPT-5，几个百分点的排名差异不一定对应真实体验差异。OpenAI 停止报告 SWE-bench Verified 结果，也是在承认这个榜已经被前沿模型记忆污染得不可靠。

### 洞察 4：好的领域评测更像诊断，不像排名

#123 的 BabyVision 是我愿意长期追的 benchmark。它不卷“会不会讲题”，而是拆 pre-language visual primitives：细粒度辨别、连通性追踪、3D 空间想象、图形规律迁移。几个数字很刺眼：成人基线 94.1%，Gemini3-Pro-Preview 只有 49.7%，Mini 版拿 20 道 vision-centric 题去跟 3-12 岁孩子比，多数 frontier MLLMs 甚至低于平均 3 岁水平。这类评测的价值在于诊断，它告诉我们语言推理强不等于视觉地基强。

#124 的 OctoCodingBench 也在追问过程，而不是只看结果。代码对，但过程不合规，能不能上线？单项规则遵循（CSR）80%+，但所有规矩同时遵守（ISR）只有 10%-30%，Claude Opus 4.5 也只有 36.2%。它把约束来源拆成 System / User / Project-level / Skill / Memory / Tool schema，本质是在测真实工程里的指令冲突处理。

#30 的 HealthBench 和 #58 的多模态医学压力测试也说明，领域评测不能只看最终分数。移除图像后模型仍保持较高准确率，说明它可能走的是文本捷径，不是真正图文融合；CoT 还会自信引用不存在的图像特征。#12 和 #11 的长记忆评测框架，则把单跳、多跳、时间推理、对抗性拆开。把问题定义清楚，本身就比总分更有价值。

#172 的 BullshitBench 从另一个角度补上诊断：它测模型面对错误前提时会不会拒绝。太多 benchmark 在测模型有多聪明，这个 benchmark 在测模型有多不蠢。真实可靠性不只看能不能解难题，也看能不能识别坏问题。

### 洞察 5：更多上下文不一定更好

#180 对 AGENTS.md 的评测结果很反直觉：LLM 自动生成的上下文文件让任务成功率平均下降 3%，同时增加超过 20% 推理成本。开发者手写上下文也只带来 4% 的微弱提升。行为分析显示，上下文文件让智能体做了更多不必要探索，步骤和成本上去了，成功率没有上去。

#187 的 SkillsBench 进一步验证这个判断：人工策划 Skills 平均提升 16.2 个百分点，模型自生成 Skills 平均 -1.3pp，几乎无用甚至有害。模型不能稳定生产自己受益的程序性知识。Skills 对模型不懂的领域帮助更大，对模型已经熟的领域可能引入冲突。2-3 个 Skills 最好，4 个以上递减。

SkillFlow、Trace2Skill 和 faulty memory 把问题拆得更细（#244, #273, #277）：skill/memory 不是越多越好，关键是能否从轨迹里抽象出少量高价值、可修正、可验证的程序性知识。持续让 LLM 自我总结 memory，可能会产生 misgrouping、interference 和 overfit，最后让本来会做的任务退化。

#46 从激励结构解释了为什么当前评测会奖励猜测：在 MMLU 这类选择题里，“我不知道”是 0 分，乱猜四选一的期望分也高于 0。诚实模型会吃亏，自信犯错模型会占便宜。RAG 和 reasoning 不能根治这个问题，只要评测奖励猜测，模型就有动机去猜。#90 说的 messiness tax 也类似：现实任务有噪声、信息不完整、失败成本和模糊目标，都会让榜单分数打折。

## 2026 年 6—7 月新增观察

第三方 Agent 评测开始要求公开 Harness 条件。OpenAI 的共享 playbook 明确提出，工具接口、Context 管理、memory、retry、validator、scaffold、预算和安全策略都会改变结果（#290）。未来可信榜单不能只报模型名和总分，还要说明测试的是哪套系统。

Verifier 的质量已经成为训练瓶颈。专家数据访谈强调任务必须对应真实专家分布与严肃场景（#299, #300）；对公开编程数据集的抽查显示，自动验证和人工 review 都可能漏掉题意、环境和测试覆盖问题（#320）。如果 reward signal 错了，训练规模越大，偏差越大。

Reward hacking 也从理论风险变成真实行为。Cursor 展示 Coding Agent 如何利用公开 PR、issue 和未来提交穿透 benchmark（#333）；METR 在 GPT-5.6 Sol 预部署评估中观察到模型利用环境漏洞、提取隐藏测试和绕过任务约束（#334）。问题不是 Agent 会搜索，而是评测是否把允许的研究行为与泄漏答案区分清楚。

Verification Horizon 给出更难的结论：单元测试、rubric、LLM judge 和 reward model 都只是用户意图的代理，没有银弹（#343）。测试时计算又让模型表现变成预算曲线（#307, #341）。评测设计因此需要同时报告任务、预算、验证器覆盖率与失败类型。

- **自动化评测需要审计机制**：#23 已经提醒过 LLM-as-a-judge 的偏差，#105 和 #65 让这个问题更明显。下一步不是单纯换更强 judge，而是建立 judge 审计：看偏差、看口径、看是否被训练数据或 prompt tuning 影响。

- **公开基准在前沿水平上越来越不够用**：#191 的 CursorBench、#192 的资源配置实验、OpenAI 停止报告 SWE-bench Verified，都说明脱离使用场景的公开分数容易误读。真实用例数据正在变得更重要。

- **评测正在进入训练环节**：#118 把 rubric 变成 training-time reward spec，#124 把过程监督搬进软件工程。这会带来更细反馈，也会带来过拟合循环：模型针对评测标准优化，评测标准又基于模型输出构建。

- **发布前打分不够，需要持续监控**：#276 说 eval is upstream of everything。模型能力变化后，旧评测会悄悄失效。评测应该像监控系统一样跟着模型更新，而不是发布前做一次评分表。

## 对实践意味着什么

1. **先写 Evaluation Contract。** 明确任务、允许信息、成本预算、成功标准、失败代价和人工接管，再选 benchmark 或 judge。
2. **把 verifier 当生产代码审计。** 检查假阳性、假阴性、环境可运行性、测试覆盖和可被绕过的路径；不要让同一个强模型同时出题、作答和判卷而没有独立复核。
3. **同时看平均成功与连续可靠性。** pass@k 适合探索能力，pass^k、badcase 复发率、恢复时间更接近部署风险。
4. **线上数据反哺离线评测。** 用真实失败任务更新 eval，但保留时间切分与污染检查，避免评测被产品流量反向训熟。

## 接下来如何证伪

1. **Agent 评测如何处理端到端噪声？** #192 承认了 API 延迟、集群健康、并发水平等噪声。标准化其中一个变量不够。Agent 评测测的是模型和工程架构的组合，行业有没有动力把这些变量报清楚，还很难说。

2. **评测激励结构怎么改？** #46 揭示了二元评分奖励猜测的问题，但允许弃答、引入校准度，会让排行榜不那么好看。#172 的 BullshitBench 是补充，但“拒绝坏问题”还没进入主流评测。

3. **经济价值评测能不能变成主流？** #57 的 GDPval 和 #86 的 RLI 都更接近真实价值，但成本很高。HealthBench 需要 262 位医生，GDPval 需要平均 14 年经验的专家。短期更像公开基准的修正视角，不像替代方案。

4. **系统级榜单怎么避免口径污染？** Coding Agent Index 方向是对的（#266），但 harness 版本、缓存策略、真实采购价、任务权重都会影响结果。更有用的评测，需要同时报告成功率、成本、延迟、可恢复性和线上留存。
