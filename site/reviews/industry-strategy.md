# 模型降价之后，AI 企业靠什么赚钱

**讨论模型商业化、云、路由、数据服务、FDE 和企业部署 · 更新至 2026.08**

---

## 核心判断：不要把使用量当成商业结果

> **AI 市场可以同时出现用户增长、Token 增长和价格下降，但这些变化不保证任何一层都能留下利润。判断一门生意是否成立，要看谁承担算力与交付成本，谁能证明任务完成，谁掌握失败与修正形成的学习资产。**

今天谈 AI 商业化，最容易混在一起的是五本账：有多少人开通或试用；模型处理了多少 Token；企业确认了多少收入；扣除推理与交付之后还剩多少毛利；客户最终接受了多少有价值的工作。五个数字可能一起上升，也可能彼此背离。

一家企业给全员开通 Copilot，说明 AI 获得了入口；月活提高，说明有人使用；调用量增长，说明计算需求增加。只有当具体流程的周期、质量、成本或收入发生可验证的改善时，商业价值才开始兑现。#397 对企业 AI “普及率”的质疑正是这个意思：从偶尔润色邮件到重构完整业务流程，都可能被统计为 adoption。它是对指标口径的提醒，不等于企业 AI 没有价值。

因此，行业分析不能从“需求很旺”直接跳到“这家公司会赚钱”。需要逐层回答：需求落在哪种任务上，结果怎样验收，推理和人工费用由谁支付，客户变大后会不会迁走，服务过程中产生的 Eval、流程和纠错经验归谁。

## Token 越多，毛利不一定越高

硅基流动的招股书提供了一个可观察的独立 MaaS 样本（#366）。按其披露，2025 年收入从 735 万元增至 5533 万元，整体毛利率从 39.4% 降至 -24%。其中公有云服务收入 2926 万元、直接成本 6408 万元，毛利率为 -119%；本地部署收入 2607 万元，毛利率为 82.5%。公司当年另投入 5421 万元推广算力，用于免费 Token 和代金券。

这些数字只代表这家公司在该年度和该业务结构下的经营结果，不能推导出“所有 MaaS 都会亏损”。它们说明的机制更有限也更有用：公有云平台需要预先准备容量、保障服务稳定，又常以低价和补贴获客；如果利用率、议价能力和客户付费跟不上，新增调用会同时增加收入与亏损。本地部署的资源承担方式、合同金额和交付内容不同，因此不能把两类毛利直接当成同一种产品的优劣对比。

重推理、视频和多 Agent 应用也面对类似约束。传统 SaaS 增加一次使用的边际成本很低，AI 产品却可能随着使用加深而增加模型调用、重试、工具执行和人工支持。若订阅价格低于重度用户的满额成本，产品只能依赖用户不把额度用完，或者通过降档、限额和积分控制消耗（#383）。核算时应从一个被接受的任务出发，把缓存、重试、工具、审核和返工全部计入，而不能停在“每百万 Token 价格”。

这也解释了为什么规模指标必须和单位经济放在一起看。Token 可以证明系统被调用，却不能证明调用产生了客户愿意持续付费的结果；收入可以增长，却可能来自补贴、低毛利转售或高强度驻场。只有 accepted task 的价值、交付成本与留存能对上，使用量才开始成为生意。

## 算力生意的关键是稳定需求和利用率

算力讨论里常被混淆的还有三件事：数据中心和 GPU 资产属于谁，未来一段时间的使用权由谁锁定，最后运行的是谁的模型。#421 对相关播客观点的评论指出，云厂商建设并运营的集群，即使主要服务某个模型，也不等于模型公司拥有底层资产。头部实验室更可能集中的是稀缺容量的使用权和模型需求，而不是所有算力资产本身。

同样，把一组新 GPU 接入开源 Serving 框架，再挂到聚合平台，并不等于获得稳定利润。服务商还要解决利用率、批处理与缓存、容量冗余、故障恢复、客户结构和长期采购。卡在满载时存在毛利空间，不代表全天能保持高负载；一次模型走红带来的调用，也不代表客户愿意签长期合同。许多云项目需要先取得客户承诺再融资建设，恰好说明稳定需求比“能把模型跑起来”更稀缺。

芯片指标也需要从实际请求倒推。#424 讨论推理芯片时提出，对小 Batch、长依赖链的 LLM Decode，只看 Peak FLOPS 可能高估真实效率；请求延迟、单次请求能耗以及二者的取舍更接近服务目标。这个判断来自对特定推理 workload 与芯片设计的分析，不能直接推出某种芯片或公司的投资结论。对 MaaS 更实际的含义是：采购算力时要同时看每个请求的成本、延迟、能耗和可用率，而不是把峰值算力乘以单价就当作产能。

未来完全可能同时出现几件事：普通 Token 继续降价，高利用率的大集群仍然稀缺，最强模型在部分任务保留溢价，提供算力的公司却因利用率不足而亏损。Dwarkesh 关于“算力可能更贵”的文章是一个基于需求增长快于供给的条件推演（#378），不是价格预测；Andrew Ho 则提醒，算力价值上升也不保证前沿实验室股东获得同等回报，因为训练下一代模型可能成为持续的竞争性资本开支（#379）。社会获得的 AI 价值、基础设施收入和实验室自由现金流，本来就是三笔不同的账。

## 路由平台必须持续创造决策价值

OpenRouter 证明，模型和推理供应商快速增加时，开发者需要统一入口来测试模型、比较 provider 的价格与吞吐，并在故障时切换（#367）。但“路由”不是一种单一能力：为任务选模型、为同一模型选 provider、在 Agent 内安排子任务、管理企业权限与数据，依赖的信息完全不同。

provider routing 的优势来自跨供应商的价格、可用率和数据政策；任务 routing 则需要知道代码是否通过测试、工单是否解决、销售线索是否转化。这些结果通常留在应用、企业流程和自己的 Eval 中。谁更接近最终验收，谁才更有机会学会“哪种配置适合哪类任务”。路由层若看不到任务结果，容易退化为采购和故障切换工具。

平台还要面对客户“毕业”。小团队愿意支付平台费来换取接入便利；模型支出变大后，稳定、高频的流量可能迁往直连或自建，只把新模型测试、峰值容量和故障 fallback 留在平台（#367）。具体迁移点因客户而异，真正的商业检验是：平台节省的持续决策成本，能否长期高于它收取的费用。仅靠第一次接入省事，很难形成大型客户的永久壁垒。

## 开放模型拿到 Token，不等于拿到最多收入

开放模型降低了企业拥有、修改和私有部署模型的门槛，也让更多团队能做蒸馏、微调和专项优化。它们会压低通用 API 的价格，但不会自动消除闭源模型和服务平台的价值。企业采购还要考虑峰值能力、稳定供给、版本维护、合规和责任归属；开放权重本身也不负责显存、调度、升级与线上故障。

Fireworks 联合创始人在访谈中称，平台每天处理超过 40 万亿 Token，其中 95% 以上来自基于客户专有数据、面向特定任务优化的模型（#406）。这是公司在访谈中的披露，统计口径未经独立核验，也不能和其他实验室的 Token 数直接横比。更值得观察的是它所描述的结构：开放模型可能取得更大的 Token run rate，闭源模型仍凭峰值能力、产品入口与企业采购获得更多收入和利润，两者可以同时发生。

这意味着“开源会赢”必须拆成更具体的问题：赢得下载、部署、Token、收入，还是利润？如果开放模型承接大量低价、可替换的推理，而闭源模型只在关键判断节点被调用，二者的使用量和价值分成会走向不同方向。DeepSeek 把护城河放在成本、迭代速度和全栈效率，而非权重保密（#376），也说明权重开放之后，服务质量与系统效率仍然可以竞争。不过，如果真实任务、企业权限、Eval 和反馈长期沉淀在别的平台，模型团队可能拥有强模型，却不掌握最接近客户工作的学习资产。

## 数据公司的产品正在从 Dataset 转向 Training Signal

模型能力变化加快后，一次性交付的数据集更容易贬值。#389 对数据行业的分析认为，客户需要的正在从“更多样本”转向持续发现模型缺什么，并把真实任务加工成可训练、可验证的信号。这个判断更适合描述行业方向，不能证明所有数据公司都已经完成转型。

真实工作记录也不会自动变成好数据。一个项目最终成功，不代表中间每个动作都正确；一次人工修改，也可能只是个人偏好。数据服务的难点逐渐转向：补全任务意图，挑出有代表性的失败，设计 Verifier，处理 credit assignment，识别 Reward Hacking，再做质量控制。环境接口会逐渐标准化，单个静态任务也会随模型变强而失效；能持续产生新状态的 Simulation、稳定判断结果的 Eval/Verifier 和生产反馈回路，才更可能形成 recurring value。

这条路线也有清楚的失败条件。如果项目仍主要依赖人力接单、客户高度集中、每批数据交付后没有持续使用，所谓 Training Signal 只是给传统外包换了名字。真正的产品化要体现在同一套任务定义、质量标准、工具和评测能重复服务多轮训练或多个客户，而不是在演示文稿里增加 RL、Environment 和 Verifier 等术语。

## 企业最该保留的是学习回路

企业为了让外部模型有用，会不断提供文档、流程、工具、判断标准和纠错经验。#361 把这称为 Reverse Information Paradox：企业不仅在购买 Token，也在教系统怎样理解自己的工作。长期有价值的不只是原始数据，还包括任务在哪里失败、人怎样修改、什么结果被接受，以及企业如何判断好坏。

这些轨迹不能未经处理就拿去训练。它们可能含有敏感信息、错误决策、无权限内容和无法归因的反馈。企业需要自己掌握 private Eval、Workflow、Trace、Feedback 与 Memory，规定谁能写入、谁能读取、如何脱敏和撤回，并保证更换基础模型后仍能继续使用。所谓 ownership，最终要落实为可导出、可审计、可迁移的能力。

FDE 的商业价值也应按这条标准衡量。现场工程师确实更容易发现数据口径、审批例外和责任人，解决远程产品团队看不到的问题（#76、#97）。但驻场本身不是壁垒。一次交付至少要留下可复用的连接器与权限模式、带真实失败样本的 Eval、以及可以迁移的 Workflow 或 Skill。若每个客户都要从头定制，模型升级后仍靠同一批专家手工修补，收入更接近高成本服务；只有现场知识不断写回产品，毛利和交付速度才可能随客户增加而改善。

## 实践工具：AI 项目商业价值检查表

| 账目 | 要问的问题 | 最低证据 |
| --- | --- | --- |
| Adoption | 谁开通、谁偶尔使用、谁把 AI 放进正式流程 | 按任务和角色分层的活跃数据 |
| Token | 哪些模型和步骤消耗最多；缓存、重试和工具费用是多少 | 完整任务级成本，而非标价 |
| 收入 | 按 Token、席位、任务、部署还是结果收费 | 合同口径与续费原因 |
| 毛利 | GPU、模型采购、补贴、FDE 和人工支持由谁承担 | 去除补贴后的分业务毛利 |
| 任务价值 | 什么叫完成；客户是否采用；带来多少节省或收入 | 可复查的验收与业务指标 |
| 学习资产 | badcase 能否归因；修正是否进入 Eval、Skill 或训练 | 权限清楚、可迁移的反馈回路 |
| 扩张 | 客户变大后会直连、自建还是继续购买 | 留存、毕业流量和单位交付工时 |

这张表不要求一家公司控制整条价值链。它只要求把自己的增长指标接回同一个问题：一个被客户接受的任务，最终贡献了多少毛利，又留下了什么下次还能使用的资产。

## 这些材料的证据边界

本文把公司财务披露、创始人访谈、行业评论和条件推演放在一起，是为了比较商业机制，不是把它们当成同等强度的证据。招股书能说明一家公司的历史业务结构，不能代表整个行业；公司口径能提示产品方向，不能替代独立核验；算力、开放模型和数据服务的长期利润分配，仍要等待更多可比财务数据和客户留存结果。

## 哪些证据会改变以上判断

1. 若独立 MaaS 和重 Token 应用取消补贴后，仍能在用量增长时稳定提高毛利，且不依赖本地部署或其他业务交叉补贴，应收缩“Token 增长可能扩大亏损”的判断。
2. 若中立路由平台长期保留大型高频客户，并获得比应用与企业 Eval 更完整的任务结果，应上调路由层的利润与学习优势。
3. 若数据服务和 FDE 公司能持续降低单位交付工时，并证明同一套 Eval、Verifier、Workflow 或训练信号可跨周期、跨客户复用，应把它们从项目制服务重新评估为产品业务。
