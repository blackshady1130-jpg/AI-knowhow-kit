# 模型降价之后，AI 企业靠什么赚钱

**讨论模型商业化、云、FDE 和企业部署 · 更新至 2026.07**

---

## 核心判断：企业最终为可验收的结果付费

> **当高质量模型更容易替换、推理价格继续下降，单纯销售 API 的利润空间可能缩小。企业仍会为更低的任务成本、完整工作流、权限管理、客户支持和可验收的业务结果付费。**

模型公司仍需要巨额训练和算力投入，前沿能力也不会立刻商品化。但企业采购的是能够完成任务的系统，模型只是其中更新较快的一层。如果更换一个 base URL 就能迁移后台任务，供应商很难只靠 token 差价长期保持议价权；如果迁移还涉及权限、历史状态、评测、合规和人员流程，更换供应商就会困难得多。

行业分析需要同时看两件事：模型能力和推理成本怎样变化，企业把模型变成稳定结果的速度怎样变化。前者决定可用的技术供给，后者决定客户愿意向谁付费。

## 模型推理毛利是否会下降

Martin Alderson 对 GLM 5.2 的文章解释了这一判断（#356）：训练需要高额前置投入，inference 随使用量产生边际成本；frontier lab 依靠 API 定价把训练投资分摊到大量调用中。当 open-weight 模型达到“足够好”、迁移成本又低时，成本敏感的 Agent workload 可能率先切换，从而压低单纯推理服务的毛利。

文章的个人体验也给出了早期采用场景：后台 PR review、批处理和非交互任务对延迟较不敏感，替换 API 相对容易；交互使用、vision 和复杂体验仍可能让闭源前沿模型保有优势。作者提到的约 90% 计算口径毛利来自 napkin math，并非经过审计的公司财务事实。它适合用于展示经济机制，不能用来断言行业当前利润率。

这条假设还忽略了几种防御：领先模型可以通过新能力重新拉开差距；订阅产品能把 API 与入口捆绑；企业合同包含安全、支持和赔偿；大客户迁移也可能受数据驻留与合规限制。因此，毛利压缩更可能先发生在可替换、可评测、后台运行的任务，而非一次性扫平模型层价值。

## 企业已经开始按任务选择不同模型

Databricks 的内部 coding benchmark 提供了比个人体验更强、但仍有边界的证据（#358）。任务来自近期人工 PR，使用隐藏测试与封闭 git 历史。结果显示，高复杂度设计任务仍依赖强模型；大量配置、flag 与日常维护可以路由给更小、更便宜的模型。

GLM 5.2 在这套 workload 中质量与 Opus 4.8 接近，文中报告单任务成本约 1.28 美元，对比 Opus 的 1.94 美元。这说明 open-weight 模型已经能进入一部分大型企业代码库的 daily-driver 区间。它没有证明 GLM 在其他组织、非代码任务或开放质量要求中同样替代 Opus。

企业通常不会为所有任务只选一个模型。更实际的做法是按任务路由：高风险、复杂推理和多模态任务使用前沿模型；可验证的中低复杂度任务使用小模型或自托管模型；再用本地 eval 持续调整。供应商需要争取的是企业中的具体任务，而不是一个总榜单排名。

## Token 单价低，不等于完成任务的成本低

Databricks 的另一个结果直接改变成本口径（#358）。Sonnet 5 的 token 单价低于 Opus 4.8，但它在任务中工作更久、读取更多内容，总 token 约为后者 1.9 倍，最终单任务成本反而更高，完成率也更低。相同模型接入不同 harness 后，部分任务成本还会相差两倍以上，质量却接近。

这意味着模型定价表无法单独预测毛利或客户 ROI。完整成本至少包括输入输出 token、缓存命中、工具调用、wall-clock、重试、人工 review、失败恢复和部署运维。对自托管 open-weight 模型，还要加入 GPU 利用率、容量冗余、工程团队和升级成本。

企业最终会比较 cost per accepted outcome。模型提供商如果能通过更好的 Harness、缓存和工具编排减少总调用，即使 token 单价较高，也可能拥有更低的任务成本。因此，运行系统也会影响定价和竞争力。

## 为什么工作流和客户反馈更难替换

模型 API 易替换，不代表工作流容易替换。IDE、办公套件、CRM 和行业系统掌握用户意图、权限、历史 artifact 与验收动作；这些数据决定何时调用模型、怎样纠错、什么结果值得保留。#245 对 IDE 入口价值的分析把开发者行为、真实任务与训练反馈连在一起；#260 的 Cursor 实践则用线上 Keep Rate 和后续行为调整不同模型的 harness。

更难复制的是失败案例和专家修正记录。团队需要知道失败来自模型、context、工具、规则还是 verifier，并将修正用于更新 Skill、eval、路由或训练数据。单纯的调用量不能替代这些记录。

Codex 将定位扩展到通用知识工作（#295），说明平台开始竞争 workspace 和 delegation layer。能够保存任务状态、跨工具执行并接入组织权限的平台，更容易成为用户工作的固定入口；但它仍要靠交付质量和信任留住用户，不能只靠默认分发。

## FDE 如何把客户项目变成可复用产品

企业 AI 的困难往往藏在本地数据口径、审批、例外和 owner 中。#76、#97 对 Forward Deployed Engineer 的讨论共同指出，通用产品团队很难在远处理解这些约束；FDE 进入现场，把模型能力接到具体流程，再把重复问题产品化。

FDE 不等于无限定制。如果每个客户都需要长期驻场、每次升级都靠人工处理，产品就很难复制。高质量 FDE 应留下三类可复用内容：连接器和权限模式；带真实失败样本的 eval；可以用于其他客户的 workflow 或 Skill。客户项目中的经验需要进入产品，交付成本才可能下降。

这也解释了为何“模型更强”与“企业落地更快”之间常有时差。组织需要重新定义任务、验收和责任，FDE 的价值是缩短这段学习周期，而不是替代客户 owner。

## 算力投入最终要看利用率和收入

训练集群和推理基础设施仍是重要门槛，但 capex 本身不能保证长期优势。#198、#223 对算力投资和工业系统的讨论提醒，真正要看的是利用率、模型迭代速度、推理效率和收入转化。闲置 GPU、低质量调用或补贴出来的 token 增长，都不能自动证明商业价值。

当行业从“谁拥有更多 GPU”转向“每单位计算产生多少被接受的工作”，云、模型公司和应用层会围绕同一结果重新分账。能降低任务总成本、提高可靠性并占据预算 owner 的一方，才更可能保留毛利。

## 实践工具：AI 项目商业价值检查表

评估一家 AI 公司或内部项目，可以逐项回答：

| 层次 | 需要检查的问题 |
| --- | --- |
| 模型 | 优势来自独占能力、价格、延迟还是模态；领先窗口多长 |
| 运行时 | Harness、缓存、路由和工具是否降低 accepted task 成本 |
| 入口 | 是否拥有任务状态、权限、artifact 与用户决策界面 |
| 数据 | badcase 能否归因；专家修正会进入 eval、Skill 或训练吗 |
| 部署 | FDE 产物能否跨客户复用；上线与接管责任归谁 |
| 商业 | 谁掌握预算；按 token、seat、任务还是结果收费 |
| 资本 | GPU 利用率、推理毛利、补贴和现金消耗怎样变化 |
| 边界 | 替换成本来自真实资产，还是合同、惯性与短期模型差距 |

如果一家公司只能说明“模型很强”，却说不清客户为什么持续付费，它还没有证明商业模式能够长期成立。

## 哪些证据会改变以上判断

1. 若前沿模型持续拉开足够大的能力差距，使企业在主要 workload 上无法用路由或 open-weight 模型替代，价值会重新集中到模型层。
2. 若内部 benchmark 显示 Harness、缓存和任务路由对总成本与质量影响很小，运行时不再是主要差异化来源。
3. 若大量 FDE 项目能在不形成通用资产的情况下保持高毛利、高续费和低交付成本，本文对“服务必须写回产品”的要求需要放宽。
