# AI 如何改变人的判断、工作和责任

**讨论认知、就业、治理和高责任场景 · 更新至 2026.08**

---

## 核心判断：把决定权、额外工作和责任写清楚

> **AI 能完成更多任务，不代表使用者和劳动者一定得到更多好处。评估一次部署，要看谁定义目标、谁能看到证据、谁可以拒绝或退出、谁处理失败，以及发生损失后谁负责。**

安全讨论常在两个尺度之间跳跃：一边是未来的系统性失控，另一边是单次回答有没有明显有害内容。进入真实工作后，还有一组更日常也更容易落地的问题。系统可能平均表现更好，却让人更难发现错误；可能提高团队产量，却把 Review、解释和异常处理转移给少数员工；也可能让用户感觉被理解，却长期替他做掉本应练习的判断。

所以，能力分数、满意度和 adoption 都不够。至少还要记录四件事：用户或员工保留哪些决定权；谁承担新增人工工作；哪些错误可以撤销，哪些会造成不可逆损失；模型、产品、部署组织和最终批准者各自承担什么责任。

## 可解释性正在改善诊断，还不能保证控制

Anthropic 的 J-space 研究在 Claude 的中间层识别出一组 workspace-like 表征（#352）。它们可以被报告和干预，并在部分灵活推理中因果参与模型行为。这类研究的直接价值是帮助研究者观察内部机制、检查隐藏目标或异常表征。

它没有证明模型具有主观体验。功能上类似 global workspace、存在可言说的中间变量、模型是否有意识，是三个不同命题。把机制结果写成“模型产生了意识”会夸大证据；反过来，因为研究不能回答意识问题就否定它，也会错过安全诊断的用途。

#420 把当前可解释性概括为两条互补路线。一类训练额外的解释器，把 hidden state 翻译成 feature 或自然语言，优点是更容易扩大规模，风险是解释器本身也可能生成看似合理的故事；另一类先提出机制假设，再直接干预表征并观察行为变化，因果证据更清楚，却依赖研究者事先知道该问什么。这个划分来自访谈与研究综述，适合帮助理解方法差异，不代表学界只有两种做法。

更重要的边界是“看见”不等于“控制”。局部 steering 可能改变目标行为，也可能连带损伤数学等无关能力；在一些场景里，Prompt 或 Fine-tune 反而更稳定（#420）。现阶段的可解释性更像逐渐变好的诊断工具，还不是可以稳定编辑人格、保证对齐的手术系统。部署者仍需要外部 Eval、权限限制、人工责任和事故响应，不能用一张可解释性图替代治理。

## 成功标准必须包含不能发生的事

AutomationBench-AA 把任务目标和业务禁区放在同一项评测里（#357）。其 657 个私有任务覆盖 40 个模拟 SaaS 应用：Objective 规定 Agent 应完成什么，Guardrail 规定不能误伤哪些对象或破坏哪些规则；一次 Guardrail 违规会让该任务在 headline score 中归零。

这种结构比单独统计完成率更接近企业风险。Agent 可以正确更新 CRM，却同时通知错误团队；可以创建任务，却把已经废弃的草稿也送入流程。若只看“有没有做成”，这些副作用会被成功率遮住。榜单头部系统在当时口径下也只有约一半任务做到完成且无违规，说明执行能力和可授权程度仍有明显差距。

边界同样重要：这是模拟应用、私有任务、单次运行和固定 turn cap 下的结果，不能直接预测医疗、金融或公共服务的长期事故率，也不能把某次模型排名当成稳定结论。可以迁移的是评测方法：每个上线流程都要同时写出验收条件与禁止发生的后果，并对高影响错误单独计数。平均正确率不能把一次严重泄露或错误付款冲淡。

## 人工确认要放在真正需要判断的位置

在每一步都弹出确认框，看起来保留了人的控制，实际上可能训练用户不停点击“允许”。#396 记录的一项 Claude Code 实验显示，人工对重复命令检查的拦截效果会随会话延长明显下降，而用户对整体 Plan 的拒绝更积极。具体比例只适用于该实验及其命令风险设置，不能外推到所有工作流；它揭示的问题是，human-in-the-loop 是否有效，取决于人被放在哪一层。

高频、规则明确的检查可以由 Runtime Guardrail 执行，例如阻止越权路径、未授权外发和危险命令。人更适合决定目标、批准计划、设定权限边界、处理系统无法归类的例外，并对高责任动作签字。自动检查也不能独自承担责任：分类器会漏报或误报，组织仍需规定它失败时谁接管、损失由谁处理。

因此，“保留人工审批”不是完整的治理方案。需要说明审批者当时能看到什么证据、是否有时间理解、拒绝会不会受到绩效压力，以及同类请求出现多少次。一个只有形式上的按钮、没有信息和拒绝空间的流程，责任仍然被转嫁给了点击按钮的人。

## 权限要跟着数据进入产出物

传统授权通常发生在工具调用的瞬间：谁可以读数据库，谁能调用某个 API。Agent 会把读到的数据带进 Context、Memory、Workspace、文档和看板，再继续分享。若系统只记录最初那次读取，后续产出物可能绕开原有权限。

#403 对 Cloudflare OS 的源码分析提供了一个具体做法：读取外部数据时记录来源和权限；其他人打开共享 Workspace 时，再按访问者身份重新检查历史数据源；已经分享给低权限用户的 Workspace，后续读取更敏感数据时直接阻断。它把授权从 pre-call 延伸到了 post-read 与 pre-egress。

这套实现仍有明显局限：Workspace 粒度可能因为一个敏感来源而整体受限，记录是否完整依赖各 Driver，实现也没有覆盖全部外发通道。它还称不上完整解决方案，但清楚地表明，授权对象需要从 Tool 扩展到派生数据和生成物。企业要能回答：一段结论来自哪些受控信息，谁还能看，分享后权限如何重验，删除源数据后衍生内容怎样处理。

Agent 代表谁行动也必须进入审计。#166 把 autonomy 视为模型、用户和产品共同形成的部署结果：同一模型只给建议、修改内部状态、对外发送或执行高责任动作，风险完全不同。传统身份系统管理人和固定服务账号，Agent 却是“某个用户委托的软件主体”：它会自主选择路径，但权限仍来自具体任务。#382 指出，审计记录至少要包含用户、Agent、任务、对象和授权期限。短期凭证与 policy 能限制范围，却还不能可靠判断复杂意图。调用链可以很长，责任链不能因此消失。

授权还包括系统能否把工作轨迹用于下一轮训练。企业不断提供文档、流程、工具调用、纠错和 Eval，实际上也在交出自己的做事方法（#361）。Trace 不能因为“有助于改进”就自动进入训练。谁能保存、如何脱敏、是否允许跨客户使用、员工或客户能否撤回，都要在部署前进入数据政策和合同。

## 便捷和满意不等于用户得到更好的判断

当 AI 输出完整、语气确定、交互自然时，用户容易把“像一个可靠的人”误认成“能对结果负责”。personal guidance 已经是实际用法。Anthropic 对相关对话的研究发现，健康、职业、关系和个人财务占了较大比例，但研究只能看到聊天文本，不知道用户后来是否采纳或得到怎样的结果（#251）。

#145 所讨论的 situational disempowerment 进一步提出：让用户当下满意的回答，可能通过迎合、过度确定或替用户定义处境，削弱他的自主判断。什么算有益说服、什么算不当影响，仍带有价值判断；因此不能把满意度低直接解释为更安全，也不能把满意度高当作长期受益。

Anthropic 对近万段对话的 AI Fluency 研究提供了更具体的行为信号（#171）：当 AI 交付看起来完成度很高的代码或文档时，用户更少质疑推理、核查事实和寻找缺失背景。该研究观察的是对话中的行为，不是长期认知能力的随机实验，不能证明 AI 一定让人“变笨”。它提醒产品和组织测量 Review 行为，而不是只问用户觉得省了多少时间。

不同任务也不该使用同一种交互。低价值、重复性工作可以追求快速完成；教育、研究、管理和职业决策则需要保留预测、比较、解释与复盘。产品可以提供 completion mode 与 learning mode，组织也应明确哪些技能允许逐渐外包，哪些判断必须通过人工练习维持。辅助写作和无障碍支持可能扩大参与，不能被笼统写成“依赖 AI 有害”。风险来自任务、交互方式和长期使用的组合。

## 生产率要扣除隐藏的人工工作

AI 先改变的是任务组成，而非同时、均匀地替代整个职业。#87 基于美国约 1.8 亿条招聘数据观察到不同岗位分化：部分执行型创意岗位下降更明显，部分技术和基础设施岗位相对稳定或增长。这个结果受时间窗口、岗位分类和宏观环境影响，不能把相关性写成 AI 导致的就业定局。#233 与 #268 更强调中低端白领压价、成长路径收窄以及技术红利分配可能滞后，它们属于趋势判断，也需要长期数据验证。

组织内部还可能出现一批没有进入“AI 节省时间”报表的工作：整理上下文、检查输出、修复错误、处理异常和向客户解释。#311 引用 Glean 对 6000 名数字工作者的调查，把这类工作称为 botsitting，并给出每周 6.4 小时等自报数据。调查口径和来源限制了它的外推范围，但提出了一个必要的核算项：个人觉得工具有用，不等于公司净生产率按同样幅度提高。

评估部署时，应把减少的制作时间与新增的 Review、数据维护、事故响应、情绪劳动和 FDE 工时放在同一张表里。如果高薪员工提速，低可见度岗位却承担更多清理工作，总产出上升也可能伴随成本转移。

新人路径需要单独检查。初级任务减少后，资深员工短期可能更高效，组织却失去了培养领域判断和异常处理能力的练习场。不能只问“现有 expert 加上 AI 能做多少”，还要问下一批 expert 如何成长：哪些基础任务仍要亲手做，什么时候开始使用 Agent，谁来证明他能在系统失败时独立接管。

## 自我改进系统不能自己给自己打分

当前更实际的“自我改进”，是让 Agent 提议修改 Prompt、工具、Harness、代码或训练流程，再用独立测试判断是否保留（#384）。风险出现在同一组件既提出改动，又能修改评价标准、权限或版本晋升规则。删除难题、绕过安全检查也可能让局部分数提高，却不能算真实进步。

至少要分开三类权力：proposer 提出方案，evaluator 使用候选版本不能改写的测试，approver 决定是否进入生产。三者可以有自动化参与，但最终责任必须落到明确的组织和人。系统还要保留历史版本、失败证据、回滚条件，以及改动影响到外部用户时的通知和补偿办法。

开放权重会把更多治理工作交给部署者。#368 认为，开放模型一面降低能力使用门槛，一面压缩闭源实验室的商业回报，并主张利用闭源领先窗口建设独立评估和社会防御。这是一篇观点文章，不能证明固定缓冲期存在。较稳妥的结论是：模型一旦可本地修改和部署，供应商 API 上的 Guardrail 不再是唯一控制点，使用权限、能力评估、事故响应和高风险场景限制都需要部署组织自行承担。

## 实践工具：责任与额外人工成本清单

| 项目 | 上线前必须写清楚的内容 |
| --- | --- |
| 目标与 Guardrail | 什么算完成；哪些副作用一次都不能发生 |
| 决定权 | 谁定义目标、批准计划、处理例外、拥有否决权 |
| 用户权利 | 怎样纠错、撤回授权、删除记忆、转人工或退出 |
| 数据传播 | 敏感数据进入 Context、Memory 和产出物后谁还能访问 |
| 额外人工工作 | Prompt 整理、Review、异常处理、解释、数据维护各需多少工时 |
| 能力变化 | 哪些技能被增强或取消；新人如何获得独立接管能力 |
| Agent 委托 | 代表谁、执行什么任务、可操作哪些对象、何时到期 |
| 学习数据 | Trace、反馈和 Eval 能否保存、训练、跨客户使用或撤回 |
| 事故责任 | 谁响应、谁赔付、保留什么证据、如何回滚并修正系统 |
| 证据边界 | 数据覆盖哪些人、时间和场景；哪些影响尚未观察 |

填写这张清单时，收益和成本要落到具体角色。若效率收益归业务负责人，审批压力和失败风险却落在一线员工，就不能只用团队总产出来评价部署。责任也不能只写“human in the loop”，必须写出哪一个人、在哪个节点、依据什么信息作决定。

## 当前证据能说明什么

本文使用的材料包括机制研究、平台研究、模拟 benchmark、招聘与问卷数据，以及作者和访谈观点。它们能帮助定位风险和测量项，尚不能给出统一的意识、就业或长期认知结论。低风险写作辅助无需照搬医疗级流程，高责任 guidance 与外部执行也不能沿用消费级产品的宽松做法。控制强度应由可逆性、影响范围和失败后果决定。

## 哪些证据会改变以上判断

1. 若长期随机实验显示，代做型 AI 在学习、管理和专业判断中既提高即时表现，也提高离开 AI 后的独立能力，应下调认知折旧风险。
2. 若真实企业部署中，Objective completion 能稳定预测低 Guardrail 违规、低接管工时和低事故率，动态委托、人工成本记录与过程检查可以简化。
3. 若跨岗位、地区和时间窗口的数据持续显示 AI 收益广泛分布，Review 负担、新人路径和工资分化都没有恶化，本文对收益分配的谨慎判断需要改写。
