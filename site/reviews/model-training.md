# 训练与推理怎样提高模型能力

**讨论预训练、后训练与推理计算的分工 · 复核于 2026-10-08**

模型变强，可以靠扩大预训练，也可以靠更好的后训练，或者在回答问题时投入更多计算。这几条路会互相影响，但花钱的位置、得到收益的时间和适合解决的问题不同。我更关心的是：下一笔算力应该投在哪里，以及得到的提升能否在实际任务中反复使用。

只看参数量，容易低估后训练；只看推理时长，又容易把反复尝试当成能力进步。判断这些变化，需要先区分模型已经学会的东西、运行时获得的信息，以及为得到一次答案付出的计算。

## 预训练要算两笔账

Scaling law 最实用的用途，是帮助分配训练资源。在同一计算预算下，模型应该多大、数据应该有多少、训练多久，不能各自决定。#330 梳理的 Kaplan、Chinchilla 与数据受限研究，讨论的正是这些取舍。训练数据反复使用也可能有收益，只是重复次数增加后，新增收益会递减，过拟合的风险也会变化。

这里有一笔容易漏掉的账：对于同一模型版本，训练投入集中发生，推理费用则随调用持续产生；后续更新还要另计训练成本。训练阶段最省算力的方案，未必是整个产品周期成本最低的方案。如果模型要承接大量请求，让相对较小的模型训练得更充分，可能值得；如果任务低频、难度高，增加单次推理投入也可能更合适。这个选择取决于预期调用量、延迟要求和能力损失，不能只从一条训练曲线上读出来。

#351 中 Diogo Almeida 对早期 scaling law 的复盘，把争议落在训练 Token、学习率日程和曲线截取方式上。这是研究者对实验设计的解释，不宜直接写成已经定论的“原论文有 bug”。将小模型实验外推到更大规模时，还要检查数据、优化器和训练设置是否发生变化。

预训练损失降低，也不意味着每一种复杂任务都会同步改善。题目是否出现在训练数据中、能力能否迁移到新分布，是另外的问题。#25 对推理与记忆的讨论提示，部分涨分可能涉及已有信息被重新利用。需要把记忆、分布内泛化与新任务迁移分开验证，而非合成一个“变聪明了”。

答错事实题，也未必意味着知识没有学进去。#428 的 WikiProfile 将“缺少知识”和“换一种问法就调不出来”分开：先给接近 Wikipedia 原文的提示，检查模型能否补出事实，再用不同措辞和关系方向提问。部分前沿模型在前一种条件下表现很好，直接问时仍会失败。这提示我们，补数据与改善知识调用应当分别诊断。

但论文的 encoding 是行为代理：它根据强提示下的回答推断知识可能已被编码，没有直接读取权重确认知识位置。样本也只覆盖 Wikipedia 的单跳事实，不能推成“全部知识已经学会，只差检索”。对动态事实，外部查询仍有必要；对这套题中可被提示唤起的稳定知识，后训练和适量推理计算才是更有针对性的候选方案。

## 后训练要解决的是行为、探索和能力整合

监督微调可以用示范告诉模型怎样回答、怎样调用工具；强化学习让模型根据反馈调整策略；蒸馏则把教师模型的行为或分布用于训练另一个模型。三者经常配合使用，并没有一套适用于全部模型和任务的固定顺序。

#407 收录的 Finbarr Timbers 访谈提出一条路线：先在数学、代码等领域训练不同专家，再通过多教师的 on-policy 蒸馏整合能力。这里的 on-policy，强调训练信号与学生自己会生成、会遇到的状态相联系，减少“示范里的步骤学得很好，自己一旦走偏就不会继续”的落差。

多教师和 OPD 都是有条件的选择。#450 的匿名研究员讨论提到，长期使用单一教师后混入另一教师的数据，在某些案例中反而降低效果；这不是“多教师必然有害”的结论，而是提醒团队重新检验学生 checkpoint、训练配方与轨迹风格是否匹配。教师输出还要持续、完整、及时：缺轮次、推理错误或不同版本混杂，会改变监督质量；等数据准备好时，教师和学生可能已经更新。比较路线应同时记录 rollout 预算、数据版本和采集周期，不能只数教师或样本。

#443 对 OPD 的实验还提醒，query 数量不等于监督量。同一道问题反复生成不同轨迹，会经过很多中间状态，每个位置都可能获得教师分布的监督。因此，“只用一道题训练”并不等于只收到一条答案。作者在小模型和限定领域中观察到，少量有差异的题目可以接近全量训练效果。

这里的状态覆盖率，是相对于全量实验产生的参考池，将教师隐向量聚类后的代理指标；覆盖更多簇，不等于覆盖所有真实任务，也没有衡量每个状态同等的训练价值。这个结果支持检查已有监督是否被有效吸收，不能用来宣布真实用户数据不重要。需求澄清、目标变化和长尾失败能否出现，仍取决于问题怎样把学生带入相关状态。

我不倾向于把 RL 限定为“只能提高已有答案的出现概率”，也不认为一次涨分就证明产生了新的通用能力。更具体的问题是：模型在什么状态下获得反馈，反馈奖励了什么，训练之后能否处理没有见过的任务。#274 对评分标准的讨论说明，如果奖励偏向格式和表面特征，模型可能学会迎合评分；更多训练会放大这种偏差。

#460 的 Sharpening Tax 将这件事拆成三个观察量：pass@1 是单次成功率，pass@K 是 K 次尝试中至少一次成功的覆盖率，pass^K 是 K 次全部成功的概率。后训练可能让部分题更稳定，同时减少另一些题在有限预算内被解出的机会。对日常交付，稳定成功更重要；对有可信验证器的搜索，低概率正确路径也有价值。

论文的开放模型对比是观察性证据：训练配方未完全公开，Base 使用轻量 Harness，后训练版默认使用数据集原有配置。因而不能把差异全部归因于 RL，也不能断言后训练必然缩小能力或只唤醒旧能力。128 次都失败，只说明在这套配置和预算里没找到解法。部署若要利用多次尝试，还须有能挑出正确结果的验证器，并计入检查成本；会付款、发消息或改生产数据的任务，也不能直接照搬可重置沙箱里的安全重试。

对 Agent 来说，训练材料还包括能运行、能重置、能判断结果的环境。综合 #454 的访谈，可以把数据生产拆成取得授权素材、搭建环境和验证器、提取专家判断，再用客户模型确认增益。专家做得对，不等于学生学得会；供应商在开源模型上验证有效，也不能替代目标 checkpoint 的反馈。#409 提出的长程环境投入因此有明确检验对象：它补的是当前模型哪一种失败，收益能否迁移，而非环境数量是否增加。

## 训练算力应该继续花在哪些题上

#442 在数学、代码和 Agentic Coding 的开源模型分析中发现，RL 收益分配并不均匀：原本较容易的问题往往改善更多，最难的问题改善有限。其受控实验还显示，在固定预算下，给每道题统一增加采样量未必更好。简单题只要偶尔出现一个错误，就可能继续占据训练批次，把预算留在已经接近解决的问题上。

Never Give Up（NGU）先少量采样：全对的题快速跳过，有对有错的题用于训练，全错的题获得更多尝试，但仍以一定概率放弃。它调整的是每题采样预算，依赖能从简单题省下足够计算、异步调度及陈旧样本处理；若几乎全是难题，分轮等待未必合算。#450、#454 所说的数据有效性随模型变化，也要求随 checkpoint 重估难度，并检查简单题是否退化。

PTGS（#460）调整的是训练 rollout 的采样温度：根据同题历史成败，难题升温以探索更多行为，易题降温以提高有效样本比例，不改 PPO 或 GRPO 的目标函数。失败记录必须影响难度估计，否则最缺成功信号的题仍不会得到探索。其小模型、两个交互环境的控制实验支持同时改善单次成功与覆盖率，不能直接外推到前沿模型；持续生成的新题还需跨题难度估计。它与 NGU 的预算分配不同，训练探索与测试时多试也应分别比较。

全错也不总意味着没有学习信号。若只有稀疏成败奖励，可以考虑专家成功轨迹做 SFT 冷启动或降低难度；可验证的部分进展则提供另一条路。T1（#456）的 Terminal rollout 可能超过 300 轮工具调用，一批消耗数百 sandbox-hours。它把奖励写成通过断言数 P 除固定常数 20，而非通过断言的比例：通过 10 项和 2 项，即使各自都完成一半，也会得到不同奖励。检查项能否代表可比工作量，因此直接影响训练信号。

T1 的细粒度标量仍在终局给出，由 Critic 与 GAE 估计前面各步对最终结果的贡献，不是每步都有独立过程奖励。完整 Critic 多花模型计算，换取每题一条轨迹也能学习的条件；PPO 与 GRPO 的结果限于论文配置，且奖励、数据与 Critic 的变化没有充分单因素消融。优先收快轨迹、取消慢任务，减少等待却改变了训练分布；验证器仍在 Agent 沙箱内，也留下被干预的风险。应从一次昂贵的执行中获得更有效的训练反馈，同时核对这些代价，而非只比较吞吐和高分。

## 多想一会儿，什么时候有用

推理时计算提供了一种不同的选择：不更新模型权重，在当前请求里多做推导、搜索、工具调用或候选验证。对于有可靠检查方法的任务，多尝试可以提高找到正确方案的机会；如果模型缺少关键事实，反复思考同一段错误信息却未必有帮助。

推理预算因此要和反馈方式一起设计。代码可以运行测试，计算可以交叉核对，动态信息可以查询来源。没有这些反馈，只是把推理链拉长，可能增加重复判断和错误自证。更多候选也要求有办法挑出好结果，否则生成得更多只增加了选择负担。

#374 记录的 Opus 5 评测中，多数主流项目在最高 effort 档表现较好，但少数项目并不单调提高。effort 是产品提供的推理投入档位，不是质量保证。现有结果不足以确定回落来自噪声、预算耗尽还是过度推理，却足以说明部署时应该同时看成功率、耗时和费用。

工具与参数内化也有不同用途。#408 中 Jason Wei 强调，能够搜索到答案，与模型熟练掌握相关知识并不相同。我的判断是，变化快、来源必须可追溯的信息应优先通过工具获取；高频且要求低延迟的稳定能力，则值得考虑训练进模型。是否划算，要将训练与维护成本摊到实际调用量上，不能简单归结为“大模型还是小模型”。

上下文管理也可以成为可训练策略。CLM（#458）让模型用代码编辑下一轮实际看到的历史，再用 RL 学习保留、更新和卸载什么。Qwen3.5-9B 在 BrowseComp-Plus 上从 28.8% 到 42.5%；同配方训练的摘要基线为 42.1%，CLM 比它少用 38.8% 的 prefix-reuse FLOPs。比较对象决定了这项结果的含义：它支持学习管理策略与计算效率，不是相对所有 Agent 的能力跃迁。RL 只覆盖一个小模型和任务分布，部分长任务采用 best-of-three；计算节省还需经过显存、吞吐、失败率与训练摊销，才可能变成更低账单。

## 架构改动，先看省了什么

模型结构会改变上述计算的成本。#418 整理的注意力机制，可以按存储历史、压缩状态和选择读取范围来理解。

一类方法通过共享或压缩 Key/Value，减少生成后续 Token 时重复使用的历史缓存，即 KV Cache。缓存占用减少，才可能为更长输入或更多并发留出空间；不同压缩方法还需要比较信息损失和实际硬件表现。

另一类方法把历史写进有限大小的递归状态，不必为每个位置持续保存同样规模的缓存，但精确找回早期细节可能更困难。稀疏注意力则减少每一步参与计算的历史位置。具体实现仍可能包含额外索引、局部窗口或混合层，不能把“有限状态”理解成整个系统内存恒定，也不能假定每种稀疏方法都完整保留原始历史。

混合结构可以让不同层承担不同任务，收益要落到长文检索、跨段综合、速度和缓存占用上。另一个方向是复用权重以增加内部深度（#453）：[Huginn](https://arxiv.org/abs/2502.05171)反复执行中间模块，在生成下一个 Token 前增加隐状态计算；[Mixture-of-Recursions](https://arxiv.org/abs/2507.10524)进一步按 Token 分配递归深度，并研究选择性缓存和 KV 共享。这与靠更长输出增加计算是不同的预算维度，两者可以共存。

参数复用首先减少相对独立加层所需的权重存储，运算并没有消失。FLOPs 随执行次数变化，KV 是否增加取决于缓存设计，时延还受显存读取、并行和调度影响。[SMELT](https://arxiv.org/abs/2609.01343)在尽量匹配每 Token FLOPs、非 Embedding 参数量和 KV 预算后，仍观察到循环架构的训练效率优势；这比同参数模型多算一遍后涨分更有解释力，但训练 FLOPs 节省不能换成推理账单降幅。输出 Token 变少也不足以识别 Loop：训练配方和停止策略同样可能缩短输出。

## 研究提速，要分清执行、选题和方法改进

自动化研究提供了一个检验“反馈能否带来进步”的具体场景。#416 分析了 PostTrainBench 的 1,338 条 Agent 轨迹与 5,111 次训练实验。在其划分的 3,557 对连续训练实验中，改变目标、数据来源或训练阶段结构的有 74 次，约占 2.1%。

在这些模型、任务和资源预算下，执行实验与修改研究路线的表现并不相同。前者把既定流程跑通，后者需要解释反证，判断是继续调参、换数据，还是放弃原假设。#441 的研究者讨论与 #447 中 Nathan Lambert 的文章也围绕这种区别展开，但它们是研究判断，不能与轨迹统计合成一个研发自动化上限。

第三层是改进“下一轮怎样研究”。#449 的 AGI HOUSE 公开圆桌并没有统一的 RSI 定义：姚顺宇强调系统能否修改训练流程与优化目标，谷雨更强调自主发现目标和学习、推理的长程耦合。按系统视角，改进上下文、调度或探索策略可以有效，不必每次更新权重；但普通 RL、自造训练数据或一次优秀 coding 结果，都不足以证明改进方法在递归变好。

Dream-RSI（#446）给出了具体的探索策略实验：把已完成探索的分支、工作区和反馈保存成可重放的树，比较先探索哪条路线、何时停止、如何分配并行任务，再把选出的策略放回在线探索。底层 coding agent 保持不变，改变的是探索策略代码。重放只覆盖已经实现的分支，不知道从未尝试的路线会怎样；因此，同预算在线验证、保留任务和退化检查，才检验它是否增加真实发现，而非更会利用旧记录。

最后还要看实验室资源。#451 中 JS Denain 与 Nathan Lambert 区分了局部实验循环加速和实验室整体进展：代码写得更快，后续训练仍可能串行等待 GPU，研究议程、评测和算力预算也未必同步改进。他们讨论用 ECI 增长斜率观察整体变化；斜率是结果信号，还会受到新增算力、评测口径和任务优化影响，不能单独证明 RSI 的因果贡献。

我会把新一轮研究产出拆开验收：执行节省了多少时间，方向选择减少了哪些无效尝试，方法改进能否在独立任务上重复有效，以及局部提速是否缩短了整体研发周期。改善其中一项已经有价值；把它称作持续自主升级，则还需要多轮、等预算的证据。
