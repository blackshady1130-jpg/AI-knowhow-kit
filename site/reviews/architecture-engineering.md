# 长程 Agent 如何保存进度、处理失败和恢复运行

**讨论上下文、任务状态、工具权限与恢复 · 复核于 2026-09-05**

长时间运行的 Agent，难点常常出现在中断之后：哪些工作已经完成，哪些结果仍待确认，外部系统是否已经被修改，从哪里继续才不会重复操作？模型再强，也需要获得这些事实。我的判断是，工程投入应优先解决任务连续性，再根据实际失败补充流程约束。

#388 对 Agent Infra 的观察和 #417 对 Harness 的分析，都指向一个变化：靠提示词教模型每一步怎么做的必要性可能下降，但保存状态、提供工具和控制操作范围的工作仍在。系统需要这些能力，不代表每个团队都要自己开发一套；先检查现有平台能提供什么，通常比从零搭建更合算。

## 一次中断，暴露哪些问题

下面是一个用于解释机制的假设示例，并非真实事故记录。

用户让 Agent 更新一条客户记录，并给项目负责人发送通知。数据库写入成功，通知服务也已经发出了消息，但回执返回前网络断开。Agent 恢复运行时，只看到上一轮“准备发送”的计划。

如果它把没有回执理解成没有执行，就可能重复发送。如果直接宣布完成，又可能掩盖真正的发送失败。此时需要查询外部服务的状态；服务若支持幂等键，可以使用同一个操作标识重试，让服务识别重复请求。如果既没有可查询的结果，也没有去重保证，就应保留“结果未知”的状态，让人判断是否重试。

这个例子说明，计划、执行记录和外部事实不能混为一谈。“我将发送”是计划，“工具返回成功”是回执，收件系统的记录才是进一步核验的依据。一个完整聊天窗口也未必能消除这些差别。

## 长期资料提前整理，当前信息按需查询

Agent 开始工作之前，需要知道业务里的字段、口径和约束。它们未必已经存在于一份整齐的知识库里：某个收入字段的含义可能写在数据处理代码中，一条例外规则可能散落在操作手册和历史案例中。

#414 对 OpenAI Data Agent 的分析强调了提前整理这些信息的价值。离线整理把代码、文档与经验变成可检索材料，在线查询则取得当前数据。这个案例没有公开完整准确率和各层独立贡献，不能据此认定越多知识层越好；它更有用的启发是，搜索失败有时因为知识尚未被整理，而非检索模型不够强。

长期资料需要标明来源、版本和适用范围；价格、库存、客户状态等动态信息则要在操作前重新查询。将一个月前的事实写进长期 Memory，并不会让它继续有效。两类内容共用一个召回入口也可以，但必须保留不同的更新和失效规则。

成本也受组织方式影响。稳定资料适合按需加载和复用，巨大的工具回执可以保存到文件，再给模型必要的摘要与路径。压缩时应保留原始证据入口，避免下游只能看到一段无法复核的结论。减少重复传输的目标，是少花钱完成同样的工作，而非追求输入越短越好。

## 任务状态要能被下一次执行读懂

一个可恢复的任务，至少要区分目标与约束、已经验证的结果、正在尝试的方案、尚未解决的问题。这些内容可以放在文件、数据库或平台提供的任务存储中，不必为了形式建立复杂框架。

#297 的动态工作流把计划、分支、中间状态和验证逻辑写成脚本，让不同执行者继续工作。它适合步骤会变化、需要反复验证的复杂任务；简单改字或一次查询，不值得为此增加多层编排。

保存状态还有一个顺序问题。外部动作发起前先留下操作标识与意图，收到回执后再更新结果，能帮助恢复时区分“未开始”和“可能已执行”。但本地日志与远端操作通常不是同一笔事务，仍可能出现未知状态。仅仅增加日志，不能宣称获得了恰好执行一次的保证。

检查点应记录恢复所需的文件和状态，分支适合保存多个实验方案。两者都需要说明覆盖范围。Git worktree 可以隔离代码文件，却不会自动隔离数据库、端口、缓存和凭证；#413 中多 Agent 开发的实践就遇到了这些问题。多个任务共享同一个测试账号，也可能通过外部系统互相干扰。

## 回滚文件，不等于撤销外部动作

在本地代码任务里，恢复一个旧版本往往很方便；客户通知、公开发布和付款却有不同后果。删除本地的发送记录，不能让对方忘记已经收到的消息。

恢复方案应该按动作设计。有些动作可直接重做，有些要通过幂等键去重，有些需要补偿操作，还有些只能停止并交给负责人处理。补偿也不等于还原历史：例如发一条更正通知，只能修正信息，不能保证此前没人据此行动。

回到开头的示例，任务恢复后应先检查客户记录和通知结果，再决定下一步。恢复时还要重新核对原目标是否有效：负责人可能变更，授权可能过期，用户可能已经手动处理。保存了进度，不代表可以不加判断地从旧计划继续执行。

工程上最值得测的也因此很具体：在不同步骤注入中断，恢复后会不会重复写入、漏掉动作或沿用过期信息？这类故障演练，比让 Agent 在理想网络里连续运行更久，更容易发现上线后的问题。

## 数据被读过以后，权限仍然有用

权限检查不能只发生在工具调用前。有权限的人让 Agent 读取薪资数据，生成一张表，再分享给没有权限的人，原来合法的读取也可能造成后续泄露。

#403 对 Cloudflare OS 源码的分析介绍了一种实现：记录 Workspace 读过的数据源及权限，其他人访问共享空间时，再以访问者身份核验这些来源。已经共享的空间继续读取更敏感资料时，也要检查是否超出共享对象的权限。

这是一种可参考的工程做法，并非成熟通用标准。分析同时指出，Workspace 粒度较粗，数据源追踪依赖具体 Driver，外部请求与模型调用等出口也没有完全统一。一个敏感来源可能限制整个空间，漏记的来源又可能绕过控制。

实际设计要沿着数据走一遍：从源系统到上下文，再到缓存、Memory、生成文件和分享出口，哪里保留来源，哪里重新检查接收者权限。对任务本身，还应限制委托人、可操作对象、授权时限和外发范围。模型能调用工具，与这次调用得到授权，是两件事。

## 模型升级时，旧约束也要重新测试

#415 收录的 Claude Code 团队分享提到，新模型发布后会移除旧的提示和约束，再根据失败逐步加回。这个做法值得借鉴，但不能理解成流程越短越好。删除一段提示后任务仍稳定完成，才说明这段提示可能已经没有必要。

我会把旧设计分成两类。一类用于弥补模型的执行习惯，例如固定拆解步骤、重复提醒搜索；另一类用于约束系统的权限、预算和外部副作用。前者可以通过对照实验逐步删减，后者即使换了强模型，也应检查是否由平台或工具层可靠执行，而非直接取消。

模型缺少知识时，先尝试补充正确资料或工具；回执不清楚时，修接口；信息充分、工具正常而任务仍反复失败，再考虑模型能力是否不足。盲目增加重试可能把错误变得更贵，盲目升级模型也可能掩盖本来容易修复的环境问题。

对于多数团队，我倾向于从单 Agent、清楚的工具和简单的进度记录开始。只有在失败记录显示需要分支、独立复核或并发时，再增加对应机制。判断架构是否合适，看的是中断后能否继续、操作能否核对、维护成本是否可控，而非组件数量。
