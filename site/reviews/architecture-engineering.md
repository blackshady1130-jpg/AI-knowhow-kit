# 长程 Agent 如何运行：Context、状态、权限与恢复

**讨论 Context、Memory、工具、状态和运行时 · 更新至 2026.08**

---

## 核心判断：强模型会减少旧脚手架，但不会替代运行控制

> **Runtime 管的是执行过程：任务进行到哪里、Agent 代表谁行动、哪些外部动作已经发生、失败后从哪里恢复、结果如何验收。它不是给模型再补一层万能能力。**

#388 对 Agent Infra 的梳理适合用来划清这条边界。模型负责理解、推理和生成，Harness 把模型、工具、Context 与验证接成可运行循环（#151）；Runtime 则承接长期执行中的状态、权限、成本和恢复。三者会互相影响，但不能混为“模型能力”。如果模型缺少任务所需的核心知识或推理能力，增加 prompt、路由和重试只会让失败变得更慢、更贵，复杂脚手架也不能替代模型升级。

模型升级后，靠近模型的固定规则确实可以变薄。Claude Code 团队的访谈经验是：新模型上线时先消融旧 prompt、tool 和 workflow，再只按新的 failure case 加回约束（#415）。#417 进一步给出一个作者分析框架：固定脚手架可能减少，工具发现、权限、恢复、线上 Eval 和协调仍要由外部系统承担。前者来自特定团队实践，后者是分析判断，都不证明所有 Agent 会沿同一路线演化；它们共同支持的工程动作只有一个——每次模型升级都重测控制层，而不是永久保留旧流程或一次性删光。

## Context 有两条供应链：离线知识编撰与在线任务状态

企业 Context 至少有两条供应链。第一条在任务开始前，把制度、产品知识、案例和操作手册离线编撰成可检索材料；第二条在运行中查询 live data，并持续记录当前计划、工具结果、失败线索和外部变化。#414 用“离线编撰 + 在线查询”解释这种分工，也明确了边界：离线材料会陈旧，Memory 会积累错误，仍需来源、版本、更新和清理机制。

两条供应链不能用同一种更新规则。离线知识要标明 owner、版本、适用范围和失效时间；在线状态要记录任务 ID、写入时间、来源工具和确认程度。原始事实与工具回执应追加保存，计划可以随进度改写，Memory 中的长期结论只有经过复核才应跨任务复用。最终目标是让 Agent 在当前步骤拿到足够且可追溯的信息，多余材料不进入窗口。

运行时还要控制信息进入窗口的方式。Manus 的工程复盘建议选择当前所需 Context，把大体量工具结果外置，并留下继续执行所需的线索（#29）。这属于特定产品经验，不是各类 Agent 的统一最优解；可复用的部分是把“大结果的存放位置”和“下一步如何找回它”一起记录。否则压缩会删掉恢复线索，全量重放又会把关键约束埋进历史。

Context 同时影响成本。稳定前缀、上下文重放和频繁工具轮次会改变缓存命中与请求开销（#380），但访谈观点和具体 serving 实现不能给出通用收益幅度。工程上应分别测量固定规则、按需知识、live query 和任务状态的读取频率，再决定哪些进入稳定前缀、哪些留在外部存储；不能为了缓存把会变化的权限和状态冻结下来。

## 文件、checkpoint 和 branch 共同保存长任务状态

聊天历史把事实、计划、工具输出、失败和解释混在同一条时间线上。窗口即使装得下，Agent 也难以稳定回答“哪个结果已验证、哪个外部动作已执行、当前可以从哪里安全继续”。长任务因此要把状态拆成可寻址、可比较、可恢复的对象。

文件保存工作产物与来源。长程实践会把计划、中间结果、测试输出和子任务汇总写入 workspace，让后续运行只读取当前步骤所需部分（#297）。文件系统的价值是可见、可查和可比较，并不保证 Agent 一定找对文件；目录仍需命名、索引、owner、生命周期和删除规则。

Checkpoint 保存某一时刻的执行位置、预算、已确认事实和待办；Effect Log 另记外部动作的意图、参数、结果、可逆性与幂等条件。#184 的工程框架提醒，发送消息、修改 CRM、创建资源和合并代码的恢复方式不同：可逆动作可以回滚，不可逆动作应设置审批点，会产生重复副作用的动作必须先查执行回执。只保存对话而不保存外部效果，恢复就可能再次执行已经完成的操作。

Branch 保存替代路线和版本血缘。#384 对 RSI 的作者分析提出保留 Harness 版本、实验分支和拒绝原因；对一般长任务，更克制的做法是只在高代价、可并行验证或需要回退的节点分支。不要把每个步骤都包装成自我改进实验，但也不要只留下“当前最高分”而丢掉失败原因。

EdgeBench 为连续状态的价值提供了特定任务证据：保留 workspace 与反馈历史，可能改善某些长程系统任务的表现（#354）。它比较的是搭载不同 Harness 的完整系统，不能据此宣布某种 Memory 架构或某个模型普遍更强。可落地的判断是：若后续决策依赖过去的测试、失败路径或反馈，就应把这些状态显式保存，并用同一任务环境验证收益。

## 权限要跟随数据和产物，不只检查工具调用

权限控制常停在“Agent 能不能调用这个工具”。这只覆盖动作发生前的一刻。Agent 读取文档后，内容可能进入 Context、Workspace、Memory、摘要和最终产物；产物再被分享或外发时，原数据的访问边界也可能随之丢失。#403 对 Cloudflare OS 实践的梳理，把授权问题从调用前延伸到读取后、共享前和外发前，说明数据传播链也要受控。

一条可审计记录应能还原 `用户—Agent—任务—工具—对象—时限—数据来源—衍生产物`。前六项来自动态委托：系统需要知道 Agent 代表谁、为哪项任务、在多长时间内操作什么对象（#382）。后两项承接数据传播：读入材料时写入来源与策略标签，生成摘要、文件或消息时保留血缘；共享和外发前，再按来源策略与接收方重新检查。

实现上可以把任务分成只读探索、有限写入和高风险发布三个阶段，权限随阶段提升，并使用短期凭证。Memory 写入也应视为一次受控传播：标明来源、作用域、失效时间和删除入口，不能因为内容已经被模型概括就解除原权限。

这仍不是成熟的统一方案。#403 记录的实践存在 Workspace 粒度偏粗、Driver 覆盖不完整、出口策略未统一等限制；#382 涉及的身份与协议也仍在变化。本文因此只把“委托链 + 数据血缘 + 出口复查”作为设计要求，不把某一产品实现写成标准。

## 失败后先找最早不可恢复错误

恢复前先问：轨迹中哪一步之后，靠正常重试已经无法回到正确结果？#395 提出的“最早不可恢复错误”提供了一个够用的分流点。它是描述性归因框架，不是自动诊断真相；本篇只使用这一步方法，不复述评测 taxonomy 或统计数字。

找到该点后，再把修复送到对应队列：模型缺知识或推理失误，换模型或补训练；所需事实没有进入窗口，修 Context；流程顺序、状态写入或恢复逻辑错误，修 Harness/Runtime；工具返回错误或接口语义不清，修工具；依赖、网络或沙箱异常，修环境；正确结果被错误判定，修 Verifier。若还无法定位，就保留轨迹、输入快照和 Effect Log，交由人工复核，不能用增加重试次数掩盖未知故障。

恢复动作由错误发生后的外部效果决定。尚未产生副作用时，可以从前一个 checkpoint 重放；已写入外部系统时，先查 Effect Log，再选择补偿、回滚或人工接管；分支中已有可验证的替代路线时，再切换 branch。恢复控制要阻断错误扩散，避免局部失误演变成重复外发、数据覆盖或错误记忆。

## Agent 可以改进 Harness，但不能修改晋级规则

Agent 可以在受控范围内搜索更好的 Context 选择、工具循环和工作流。#355 建议使用 proposer–evaluate–accept：候选系统提出变更，在固定环境中运行评测，只有达到预设门槛才晋级。#384 补充版本分支、实验血缘和拒绝原因，使每次改动可复现、可撤销。两者都属于方法框架，不证明所有工作流都适合自动改 Harness。

三类对象必须留在候选系统权限之外：held-out eval 及其答案、权限与资源上限、关键节点的人工验收。#334 所讨论的预部署风险案例提醒，优化系统会寻找测试和环境中的意外路径；如果 proposer 能同时修改 Verifier、查看 held-out 数据或扩大自身权限，分数上涨就不能证明能力改善。

因此，Agent 可以尝试不同实现，但晋级规则应由独立负责人维护。每次接受变更时记录候选版本、评测集版本、成本、失败项、审批人和回滚点；线上失败案例只能进入下一轮候选或回归集，不能直接改写生产规则。

## 实践工具：长程 Agent 运行清单

| 模块 | 启动前必须写清的检查 |
| --- | --- |
| 目标 | 最终 artifact、完成条件、预算、超时和人工接管点 |
| Context | 离线知识版本、live query 来源、窗口选择规则和 Memory 失效时间 |
| 状态 | workspace 路径、checkpoint 频率、branch 条件和事实来源 |
| 权限 | 委托人、任务、工具、对象、时限、数据标签和外发复查 |
| 验证 | 本地检查、独立 Verifier、held-out case 与人工抽检 |
| 恢复 | 最早不可恢复错误、Effect Log、回滚/补偿动作和接管入口 |
| 成本 | 稳定前缀、重放范围、工具轮次、缓存指标和总预算 |
| 学习写回 | 可进入回归集的 badcase、review owner、晋级门槛和回滚点 |

## 这套方法不适用于哪些情况

一次性、低风险、无外部副作用的短任务，不需要完整 checkpoint、branch 和动态委托；保存最终输入输出并做一次结果检查通常足够。控制层的复杂度应由任务时长、外部副作用和恢复代价决定。

模型、知识和工具构成任务前提。必要知识缺失、关键推理无法完成或工具不提供所需操作时，应停止扩建控制层，改为换模型、补数据或重定任务；增加流程节点只会放大成本与定位难度。

对医疗、金融、高权限生产操作等高风险任务，这份清单又不够。它没有替代领域合规、独立审批、事故响应和责任主体；Runtime 只能执行这些制度，不能自行定义可接受风险。

## 哪些证据会改变以上判断

1. 若同一模型在没有持久状态、Effect Log 和专门恢复的简单 Runtime 中，能持续完成跨小时且有外部副作用的真实任务，并在成本、可靠性和事故率上不差于受控系统，可以删减状态与恢复设计。
2. 若模型升级后，结构化 Context、动态委托、数据血缘和分阶段权限在多类真实任务中反复降低成功率，且没有减少越权或恢复事故，说明控制层已经过度工程化，应缩小适用范围。
3. 若自动搜索的 Harness 在独立 held-out 任务、维护成本和安全审计上长期超过人工方案，且候选系统无法接触 Verifier、答案和权限上限，可以下调人工 workflow 设计的比重。
