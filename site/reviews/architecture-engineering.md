# 长程 Agent 如何运行：Context、状态、权限与恢复

**讨论 Context、Memory、工具、状态和运行时 · 更新至 2026.08**

---

## 核心判断：Harness 负责模型之外的运行工作

> **Harness 负责选择当前 context、调用工具、保存状态、限制权限、检查结果，并处理失败后的恢复。同一个模型接入不同 Harness 后，完成任务的效果可能明显不同。**

Harness 不只是高级 prompt。长程 Agent 可能读到过期规则、忘记中间产物、重复执行外部操作、错把局部测试当成最终验收，或者在恢复时覆盖已经完成的工作。这些问题需要状态机、文件、权限、日志和 verifier，单靠提示词无法解决。模型升级后，旧提示词可以变短；运行时对状态、工具和结果的责任不会随之消失。

Lilian Weng 将 Harness 的范围扩展到 structured context、workflow、代码和 optimizer（#355）。这意味着 self-improvement 不一定先修改模型权重，也可以先改进信息选择、工具循环和评价机制。

## Context 管理要区分四类信息

#13 把 context 操作归纳为写入、筛选、压缩和隔离；Manus 的工程复盘（#29）则把这些动作落到 KV-cache、工具设计和可恢复执行。两份材料都把长 context 处理成分层存储与按需装载问题。K3 的 BrowseComp 对照又显示，经过 compaction 的约 300K 轨迹略高于关闭 Context Management 的完整 1M 轨迹（#377）。这只是单项评测，但足以说明窗口容量与有效信息不是同一个指标。

至少要区分四类信息：当前步骤需要的工作上下文；可验证的原始事实和产物；从多次执行中总结出的操作经验；用户或组织的长期信息。它们的更新规则不同。原始 trace 应持续追加；临时计划可以改写；Skill 需要版本和回归测试；用户事实则需要权限、来源和删除机制。

真实用户已经在用关闭功能表达不信任。一次 Context Infra 现场交流中，十余位重度 Coding Agent 用户表示会主动删除、重置甚至关闭自动 Memory，因为系统可能把临时任务和偶发偏好写成长期事实，并在不可见的情况下再次调用（#369）。这不是统计意义上的用户调查，却把四个产品要求说得很具体：写入要准确、作用域要清楚、内容可见可删、调用可以追踪。

巨型 AGENTS.md 失败的原因也在这里。OpenAI 内部实践最终把入口文件降为目录，让 agent 按需读取知识库（#151）；Skills 的 description 承担触发条件，具体指令、脚本和素材留在可探索目录（#199）。#180 的对照实验进一步显示，自动生成的 context 文件可能让成功率下降 3%、推理成本增加 20% 以上。信息变多会扩大探索面，却不保证关键约束更容易被找到。

Claude Code 面向新模型时删除超过 80% 的系统提示词，coding eval 没有出现可测损失（#370）。被删掉的是重复、冲突或已经被模型内化的常驻规则；低频知识转向按需 Skill，工具约束留在接口，结果仍由代码和测试验收。这个案例支持定期删减旧脚手架，不支持“Harness 已经不重要”。

## Harness 也会影响推理成本

Agent workload 会反复读取 Context、调用工具、验证和重试。System Prompt 加入动态时间、工具定义频繁变动、历史状态每轮整段重放，都会破坏 Prefix Cache；定时任务集中触发还会制造流量峰值（#380）。因此，Context 设计同时是行为问题和成本问题。

缓存友好不等于把上下文永久冻结。稳定前缀可以承载不变规则，任务状态与低频知识按需加载，外部结果通过结构化 artifact 返回。K3 把消息协议、Context Management 和推理缓存一起设计（#377），说明模型、Harness 与 serving 已经在同一条系统链上。具体收益仍取决于请求分布、缓存实现和硬件，不能从单个模型报告直接外推。

## 为什么 Agent 常用文件系统保存工作状态

文件系统可以持久保存内容、按路径查找、比较版本，也方便人工检查。计划、测试输出、失败日志和中间数据不必一直放在 prompt 中；下一次运行只读取当前步骤需要的部分。与完全隐藏在向量库或模型摘要里的“记忆”相比，文件还保留了来源和修改记录。

这也是动态工作流能成立的基础。Anthropic 的长程实践用脚本保存中间状态、派发子任务并汇总验证结果（#297）；Claude Code 的建设者把工作描述为设计 loops，让计划、执行、测试和修正形成可检查的循环（#304）。运行时围绕不断变化、可被工具操作的 workspace 组织，而不是围绕聊天记录组织。

边界同样清楚：文件系统不会自动带来正确检索，也不等于长期记忆。命名混乱、重复 artifact 和失效规则会把问题从 token 窗口转移到目录。每类文件仍需要 owner、生命周期、索引和删除策略。

## 长时间任务需要保存失败和反馈

EdgeBench 为状态连续性提供了可量化证据（#354）。在 Opus 4.8 的 17 个任务上，保留 workspace 和反馈历史连续运行 12 小时得分 43.0；六次独立运行 2 小时再取最好结果为 36.1。Agent 在前一种设置中可以复用测试结果、失败路径和隐藏 judge 的反馈，后者每次都要重新摸索。

这个结果说明，长 context 和长时间工作不是一回事。后续决策需要知道：尝试过什么、为什么失败、哪些产物已经验证、还剩多少预算、哪些外部操作已经发生。如果这些信息没有结构化保存，即使窗口足够长，模型也可能在大量历史中重复犯错。

EdgeBench 的比较仍是系统比较。论文中的模型使用了不同 harness，任务汇总曲线也不代表每个任务都平滑进步。因此它支持“状态连续性有价值”，但不能单独证明某种 memory 架构或某个模型更优。

## 恢复需要保存外部动作和版本分支

传统容器和任务队列更适合短时、确定性、近似无状态的工作；Agent 往往运行更久、执行路径不确定，还会修改外部系统。#184 提出的 Effect Log、能力隔离和分叉恢复，说明这类任务不能只靠“失败后重试”。

Effect Log 要记录的不只是模型输出，而是外部动作的意图、参数、结果和可逆性。例如发送邮件、修改 CRM、创建云资源和合并代码，恢复方式完全不同。可逆动作可以回滚；不可逆动作需要审批点；重复执行会产生副作用的动作要有 idempotency key。只有把这些差异写进运行时，checkpoint 才不只是保存对话历史。

Sandbox 和 permission 也应与任务阶段绑定。探索期可以只读，形成计划后再授予有限写权限；接近发布时增加人工确认。权限应当随任务进度调整，而不是一次性开放整台电脑。

恢复不只发生在单次任务中。#384 对 RSI 的讨论把 backtracking 扩展到系统改进：保存不同 Harness 版本、失败分支、实验血缘与拒绝原因，在条件变化后允许重新启用旧路线。只有“当前最高分版本”的线性历史会丢失负结果，也可能让搜索过早停在局部最优。对一般 Agent 产品，最低要求是保留 checkpoint、失败原因和可撤销的版本迁移；不需要把每个工作流都包装成 RSI。

## 权限要记录 Agent 代表谁行动

传统身份系统通常区分人和服务账号；Agent 同时代表某个用户，又会自主选择工具与操作路径。只知道“这是哪个 Agent”还不够，系统需要记录它在代表谁、为哪项任务、以什么范围调用哪个工具（#382）。长期 API Key 无法表达这种动态委托。

一条可审计的授权记录至少包含 `用户—Agent—任务—工具—对象—时限`。高风险动作在执行前重新检查任务意图与对象范围，完成后把结果写入 Effect Log。当前 Agent Identity 产品能处理短期凭证和委托链，但“当前操作是否仍符合用户原始意图”还没有成熟的通用判断方法；这一限制应当由更窄权限和人工确认补上，而不是交给另一个模型猜测。

## Agent 可以改进 Harness，但不能自己修改评分规则

#355 讨论了一条较实际的自我改进路径：先让模型修改 context 函数、workflow 和代码，而不是直接修改 weights。候选 Harness 可以包含源代码、分数、轨迹和状态更新，coding agent 提出修改后，再通过 propose–evaluate–accept 流程筛选。#384 把它进一步落到版本树、私有测试、Sandbox、灰度和回滚，重点不在“自动生成更多 Prompt”，而在每次改动都能复现和撤销。

但自我优化只有在评价信号足够清楚时才容易工作。代码测试、封闭 benchmark 和可重复实验提供了密集反馈；科研 taste、维护性、长期产品质量和组织协作很难压成单一 utility。更危险的是，若 proposer 同时能改 verifier、权限或 held-out 数据，系统会优先找到评分漏洞。#334 展示的 Agent 利用隐藏测试和环境漏洞，已经说明优化器会搜索我们没有预料到的路径。

因此，至少三类对象要留在循环之外：不可由候选 Harness 修改的 held-out eval；权限与资源上限；关键节点的人工验收。Self-improvement 可以搜索实现，不能同时重写成功定义和安全边界。

## 实践工具：长程 Agent 运行清单

启动长任务前，可以用一页 **长程 Agent 运行清单** 写清以下内容：

| 模块 | 需要明确的内容 |
| --- | --- |
| 目标与结束 | 可验收 artifact、完成条件、预算和超时 |
| Context | 固定规则、按需资料、压缩策略、Memory 作用域与失效时间 |
| 状态 | workspace、checkpoint、事实来源、Skill 版本、失败分支 |
| 工具与权限 | 代表谁行动、对象范围、短期凭证、外部副作用、审批节点 |
| 验证 | 本地检查、外部 judge、held-out case、人工抽检 |
| 恢复 | 可重试错误、回滚动作、Effect Log、接管入口 |
| 推理成本 | 稳定前缀、缓存命中、上下文重放、工具轮次与流量峰值 |
| 学习写回 | 哪些 badcase 能改 Skill，谁 review，如何回归 |

这张清单方便团队排查失败来自模型推理、context 选择、工具执行、状态保存还是 verifier，而不是把所有问题都归为“模型还不够强”。

## 这套方法不适用于哪些情况

Harness 无法把缺少核心知识和推理能力的模型包装成前沿模型。#355 引用的自我改进实验里，强模型能改进 improver，较弱模型反而退化；这说明外部结构与模型智能互补。另一方面，新模型也可能内化一部分曾由 workflow 手写的启发式，使旧 Harness 变成阻力。架构应当支持消融、替换和回滚，而不是围绕某一代模型永久固化。

## 哪些证据会改变以上判断

1. 若同一模型在无持久状态、无专门恢复的简单运行时中，持续完成跨小时、有副作用的真实任务，并达到相同成本与可靠性，运行清单中的状态管理可以大幅简化。
2. 若自动搜索得到的 Harness 在严格 held-out 任务、维护成本和安全审计上长期超过专家设计，且不依赖改写 verifier，人工 workflow 设计的重要性应当下调。
3. 若模型升级后，结构化 context、Effect Log、动态委托和分阶段权限在真实任务中反复降低成功率且没有减少事故，说明这些外部约束已经过度工程化，需要缩减控制层。
