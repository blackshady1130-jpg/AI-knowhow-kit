# 架构与工程：从 Prompt Engineering 到 Harness Engineering

**覆盖 120 篇判读 · 2024-11 – 2026-06**

---

## 本章核心判断

> **模型能力只有进入可管理的运行系统，才能变成稳定能力。** Harness 的价值不在于给模型再套一层复杂流程，而在于把 Context、工具、状态、权限、结束条件、验证与错误恢复外化为可检查的结构。

Agent 架构与工程一直在追一个很实际的问题：**模型已经足够会说话、会写代码、会调用工具之后，系统该怎么接住它？**

过去一年，我看到这条线大概走过三步：

- **Prompt Engineering**（~2024）：重点是把一句指令写清楚，问法本身就是能力。
- **Context Engineering**（2025 中）：重点变成给模型准备什么信息，哪些该放进来，哪些必须挡在外面。
- **Harness Engineering**（2026 初）：重点继续往外移，开始关心环境、约束、状态、成本、权限和恢复机制。

这三步不是严格的阶段划分。更像是工程师的注意力一路往外挪：先盯输入，再盯上下文，最后盯模型运行时身边的整套系统。

4-5 月新增材料把这个变化说得更具体。Claude Managed Agents 把长时任务、状态管理、事件流和计费收回平台侧（#229）；Cursor 明确说同一个模型也要按版本持续调 harness（#260）；Claude Code 把 prompt caching 当成控制长程 agent 成本的关键部件（#250）。这些材料放在一起看，Harness Engineering 已经不是“会写提示词”的进阶版，而是在变成模型公司、IDE 和云平台都要抢的位置。

---

## 在研究主线中的位置

如果模型训练回答“系统最多可能会什么”，架构与工程回答“这项能力在什么条件下能持续工作”。它连接上游能力与下游评测：一方面为模型提供正确的事实和动作空间，另一方面为 verifier、人工接管和经验回流留下可观测状态。

## 关键判断

### 洞察 1：上下文很重要，但塞太多通常会坏事

这条判断在本主题里出现得最多，也最稳定。

2025 年 6 月，Gemini 模型负责人和 OpenAI 联创 AK 几乎同时提出“上下文工程”（#13, #14）。这件事的意义不在于又发明了一个新词，而在于大家开始承认：模型表现不好，很多时候不是模型不会，而是我们给它看的东西太乱、太旧、太多。

#13 把常见做法分成四类：写入式、筛选式、压缩式、隔离式。Manus 的实战分享（#29）和 9 月的阶段性汇总（#52）说明，这套思路不是纸面分类，确实能落到工程里。

但我现在更看重另一个反面结论：**无关信息不是中性噪声，它会抢模型注意力。** 长上下文不会替代 RAG，两者更像分工：RAG 先粗筛，长上下文再处理（#13）。#196 说得更极端：“The best context is no context”。这句话有点狠，但方向是对的：Agent 越轻，越不容易被无关材料拖偏。

到 2026 年初，#140 用 9,649 次实验把这件事量化了。文件原生架构对前沿模型有帮助，但对开源模型反而可能是负收益；紧凑格式也不一定省 token，因为 grep 输出密度高，会产生“grep 税”。所以格式不是第一变量，模型是否熟悉这种信息形态，才更关键。

### 洞察 2：文件系统正在变成 Agent 最顺手的工作台

这条线不是某一家公司单独讲出来的，而是几个来源各自碰到了同一个东西。

Manus（#29）先说得很直白：把文件系统当作“终极上下文”。网页内容可以从上下文里删掉，只要 URL 还在，Agent 随时能找回来；中间产物写成文件，也比一直塞在对话里更可控。

Cursor 的上下文管理文章（#115）也给出类似判断：未来 LLM 工具的最佳接口还不确定，但文件是一个简单、强大的基础单元。这个说法听起来朴素，但很重要。文件天然持久、可 diff、可搜索、可回滚，比临时对话上下文可靠得多。

OpenAI 内部 Harness Engineering 实践（#151）进一步把这个问题讲透了：一个巨大的 AGENTS.md 最后失败了，因为它过时快、占上下文，还会把模型带进无关细节。更好的做法是把 AGENTS.md 降级成目录，指向 docs/知识库，让信息按需暴露。Anthropic 的 Skills 设计（#199）也一样：Skill 不是一篇 markdown，而是一组 Agent 可以探索和使用的文件。

这背后的工程直觉很简单：上下文窗口有限时，不要把所有东西塞进 prompt；让 prompt 成为索引，让 Agent 自己按需取。数据库里没人喜欢全表扫描，Agent 也一样。

### 洞察 3：工具设计会直接改变 Agent 的思路

前 Manus 员工（#99）有个判断我觉得很准：自定义 Tool 像“外语”。说明书越长，模型越容易犯错；read/grep/edit 这类透明、原子化工具反而更稳。换句话说，工具不是外设，它会进入模型的推理路径。

Anthropic 的案例（#185）从产品侧验证了这一点。AskUserQuestion 工具怎么设计，Todo 怎么升级到 Task，从 RAG 转向 Grep+Skills，表面是在改工具，实际是在改 Agent 能看到的动作空间。工具越接近模型已经熟悉的操作方式，模型越不需要猜。

SkillsBench（#187）给了一个很有用的边界：2-3 个 Skills 效果最好，4 个以上就开始递减；中等长度的 Skills 胜过面面俱到的大文档。更有意思的是，Skills 对模型不熟的领域帮助更大，对模型已经熟的软件工程领域，反而可能引入冲突。

新增的 SkillFlow、Trace2Skill 和 faulty memory 研究把这个问题又往前推了一步（#244, #273, #277）。经验当然可以沉淀成 skill，但不能等同于“每次做完让模型总结一条 memory”。有价值的是保留轨迹、验证结果、合并重复经验，再抽象成可迁移 SOP。否则持续改写的 textual memory 很容易把真实证据慢慢替换成模型自己的猜测。#288 的“先写 Skill 再执行”也是这个逻辑：价值不在格式，而在把成功标准、常见错误和确定性工具提前写清楚。

### 洞察 4：Harness 工程的本质是把判断标准外化

2026 年初，讨论的重心开始从“怎么管理上下文”转到“怎么设计约束系统”。

#188 把这条线放进控制论历史：瓦特离心调速器、Kubernetes、AI Agent。这个类比有点大，但抓住了一个点：工程师的工作正在从直接执行，变成设计反馈回路。对 Agent 来说，关键不是让模型自由发挥，而是把什么能做、什么不能做、做完怎么验收写成可执行结构。

DeepMind 的 AutoHarness（#197）是一个很清楚的例子。它让 LLM 生成约束代码（is_legal_action + propose_action），在 145 个游戏上把合法动作率推到 100%。在这些场景里，Harness-as-Policy 甚至可以用纯代码策略替代推理时的 LLM 调用，成本几乎归零。

但这个结论不能随便外推。AutoHarness 主要在 1P 游戏中验证，2P 场景还要 MCTS 等搜索；真实业务里还有权限、状态、副作用、异常恢复。完整的 harness 至少要有动作合法性、Effect Log、知识与约束三层（#197），目前没有哪一层已经成熟。

4-5 月新增材料让我更确信一件事：harness 本身也会变成技术债。#253 和 #260 都说明，模型版本一变，旧 harness 可能马上失效。今天外部系统帮模型补的能力，下一版模型可能已经内化；今天有效的 scaffold，明天可能碍手。长期资产不一定是某套 workflow，而是任务样本、评估集、失败记录和领域 know-how。

### 洞察 5：Agent Infra 要解决的不是“跑起来”，而是“错了能收回来”

Jeff Dean 在对话中（#189）提到，Agent 改变了系统的执行语义：从确定性任务，变成概率性、长程、带状态的任务。这会动摇很多传统基础设施默认前提。

#184 的工程分析补了一个现实角度：K8s、Firecracker 这些系统主要为短时、确定性、无状态任务设计；Agent 执行则经常是长程、概率性、带副作用的。两者天然错配。解决方案指向三件事：Effect Log、能力隔离、分叉恢复。尤其是 Effect Log，把外部世界的副作用写成类似 write-ahead log 的结构，才有机会恢复和审计。

#119 的提醒也很实用：别把“更大 context window”当成解法。生产级 Agent 真正麻烦的地方，是 context runtime、failure semantics 和 cost control。并发、工具不稳定、状态丢失、缓存失效，这些问题不会因为窗口变大就消失。

Prompt caching、主动 compaction、sandbox、observability、状态恢复和责任链，正在变成生产级 agent 的必备词汇（#231, #250, #285, #289）。这些词合在一起，其实是在回答四个问题：谁授权、谁执行、谁验收、谁负责。这个责任链不清楚，Agent 越会操作工具，越可能把错误写进真实系统。

## 2026 年 6—7 月新增观察

长任务正在迫使 Harness 从 prompt 模板变成外部状态系统。Anthropic 的 Dynamic Workflows 用可执行脚本编排计划、分支、中间状态和验证（#297）；长时运行 Agent 的工程分享则把 model、harness 与同步机制明确解耦，要求外部状态、human contract、trace debugging 和错误恢复共同存在（#308）。单个上下文窗口不应同时承担计划、执行、记忆和自我验证。

Memory 也开始从功能点变成数据基础设施。Dreaming 关注记忆的新鲜度、偏好变化和时间状态（#301）；Agent-native Memory 进一步要求写入、更新、去重、版本和生命周期治理（#331）。KV cache 与 Engram 的讨论又把运行时记忆和长期内化拆开：哪些状态应该缓存，哪些知识应该进入 adapter/weights，是两种不同问题（#346, #347）。

“自动自我改进”需要降温。把经验不断写入 Memory、SOP 和 Harness 会让外部上下文越来越厚，并不等于模型学会了（#337）。更可靠的路径是保留轨迹、验证效果、合并重复规则，再决定写回 Skill、Eval 还是训练数据。Learning on the job 的难点也在这里：真实商业任务很难像 Coding 环境那样低成本重置和并行 rollout（#336）。

检索层也在继续结构化。SAG 用 SQL 在查询时动态连接实体与事件，试图以较低维护成本解决多跳检索断链（#350）。它提醒我们，Context Infra 的问题不只是召回更多文本，而是如何保存关系、时间与可更新状态。

1. **AGENTS.md 应该从“知识大包”退回“目录”**
   早期（#29, #63）很多人倾向把尽可能多的项目知识写进 AGENTS.md。#151 的 OpenAI 内部实践否定了这个方向：巨大的 AGENTS.md 会过时，也浪费上下文。#179 说明 AGENTS.md 确实能提效（时间 -29%，token -17%），但前提是精简、可导航，而不是堆材料。

2. **上下文工程不会因为模型变强就消失**
   #72 曾判断很多上下文工程会被模型能力覆盖。但一年后的证据更像是在说：模型升级会改变具体做法，不会消灭上下文管理。#131 提到的 cache/compaction，#140 提到的 file-native 差异，都说明这里还有大量工程问题。

3. **记忆不是模型特性，而是系统设计**
   #109 说记忆重要但没有标准解法，#117 的 Tolan 案例则说明，产品差异可能来自每一轮如何重建上下文。底模趋同时，记忆/上下文策略会变成产品差异的一部分。

4. **harness 需要持续评估和替换**
   #253 和 #260 共同指向一个麻烦：harness 会随着模型升级变旧。下一阶段的工程能力，不是搭完一套 agent 框架就结束，而是持续评估、裁剪、替换，必要时自动生成更适配当前模型的 harness。

## 对实践意味着什么

1. **把 Harness 当运行合同。** 明确输入、外部状态、允许动作、checkpoint、结束条件、失败恢复和人工接管，不让模型自己猜系统边界。
2. **Context 采用渐进式披露。** 入口文件做目录，证据与规则按需读取；每增加一段长期上下文，都要验证它是否提升成功率而非只增加探索。
3. **分开保存事实、经验与策略。** 原始 trace、用户事实、可复用 Skill 和临时工作状态采用不同生命周期，避免模型总结覆盖真实证据。
4. **Harness 必须随模型升级复评。** 新模型可能让旧编排成为技术债；保留可替换、可消融和可回滚的结构。

## 接下来如何证伪

1. **Harness Engineering 在现实软件团队里能不能落地？** 绝大多数软件不像 K8s、Linux 那样有完整 RFC、测试和讨论。很多团队是边开发边补规则。Harness 思路在这种环境下能不能提效，还是会变成新的形式主义？（#188）

2. **谁来为概率性执行的冗余买单？** 独立模型写两遍、跑三个副本、投票验证，都意味着 2-3 倍成本。对还在找 PMF 的 Agent 产品，这个账能不能打平？（#189）

3. **OS 层与 Application 层的状态边界在哪？** 如果 Agent OS 足够强，可以自己管理持久记忆和项目上下文，很多 Application 的领域状态优势会被削弱。Application 的壁垒要看 OS 层通用记忆管理能做到什么程度。（#196）

4. **托管运行时会让生态更开放，还是更集中？** Anthropic 开始收拢 Managed Agents 与 runtime/control plane（#229），OpenAI、Cursor、LangChain 也在争夺执行环境。工具协议可能越来越开放，但真正值钱的状态层和运行层，反而可能越来越集中。
