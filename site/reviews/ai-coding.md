# 代码生成变便宜以后：验证、路由与维护成为新成本

**覆盖 Coding Agent、工程协作与生产力相关判读 · 更新至 2026.07**

---

## 核心判断：AI Coding 重排了成本，没有取消工程

> **代码生成的边际成本快速下降后，软件交付的瓶颈转向任务定义、验证、模型路由、review、集成和长期维护。AI Coding 先跑出来，是因为软件工程已有高密度反馈和可回滚基础设施；这种优势不能直接外推到低反馈工作。**

“模型写了多少代码”越来越像一个中间指标。代码可能编译却不符合需求，测试可能通过却覆盖不足，PR 数量增长也可能把 review 队列推成新的瓶颈。真正的生产力变化要从需求进入系统开始，一直算到上线后的维护与故障。

AI Coding 的特殊价值，是它让 Agent 时代的几个问题提前暴露：怎样给 context、怎样定义完成、何时用小模型、如何保存中间状态、谁批准合并，以及一次成功是否值得它消耗的 token 与人工注意力。

## 为什么代码是高反馈验证场

代码天然拥有可执行 artifact。编译器、类型检查、单元测试、diff、Git 历史、CI、review 和 rollback 构成多层反馈；#111 对程序员率先受益的解释正落在这里。#27 所说的“可验证性边界”也并非模型只能做代码，而是结果越容易被外部系统判断，Agent 越容易反复修正。

高反馈不等于自动正确。#124 的 OctoCodingBench 区分单条规则遵循与多条规则同时满足：模型可以分别理解各项约束，却在一次真实改动中顾此失彼。#289 强调 Git、PR 和 review 是责任容器，正因为生成过程并不天然可信。测试本身也可能有问题；#360 对 SWE-Bench Pro 的审计估计约 30% 任务存在不同类型缺陷，提醒我们“通过测试”只在测试成立时有意义。

这个边界决定了 Coding 的经验怎样迁移。财务、销售和管理任务若缺少版本历史、可重放环境和独立 verifier，就不能照搬“让 Agent 多试几次”的开发模式。

## 局部提速会把瓶颈推向下游

METR 的随机对照实验提供了一个反直觉样本：参与研究的资深开发者使用 AI 后，客观完成时间慢了 19%，主观却认为自己快了 20%（#178）。它覆盖特定开发者和熟悉代码库，不能代表整个行业；但“主观流畅感与端到端速度可能相反”这一点值得保留。生成等待、检查陌生代码、修复近似正确的实现，都会被使用者低估。

另一侧也有真实增量。重度使用 Codex 的工程师提交更多 PR（#156）；Cursor 2026 春季数据看到代码量、mega PR 和 tool calls 上升（#292）。这些结果说明产出入口扩大了，却没有自动回答 review 时长、返工率、线上故障和维护债务。企业开始限制 token 使用（#293），本质上是在把 adoption 指标改成单位有效产出。

约束理论给出更好的测量单位：找到当前交付链的瓶颈，再观察 AI 是否缩短整条链路。若瓶颈已经从编码迁到 code review，继续增加生成量会扩大在制品，而非提高吞吐。

## 模型路由要从真实工作负载出发

Databricks 用近期人工编写、已经合并的 PR 构建内部 benchmark（#358）。他们移除原始实现，保留任务说明和隐藏测试，封闭 git 历史并做人工抽样检查。结果出现清楚的能力分层：高复杂度设计和深层代码任务需要强模型，配置、flag 和日常维护等中低复杂度任务可以交给更小、更便宜的模型。

GLM 5.2 在这套任务中进入最高能力档，质量与 Opus 4.8 接近，文中报告的单任务成本约为 1.28 美元，对比 Opus 的 1.94 美元。这个结果支持“open-weight 模型已经进入某些大型企业代码 workload”，但边界很具体：Databricks 内部代码库、可测试任务、当时模型与 harness。它不是跨企业、跨语言的普遍质量结论。

更重要的反例来自 token 单价。Sonnet 5 单 token 更便宜，却因工作时间更长、读取内容更多，总 token 约为 Opus 4.8 的 1.9 倍，最终任务成本更高且完成率更低。工程选型应该优化 cost per accepted task，而不是 price per token。

## Harness 可以把模型价差放大或抵消

Databricks 还发现，相同模型和 thinking effort 接入不同 harness 后，部分任务成本相差两倍以上而质量接近（#358）。表现更高效的 Pi 每轮重发 context 约少三倍。缓存、context 选择、工具循环和终止策略会直接改变总 token；它们不是模型之外可以忽略的包装。

Cursor 针对不同模型调 harness、用线上 Keep Rate 与后续用户行为验证结果（#260）；Artificial Analysis 把 runtime 成本和延迟带入 Coding Agent 比较（#266）。这些实践指向同一采购单位：比较 coding system，而非只替换模型名称。

Harness 也会制造维护成本。规则越多，模型越可能在冲突上下文中多做无效探索；#180 的实验显示自动生成的 AGENTS.md 让成功率下降、推理成本上升。入口文件适合做导航，详细知识按需读取，并通过失败案例回归，而不是把仓库说明堆成第二份代码库。

## 测试既是生产基础设施，也是治理对象

#360 的意义不只是某个榜单失准。它把 coding eval 拆成任务数据、prompt、hidden tests、环境和 agent 轨迹五个可审计对象。过严测试会处罚合理实现，覆盖不足又会放过残缺修复；模型失败与通过都可能被错误解释。

真实开发允许查文档、搜索代码和参考历史模式，公开 benchmark 又必须防止原始答案泄漏（#333）。强 Agent 还会主动寻找隐藏测试或环境漏洞（#334）。因此，企业内部 eval 最好取近期真实任务，采用时间切分与封闭历史；确定性测试之外保留人工抽检，检查实现质量、可维护性和是否走了预期路径。

测试治理也应进入生产。由 AI 新增的测试需要 review；失败用例要标记是需求问题、实现问题还是测试问题；被频繁绕过的 verifier 应升级。让生成和验证一起扩张，才能避免“更多代码、同样少的判断力”。

## 人的角色从输入者转向责任节点

Plan → Annotate → Execute 是目前较稳的协作形式（#163）：Agent 写计划，人直接标注目标、影响范围和验收缺口，批准后再执行。它让人类注意力集中在高杠杆决策，而不是逐 token 监督。Cognition 的 multi-agent 实践也更接近“一名执行 Agent 加若干 intelligence 角色”，而非多人同时修改同一代码面（#246）。

40 万个 Claude Code session 的分析显示，非软件职业用户也能借 Agent 编程，但领域理解、清楚指令和发现错误的能力仍拉开差距（#318）。这解释了为何 expertise 没有随着生成降价而消失：专家的价值更多体现在选择问题、识别隐患和接受责任。

## 实践工具：工作负载路由表与全成本账本

先按风险和可验证性给任务分层，再路由模型：

| 任务层 | 例子 | 默认路由 | 必要验证 |
| --- | --- | --- | --- |
| 低风险、高可验 | 配置、flag、机械迁移 | 小模型或低 effort | lint、单测、diff |
| 中风险、边界清楚 | 局部功能、测试补齐 | 中档模型 | 集成测试、owner review |
| 高风险、结构性 | 架构变更、数据迁移、权限 | 强模型 + 书面计划 | 专家评审、演练、回滚 |
| 低可验、需求开放 | 新产品方向、复杂重构 | 人主导探索，Agent 辅助 | 原型、用户证据、阶段决策 |

每次路由同时记一笔全成本：模型与 token、wall-clock、重试、review、返工、CI、部署故障和未来维护。最终指标用 accepted task、cycle time 和逃逸缺陷，不用生成代码量代替。

## 适用边界

这套方法更适合有代码库、自动测试和明确 owner 的工程组织。原型、一次性脚本和个人工具可以接受更轻的流程；安全关键、金融或基础设施变更则需要更严格的人工节点。Databricks 的路由结果和各家内部数据说明方向，不提供可直接复制的模型名单。模型版本、价格和 harness 会变化，路由表必须由本地 eval 更新。

## 如何证伪这套成本判断

1. 若独立研究在熟悉代码库与陌生代码库中都显示 AI 同时降低 coding、review、返工和维护成本，瓶颈迁移将不再是主要约束。
2. 若同一真实 workload 上，模型排名对 Harness、预算和成本口径不敏感，系统级选型可以简化为模型级选型。
3. 若生成代码量或 PR 数长期稳定预测用户价值、故障率和团队吞吐，全成本账本可以收缩；目前证据只支持把它们当中间指标。
