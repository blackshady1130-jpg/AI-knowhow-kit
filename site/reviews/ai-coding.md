# AI Coding 如何改变软件开发的成本

**讨论 Coding Agent、工程协作和生产力 · 更新至 2026.08**

---

## 核心判断：代码生成变便宜，交付成本会转移

> **AI 降低了写代码和尝试方案的成本，但需求澄清、测试、Review、集成、上线和维护仍要由工程系统承担。判断 AI Coding 是否提高生产力，要从任务提出算到结果被接受，不能只统计生成了多少代码。**

软件工程较早受益于 Agent，不只是因为训练数据里有很多代码。代码可以编译、运行、比较 diff、执行测试、回滚版本；Git 和 CI 还能记录谁改了什么、哪一步失败。模型因此能在一次任务里获得多轮反馈，而不是提交答案后才知道对错。

但可验证不等于容易交付。需求可能含糊，测试可能漏掉关键约束，局部修改也可能破坏性能、安全或后续维护。代码生成越快，这些原本分散在开发流程中的成本越容易集中到 Review 和验收阶段。

## Coding 发展较快，因为结果可以运行和回滚

#111 对程序员率先受益的解释，重点就是代码已经有编译器、类型检查、测试、Git、Review 和 rollback。#27 进一步指出，外部系统越容易判断结果，Agent 越能根据反馈修正。这些条件让 Coding 成为 Agent 的理想试验场，但不能推出模型只能处理代码。

反馈也有层次。单元测试能检查某个函数，集成测试能检查组件协作，diff 和代码历史帮助人判断改动范围。#124 的 OctoCodingBench 说明，模型可以分别理解多条规则，却在一次修改中顾此失彼；#373 的 WorkBuddyBench Code track 则把需求理解、仓库探索、实现和隐藏测试放进同一个 workspace 任务。后者不要求复制唯一 gold patch，更接近工程交付，但分数仍属于模型、Harness、环境和测试组成的完整系统。

这套条件也是 Coding 经验向其他行业迁移时最容易被忽略的部分。财务、销售或管理任务如果没有版本历史、可重放环境和独立验收，就不能照搬“让 Agent 多试几次”。多试只会积累更多难以核对的中间结果。

## 写代码更快，项目不一定更快

METR 的随机对照实验提供了一个反直觉样本：参与研究的资深开发者使用 AI 后，客观完成时间慢了 19%，主观却认为自己快了 20%（#178）。研究覆盖的是特定开发者和熟悉代码库，不能代表整个行业；它能支持的结论更窄——交互流畅和代码出现得快，可能让人低估等待、检查和返工时间。

另一侧也有真实增量。重度使用 Codex 的工程师提交了更多 PR（#156）；Cursor 的 2026 年春季数据看到代码量、mega PR 和 tool calls 上升（#292）。这些指标证明产出量增加，却没有回答 Review 时长、返工、故障和维护债务是否下降。企业开始限制 Token 使用（#293），也说明调用量已经不能单独代表价值。

多 Agent 会把这个问题放大。#413 记录的 ADE 实践可以同时管理多个 Coding Agent、worktree、Terminal、Browser、Review 和 PR。并发任务更容易启动后，人的注意力并不会同步增加：谁卡住了、哪个改动风险最高、哪份结果值得先看，都会变成新的排队问题。若团队一天只能认真验收五个变更，同时启动二十个 Agent 不会得到四倍吞吐，只会更快堆出待审 PR。

工程团队应先找出当前 cycle time 最长的环节。如果编码最慢，Agent 可能直接提速；如果瓶颈已经转到需求决策、Review、CI 或发布，继续提高生成量可能让交付更慢。

## 模型、effort 和 Harness 要按任务选择

Databricks 用近期人工编写、已经合并的 PR 构建内部 benchmark（#358）。他们移除原始实现，保留任务说明和隐藏测试，封闭 Git 历史并做人工抽样。结果出现了任务分层：高复杂度设计和深层代码任务需要更强模型，配置、flag 和日常维护可以交给更小、更便宜的模型。

文中报告 GLM 5.2 在这套内部任务上的单任务成本约为 1.28 美元，Opus 4.8 约为 1.94 美元；Sonnet 5 虽然单 Token 更便宜，总 Token 却约为 Opus 4.8 的 1.9 倍，最终成本更高且完成率更低。这些数字只适用于当时的 Databricks 代码库、模型、Harness 和计价方式，不能直接变成其他团队的采购表。它们真正说明的是：应比较 cost per accepted task，而不是 price per token。

同一个模型也不能默认 effort 越高越好。Opus 5 的 FrontierCode 主集与扩展集最高分出现在 medium，max 反而回落；与此同时，大多数主流评测仍由 max 取得最好结果（#374）。对真实 Coding 任务，应一起记录完成率、错误修改、Token、wall-clock 和 Review 时间，在本地任务上寻找合适档位。

Harness 也要跟着模型更新。#415 收录的 Claude Code 团队经验是：新模型发布时先消融旧 prompt、tool 和 workflow，再根据新的 failure case 加回必要约束。删掉的是模型已经内化、彼此冲突或没有继续带来收益的脚手架，测试、权限和验收并没有随之消失。#405 讨论的 DSH 更进一步，允许运行时替换 Agent loop；这为自修改 Harness 留出空间，也带来生命周期、状态迁移和回滚复杂度。当前材料不足以证明这种架构适合普通 Coding Agent。

## 测试通过之前，先确认测试可信

测试是 Coding Agent 的优势，也是可能被误读的地方。#360 对 SWE-Bench Pro 的审计估计约 30% 任务存在不同类型缺陷：有些测试过严，会处罚合理实现；有些覆盖不足，会放过残缺修复。这个比例属于该审计样本，不能外推到所有代码评测。

企业内部更实用的做法是使用近期真实任务、时间切分和封闭历史；确定性测试之外再抽查需求覆盖、可维护性和改动路径。真实开发者查询文档、搜索代码和参考提交历史通常合理，读取 benchmark 的原始 patch 却可能构成答案泄漏（#333）。强 Agent 还会寻找隐藏测试和环境漏洞（#334），所以通过与失败都要留下轨迹，判断究竟是实现、需求还是测试出了问题。团队还应为测试质量指定 owner，把被绕过、误判和覆盖不足的案例放进回归集；更完整的 Verifier 校准和失败归因方法见“评测与基准”。

## 人应检查计划和风险，不要逐条批准命令

Plan → Annotate → Execute 仍是一种有效协作方式（#163）：Agent 先写计划，人直接标注目标、影响范围、验收缺口和不可触碰的边界，批准后再执行。它把人的注意力放在需求和风险上，而不是逐 Token 监督。

#396 收录的数据进一步说明了控制点为什么要上移。在所述 1,053 人实验中，人工只拦截了 13.6% 的危险命令，后台分类器拦截率为 89%；全量行为数据里，用户对单条 permission prompt 的批准率达到 97%，对整体 Plan 的拒绝率却有 39%。这些数字来自 Claude Code 的特定实验和产品设置，不能证明自动分类器在所有场景都优于人。它们至少说明，高频确认框很容易退化为快速点击，而计划、权限边界和异常分支更可能得到认真检查。

更合适的分工是：Runtime 负责按规则持续拦截，人负责定义目标、对象范围、生产权限和高风险例外；执行中出现规则外情况时再暂停。最终合并仍由明确 owner 批准，并保留 diff、测试、失败记录和回滚点。

## 多 Agent 的上限取决于团队能验收多少结果

#413 的实践指出，worktree 可以隔离文件修改，却不能自动隔离端口、数据库、Cache、登录状态和其他运行资源。并行任务还需要清楚的状态索引：谁在运行、谁等待权限、谁已完成、谁产生冲突。否则 Agent 数量增长会把协调问题藏进一排终端窗口。

验收界面也应匹配产物。代码适合看 diff、测试和静态检查；网页要直接看渲染结果；数据迁移要看前后计数、抽样和回滚演练。通用聊天窗口很难承担所有验收。团队真正需要扩展的，不只是 Agent 的执行能力，还有发现异常、排序风险和检查不同 artifact 的能力。

多 Agent 适合边界清楚、可独立验证的任务。多个 Agent 同时修改同一模块、共享数据库或争用同一环境时，协调成本可能高于并发收益。此时减少并发、明确单一执行者，往往比增加更多“分析角色”更可靠。

## 实践工具：任务分级与成本记录表

| 任务层 | 例子 | 默认安排 | 必须记录的验收与成本 |
| --- | --- | --- | --- |
| 低风险、高可验 | 配置、flag、机械迁移 | 小模型或低 effort | lint、单测、diff、wall-clock |
| 中风险、边界清楚 | 局部功能、测试补齐 | 中档模型；必要时并行探索 | 集成测试、owner Review、返工 |
| 高风险、结构性 | 架构变更、数据迁移、权限 | 强模型 + 书面计划 | 专家评审、演练、回滚、逃逸缺陷 |
| 低可验、需求开放 | 新方向、复杂重构 | 人主导探索，Agent 辅助 | 原型、用户证据、阶段决策 |

每次任务记录模型、effort、Harness、Token、wall-clock、重试、Review、返工、CI、发布故障和未来维护。最终指标使用 accepted task、cycle time 和 escaped defects；生成代码量只用于解释工作量变化，不用于替代交付结果。

## 这套方法适用于哪些团队

这套方法更适合有代码库、自动测试、版本管理和明确 owner 的工程组织。原型、一次性脚本和个人工具可以采用更轻的流程；安全关键、金融或基础设施变更需要更严格的权限和人工节点。模型版本、价格与 Harness 会持续变化，路由表只能由团队自己的任务和成本数据更新。

## 哪些证据会改变以上判断

1. 若独立研究在熟悉与陌生代码库中都显示 AI 同时降低编码、Review、返工和维护成本，且没有把工作转移给其他角色，瓶颈迁移将不再是主要约束。
2. 若同一真实 workload 上，模型排名对 Harness、effort、预算和成本口径长期不敏感，系统级选型可以简化为模型级选型。
3. 若大量真实团队在多 Agent 并发增加后，cycle time 持续下降且 Review 队列、冲突和逃逸缺陷没有上升，人的注意力就不再是主要扩展上限。
