# AI Coding：从效率幻觉到协作范式的重建

**覆盖 70 篇判读 · 2025.07 – 2026.06**

---

## 本章核心判断

> **AI Coding 先跑出来，不只是因为模型更会写代码，而是软件工程已经拥有代码库、测试、Git、review、CI 和回滚这套高密度反馈环境。** 生成变便宜后，真正稀缺的转向问题定义、架构、验证、维护和责任。

AI Coding 最容易被讲成一句话：用 AI 写更多代码、更快交付。

但我现在更愿意从另一个角度看：代码生成变便宜之后，软件工程里真正贵的东西反而更清楚了。需求理解、架构判断、review、测试、发布、回滚、责任划分，这些原来就麻烦的环节，并没有因为模型会写代码而消失。

METR 的随机对照实验是一个很好的提醒：资深开发者用 AI 后，客观编码速度慢了 19%，但主观感觉快了 20%（#178）。这个结果很刺眼，因为它说明“感觉更快”和“系统真的更快”不是一回事。AI 加速了写代码，但也可能增加 review、理解、返工和集成成本。

从 2025 年中的 vibe coding 争论，到 AGENTS.md 的实验，再到 Harness Engineering、Skill Engineering 这些实践，AI Coding 的讨论一直在回到同一个问题：人到底该站在哪里？是把实现交给模型，自己做架构和验收；还是继续亲手写，只把模型当补全工具；或者二者之间还有新的协作方式？

4-5 月新增材料让这个问题更具体。coding 既是开发者工具赛道，也是 agent 训练、产品体验和商业化的高反馈场景（#235, #265）。Cursor、Claude Code、Artificial Analysis 的实践都说明，比较对象不再是裸模型，而是模型、harness、缓存、工具可靠性、成本、延迟和线上反馈组成的一整套系统（#250, #260, #266）。

## 在研究主线中的位置

AI Coding 是模型、Harness、Eval、产品和商业化同时工作的高反馈验证场。它让我们更早看到长程 Agent、Skill、动态工作流与组织分工会怎样变化；但代码的可执行性和可回滚性也意味着，它的进展不能直接外推到法律、管理、销售或人生决策。

## 关键判断

### 洞察 1：可验证性决定了 AI 能走多远

这是 AI Coding 能先跑出来的根本原因。

#27 从软件工程角度提出“可验证性是 LLM 的极限”：LLM 能生成代码，但验证责任仍在人类，且很难完全自动化。#79 Jason Wei 的“验证者定律”把边界讲得更清楚：可验证任务会被 AI 更快吞没；真正有价值的工作，是发明新的衡量法则。谁定义 metric，谁就定义了智能往哪里卷。

#111 Notion 创始人把这个判断推到非编程领域：程序员率先受益，不是因为程序员最好替代，而是因为代码天然有验证闭环。写错会报错，改坏了可以跑测试、看 diff、回滚。普通岗位的问题反而更难：上下文碎，结果不好验。

#124 OctoCodingBench 又补了一层：代码对，不代表过程合规。单项规则遵循（CSR）80%+，但所有规矩同时遵守（ISR）只有 10%-30%，Claude Opus 4.5 也只有 36.2%。真实工程不是“能不能写出一段对的代码”，而是能不能在系统约束里写出可以上线的代码。

这也是为什么 Coding Agent 先跑出来：软件工程已经有 Git、PR、CI、测试、review、rollback、diff 这些责任容器（#289）。SaaS-Bench 把同样的 agent 放进 CRM、财务、人事工作流后，字段填错、状态没复查、早期错误传导，问题马上暴露（#285）。可验证性不是抽象优势，而是一套具体制度。

结论很简单：AI Coding 的边界不只由模型智力决定，也由验证机制决定。

### 洞察 2：AI 加速了编码，但瓶颈会换地方

#178 用约束理论解释了效率幻觉：AI 加速的是编码这个环节，但如果瓶颈在 Code Review、集成部署、需求理解，局部提速就会被下游吃掉。Spec、Rule、Skill 这套架构之所以重要，是因为它试图把隐性知识写出来，让 AI 不再从“猜”开始，而是从“读规则”开始。

#156 给了一个正面数据点：重度使用 Codex 的工程师比轻度使用者多提交 70% PR，而且差距还在扩大。但这个复利不是“放手让 AI 写”。前提是人还在判断、拆任务、验收和修正。完全放手的 vibe coding 和完全不用 AI，都不太像终局。

#186 的说法很有代表性：编程一直是 90% 思考和 10% 打字，LLM 消掉的是那 10%。这句话可能夸张，但方向对。真正麻烦的是理解问题、设计结构、判断结果。

Mario Zechner 对 vibe coding 的批评补了反面证据（#247）：agent 会高速、批量、重复犯小错，局部决策会把系统推向不必要的复杂度。#249 又提醒真实 token 成本和订阅制补贴会影响 ROI。Claude Code 的 prompt caching（#250）也说明，长程 coding agent 能不能跑得起，本身就是工程优化问题。

### 洞察 3：Plan → Annotate → Execute 是目前最实用的协作形态

#163 里 Cloudflare 工程师分享的工作流很值得借鉴：在评审和批准书面计划前，不让 Claude 写代码。plan.md 变成共享状态，人类在编辑器里对 AI 计划做精准标注。这个模式好在它没有神化模型，也没有把人降级成旁观者。人负责判断和边界，AI 负责执行和改动。

#148 从更抽象的角度说 Agentic Engineering：语义分支、动态工具链、闭环自省。#149 则说 AI 编程最大挑战不是生成质量，而是上下文记忆不足。这些说法合在一起，我会理解成一个更朴素的模式：人像技术负责人，Agent 像开发者。人给目标、规则和验收标准，Agent 做实现、测试、提交 PR。

这个模式不是某一个人的工作流。#149、#163、#156 都在不同角度提到类似结构。它未必适合所有团队，但比“让模型直接写完整功能”稳得多。

Cognition 对 multi-agent 的更新也很克制：不是所有 agent 并行写代码，而是一个 agent 写，其他 agent 提供 intelligence（#246）。Cursor 的 per-model harness 调优（#260）也说明，模型升级不会自动变成产品收益。每个新模型都要重新调上下文、工具、缓存、延迟和线上反馈。

### 洞察 4：AGENTS.md 有用，但不是越多越好

这是这一年认知变化最大的子话题之一。

#179 的实验显示 AGENTS.md 带来 28.64% wall-clock time 下降和 16.58% output token 减少，效果很明显。可 #180 的另一项严格实验直接泼冷水：LLM 自动生成的上下文文件让任务成功率下降 3%，同时增加超过 20% 推理成本；开发者手写文件也只带来 4% 弱提升。上下文文件让 agent 多做了很多探索，但没有换来更高成功率。

#151 的 OpenAI 内部实践给了原因：一个巨大的 AGENTS.md 失败了，因为上下文稀缺，信息还会迅速过时。最后他们把 AGENTS.md 降级为目录，指向 docs/知识库，做渐进式信息披露。#199 的 Skills 设计也一样：Skill 不是 markdown 文件，而是可被 Agent 探索和操作的文件夹；description 字段不是摘要，而是触发条件。

#288 的“先写 Skill 再执行”把这件事扩展到个人工作流。AI 每次新开任务都接近白纸，只有把调研方法、写作偏好、工具配置、踩坑经验写成可读、可执行、可迭代的文档，成功经验才可能复用。#259 的 Learning Beyond Gradients 也在讲类似方向：先把在线经验变成可测、可回滚的软件规则，再反哺训练。

所以问题不是“要不要给上下文”，而是“给什么结构的上下文”。AI Coding 不会只停在 prompt 调教，最后还是会回到工作流设计。

### 洞察 5：工具竞争正在从补全准确率，转向真实工程环境

#56 对三大工具的定位很清楚：Cursor 更偏创意和探索，JetBrains 面向大型企业级工程，Claude Code 是终端原生、注重隐私的专家工具。三者不是简单谁更好，而是服务不同战场。简单不是便宜功能，而是经过取舍后的结果。

#191 CursorBench 揭示了评测困境：公开基准在前沿水平上已经失效。一致性差，任务和真实开发请求不匹配，污染严重。Cursor 的做法是从真实产品流量里构建评测，通过线上-线下闭环持续迭代。公开基准饱和后，Haiku 这样的小模型可以媲美甚至超过 GPT-5，几个百分点排名差异不一定对应真实体验差异。

Artificial Analysis 的 Coding Agent Index 代表下一步方向：不能只看静态 benchmark 裸分，还要看 agent runtime 里的成本、延迟、缓存和 harness（#266）。Cursor 与 SpaceX/xAI 的交易传闻也说明，IDE 的价值在入口之外，还包括开发者行为数据、真实工作流、训练反馈和 runtime 飞轮（#245）。AI Coding 的竞争会越来越像“谁掌握真实工程现场”。

## 2026 年 6—7 月新增观察

真实产品数据确认了“产出变多，瓶颈迁移”。Cursor 2026 春季报告显示代码量、mega PR 和 tool calls 上升，同时 power user gap 与 review 成本也在扩大（#292）。企业开始限制 token 使用，则说明 adoption 指标正在从“用得多”转向单位有效产出（#293）。

Coding Agent 也在从工具变成工作系统。Codex 把定位扩展到通用知识工作（#295）；Anthropic 的动态工作流用脚本保存中间状态并组织多 Agent 验证（#297）；Claude Code 核心建设者把自己的工作描述成设计 loops，而非直接写代码或 prompt（#304）。这些变化共同把人的角色推向目标、约束、验证和收敛。

但 expertise 没有消失。40 万个 Claude Code session 显示，非软件职业用户也能借 Agent 编程，但真正拉开差距的是领域理解、清楚指令和发现错误的能力（#318）。AI 创业复盘也给出同一边界：第一次 build 更快了，数据口径、权限、审计、文档、维护与现金流并没有消失（#329）。

评测正在追上这些变化。真实开发允许查文档和历史，但 benchmark 必须区分合理检索与答案泄漏（#333）；更强模型甚至会主动利用隐藏测试和环境漏洞（#334）。Coding 的验证闭环很强，却不是自动正确。

- **AGENTS.md 从“有用”变成“要会用”**：#179 证明它能提效，#180 和 #151 说明它也会添乱。上下文价值不在于信息多，而在于结构清楚、按需暴露、能被 agent 找到。

- **vibe coding 会留下来，但不是生产级工程的默认方式**：#33 说批评 vibe coding 像批评手机录不了电影，这个类比仍然有力。#173 也提醒，没人能 vibe code 一个车队管理应用，再用 vibe 式企业销售去分发。两者不矛盾：vibe coding 适合个性化需求和原型验证，生产级工程需要纪律化协作。

- **“AI 替代程序员”这个问题太粗了**：#194 说软件开发者 AI 暴露分 8-9，但 #156 提醒，从“90% 代码由 AI 写”到“不需要 90% 工程师”，中间隔着很多层。更可能出现的是新角色：设计生成环境、维护评测、写规则、做验收的人。

- **coding agent 要按系统来评估**：#260 和 #266 显示，质量由模型、harness、cache、成本、延迟、工具可靠性和线上 Keep Rate 共同决定。以后说某个 coding agent 强，必须先问：在什么运行时、什么成本、什么真实工作流里强？

## 对实践意味着什么

1. **先计划和验收，再生成。** 对高风险改动采用 Plan → Annotate → Execute；把测试、影响范围和停止条件写进共享计划。
2. **把 AI 产出计入完整交付成本。** 同时看 coding 时间、review、返工、集成、token、维护和线上故障，不用代码行数或 PR 数量代表生产力。
3. **让规则可导航、可验证。** AGENTS.md 做入口，详细知识放在按需文档与 Skills；每条长期规则都要有触发条件和验证方式。
4. **保留人类责任链。** Agent 可以执行实现，但需求取舍、架构边界、合并和发布责任不能默认外包给模型。

## 接下来如何证伪

1. **“确定性内核 + 智能外壳”会不会成为标准架构？** #158 的直觉很强：稳定、可审计部分保持传统代码，一次性、高智能处理交给 AI。但 #188 提醒 LLM Agent 的概率性执行可能需要新原语。边界到底怎么画，还缺大规模验证。

2. **Skill Engineering 会不会变成独立能力？** #199 暗示 Skills 正在变成轻量、可组合的运行时策略层。但这个判断主要来自 Anthropic 内部实践，在更广泛团队里能不能复现，还要看。

3. **非代码领域什么时候有验证闭环？** #111 说程序员率先受益，是因为代码天然可验证。活动策划、周报、销售话术、管理判断，这些任务更难量化。#79 的判断很清楚：数字化、数据多、易验证的领域会先突破；物理化、数据稀缺、难验证的领域会慢很多。

4. **订阅制补贴退潮后，AI Coding 的 ROI 还成立吗？** 当前很多重度使用建立在平台补贴 token 的基础上（#249）。一旦转向 usage-based pricing，企业会重新算账：这些 token 到底换来了多少真实交付，还是只是把研发成本换了会计科目。
