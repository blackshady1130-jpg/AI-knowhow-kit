# AI Coding 如何改变软件开发的成本和机会

**讨论交付效率、新增任务与开发分工 · 复核于 2026-10-08**

AI Coding 的收益至少有三种：同样的工作做得更快，同样的时间得到更好的结果，以及做成过去不值得投入的事情。只统计生成代码量，会漏掉后两种；只强调 Review 和维护成本，又容易低估第三种。

我的判断是，AI 会降低尝试软件方案的门槛，但成熟项目和个人小工具会走出不同的使用方式。前者必须把生成速度接到测试、集成和维护上，后者则可能先从一个足够有用、随时可替换的小程序开始。不能拿同一套生产率指标评价二者。

## 代码为什么适合较早交给 Agent

代码有一组相对方便的反馈工具：可以执行、比较差异、跑测试，也可以用版本管理保留修改前的状态。Agent 改错之后，只要环境和反馈足够清楚，就有机会定位问题、再次尝试。这使它比许多只能等待现实反馈的工作更容易形成短周期迭代。

但“能运行”只是一个检查条件。程序可能算错业务口径，测试可能覆盖不足，修复也可能引入维护负担。代码任务适合自动化的程度，取决于需求能否说明白、结果能否检查、失败后能否恢复，而不只是语言或代码行数。

这也解释了同一工具在不同项目里的体验差异。边界清楚的脚本、小功能和重复性维护，往往容易给出完成标准；涉及隐含约定、历史兼容和跨团队依赖的改动，需要更多上下文。模型强弱重要，项目能否让它获得正确反馈也同样影响交付。

## 效率实验要连同时间一起读

#178 收录了对 METR 实验的讨论：资深开发者使用 AI 后，完成任务的时间增加了 19%，事后却主观认为自己快了约 20%。这是 2025 年初、特定开发者在熟悉开源代码库中的实验，不应被当作今天 AI Coding 效率的固定结论。

METR 在 2026 年 2 月的后续说明中报告了一些提速信号，但参与者不愿放弃 AI、选择性提交任务，以及并行 Agent 的计时困难，使新结果不足以可靠估计提速幅度。作者认为早期结果可能已不代表当时工具的效果，也没有据此宣称获得了确定的普遍增益。[METR 后续研究说明](https://metr.org/blog/2026-02-24-uplift-update/)

这两次研究放在一起，更值得保留的教训是：工具会变，使用者会适应，任务也会随之改变。旧实验需要标明时间，个人感受需要用工作记录校准，而不同版本、不同任务的数字不能简单拼成行业趋势线。

团队比较效率时，应同时记录工程师实际投入的时间和任务从开始到交付的日历时间。Agent 运行期间，人可能处理别的事；等待 Review 的一天，也不等于审核人工作了一天。把这些时间混在一起，容易高估或低估收益。

代码执行环节的提速，也不能同比换算成整个项目提速。#441 的研究者讨论中，John Schulman 强调，实现更快以后，选择实验、解释异常和决定下一步仍会占用时间；#447 中 Nathan Lambert 还强调研究中的沟通与共同标准。它们是对研发工作的判断，但对软件团队有直接启发：需求澄清、方案选择、结果解释和协作等待，都应计入交付周期。

如果生成代码只占原来工时的一小部分，再大的局部提速也不会原样传到项目。反过来，快速生成原型可能让团队更早发现需求不对，从而省掉后续开发。这类收益要从任务记录和实际采用的方案观察，既不能只算敲代码时间，也不能把所有管理成本归给 AI。

## 新增的软件，未必原本就有开发预算

#97 对用户生成软件的讨论提供了另一个角度：软件可以围绕一个具体任务即时生成、执行和修改，不必都先长成一个长期维护的通用应用。

个人网页、文件整理脚本、临时的数据对照工具，就是容易理解的例子。这里的反事实可能不是“请工程师做需要两天”，而是“没有 AI 就暂时不做”。如果直接把工程师报价全部算成节省，收益会被夸大；如果因为没有历史工时就认为收益为零，又会漏掉新增能力。

我会看这个工具是否真的被使用，解决的问题是否原本长期搁置，以及后续维护是否仍然划算。一次性工具用完即弃可以是合理选择；接入重要数据、被多人依赖以后，则需要补上测试、权限和维护安排。

这也让“写得更多”有了两种相反含义。一种是为了完成同一任务生成了冗余代码，另一种是实现了以前做不到的功能。团队需要追踪实际采用的成果，不能只用代码量或 PR 数量区分二者。

## 模型选择，应把难度和风险分开

Databricks 用近期真实 PR 在内部代码库里比较 Coding Agent（#358）。其中一个结果是，Token 单价更低的模型，可能因为读取内容更多、执行更久而花费更高。这是该代码库与配置下的观察，不能直接变成其他团队的采购表，却说明应比较完成一项合格任务的总成本。

任务难度决定模型需要理解和推理到什么程度，风险则决定如何限制执行、验证和发布。一个算法实验可以很难，但只在隔离目录里运行；一行权限配置看起来简单，却可能影响整个生产系统。昂贵模型不能替代权限检查，小模型也不应因为任务简单就获得更宽的操作范围。

选型可以先用代表性任务比较几种配置，统计成功、重试和人工修正。稳定、容易验证的任务再尝试降低成本；需求模糊或错误反复出现的任务，先弄清缺的是信息、能力还是检查手段，不要只会把 effort 调高。

模型升级后也应重新检查 Harness。#415 收录的团队实践，是先移除旧约束，再看哪些失败仍然存在；#440 对 Skills、提示词和 AGENTS.md 的建议，则把问题具体到过宽的触发条件、重复阅读和过度规定步骤。

我会将旧指令分成三类审计。项目事实，例如目录约定和业务字段，应检查是否过期，并在相关任务中提供；权限与验收要求，例如可修改范围、发布授权和必要回归，应继续可靠执行；为弥补旧模型而写的固定步骤，则可以做删除前后的对照测试。三类内容混在一起，容易把安全要求当成累赘，也容易让一次小改动加载整套无关流程。

强模型仍需要专业工作方法和项目约束，不能由此得出“不需要 Skill”。更有价值的调整是缩小触发范围，保留完成标准、必要资源和已验证经验，把重复教模型如何搜索、如何拆每一步的指令交给实际失败来证明。多人使用不同模型的仓库，还要避免只按一个模型的表现删除共享指导。

## 审核应集中到人能作出判断的位置

高频弹出的命令确认框，未必提供了有效审查。#396 收录的 Claude Code 实验与产品数据提示，确认疲劳需要认真对待。但命令批准率与计划拒绝率不是同一种衡量，不能直接据此宣布计划审批一定更安全。具体实验和区别，在“AI 产品与交互”中展开。

对于开发任务，更有用的审核入口通常是修改目标、实际 diff、检查结果和潜在影响。人应能看见哪些检查由工具完成，哪些只是 Agent 的解释，哪些部分尚未验证；完整日志留作追溯，不应是判断能否发布的唯一入口。

测试也要有人维护质量。Agent 可以补测试，但若实现和测试都围绕同一个错误假设展开，两者一致并不能证明需求正确。重要改动需要检查验收标准，并抽查关键路径；完整的评分校准与失败归因方法由“评测与基准”讨论。

RecreationWorld（#455）的 PhotoCollage 案例给了一个直观例子：页面看起来可以使用，但连续操作后执行撤销，只恢复了布局，没有恢复旋转。第一张截图看不出这种错误。检查生成的软件，需要实际走过操作顺序，核对计算、撤销和保存后的状态；具体检查项应来自需求，而非只比较外观。论文展示了 Agent 发现并修补问题的过程，但这段案例不能证明补丁通过了全部隐藏测试。

科研复现提供了另一种交付参照。PaperBenchX（#468）要求提交可执行入口、代码与获准使用的输入数据，再清掉旧产物独立重跑。由此提炼到软件开发的建议是：交付应写明依赖、配置与输入，测试证据绑定最终代码版本；干净启动暴露的缺文件、隐含环境和残留状态，不能由一句“我这里跑过”补齐。这是从科研案例推导的软件交付方法，不是该基准已经测出的软件生产率收益。

最后一次修改后，应重新加载相关部分、复查受影响路径。环境或时间不够时，明确哪一版做过哪些检查、最后改动还有什么未确认；旧版通过记录仍可保留，但不能替新版作保。

审核本身还会继续自动化。独立检查、静态分析和回归测试可以承担一部分重复工作，人的精力应留给难以形式化的要求、异常和高后果选择。人工验收是当前许多团队的瓶颈，不应被写成永远不变的上限。

## 多 Agent 要看已交付任务，而不只看并发数

#413 中 Orca 的产品实践提到，同时运行很多 Agent 之后，困难转向了辨别谁完成、谁卡住、谁等待权限，以及先检查哪个结果。并发增加可以缩短等待，也可能更快堆积待审核的改动。

任务拆分因此需要考虑合并成本。彼此独立的文档或模块可以并行；都要修改同一接口、依赖同一数据迁移的任务，即使分到不同 worktree，最终仍要协调。worktree 隔离文件，不会自动隔离数据库、端口和登录状态。

我更愿意看一段时间内真正交付了多少有用改动，平均等待 Review 多久，合并后故障和返工是否增加。如果任务完成速度提高，审核队列却越来越长，下一步该优化的是差异展示、风险排序或任务粒度，继续加 Agent 未必有收益。

对已经使用 AI 的团队，一份简单记录就能比使用率提供更多信息：

| 观察对象 | 记录什么 |
| --- | --- |
| 原有任务 | 实际人工投入、交付周期、调用费用、返工与上线故障 |
| 新增任务 | 为什么过去没做、成果是否采用、后续维护是否值得 |
| 模型配置 | 同类任务成功率、重试、审核负担及降档后的变化 |
| 并行开发 | 完成队列、等待审核时间、合并冲突与共享资源问题 |

我会分别判断两件事：AI 是否让现有软件交付更有效率，是否让更多人有能力做出自己需要的软件。前者需要成本与质量记录，后者需要真实使用和持续价值。两者都值得追踪，也都不适合用“生成了多少代码”代替。
