# 七篇主题文章编辑设计

## 目标

在保留七个既有主题名称和“主题文章 + Notes 证据”结构的前提下，重新划分七篇文章的职责，吸收 Notes #387–#424 中真正改变判断的材料，并减少文章之间的重复。

本轮不是把 38 条新 Notes 平均塞进七篇文章。文章负责稳定判断，Notes 负责持续更新的案例和证据。新材料只有在增加机制、边界、反例、决策或可执行方法时才进入正文；进入正文的新内容应尽量替换重复内容，使单篇长度保持在约 4,500–5,800 个字符。

## 读者与写作口径

- 面向希望理解 AI 模型、Agent、产品和产业变化的公开读者，不假设其具有模型训练或基础设施背景。
- 第一屏先给清楚判断，再解释机制和证据。
- 小标题直接说明本节回答什么，不使用翻译感强、故意抽象或制造气势的表达。
- 事实、来源观点、作者判断和待验证推断必须分开。
- 保留必要的数字、模型名、论文名、技术术语和适用边界；不为了缩短文章而删除限制条件。
- 不把 Notes 的 `why/comments` 改造成标签或统一机器摘要，也不覆盖作者原有判断。

## 七篇文章的职责

| 主题 | 正文只负责回答的问题 | 不在本文重复展开 |
| --- | --- | --- |
| 模型推理与训练 | 模型能力由哪些训练、推理和运行条件共同生产 | Harness 的运行细节、评测审计流程 |
| 架构与工程 | Agent 怎样保存状态、控制权限、恢复失败并持续运行 | 产品界面、行业利润分配 |
| 评测与基准 | 怎样判断任务是否完成，并定位失败发生在哪一层 | 通用运行时设计、软件开发组织方式 |
| AI Coding | 代码生成降价后，软件工程的时间和成本怎样迁移 | 通用 benchmark 审计、Harness 全部机制 |
| AI 产品与交互 | 用户怎样发起、观察、授权、验收和接管 Agent | 底层 Runtime 实现、宏观就业判断 |
| 行业格局与企业战略 | 谁承担成本、掌握任务结果和学习资产，并获得利润 | 模型机制细节、产品交互组件 |
| AI 安全与影响 | 谁拥有决定权，风险、额外工作和责任由谁承担 | Runtime 实现教程、完整产品设计方法 |

## 跨文章去重规则

1. 每个核心判断只设一个主归属文章。其他文章需要该判断时，只说明它对本主题的影响，并链接相应 Note。
2. 同一组数字不在三篇文章中完整复述。例如 Harness 成本差异属于 AI Coding 的主要证据；评测文章只用它证明系统配置会改变结果；行业文章只用它说明应比较 `cost per accepted task`。
3. `实践工具` 和 `哪些证据会改变判断` 可以保留，因为它们分别承担行动与证伪功能；不要求七篇采用完全相同的段落节奏和标题格式。
4. 文章中的表格必须服务本篇独有的判断。若表格只是重新列举正文观点，则合并或删除。
5. 对相同 Note 的二次引用，要增加新的后果、边界或决策，不复述同一段机制。

## 单篇设计

### 1. 模型推理与训练

**文章任务：** 解释能力提升为何不能只归因于参数或某一种训练算法。

**建议结构：**

1. 比较模型前，先固定数据、训练、推理和运行条件。
2. Post-training 已从算法配方变成环境、教师、Verifier、rollout 和版本编排系统。
3. Agent 可以在既定路线内持续优化，但还不擅长根据证据主动更换研究路线。
4. Attention、Context 和 reasoning effort 改变的是信息保存、计算预算与任务成本，不是单调的质量旋钮。
5. 用模型比较清单统一记录能力主张、环境、预算、成本和边界。

**优先吸收：** #407、#416、#418；#408 和 #409 用于限定“小模型 + 工具”以及 post-training 的适用范围。

**迁移与压缩：**

- J-space 的主要讨论迁移到“AI 安全与影响”，本篇只保留一句说明内部机制研究不能直接替代任务评测。
- 扩散语言模型的生成顺序压缩为一个反例，不再承担独立主线。
- #419 和 #423 由“评测与基准”展开，本篇只说明 reward 与发布分数依赖评测条件。

### 2. 架构与工程

**文章任务：** 解释模型之外的 Runtime 为什么仍然存在，以及它具体负责什么。

**建议结构：**

1. 强模型会吃掉旧脚手架，但不会消除状态、权限、恢复和验证。
2. Context 由离线知识编撰与在线任务状态共同组成，不是把更多内容塞进窗口。
3. 文件、checkpoint、branch 和失败记录共同保存长任务状态。
4. 权限从调用前检查延伸到读取后、共享前和外发前。
5. 失败处理先定位最早不可恢复错误，再决定改模型、Harness、工具还是环境。
6. Harness 可以被 Agent 改进，但候选系统不能同时改写 held-out eval、权限上限和晋级规则。

**优先吸收：** #388、#403、#414、#415、#417；#395 只引入故障归因方法。

**合并与压缩：**

- 合并“文件系统保存工作状态”和“长时间任务保存失败和反馈”，避免两节重复解释状态连续性。
- 将 Claude Code 删除系统提示词、Raft 对 Harness 的判断和 Grok Bot 框架合并为一个结论：靠近模型的脚手架变薄，运行控制层变厚。
- 权限章节新增数据来源和衍生产物传播，不再只写工具调用和短期凭证。

### 3. 评测与基准

**文章任务：** 从“看分数”推进到“检查任务、校准标准、定位失败和测量可靠性”。

**建议结构：**

1. 逐项检查任务、环境和 hidden requirements。
2. 先声明结果属于模型还是完整 Agent 系统。
3. Rubric 是任务规格，不是天然真值；Judge 和 Rubric 都需要校准。
4. 找到最早不可恢复失败，区分模型、Harness、工具、环境和 Verifier。
5. 对真实工作同时报告单次成功、连续成功、副作用、成本和接管。
6. 用统一结果行披露模型、effort、Harness、版本、工具、预算、Verifier 和成本。

**优先吸收：** #395、#399、#410、#419、#423。

**合并与压缩：**

- WorkBuddyBench 保留“不同 artifact 使用不同证据结构”的结论，压缩各 track 的评分器比例。
- #399 用作 pass@1、pass@5 与 pass^5 的具体案例，替换部分抽象可靠性说明。
- #423 用作跨厂商同榜不同配置的最新证据，不在正文复刻完整六模型矩阵。

### 4. AI Coding

**文章任务：** 解释代码生成成本下降后，瓶颈为什么迁移到任务定义、测试、Review、集成和维护。

**建议结构：**

1. Coding 发展较快，因为代码有可运行、可比较和可回滚的反馈。
2. 生成更快不等于项目更快；先测 cycle time 和 Review queue。
3. 模型、effort 和 Harness 按任务风险与 `cost per accepted task` 路由。
4. 测试也会错，但详细 benchmark 审计交给“评测与基准”。
5. 人的控制点从逐条命令确认上移到计划、风险边界、异常和最终验收。
6. 多 Agent 并发的上限由团队能消化多少审查与决策决定。

**优先吸收：** #396、#413、#415；#405 只作为“自修改 Harness 仍是未证实方向”的边界。

**迁移与压缩：**

- OpenCode 的流量、收入和平台竞争信息移出正文，不再用产业数据证明软件工程机制。
- SWE-Bench 任务审计只保留它对内部测试的启示，完整方法放在评测文章。
- 把 Plan → Annotate → Execute 与逐条确认失效合并成人工控制位置的变化。

### 5. AI 产品与交互

**文章任务：** 解释一个 Agent 产品怎样让用户理解并控制任务，而不是只增加聊天框和确认弹窗。

**建议结构：**

1. 触发：系统如何判断这是一项需要改变外部状态的任务，而不是对话中的关键词。
2. 状态：展示已知事实、模型推断、等待操作、已产生副作用和待决策分支。
3. 权限：按对象、可逆性和风险设置运行时规则，减少低价值确认。
4. 验收：不同 artifact 使用 diff、页面、表格、Slides 或日志等不同 Review 界面。
5. 接管：说明卡点，保留 workspace、委托链和 action log，让人从当前状态继续。
6. Memory：记录来源、作用域、版本和调用历史，并允许用户纠错和删除。

**优先吸收：** #390、#396、#403、#410、#413。

**迁移与压缩：**

- GPT-Live 不再作为独立产品趋势展开，只用于说明前后台任务、打断和状态同步。
- “把真实失败转成 Eval”压缩成结尾的数据回流，不在本文重新解释评测方法。
- #403 在本文强调用户能否理解和控制分享；底层三平面实现由架构文章负责。

### 6. 行业格局与企业战略

**文章任务：** 解释模型降价之后，AI 产业各层怎样承担成本和获得利润。

**建议结构：**

1. 先把 Adoption、Token、收入、毛利和任务价值分开。
2. 推理供给的门槛是容量、利用率、延迟、能耗和稳定需求，不只是把模型跑起来。
3. 路由层只有掌握持续决策和结果数据，才能长期覆盖平台费与客户毕业风险。
4. 开放模型可以获得更多 Token，闭源模型仍可能获得更多收入；两本账可以同时成立。
5. 数据市场从一次性 Dataset 转向持续 Training Signal、Environment、Verifier 和 QC。
6. 企业与 FDE 的长期资产是 Eval、Workflow、权限模式和真实失败回路。

**优先吸收：** #389、#397、#406、#421、#424。

**边界处理：**

- #402 的公司数字和推理资产判断来自非公开传闻，不作为正文事实；若保留，只能明确标为待验证假设。
- #421 用于区分算力资产所有权、使用权和模型需求，不沿用“几家公司拥有全球算力”的宽口径。
- #424 只解释推理目标函数为何从 Peak FLOPS 转向请求延迟、能耗和利用率，不扩写为芯片投资判断。

### 7. AI 安全与影响

**文章任务：** 解释 AI 部署中的决定权、风险、额外人工工作和责任怎样分配。

**建议结构：**

1. 模型内部机制可以帮助诊断，但不能直接证明意识，也不能保证可以稳定控制行为。
2. 任务完成必须同时满足业务 Guardrail，平均成功率不能掩盖严重副作用。
3. 高频人工确认会退化为盖章；人应定义目标和高风险边界，运行时负责持续检查。
4. 授权不仅覆盖工具调用，也覆盖 Context、Memory、Workspace 和衍生产物的传播。
5. AI 可能改变人的判断练习、初级工作、Review 负担和专家培养路径。
6. 自我改进系统的 proposer、evaluator 和 approver 需要分离，责任不能因调用链变长而消失。

**优先吸收：** #396、#403、#420。

**迁移与压缩：**

- J-space 主要放在本文，并与 #420 的两类可解释性路线合并；结论限定为“诊断能力在进步，控制仍不成熟”。
- 实时语音的交互细节移到产品文章，本文只保留自然交互可能放大过度信任。
- #400 涉及快速变化的安全漏洞与敏感归因，本轮不作为正文主线；如后续加入，应重新核验论文、厂商修复状态和可复现边界。

## 写作工作流

每篇文章按同一套编辑纪律处理，但不强制相同版式：

1. 建立 claim ledger，记录现有主张、首次出现位置、证据、边界和跨文重复。
2. 给每一节指定一个动作：定义、解释机制、给证据、限定边界、比较或提供工具。
3. 先移动、合并和删除重复主张，再添加新 Notes；不从局部换词开始。
4. 每个正文段落至少增加一种信息：证据、机制、边界、后果、反例、决策或下一步。
5. 完成结构后再做句子级检查，删除无必要的“真正”“值得注意”“这说明”等连接性拐杖词。
6. 保留有实际对比作用的“不是 A，而是 B”，不把句式扫描当作禁词表。
7. 每篇交付时附新增、删除、迁移的 Note ID 和保留的扫描命中，便于人工复核。

## 验收标准

### 内容

- 七篇文章各有一个清楚、互不替代的主问题。
- 新增内容来自 #387–#424 的高信号 Notes 或其原文，不为了追求“最新”加入低增量材料。
- 同一核心机制只在主归属文章完整解释，其他文章不重复抄写。
- 每个数字、专有名词、因果判断和结论边界都能回到现有 Note、原文或明确标注的作者判断。
- 不把公司口径、访谈观点、单一 benchmark 或论文实验升级成普遍事实。

### 语言

- 标题和小标题使用读者一眼能懂的中文。
- 删除低信息量总结、空泛升格和重复结论。
- 保留必要的反例、限制条件和作者的判断语气，不把全文抹平成统一的企业报告。
- `removing-ai-slop` 扫描结果逐条标记为修正、合理保留或不确定，不追求零命中。

### 仓库与站点

- `notes/**`、页面 UI、JavaScript 和数据结构没有变化。
- 所有文章内 `#ID` 都存在于 Notes 索引并能被页面解析。
- 完整测试、JavaScript 语法检查和 `git diff --check` 通过。
- 七篇全部确认后，才更新文章复核日期、重建 `site/data.json` 并准备发布；发布需要用户再次明确确认。
