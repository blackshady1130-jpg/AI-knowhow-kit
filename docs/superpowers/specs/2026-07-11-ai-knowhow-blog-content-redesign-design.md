# AI Knowhow Blog Content Redesign

日期：2026-07-11  
分支：`codex/blog-content-redesign`

## 1. 目标

把网站从“按七个主题分类的 AI 资料库”升级为一项能够同时服务三种目的的公开资产：

1. 首页先建立 Yantao 的个人主张，让第一次访问的人在一分钟内理解他长期研究什么、判断问题的方法是什么。
2. 七篇主题文章继续服务 AI 同行深读，保留证据、边界和持续更新能力。
3. notes 作为可追溯证据层，优先呈现用户手写判断及其对综述的贡献，而不是形成按时间堆叠的信息墙。
4. 提供克制、明确的合作入口，面向愿意交流真实工作流、Agent 失败案例、评测与企业部署问题的人。

## 2. 对外主张

首页核心主张固定为：

> 研究模型如何进入真实组织，并把使用过程变成可验证、可持续改进的学习闭环。

辅助说明：

> 我持续跟踪模型训练、Context、Harness、Eval、AI 产品与企业部署。关注的不只是模型又强了多少，也包括谁定义任务、谁验收结果、失败如何回流，以及组织是否真的获得了可复用能力。

这条主张不把用户包装成生产级 FDE 工程师。对外身份仍以 AI 战略、行业研究、业务分析和部署学习问题为主，工程实现边界保持诚实。

## 3. 信息架构

### 3.1 首页：主张优先

首页按以下顺序组织：

1. Hero：主张、辅助说明、两个阅读入口和一个合作入口。
2. “我持续追问的三个问题”：能力如何形成、结果如何验证、经验如何回流。
3. “一条研究主线”：模型能力 → Context/Harness → Eval/Verifier → 产品与工作流 → Deployment/ROI → 人与治理。
4. “七个研究章节”：保留现有七主题，但说明每章在主线中的角色；AI Coding 明确标为高反馈验证场，而不是与其他层完全平行的分类。
5. “最近更新”：展示最近新增且判断密度高的 notes。
6. “关于我与合作”：公开安全口径、适合交流的问题、联系方式。

规模数据仍保留，但从首屏主角降为可信度辅助信息。

### 3.2 七篇深读：统一骨架，不写成同一篇文章

七篇文章保留独立主题，但改成同一套可扫描结构：

1. 本章核心判断：一句能单独引用的判断。
2. 它在主线中的位置：解释与前后章节的关系。
3. 三至五个关键判断：每个判断采用“结论 → 证据 → 边界/反例”。
4. 2026 年 6—7 月新增了什么：明确哪些新 notes 改变或加强了原判断。
5. 对产品、团队或研究者意味着什么：给可行动含义。
6. 接下来如何证伪：保留观察问题和失效条件。

七章的角色定义：

| 章节 | 在主线中的角色 | 核心问题 |
|---|---|---|
| 模型推理与训练 | 能力供给层 | 能力来自哪里，哪些提升能迁移到真实任务？ |
| 架构与工程 | 运行系统层 | Context、Harness、工具、状态和恢复如何接住模型？ |
| 评测与基准 | 验证与治理层 | 谁定义成功，如何避免 verifier 和环境噪声制造假进步？ |
| AI Coding | 高反馈验证场 | 为什么 Coding 先跑出来，它能为其他 Agent 场景提供什么、不能提供什么？ |
| AI 产品与交互 | 工作流入口层 | 模型能力如何变成可授权、可接管、可持续使用的产品？ |
| 行业格局与企业战略 | 部署与价值捕获层 | 谁掌握算力、运行时、客户反馈、预算和 ROI？ |
| AI 影响与安全 | 结果与责任层 | 当 AI 进入真实生活和组织，谁承担长期后果？ |

### 3.3 Notes：从时间流改为证据浏览

每个主题页的 notes 区分成三种视图：

- `综述引用`：默认视图，只显示本篇综述实际引用的 note，帮助读者核对证据。
- `最近更新`：展示该主题最近新增的 notes，说明判断如何演化。
- `全部判读`：支持关键词搜索和类型筛选，分批加载，避免一次渲染 50—100 张卡片。

每张 note 卡片的阅读顺序：

1. 标题与来源链接。
2. 用户的“我的判断”（`why_short`），作为卡片主体。
3. 日期、证据类型及“综述引用”状态。
4. 主题与关键词降为辅助信息。
5. 完整 `why` 按需展开。

本轮不新增机器生成的摘要字段，不改写用户的 `why/comments`，也不设计新的庞大标签体系。

## 4. 数据设计

`site/topics.json` 为每个主题补充：

- `chapter`：章节序号或角色标签。
- `question`：本章回答的问题。
- `thesis`：首页与主题 Hero 使用的当前判断。
- `role`：在研究主线中的位置。

`site/build_data.py`：

- 继续以 `notes/AI行业扫描_keywords.jsonl` 为唯一 notes 主索引。
- 校验每条 note 都有主题映射。
- 生成 350 条 notes 的站点数据。
- 从综述 Markdown 中提取 `#id` 引用，输出每个主题的 `review_note_ids`。
- `generated_at` 使用实际构建日期，页面页脚从数据读取，不再硬编码旧日期。

`site/topic_assignments.json` 为 290—350 号 notes 增加 1—3 个主题映射。映射依据对象、机制和用户手写 `why`，不只根据标题关键词。

## 5. 视觉与交互边界

本轮优先改内容层级和阅读路径，不重做技术栈：

- 继续使用单页静态 HTML、Tailwind CDN、Marked 和 `data.json`。
- 保留现有蓝紫色基调，改进层级、留白、移动端信息密度和按钮语义。
- 不引入框架、构建依赖、登录、数据库、埋点或 CMS。
- 不使用装饰性 AI 图片；个人主张依靠文字、层级与轻量 CSS 流程线表达。
- URL hash 兼容现有 `#home` 与 `#topic/<name>`。

## 6. 合作入口

合作区不使用泛化的“欢迎合作”。明确列出适合交流的三类问题：

1. Agent/AI 工作流为什么在真实组织里失败。
2. 如何定义任务、Context、Eval、Verifier、人工接管与结果验收。
3. 如何把 badcase、专家修正和客户反馈写回产品、Skill、评测或训练数据。

CTA 文案为“交流真实工作流”，点击后跳到联系方式区域；保留邮箱和微信，不增加表单。

## 7. 验收标准

1. 首页首屏明确出现核心主张、主线阅读入口和合作入口。
2. 首页用可理解的因果链串起七个研究章节，不再只展示平行分类。
3. 七篇综述均包含核心判断、主线位置、新增观察、行动含义和证伪问题。
4. 350 条 notes 全部进入 `site/data.json`，290—350 均完成主题映射。
5. 所有综述 `#id` 引用均指向存在的 note；每篇至少引用一条 290—350 的新增 note。
6. notes 默认显示综述引用，可切换最近更新和全部判读；全部视图支持搜索、类型筛选与分批加载。
7. 用户手写 `why` 保持原文，卡片优先展示 `why_short`，完整内容按需展开。
8. 页面在桌面与移动宽度下均无横向溢出，hash 路由、外链、展开与筛选可用。
9. `main` 不发生修改；所有内容仅提交到 `codex/blog-content-redesign`。

## 8. 非目标

- 本轮不建立 outcomes ledger、CRM 或网站分析后台。
- 不把七个主题改成新的 notes 数据字段体系。
- 不自动发布或合并到 `main`。
- 不承诺流量增长；本轮验收聚焦定位清晰度、内容结构和证据可用性。
